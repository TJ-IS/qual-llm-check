# A knowledge-based system for performing reverse engineering of relational databases

Roger H.L. Chiang

Nanyang Technological University, Singapore 2263

A knowledge-based system, called the Knowledge Extraction System (KES), is presented which performs the process of reverse engineering of relational databases. KES generates an extended entity–relationship (EER) model from a relational database. Within its extraction procedure, domain semantics are obtained by analyzing the data schema and data instances of an existing database, by using heuristics, or asking the user. Relations and attributes are classified into several categories and then converted into the corresponding modelling structures of the EER model. KES demonstrates how knowledge-based system technology can be applied to ease the work of database reverse engineering. It also illustrates that the reverse engineering process can be implemented at a high level of automation. To do so, KES is integrated with the target database management system so that data can be analyzed directly through dynamic SQL queries.

Keywords: Database reverse engineering; Relational databases; Knowledge-based systems; Database management systems; Extended entity–relationship model.

## 1. Introduction

Database reverse engineering is a relatively new area of research that deals with the problem of comprehending existing database systems and recovering the detailed semantics (e.g., design specifications) embodied within them $[19]$ . It is a process of examination and extraction, which obtains a sufficient understanding of the system and its application domain to make appropriate changes $[5]$ . Figure 1 illustrates the concept of database reverse engineering. In general, the application of database reverse engineering technology has many advantages, such as the ability to leverage assets, reduce maintenance costs, facilitate technology transition, provide reliability to system upgrades leading to user satisfaction, etc. $[19]$ .

Several researchers have provided some means for translating a relational data schema into an entity–relationship (ER) model $[6,7,9,10,11,13,14]$ . There are, however, three common problems of research in this area. First, previous work seems to overestimate the possibility of automating the reverse engineering process. Some methods generate a conceptual model almost without any interaction with the user. Nevertheless, consultation with the user is imperative to capture the essential domain semantics $[8]$ . Second, the results generated by the above methods are often closely tied to the existing data schema and, therefore, may become just graphical means of representing the actual physical implementation of the database. Third, no research or tools for database reverse engineering have ever considered how to obtain domain semantics, such as inclusion dependencies and integrity constraints, by analyzing data instances (the extension) of an existing database.

The overall object of this research is to provide solutions of these problems. A knowledge-based system, called the Knowledge Extraction System (KES), has been developed to perform the reverse engineering process. This system demonstrates how knowledge-based system technology can be applied to ease the work of database reverse engineering. It also illustrates that an EER model containing rich domain semantics can be generated from an existing database at a high level of automation. In this paper, the term “domain semantics” refers to information about the application domain that should be captured during the requirements specification phase of database design.

## 2. Knowledge extraction system

The Knowledge Extraction System (KES) is written in Arity Prolog and Microsoft C, integrated with the ORACLE RDBMS [15], and runs on an IBM PC/AT. The extraction procedure is written in Prolog. C is used to integrate the extraction processor with the ORACLE RDBMS, so that the extraction processor can analyze data instances by querying the database.

## 2.1. Innovations

The development of KES has the following innovations:

Semantically rich EER model. KES obtains an EER model that is semantically richer than the data schema which is currently implemented by the existing database. Note that we do not assume that the database was originally designed using an EER approach. Indeed, a common reason for performing reverse engineering is that the original design process and subsequent maintenance (the left-hand side of Figure 1) were not well documented and not carried out in a methodical manner. Thus the question of what the original design specifications were is unanswerable, and often uninteresting, since good design methods cannot be assumed to have been followed.

High level of automation. Because of the limited semantic expressiveness of the older (and even current) database management systems (DBMSs), semantic degradations occur during the design and maintenance of a database $[8]$ . KES illustrates that database reverse engineering cannot be a totally automated process. Necessary domain semantics must be obtained from sources other than the target DBMS in order to generate the EER model. One obvious way to do so is by asking a knowledgeable user, (e.g., a database administrator (DBA), a database designer or a system analyst, or even the end-user). However, another important objective in the development of KES is to reduce the amount of unnecessary user interaction, so that the reverse engineering process can be implemented at a high level of automation. Otherwise, it would be the user who generates the EER model, not the system $[11]$ . Thus, KES interacts with the user only when the required semantics cannot be obtained automatically.

Sources of domain semantics for reverse engineering. KES uses not only data schema and extraction rules, but also data instances and heuristics in order to generate a semantically rich EER model from an existing database. Extraction rules and heuristics contain the knowledge necessary for database reverse engineering, which are encoded as production rules and used by KES $^{1}$ . Additionally, the presence of the data instances populating the database can provide information that was not available at design time, so that we should expect an EER model which incorporates that information, together with the direct results of the original design decisions (i.e. the data schema of the database), to be superior to the original design.

For example, KES employs heuristics and inference rules to discover inclusion dependencies automatically, because the majority of the information that can be used to identify relationship types is contained in inclusion dependencies $[2,10]$ .

System integration. KES employs the technology of knowledge-based systems $[16]$ , which makes the reverse engineering process thorough and systematic and, of course, done faster than if done manually. Therefore, KES could assist database administrators (DBAs) in obtaining conceptual models from existing databases in a quick and easy way. KES also illustrates how the integration of database and knowledge-based systems can ease the task of database reverse engineering $[18]$ .

## 2.2. System architecture

KES has six basic components. Figure 2 shows the architecture of KES and the predominant information flows among its components.

Reverse engineering processor. The reverse engineering processor is the kernel of KES. Its major functions are to: (1) implement the extraction procedure; (2) interact with the user and the target DBMS to obtain information, and (3) maintain the knowledge base of KES.

Knowledge base. The knowledge base contains extraction rules and heuristics encoded as production rules that are used by the extraction procedure to generate EER models. The resulting EER model is stored here for further reference. The user can request reverse engineering results from KES through the user interface. The contents of the knowledge base are maintained in the form of Prolog clauses so that the reverse engineering processor can access them directly without translation.

![](/api/attachments/VDF5KW89/fulltext/images/435babd55fdc88e4d9cc32b14fc83e5abad1c7afb046566988a1b6625ba61f1a.jpg)  
Fig. 2. Architecture of the Knowledge Extraction System.

System interface. The system interface assists the reverse engineering processor in communicating with the target DBMS; in this case, ORACLE RDBMS. It is written in C. The interface accepts dynamic SQL queries from the processor and then sends them to the DBMS. The current interface is written specially for the ORACLE RDBMS. However, there must be a separate system interface for each different target DBMS.

User interface. The user interface allows the reverse engineering processor to interact with the user. The reverse engineering processor uses this interface to obtain the essential semantics, whenever required domain semantics cannot be inferred from the data schema or there are ambiguities that cannot be solved automatically by the system. The user interface is written in Prolog.

Database management system. The target DBMS for KES is the ORACLE RDBMS. Its data dictionary contains information about the data schema. However, the data definition language of ORACLE RDBMS cannot specify primary keys and integrity constraints such as inclusion dependencies.

Existing database. An existing database contains data of an application domain, which is under the control of the target DBMS. The presence of the data populating the existing database provides detailed information of the application domain. KES, therefore, is developed to take advantage of the large volume of data in an existing database in order to discover domain semantics. The extraction procedure analyzes data instances to: (1) verify the proposed inclusion dependencies, and (2) determine the candidate keys. As a result, the necessary information can be obtained directly from the database through dynamic SQL queries.

## 2.3. The extraction procedure

The extraction procedure of KES is a rule-based, data-driven procedure. The procedure consists of seven steps which are executed in sequence:

1. obtain information about the data schema,

2. classify relations,

3. classify attributes,

4. discover inclusion dependencies,

5. identify entity types,

6. identify relationship types,

7. assign non-key attributes to entity and relationship types.

Figure 3 shows these steps, and the input, output and operations for each. Section 3 details the execution of each step. The appendix contain excerpts from a session of the extraction procedure.

## 2.4. Extended entity–relationship model

The extended entity–relationship model is used as the conceptual model in this research. The entity–relationship (ER) model is most widely used approach to conceptual modelling [17], originally proposed by Chen [3]. Its fundamental modelling structures are entities, relationships, and their associated attributes. An entity is an independent object of interest in reality. A relationship is an association among entities. Attributes identify properties for entities and relationships. Some attributes may be identifiers (keys).

Using the original ER model as a conceptual model, however, has proved difficult because of the inadequacy of the initial modelling structures [17]. The extended entity–relationship model used here includes data abstractions such as aggregation and generalization in order to represent the detailed domain semantics.

## 2.5. Requirements of input databases

KES currently does not attempt to generate EER models for all existing databases. An existing database must satisfy a limited set of requirements in order for an EER model to be generated at a high level automation. Future research will attempt to relax some of these requirements.

![](/api/attachments/VDF5KW89/fulltext/images/a3e6cc39f4331397787877f80d9116fe2dc069fb1108a40f7ec019da6e03e629.jpg)  
Fig. 3. The extraction procedure of KES.

3NF relations. KES requires that the relations of the input database are in at least Third Normal Form (3NF). This requirement simplifies the extraction procedure by working with relations, each of which corresponds to one entity type or one relationship type, rather than relations that correspond to more than one entity type or a mixture of entity and relationship types. If there is a non-3NF relation in the input database, then this relation will be converted into an EER modelling structure which represents more than one entity type or a mixture of relationship types and entity types. It can be decomposed into detailed modelling structures manually.

Consistent naming of key attributes. KES requires that a consistent naming convention is applied to key attributes of the input database. That is, if key attributes have the same domain, then they have the same name throughout all relations. This requirement allows: (1) each relation and attribute to be classified into its proper category in steps 2 and 3 of Figure 3 at a high level of automation, and (2) all possible key-based inclusion dependencies to be detected automatically in step 4 of Figure 3.

No error data in key attributes. The input database does not contain any erroneous data instances in its key attributes. This requirement allows proposed inclusion dependencies to be discovered in step 4 of Figure 3.

## 3. Extraction procedure

A major problem of generating an EER model for an existing database is that there is generally no one-to-one mapping between input relational structures and their corresponding EER modelling structures. For example, a relation can be translated into one of several different EER structures. The extraction procedure, therefore, must have essential domain semantics to make the proper translations. The resulting EER model can then be used as a meaningful and comprehensive tool to interpret the application domain.

In order to perform the reverse engineering process at a high level of automation with minimal user involvement, the extraction procedure obtains required domain semantics for reverse engineering in the following sequence.

1. If the required domain semantics are stored in the target DBMS, obtain them directly from the DBMS; for example, the data schema which is currently implemented by the database.

2. If the required domain semantics cannot be obtained directly from the target DBMS, analyze the data schema and/or data instances to obtain them if possible; for example, inclusion dependencies.

3. If the required domain semantics cannot be obtained by either of the above ways, ask the user to supply them; for example, names for relationship types identified by the foreign keys.

This section discusses the execution of the extraction procedure by KES with the emphasis on the distinction between operations which can be executed automatically by KES and operations where consultation with the user is necessary as illustrated in the appendix. Table 4 presented in Section 3.9 summarizes these operations.

## 3.1. Obtain information about the data schema

Initially, the extraction procedure must obtain the data schema which includes relation names, attributes names, and primary keys. Information about the relation and attribute names is obtained directly from the data dictionary by querying the database. Since the ORACLE RDBMS's data dictionary does not provide a specific way to store information about keys, the extraction procedure uses attributes' properties (non-null and uniquely indexed) to detect the possible primary key attributes for each relation. If a relation has only one attribute that can be the possible primary key attribute, then the extraction procedure automatically identifies this attribute as the primary key. Otherwise, the user must specify the primary key for the relation. Figure 4 shows an example of a relational data schema with the primary keys identified. This data schema is used throughout this section and the appendix for discussing the extraction procedure $^{2}$ .

## 3.2. Classify relations

Relations and attributes are classified based upon classification schemes that extend the work of Dumpala and Arora [7] and Navathe and Awong [14]. The classification simplifies the extraction procedure so that the classified relations and attributes can be converted into their proper EER modelling structures in a systematic fashion.

PERSON: [SSN, name, address]

EMPLOYEE: [SSN, name, salary, hired-date]

MANAGER: [SSN, rank, promotion-date, deptno]

CUSTOMER: [SSN, custid, name, credit]

DEPARTMENT: [DEPTNO, dept-name, location]

PRODUCT: [PRODID, description]

PRICE: [PRODID, minprice, maxprice]

ORDER: [ORDID, order-date, prodid, custid]

CARRIER: [CARRIER-ID, name, address]

PROJECT: [PROJNAME, DEPTNO, budget]

WORK-FOR: [SSN, DEPTNO, start-date]

CAN-PRODUCE: [DEPTNO, PRODID, unit-cost]

SHIPMENT: [PACK#, ORDID, ship-date, carrier-id]

Fig. 4. A relational data schema.

A relation is classified mainly based upon the properties of its primary key; that is, the comparison of its primary key with keys of other relations. Each relation is classified into one and only one of the following four categories: Strong entity relation, Weak entity relation, Regular relationship relation, and Specific relationship relation.

Strong entity relation. A relation is classified as a strong entity relation if its primary key does not properly contain a key of any other relation. In Figure 4, employee manager, and department are examples of strong entity relations. WORKFOR is not a strong entity relation because its primary key, [SSN, DEPTNO], properly contains the primary keys of employee or manager, and department.

Weak entity relation. A weak entity relation contains multiple attributes in its primary key that meets all of the following requirements:

1. A proper subset of its primary key, K1, contains the keys of entity relations (strong and/or weak).

2. The remaining attributes of the primary key do not contain a key of any other relation.

3. This relation represents an entity type whose identifier must properly contain keys of other entity types (i.e., K1). This requirement must be confirmed by the user.

Consider the PROJECT relation in Figure 4. One of its primary key attributes, DEPTNO, appears as the primary key of DEPARTMENT, which is a strong entity relation. Another primary key attribute, PROJNAME, is not a key of any other relation. If PROJECT represents an entity type, then it is classified as a weak entity type.

Regular relationship relation. If a relation's primary key is formed fully by the concatenation of keys of entity relations, then it is classified as a regular relationship relation. For example, the CAN-PRODUCE relation in Figure 4 is a regular relationship relation, because its primary key, [DEPTNO, PRODID], is formed fully by the concatenation of the primary keys of DEPARTMENT, and PRODUCT or PRICE.

Specific relationship relation. If a relation's primary key satisfies the first and second requirements of a weak entity relation, and this relation cannot be treated as a weak entity relation, then it is classified as a specific relationship relation. Consider the “shipment” relation in Figure 4. PACK# is not a key of any other relation. “Shipment” is classified as a specific relationship relation, if it does not satisfy the third requirement of the weak entity relations. In this case, it implies that PACK# represents an entity type that contains it as the only attribute.

Information about primary keys is first employed to classify both strong entity relations and those regular relationship relations that contain only primary keys of strong entity relations. The primary keys of the remaining relations properly contain attributes that do not appear as a primary key of any other strong relation. If the primary key attributes which do not appear as primary key attributes in any strong entity relation do appear as the non-primary-key attributes in other strong entity relations (which are verified as candidate key(s) by the analysis of data instances), then this relation is classified as a regular relationship relation. Consider the PROJECT relation in Figure 4. It is classified as a regular relationship relation, if PROJNAME is a candidate key for some strong entity relation. It means that a strong entity relation has PROJNAME as a non-primary-key attribute which contains non-null and unique values in data instances. The information about candidate keys will be used later in formulating inclusion dependencies.

Suppose PROJNAME is not a candidate key of any other strong entity relation. In order to classify PROJECT, additional domain semantics must be obtained which cannot be inferred from the data schema and data instances. In this case, the extraction procedure must ask the user to classify PROJECT to be either a weak entity relation or a specific relationship relation. PROJECT is classified as a weak entity relation, if it represents an entity type. It is classified as a specific relationship relation, if PROJNAME represents the key of an entity type which is not represented by a separate entity relation. The user must confirm one of these two possible situations for PROJNAME.

## 3.3. Classify attributes

Attributes are classified automatically after relations are classified. First, attributes are classified depending upon whether they are attributes of a relation's primary key. Then, depending on the type of relation, attributes of the primary key are divided into three categories. Non-primary-key attributes are classified into two. Similarly, each attribute is classified into one and only one of the following categories: Primary key attribute, Dangling key attribute, General key attribute, Foreign key attribute, and Non-key attribute.

Primary key attribute (PKA). Primary key attributes are (1) attributes of strong entity relations' primary keys, (2) attributes of weak entity relations' primary key which appear as keys for some entity relations (strong and/or weak), and (3) attributes of relationship relations' primary keys which appear as keys of some entity relations.

Dangling key attribute (DKA). The attributes of the primary key of a weak entity relation which do not appear as keys of any other relations, are classified as dangling key attributes.

General key attribute (GKA). The attributes of the primary key of a specific relationship relation which do not appear as keys of any other relations, are classified as general key attributes.

Foreign key attribute (FKA). If a non-primary key attribute (possibly composite) of a given relation appears as a key of another entity relation (strong or weak), then it is a foreign key attribute of the (given) relation.

Non-key attribute (NKA). If attributes cannot be classified into any of the above four categories then they are non-key attributes. The classification of attributes is shown in Table 1.

## 3.4. Discover inclusion dependencies

Inclusion dependencies are needed in the identification of relationship types. There are three steps in discovering inclusion dependencies. An inclusion dependency is denoted as $A.X \ll B.Y$ , where A and B are relations, X is an attribute or a set of attributes of A and Y is an attribute or a set of attributes of B. X and Y must have an equal number of attributes. This inclusion dependency states that the set of values appearing in A.X is a subset of the set of values appearing in B.Y.

Propose possible inclusion dependencies. The first step is to identify all possible inclusion dependencies. The following heuristics are used to detect key-based inclusion dependencies automatically.

1. If two strong entity relations, A and B, have the same key, X, then, there may be an inclusion dependency between A.X and B.X; that is, either $A.X \ll B.X$ or $B.X \ll A.X$ . The inclusion dependencies are used to identify is-a relationships and generalization hierarchies.

2. If the key, X, of an entity relation (strong or weak), A, appears as a foreign key, x, of another relation, B, then, there may be an inclusion dependency between B.x and A.X, denoted as $B.x \ll A.X$ . These inclusion dependencies are used to identify binary relationships represented by foreign keys.

3. If the primary key attributes, X, of a relationship relation or a weak entity relation, S, appear as a key of an entity relation (strong or weak), A, then there may be an inclusion dependency between S.X and A.X, denoted as $S.X \ll A.X$ . These inclusion dependencies are used to determine owner entity types for weak entity types and participating entity types for relationship types identified by relationship relations.

The above heuristics are not sufficient to identify all possible inclusion dependencies. Suppose a set of non-key attributes appears in two relations, then an inclusion dependency may exist to represent a binary relationship. For this reason, the extraction procedure allows the user to specify inclusion dependencies between non-key attributes. For example, the user specifies an inclusion dependency, ORDER.[custid] ≪ CUSTOMER.[custid].

Reject invalid inclusion dependencies. All of the proposed inclusion dependencies are subject to further verification. The extraction procedure formulates two SQL queries for each proposed inclusion dependency, and then issues these queries to the target DBMS. The queried results are used to rejected invalid inclusion dependencies automatically. Consider the proposed inclusion dependency between PERSON.[SSN] and CUSTOMER.[SSN]. The following SQL queries are formulated by the extraction procedure:

Q1 = select count(\*) from PERSON where SSN not in (select SSN from CUSTOMER)
Q2 = select count(\*) from CUSTOMER where SSN not in (select SSN from PERSON)

SSN not in (select SSN from PERSON)
If Q1 = 0, then PERSON.[SSN] ≪ CUSTOMER.[SSN] holds. The same interpretation holds for Q2 = 0. If Q1 = 0 and Q2 = 0, then PERSON.[SSN] = CUSTOMER.[SSN] holds.

If a relation's foreign key attributes do not appear in any valid inclusion dependencies, then they are reclassified as non-key attributes.

Remove redundant inclusion dependencies. Inference rules of inclusion dependencies (projection and transitivity) [2] are used to remove redundant inclusion dependencies. There are two reasons for doing so. First, a redundant inclusion dependency can identify a redundant is-a relationship [10]. Second, a redundant inclusion dependency can lead to the identification of wrong participating entity types for relationships. Consider the following inclusion dependencies:

$$
\text { WORK - FOR. } [ \text { DEPTNO } ] \ll \text { DEPARTMENT. } [ \text { DEPTNO } ]
$$

WORK-FOR.[SSN] $\ll$ EMPLOYEE.[SSN]

EMPLOYEE.[SSN] $\ll$ PERSON.[SSN]

$$
\text { WORK - FOR. } [ \text { SSN } ] \ll \text { PERSON. } [ \text { SSN } ]
$$

The last inclusion dependency is redundant. If it is used to infer the participating entity types for the relationship type, work-for, then the entity type, Person, may become the participating entity type. However, Person should not be the participating entity type of work-for based upon the is-a relationship from Employee to Person and a binary relationship between Employee and Department.

## 3.5. Identify entity types

Entity types must be identified first so that relationships among them can then be identified. Strong entity relations are converted into strong entity types. Weak entity relations are translated into weak entity types and corresponding identifying relationships. The name of each entity relation is assigned to be that of the corresponding entity type.

For each weak entity relation, a weak entity type is identified with the dangling key attributes of the weak relation as its key attributes. In addition, an identifying relationship is specified between the weak entity type and its identifying owner(s). The identifying owner is determined by referring to inclusion dependencies. The extraction procedure provides a constant name for identifying relationships, called DEPENDENT. The user may change this name to provide one which captures the proper semantics of a particular identifying relationship.

## 3.6. Identify relationship types

KES identifies five kinds of relationships. Mainly, relationship relations are converted into relationship types. Consider the regular relationship relation, WORK-FOR, in Table 2. DEPTNO is a primary key attribute and it also appears as the primary key of the strong entity relation,

DEPARTMENT. This is not a sufficient indication that the entity type identified by DEPARTMENT is a participating entity for the relationship type identified by WORK-FOR. There are other kinds of relationships that must be identified by inclusion dependencies rather than by relationship relations, such as is-a relationships and binary relationships represented by foreign keys. Thus, the cross reference between key attributes and inclusion dependencies determines how relationship types are identified. Inclusion dependencies play a crucial role in determining participating entity types for each relationship type.

The extraction procedure currently only specifies the default cardinality ratios for binary relationships. The default cardinality ratios are: (1) 1:1 for is-a and inclusion relationships, (2) 1:N for relationships identified by foreign keys and inclusion dependencies between non-key attributes, (3) 1:N for binary identifying relationships for weak entity types, and (4) N:M for relationships identified by relationship relations.

Is-a and inclusion relationships. The extraction procedure identifies is-a relationships by the following rule: if two entity types have the same key and there is an inclusion dependency between them, then an is-a relationship is inferred. Consider EMPLOYEE and MANAGER in Table 2, and an inclusion dependency, MANAGER.[SSN] $\ll$ EMPLOYEE.[SSN]. The extraction procedure identifies an is-a relationship from Manager to Employee. If two entity types, (e.g., Product and Price), have, not only the same key, but also the same set of data instances in the key, then the user is asked to specify the proper type of inclusion relationship between them, such as $A$ is-a $B$ , $A$ is-a-kind-of $B$ , $A$ is-part-of $B$ , etc.

Generalization hierarchies. Generalization specifies that a generic entity type is the union of a set of non-overlapping specific entity types. If Customer and Employee are subclasses related to the same generic entity type, Person, there may be a generalization hierarchy among them. The extraction procedure uses the following criteria to identify generalization hierarchies:

1. There is a complete covering of the generic entity type. That is, every occurrence of the generic entity type appears in at least one of the specific entity type. For example, if each instance of Person is an instance of Customer, and/or Employee, then Customer and Employee form a complete covering of Person.

2. There is a non-overlapping partition of the generic entity type. That is, every occurrence of the generic entity type appears in at most one of the specific entity types. For example, if an instance of Person is an instance of either Customer or Employee, but not both, then Customer and Employee are non-overlapping subsets of Person.

Binary relationships. A foreign key in an entity relation is converted into a binary relationship type, which consists of two participating entity types. One is identified by the relation containing the foreign key and the other is identified by the relation whose key is the same as the foreign key. In order to determine the second participating entity type, there must be an inclusion dependency for the foreign key. Since the name of this kind of relationship is not represented in the data dictionary, the user must specify one. If the foreign key is also a candidate key, then the binary relation could be an is-a relationship.

The translation of specific relationship relations is similar to that of regular ones, except that the extraction procedure must first identify entity types for general key attribute. The user must determine how many new entity types should be identified, if a specific relationship relation contains multiple general key attributes. For each new entity type, a name must be provided by the user.

Aggregate relationships. A foreign key in a relationship relation is converted into an aggregate relationship type which associates an entity type with a relationship type. There are two steps in the identification of this kind of relationship. First, the aggregation abstraction is employed to treat the relationship type which is identified by the relationship relation having this foreign key as a composite entity type [12]. Then, an aggregate relationship type is identified between this composite entity type and an entity type containing the foreign key as a key.

## 3.7. Assign non-key attributes

The extraction procedure assigns non-key attributes as descriptive attributes to entity and relationship types. The manner in which the non-key attributes for a relation are assigned depends on: (1) the relation's type (for example, a regular relationship relation); (2) whether the relation contains foreign keys; and (3) the meaning of the particular non-key attribute in the relation. The extraction procedure can assign non-key attributes automatically, except non-key attributes of relations that contain foreign keys. For these relations, the extraction procedure asks the user to assign them to the proper modelling structures in the EER model.

## 4. Conclusion and future research

A knowledge-based system, called the Knowledge Extraction System, has been developed to implement the process of reverse engineering of relational databases. This system asks the user to provide information only when it is necessary and cannot be obtained automatically. As a result, the reverse engineering process can be executed at a high level of automation.

There are a number of possible extensions of this research. First, the system needs to consider how to relax the requirements of input databases. For example, the input database contains erroneous data in the key attributes, which will imply that certain inclusion dependencies should not be rejected because of erroneous data. Second, the extraction procedure should consider not only relations, but also views of the input databases. Third, the EER model obtained from the extraction system could be refined and enhanced by incorporating additional heuristics and domain knowledge. For example, redundant attributes for entity types in is-a hierarchies can be detected and removed according to the property inheritance principle [1]. Finally, a set of integrity constraints for the existing database can be proposed based on the resulting EER model and discovered inclusion dependencies.
