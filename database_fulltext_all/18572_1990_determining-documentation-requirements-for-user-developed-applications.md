# Determining documentation requirements for user-developed applications

Joan K. Pierson, Karen A. Forcht

and Faye P. Teer

Information and Decision Sciences Department, James Madison University, Harrisonburg, VA 22807, USA

Adequate documentation of user-developed applications is important to insure that they are developed in accordance with appropriate quality assurance methods, that they can be properly used, and that they can be maintained. A study of opinions of information center personnel indicates that not all user-developed applications have the same level of documentation requirements. Thirteen factors affecting the documentation requirement level of an application are identified and ranked. The top-ranked factors are: maintenance requirements, the use of output by another system, financial impact, scope of application, and its complexity. Forms of documentation preferred for different application types – modelling, data analysis, simple query, report preparation, transaction processing, and graphics – are also identified and ranked for applications with low and high documentation requirements. Two forms of documentation, user's instructions and narrative descriptions, are recommended as appropriate for all applications, regardless of their type or documentation requirement level. The appropriateness of other forms of documentation such as output layouts, design documents, and hardware/software requirements depends on the level of documentation requirements, and the type of application.

Keywords: Documentation, End user, End user computing, End user developed applications, End user documentation, User developed applications, Management of information systems, Managing end user computing, User developed systems.

The widespread use of computers by personnel whose main responsibilities are not directly related to information systems has given rise to a multitude of management problems. ## User-Developed Applications

A review of literature regarding UDA reveals evidence of a lack of enforcement of standard development methodologies and quality assurance practices during applications development by end users in most organizations. The need for documentation standards along with other quality control practices is identified in several studies [2] [5] [14] [29].

Traditional application development methods include practices to assure the quality of the system during all phases of a development project. Adequately documenting a system during its development has long been accepted as a crucial quality assurance task. Documentation is also one of the factors considered in measuring user satisfaction $[18]$ $[9]$ and the ease with which systems can be maintained $[6]$ $[12]$ $[23]$ $[38]$ .

Two reasons for the lack of documentation of UDA are readily apparent. First is the diversity of the applications themselves in scope, type, and development tools used. Secondly, EUC is a relatively new phenomenon and still in its early growth stages.

## Classifications of User-Developed Applications

The diversity of UDA is seen in the number of classifications that have been proposed.

\- Scope of the application. Personal, departmental, or multidepartmental (sometimes called organizational or corporate). The latter type of system is often multifunctional as well. Rockart and Flannery [35] noted that the “breadth of impact of these [multidepartmental] systems was surprising to us and to the management of the 1 companies we studied.”

\- Type of application modelling. Transaction processing, data analysis, simple inquiry, report preparation, and graphics are application types included in one taxonomy used by Rivard and Huff. Rockart and Flannery classify UDA as complex analysis, inquiry/simple analysis, report generation or operational systems.

\- Software development tools employed. Report generators, modelling languages, spreadsheet packages, word processors, query languages, graphics generators, and fourth generation languages [2].

Given the variations in UDAs, it is not difficult to understand why broad management concerns exist or why documentation standards are difficult to formulate.

Another plausible explanation for the lack of established management controls of UDAs is simply that the time has not been right until now to develop and apply such controls. Nolan's six-stage model of information system growth [30] identifies two stages (initiation and contagion) through which an information system moves before the control stage (the third stage) is reached.

The first phase is characterized by low control, some slack, and little or no information system planning. During the second phase, contagion, greater slack is given to encourage use; there is still a lack of planning. Nolan predicts that costs will rise in the second stage and that costs from lack of integration will become visible. During the third stage – the control phase – a high level of controls are put into place. Information system planning is given increased emphasis, thereby providing the basis for the system to move through the integration and data administration stages to maturity.

In view of the attention now directed toward EUC management, it may be reasonable to assume that in many organizations EUC is entering or is in the third, the control, stage.

## Study of UDA Documentation Requirements

This study was undertaken in response to a perceived need to examine documentation requirements of UDA within the broad context of management of user computing. Specifically, the purpose of the project was to provide a framework that can be used to formulate documentation guidelines and standards for a broad spectrum of UDA. Research questions for the project were:

1. Do all UDAs have the same level of documentation requirements? In other words, do some UDAs require more documentation than others?

2. If there are differences between documentation requirements for UDA, what factors affect the documentation requirements?

3. If there are differences, are the same forms of documentation appropriate for all UDA classifications (modelling, data analysis, simple query, report preparation, transaction processing, and graphics) with low documentation requirements?

4. Also, if there are differences, are the same forms of documentation appropriate for all UDA classifications with high documentation requirements?

## Methodology

The research project began with a review of the published literature on documentation for both traditionally developed and user-developed applications and of data gathered informally in a few test sites. Preliminary investigations led to the conclusion that documentation was indeed an issue that warranted in-depth investigation.

## The Survey Instrument

A preliminary model of fourteen candidate factors affecting the level of documentation requirements and thirteen forms of documentation was formulated. The candidate factors and forms of documentation were gleaned from user-computing literature and from suggestions by information systems practitioners and information center personnel at three test sites – a manufacturing company, a hospital, and a large midwestern university. Rivard's and Huff 's classification of UDAs based on type of application was selected for use in the study [33].

The questionnaire was field-tested by over 20 members of a regional association of information center personnel from the public and private sectors, the Virginia Information Center Exchange, at one of their regular meetings. ## Survey Population

The actual study population consisted of 135 members of the Information Center Managers Association of New York selected from the total membership on the criterion of regular participation in the activities of that organization. The group is composed of managers with responsibility for EUC, many of whom have considerable experience in large organizations where EUC has been a recognized form of computing for several years. The group was chosen because of its primary mission as a user-computing management association and because of the size of its membership.

The president and governing board endorsed the project, and the president provided the names and addresses of 135 individuals who regularly attend the meetings. The questionnaire was sent with a cover letter explaining the purpose of the study and noting the president's endorsement. A follow-up letter was sent to those who had not replied within four weeks.

Of the 135 questionnaires sent, 54 were returned, a 40.0 percent response rate. Eight of the questionnaires were discarded because of incomplete responses.

A profile of the responses (see Table 3) in each returned questionnaire was then developed using the following guidelines:

\- Response 1, “needed for most or all applications,” was interpreted as a recommendation that the form of documentation be used for most applications, even with low [few] documentation requirements.

\- Responses 1 and 2, “needed for most or all applications,” and “needed only for applications with high documentation requirements,” were combined to produce a profile of respondents’ recommendations for specific documentation items for applications with high [many] documentation requirements. The rationale for the combination of responses was that documentation forms recommended for “most or all applications” included applications with high documentation requirements.

\- The third category in the profile was for Responses 3, the response that a specific form of documentation was “not appropriate” for a particular UDA application.

## Limitations

This research has some limitations:

1. First, the values obtained are participants' perceptions and are not objective measures.

2. Because random sampling techniques were not used, caution should be employed in generalizing the results to other populations.

3. Only New York City area organizations were surveyed. This causes a geographical bias, because of the area's high concentration of corporate headquarters and financial organizations.

4. Only opinions of end-user computing managers were solicited, and a bias is caused by omitting opinions of the users themselves or of managers in other organizational areas.

5. Finally, a non-response bias may exist (i.e., the 60 percent who did not respond may have a different bias).

## Findings

The results of the research represent a framework for formulating documentation guidelines for UDAs; they cannot, however, be generalized to a larger population.

## Demographics

Demographics of the respondents and their organizations appear in Table 4. Respondents' organizations are grouped according to standard industrial code or type of public institution. Only four responses came from personnel who worked in organizations with no formal information center. The majority of the respondents list their job title as information center manager, assistant manager, project leader, or consultant.

H2: There are no significant differences in the proportions of recommendations for the documentation form across the six UDA categories.

Cochran's Q test was used to test the null hypothesis for each documentation form. The tests were conducted at a one percent level of significance with $6 - 1 = 5$ degrees of freedom.

The results of the analysis appear in Table 9. The Cochran's Q statistic for the first form of documentation tested, user's instructions, is 6.1364 which is less than the critical value at the one percent level of significance. Therefore, the null hypothesis is accepted and the recommendations for user's instructions are considered to be proportionally uniform across the six UDA categories.

For the second form of documentation, narrative descriptions, the Cochran's Q is 8.9535 which is also less than the critical value at the one percent level of significance. The null hypothesis is accepted again, and the recommendations for narrative descriptions are considered to be proportionally uniform across the six UDA categories.

The values of the Cochran's Q statistic for the remaining eleven forms of documentation are above the critical value at the one percent level of significance. Therefore, the null hypothesis is rejected for these eleven forms of documentation and the recommendations for them are considered not to be proportionally uniform across the six UDA categories.

Of the eleven documentation forms that are not uniformly recommended, ten forms are recommended most often for the UDA category of transaction processing. Only one documentation form – hardware/software requirements – is recommended more often for another category, that of graphics applications.

## Conclusions and Implications

User computing is an activity that must be managed if an organization is to reap the maximum benefits from the increased use of computers by personnel not classified as information systems professionals. Adequate documentation of UDA is important to insure that such applications are developed in accordance with appropriate quality assurance methods, that they can be used properly, and that they can be maintained. The following recommendations are based on the results of this study of documentation requirements for UDA.

Conclusion 1: Not all UDAs have the same level of documentation requirements.

## Recommendations:

\- To determine the appropriate level of documentation, each UDA should be evaluated according to the factors affecting documentation level. The factors proposed in this study (maintenance requirements, use of output by another system, etc.) can be used by EUC managers as a framework to formulate specific guidelines. User-developers can use these guidelines to assist in determining the appropriate level of documentation requirements for UDAs.

Conclusion 2: Recommendations for forms of documentation for UDAs with low levels of documentation requirements vary among the UDA application categories. Only user's instructions and narrative descriptions are uniformly recommended for all application types. Ten documentation items are recommended more often for transaction processing applications than for modelling, data analysis, simple query, report preparation, and graphics applications. Hardware/software requirements are recommended most often for graphics applications.

## Recommendations:

\- Separate minimum documentation guidelines should be established for each of the six UDA categories.

\- User's instructions and narrative descriptions should be a part of each set of documentation guidelines.

\- Graphics application guidelines should include hardware/software requirements.

\- Transaction processing application guidelines should specify a greater number of documentation items than other UDA types.

Conclusion 3: Recommendations for forms of documentation for UDAs with high levels of documentation requirements also vary among the six UDA classifications. User's instructions, narrative descriptions, input data descriptions, and output descriptions are the four forms of documentation that are uniformly recommended. Eight forms of documentation are recommended more often for transaction processing applications than the other UDA application types. Hardware/software requirements are recommended most often for graphics applications.

## Recommendations:

\- Separate documentation guidelines should be established for each of the six UDA categories for applications with high documentation requirements.

\- The guidelines should include user's instructions, narrative descriptions, input data descriptions, output descriptions, plus other forms of documentation appropriate to the particular type of UDA.

\- Guidelines for graphics applications should require hardware/software descriptions.

\- More documentation items should be included for transaction processing applications than other UDA types.
