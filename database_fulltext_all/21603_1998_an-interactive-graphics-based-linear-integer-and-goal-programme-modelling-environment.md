## Abstract

Model development packages have, in recent years, become a standard tool for the development of linear and integer programmes. This can be seen by the popularity of such algebraic modelling languages as GAMS, AMPL etc. Traditionally, they have been designed around text based systems, and therefore offer a formal and structured declarative language for model definition. However, with the onset of graphics-based operating systems, standard graphical screen objects can be utilised to offer a fully interactive and guided model development package. It is noted by Greenberg that providing analysis tools to the modeller offers a form of intelligent computer assistance. Therefore, it is a natural extension to the modelling package to provide an encapsulated environment for the investigation and development of linear, integer and goal programmes. A complete interactive graphics-based environment for the process of developing, solving and analysing linear, integer and goal programmes named MoGLI is presented. The specifications of the package are discussed for such anŽ . environment. User-interface screens for model definition are introduced and described, together with a formal algebraic modelling language developed primarily for model processing, although model definition can be performed in either mode. The integration of analysis tools such as preprocessing routines and infeasibility analysis routines are also described, together with standard model information screens. q 1998 Elsevier Science B.V. ## 1. Introduction

Many practitioners have described the process for solving problems using operational research techniques. Taha 24 describes five major ‘phases’ of an <sup>w</sup> <sup>x</sup> OR project and Pai-Chun et al. 21 further refine <sup>w</sup> <sup>x</sup> and qualify these phases specifically for the solution process of an LP problem. For the case of linear, integer and goal programming, the complete process is partly iterative consisting of the following distinct stages.

Ž . 1 Identification of a problem which can be optimised as an $\mathrm { L P / I P / G P }$ using the appropriate techniques.

Ž . 2 Investigation and formalisation of the problem, defining and formulating the problem in a structured form.

Ž . 3 Building a suitable model representation of the problem, constructing it in a form suitable for optimisation including data-management .Ž .

Ž . 4 Pre-analyse the model, using a standard routine 2,18 in order to offer some initial information<sup>w</sup> <sup>x</sup> about the model. This stage is optional .Ž .

Ž . 5 Optimisation of the model, using the desired solution technique in order to solve the model.

Ž . 6 Analyse the solution, validating the model. If the solution is determined satisfactory then it may be implemented. However, if the solution is determined infeasible, unbounded, obviously incorrect or simply not implementable, then the modeller must return to stage 3 or possibly stage 2 in order to analyse the Ž . inconsistencies.

Modelling is concerned primarily with stages 2 and 3 above and is the key stage in the process. It is during stage 3 where a real-life situation is translated into a representation suitable for analysis by computers. The format of representation used can vary dramatically, depending on how close a modelling system allows the modeller to represent the situation under consideration. The extremes of model definition are the human viewpoint, where general description of the scenario is preferred, and conversely the optimiser point of reference, where an unambiguous and precise computer structure is required. Eventually, the optimiser’s requirements must be satisfied for the model to be solved, so a compromise has to be made on the human viewpoint, but one which allows the model to be ‘converted’ orŽ . generated by a specific routine into the format necessitated by the optimiser.

There are a variety of methods in which this procedure may be performed. The least efficient, for even small models, is to input the model directly in MPS format 20 for a solver to interpret. Program- <sup>w</sup> <sup>x</sup> ming languages, such as FORTRAN, C<sup>r</sup>C<sup>qq</sup>, PASCAL etc., can be used to manipulate given data, thus constructing the MPS file necessary for solution. This requires substantial programming knowledge, but more importantly does not offer effective model management due to its specialisation. Less technical knowledge is needed for other types of model development approaches such as matrix description languages, block schematic languages 29 <sup>w</sup> <sup>x</sup> and modelling languages 23,6,11,10,19 . Popular <sup>w</sup> <sup>x</sup> spreadsheets such as Microsoft Excel and Lotus 123 also offer optimisation methods for use in the spreadsheet. However, spreadsheets do not make use of set or index management for data and variables, Ž . which is fundamental to mathematical modelling.

It is accepted that, in the general case, a modelling language is the most effective way of accurately defining a given situation as an LP<sup>r</sup>IP<sup>r</sup>GP. Before the introduction of modelling languages in the 1980’s, the general method for building such a model was to use a matrix generator 3 . This would involve writing specific computer programmes in order to create representations for models suitable for optimisation. Typically this would require a different programme for each model. Fourer 9 gives a<sup>w</sup> <sup>x</sup> thorough discussion of the differences between matrix generators and algebraic modelling languages.

The ‘ideal’ modelling environment which should be used as a basis for an LP<sup>r</sup>IP<sup>r</sup>GP modelling package includes;

<sup>Ø</sup> controlling the complete modelling and solution process

<sup>Ø</sup> being appeasing to both OR professionals and decision makers, allowing general ease of use and good understanding of the problem

<sup>Ø</sup> incorporating a model definition facility requiring low technical computer-language knowledge, making model manipulation straightforward.

Geoffrion 12 describes similar aims and notes the<sup>w</sup> <sup>x</sup> difficulties in attaining such a framework. ‘Visualization and optimisation’ is discussed in a review by Jones 17 .<sup>w</sup> <sup>x</sup>

In a general LP<sup>r</sup>IP<sup>r</sup>GP modelling utility, little automatic model definition can be applied unless dealing with a specific group of problems i.e. net-Ž works . Therefore, in most cases knowledge of LP. system capabilities and requirements is a requisite skill needed by the modeller. Thus, automatic model creation with specific parameters is an unrealistic expectation in terms of intelligence of the system. However, the modelling environment can control the complete modelling and solution process offering straightforward use to analyse various aspects of the model under development. Greenberg has developed ANALYZE 13–15 using such a philosophy. Fur- <sup>w</sup> <sup>x</sup> thermore, facilities such as a pre-analysis routine, links to a solution method and direct infeasibility analysis all combine to offer ‘intelligent’ analysis of the model in a complete integrated environment. Greenberg 13 notes such analysis tools as a form of<sup>w</sup> <sup>x</sup> intelligent computer assistance which should be available to the modeller.

Section 2 of this paper gives a brief overview of currently available commercial modelling systems. The specifications of an ‘intelligent’ modelling environment for the development and general processing of LP<sup>r</sup>IP<sup>r</sup>GP are then discussed in Section 3. These ideas have been captured in order to form a complete modelling environment for developing LP<sup>r</sup>IP<sup>r</sup>GP, named MoGLI. The interactive environment designed is detailed in Section 4, showing the techniques applied to allow model building using a familiar graphical user-interface—MS Windows. The MoGLI declarative language is formally described in object form, in Section 5, detailing further general technical operations. Integration of the analysis tools, optimiser and other system facilities are finally described, in Section 6.

## 2. Overview of commercial LP modelling systems

A recent survey of currently available algebraic modelling languages, including alternatives, is given by Sharda and Rampal 22 , detailing the various <sup>w</sup> <sup>x</sup> capabilities offered by commercially available packages highlighting their differences.

Traditionally, the user-interface of modelling languages is command oriented, although menu driven environments are offered by such systems as AIMMS and MPL. Links to popular solvers or optimisers Ž . are common, both internally and externally to the modelling language, as are presolve routines. Any solvers can be attached to most modelling languages, especially those solvers which offer the standard MPS input format. IIS detection, infeasibility analysis routines, are becoming more available with solvers and therefore callable by the modelling language through the solver itself.

Most modelling packages offer data import facilities. Variable bound information is a standard feature, although semi-continuous variables, and SOS1 and SOS2 types see Williams 30 are not always Ž <sup>w</sup> <sup>x</sup>. included. Modelling language ML syntax checking Ž . and model integrity checking is offered by all packages. On-line help is an aid offered by systems using a system shell to control the process, which those languages used in a generic text editor cannot offer.

They are also available over most types of operating system, due to the portability of the text based programming languages that they were originally developed in. Some have been converted into graphical environments, especially MS Windows, although using the modelling package is typically the same for model development as previously.

## 3. Specifications of a modelling language for LP<sup>r</sup> IP<sup>r</sup>GP

In order to achieve a modelling environment encompassing the criteria described in Section 1, MoGLI has been designed according to the following specification:

<sup>Ø</sup> Primarily, the modelling system is capable of building linear, integer and goal programmes, using their relative terminologies.

<sup>Ø</sup> A graphical user-interface is incorporated—i.e. MS Windows.

<sup>Ø</sup> MoGLI aims to control the whole environment for LP<sup>r</sup>IP<sup>r</sup>GP processing.

<sup>Ø</sup> An interactive approach is the main technique for model building.

<sup>Ø</sup> No formal declarative modelling language knowledge is necessary, although it is available for experienced users.

<sup>Ø</sup> Models are constructed in a row-wise format, typically how the majority of LP<sup>r</sup>IP<sup>r</sup>GP models are envisaged.

<sup>Ø</sup> Modelling errors are available in the form of descriptive messages, highlighting syntax errors and simple model anomalies.

<sup>Ø</sup> There are full links to a matrix representation viewer, pre-analysis, infeasibility analysis and the possibility of any commercial optimiser.

<sup>Ø</sup> No specialist knowledge of external software is required, i.e. the optimiser is linked just through a selection button.

<sup>Ø</sup> The capability of also being run from a windows command-line, e.g. in batch processing mode.

As with most software packages, there is a certain amount of background knowledge required to use MoGLI effectively. For example, the system can guide the user through the requirements to build a model, but prior knowledge of linear programming is required to understand and build a representative model of the situation being analysed. Also, the knowledge of simple sum structures, as in any spreadsheet is assumed in order to construct necessary constraints.

The most popular commercial model development packages, such as AMPL 10 , GAMS 6 and MPL<sup>w</sup> <sup>x</sup> <sup>w x</sup> <sup>w</sup> <sup>x</sup> 19 , typically concentrate on the modelling language in order to define and manage a model. Although in recent versions of MPL more assistance is given to the user through menu systems for model control. The MoGLI prototype, however, aims to provide a model development interface which is not syntax driven, but uses specifically designed screen layouts for model development. This removes a significant amount of the language knowledge needed by a user to develop models, making further use of the ‘userfriendly’ graphical environment.

Incorporating the specifications detailed above, the modeller is offered a complete environment to control the processing of an LP<sup>r</sup>IP<sup>r</sup>GP model throughout its development. In this way software knowledge is kept to a minimum, using optimisers, pre-analysers and infeasibility analysers as ‘blackbox’ routines, driven by a standard menu system. The translation of necessary results is returned to the modelling environment for further analysis, with full access to the model under investigation.

Currently, portability is possibly the only negative issue of a package developed in an object oriented graphical environment. However, this is becoming less important as technology advances, especially with the growth in power of desktop computers and the efficiency of optimisation packages. Therefore, for many real-life problems, a single common desktop computer is sufficient.

## 6. System integration

Model analysis tools, pre-analysis and infeasibility analysis, are typically built into an optimisation package, accompanying the solution method s ,Ž . which is currently treated as a black-box function during the problem solving stages. In order to fulfil the requirements of a complete model processing environment, in conjunction with the modelling system, it is necessary to allow full and seamless access to a solution method, a pre-analysis routine and infeasibility analysis aids 16 . This should provide full interaction between the modules enabling the modeller to interactively build the corresponding model, pre-analyse the model, solve the model and perform infeasibility analysis if necessary . DolkŽ . and Kottemann 8 discusses a specific model manip-<sup>w</sup> <sup>x</sup> ulation language for model management and integration.

An optimiser can employ a revised simplex based solution algorithm and<sup>r</sup>or an interior point solution algorithm for $\mathrm { L P / I P / G P } .$ A pre-analysis routine, typically consisting of a number of independent procedures iteratively combined 5,2,18 , is fundamen- <sup>w</sup> <sup>x</sup> tally a distinct module, whether it has been developed into the optimisation package, as part of the modelling system or as a separate programme. Also,

IIS detection algorithms, especially GPIIS, are efficiently incorporated into a revised simplex framework 28,7 . Thus, whichever tool is to be invoked in<sup>w</sup> <sup>x</sup> the modelling environment, no detailed knowledge is necessarily required by the modeller concerning the implementation of these tools.

Specific structures allow suitable reporting of the results, obtained from pre-analysis and infeasibility analysis, in the modelling system. The information obtained can be saved to an external text file, allowing the modelling system to report such results in any format output by a module. However, if the structure advised by the modelling system is not available, then further manipulation of the results is limited. Integrated system facilities which MoGLI offers at present are initial model analysis, a matrix representation viewer and a model statistics report, and extended model analysis, a pre-analysis module, an infeasibility analysis module and an optimiser communication module.

## 6.4. Single<sup>r</sup>multiple IIS detection

## 6.5. Infeasibility set detection

However, the final section of the file, as shown in Fig. 5, details the infeasibility set results. This consists of three lines; the first gives the number of constraint members in the infeasibility set, the second gives the index numbers of these constraints and the third offers an optional flag signalling the authenticity of the infeasibility set. If this flag is ON in the infeasibility analysis options, then the optimiser is recalled to check the feasibility of the constraints in the model which are not members of the reported infeasibility set.

## 7. Summary and conclusions

MoGLI is a system which encapsulates the com plete model development process, from representing an initial model to finding an implementable solution, incorporating all of the tools necessary for model building, analysis and solution. The environment is interactive in nature, developed in the most popular graphical user-interface—MS Windows— using the familiar screen objects for model representation although the arguments hold for any suchŽ operating system . Therefore, this significantly re-. duces the knowledge-base required concerning traditional programming languages and software implementation.

MoGLI takes advantage of the graphical environment to allow model definition in an interactive fashion, which requires no specialised knowledge of an algebraic modelling language in order to develop a model. However, a good knowledge of linear programming is a necessary requirement for the modeller to have in order to develop representative and useful models. Capability for the modeller to use the underlying modelling language explicitly is possible, if required, with the option of switching between definition modes.

Generally, a modelling system is the ideal environment in which to combine the necessary model analysis tools into a complete framework, as is highlighted by the majority of the popular commercial modelling packages. MoGLI achieves this by offering the modeller an algebraic modelling language for definition of a linear, integer or goal programme, a pre-analysis routine for investigation into the model, various IIS detection options forming the infeasibility analysis aids and the ability to link to any preferred optimiser.

The seamless integration of the model analysis tools within MoGLI is an important feature of the environment. As well as the matrix representation viewer and the model statistics information, there is the capability to use any tools offered by any optimisation package, as programme parameters can be set in a variety of ways. However, for the development of MoGLI, the large-scale sparse linear and integer programme solver, LIPSYS, and the goal programme solver, GPSYS 26 , have been integrated into the<sup>w</sup> <sup>x</sup> environment.

The techniques described in this paper offer an effective environment for the development of LP<sup>r</sup>IP<sup>r</sup>GP. The simple availability of the described analysis tools in an interactive graphical user-interface, aids the modeller greatly. Such a system would be of use to the most-experienced analyst, but also to those relatively new to LP<sup>r</sup>IP<sup>r</sup>GP development.
