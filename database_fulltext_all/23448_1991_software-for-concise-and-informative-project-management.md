# Software for concise and informative project management

P C RHODES

Department of Computing, University of Bradford, UK

Abstract: Managing a project is an involved and many faceted job requiring a combination of management, organization and technical skills. Current methods tend to be based on lifecycle principles and so are project management tools. Additionally, project management is learnt by a process of 'coming up through the ranks'. Modern methods of structured analysis and design, computer aided coding and the move towards prototyping cause one to question whether or not the current management style, the support tools and training methods are going to be appropriate for tomorrow's technology. This paper proposes an alternative model of management and examines it to see whether or not it is better suited to modern methods, to being computer aided and to training the next generation of project managers.

## Introduction

The principle of software engineering is to apply a systematic methodology to the development of computer software. Traditionally (Archibald, 1976; Boehm, 1976; Enger, 1981; Hennell, 1985), it advocates that the task of software development is broken down into a series of reviewable stages which form the project lifecycle. These stages are typically

(1) Requirements Analysis;

(2) Functional Specification;

(3) Analysis;

(4) Design;

(5) Coding;

(6) Testing;

(7) Implementation;

(8) Maintenance.

Many companies now require their project managers to produce a formal project plan. This will contain details of the proposed organization and staffing of the development team. It will also contain estimates of costs and plans for controlling the project's budget and will define a method of assessing the progress of the project usually by the use of milestones and baselines. In addition, it will give details of the techniques which are to be used to ensure the quality of the final product and methods for controlling change and recording issued versions of software, i.e. configuration management.

Since the lifecycle model is assumed to be the model for the project, the former activities follow the lifecycle mentality. For example baselines are likely to be set at the completion of one of the lifecycle stages and milestones chosen to tie completion of parts of the lifecycle to particular dates along the way to project completion. The method assumes that in an ideal world software development is a linear process and one only has to backtrack if someone, somewhere, has made a mistake (Parr, 1980).

As a result, rigid time-based planning procedures such as PERT are used to plan projects. These methods make backtracking very difficult and reinforce the feeling that to rework a previous stage is a major disaster. This is in spite of the fact that every practitioner knows that the nature of the job is iterative and some reworking of earlier stages is almost inevitable (Zave, 1980).

The lifecycle model has not only put the project manager in a straitjacket it has also fragmented the supporting tools. If one surveys these tools (START Guide, 1987) one finds different tools for all stages of the lifecycle. Moreover, these tools do not operate in unison and, in spite of attempts to produce a standard interface for this type of tool (Bourgignon 1985), one can easily observe (START Guide, 1987) that the tools overlap and leave gaps in the overall process, making the choice of a complete set of interconnected tools impossible. This is because the lifecycle model with its linear progression through several stages, which are perceived to be fundamentally different, causes fragmentation and duplication of tools.

Strict linear progression and fragmented supporting tools are not the only disadvantages of adopting a lifecycle model. Another disadvantage is the progression of staff. Traditionally, there has been a tendency for staff to follow the lifecycle backwards during their career progression. For example, a new recruit will start doing maintenance, move through coding to design, finally moving to analysis and then onto managing small projects. This can be a long tedious process which does nothing to foster a team spirit or an understanding of the problems of management and goes against modern cognitive approaches to management (Trist et al, 1965).

If, indeed, it is our model of the management process which causes the undesirable consequences then it is reasonable to try alternative models and see if the problems can be avoided. This paper proposes one alternative model and examines the effects of its properties on the above problems.

## An alternative model

Many systems are now analysed and designed using a top down hierarchical approach. In fact, there is even a trend towards specifying a system in a top down manner (De Marco, 1979). Since this approach is proving sound, reliable and practical for the technical aspects of the work, it is an approach which might be worth pursuing for the management of the project.

Indeed, one of the justifications of the current method of management (Lock, 1984) is that it maps on to the lifecycle view of a project. It is equally justifiable to argue that since many modern analysis and design formalisms (Clare and Coe, 1988) take a hierarchical view of a system, a management method which mapped onto this hierarchical approach would be appropriate. In any event, it suggests an alternative model which can be used to investigate the issues raised earlier.

Top down hierarchical analysis and design considers a system as a whole and then identifies subsystems which, together, make up the whole system. Each subsystem is treated in exactly the same way as the original system and the process continues until a desired degree of resolution is achieved and the system can be uniquely and completely specified. If we take the same approach for the management of a project then the management model will take the form of a tree. This is quite desirable. The theory of trees is well developed (Tenenbaum and Aubenstein, 1986). Other structures, such as networks, can be transposed into trees (by duplicating nodes if necessary) and these techniques have worked successfully in other areas, e.g. databases. However, if we are to use a tree structure we must observe the fundamental principle of a tree, i.e. any subtree must also be a tree itself. This has the consequence that a leaf, being a subtree of one node, must have the same properties, and be subject to the same operations, as the root. Therefore, we need to postulate the existence of a tree of project components such that each component of the project has the same properties and where each may be subject to the same operations. This is not a difficult concept. Every project is composed of several sub-projects which in turn are composed of sub-sub-projects etc.

It does, however, contrast markedly with the conventional view of project lifecycles which envisages the project passing through several distinct phases (Archibald, 1976). The requirements for people, skills and resources change as the project passes through each of these phases. Consequently, the organizational structure is also thought to require changing for each phase of the lifecycle. Conventional project management, therefore, tackles the project stage by stage (Parr, 1980).

However, there is no fundamental reason why a hierarchical decomposition should not be used to manage a project. Figure 1 shows a project broken down into a component tree. The root of the tree, component A, is the entire project. This project is composed of the components B, C, D and E. Each of these are projects in their own right and when all are complete A will be complete also. Similarly the component B is a project composed of the four sub-projects F, G, H and I. Once they are all complete B will be complete also. The components C and D on the other hand, are small enough to not require being broken down into sub-projects.

How small is ‘small enough to not require being broken down’ (Brookes 1974)? At the end of the day a project is implemented by individuals. There are many reasons why the smallest component, the leaves of the tree, should be one man projects. They may be one-week projects or one man-year projects, but if they can be done by one person they are suitably small. There are many obvious advantages to this. Most people work best when given responsibility for their own clearly defined area. Since all the components have the same form the leaf is a one-man project and the person is project manager of his/her own component. The overall project manager also has a clearly identified member of his/her team for each component. In addition, a team leader, allocated the component H, has a clear responsibility within the management structure.

This clearly already addresses some of the problems mentioned earlier. The management style is now compatible with the cognitive approach to management. Software professionals should respond well to the delegation of responsibility and the accountability which goes with it. In addition, there is now an obvious progression and ample scope for in-job training and early appreciation of the problems associated with the higher levels of management.

## Defining a component

Since every component has to be a project in its own right the management of each component still has to be defined. Ironically, the obvious method to adopt is based on the old lifecycle model. Each component should be completed in a series of stages and these stages could be, but do not necessarily have to be, those of the software lifecycle, i.e. requirements analysis, functional specification, analysis, design etc.

Every component has to have the same set of stages but, since every individual has their own idea of what the stages should be, the stages chosen for a particular project should represent a board consensus for the project. Some people closely link the lifecycle stages with the configuration management concept of baselines (Bersoff et al, 1980). Some projects require many baselines, some require few, but it has to be remembered that the stages must always be relevant to every component.

At this stage, it is pertinent to hesitate and see where all this is leading. Is the theory leaving reality far behind? On closer examination it can be shown that it is not. All that is required is a more thorough approach. As an example, consider the usual starting place for a project, the user requirements document or functional specification. It may be the first stage of the root component. Is there any reason why it should not be the first stage of every component? No, indeed there is every reason why it should be. Each is its own little project. Each should specifically state what part of the functionality it is responsible for.

Similarly, projects are often split into software and hardware. At first sight this too would be impossible with the system proposed here but again, this is not the case. The software must run on hardware, even if it already exists it is a good idea to write down its functionality. It will at least confirm that the existing equipment is suitable. The same is true for all other stages of a component. A particular stage in one component may be trivial, it may even be empty, in which case it is only present in order to allow conformity across components. But, this restriction does not seem insurmountable and the benefits which can be gained from the enforced uniformity (discussed later) far outweigh the disadvantages.

## Definition of a 'manageable' component

It is now necessary to consider in detail what form a component should take. Whatever form is given to one component must be given to all components in order to conform with the proposed model. To comply with the now well accepted practices of configuration management (Bersoff et al, 1980) each component should have a set of 'states'. Typically, the states required are shown down the left hand side of Figure 2.

Each component will be started at some time and hopefully will eventually be completed. The ‘actual start’ and ‘actual finish’ states are therefore self-explanatory. However, the project plan should state when it should have been started and when it should have been completed, the ‘scheduled start’ and 'scheduled finish' respectively. These four states are, therefore, not surprising.

The last state ‘required change’ may, however, not be quite as obvious. Many components, once finished, will require to be changed for one reason or another, even though every attempt is made to avoid it. The principles of configuration management require this fact to be recorded. In addition, it is desirable to establish the consequential effect of change and it seems prudent to plan a data structure with the facility for doing so.

On the right hand side of Figure 2 these five states have been collected together into the two main configuration management concepts, namely the 'development object' and the 'configurable item' (Bersoff et al, 1980). The nature and number of individual stages would be left for the user to define. In this way, the project can be run according to 'in-house practices' or the demands of an individual project. The only restrictions on the choice is that they must apply across the board and not be specific to one component.

Components, therefore, go through various states and have various stages. It is immediately obvious, however, that each stage can be, at some time or other, in any one of the states. The states and stages of a component form a matrix of the type shown in Figure 2. Any particular stage may be unable to start whilst another is already finished and yet others are in the process of being completed.

One can appreciate that even if the knowledge about each matrix element is restricted to a simple ‘done’ or ‘not done’, a fairly complete understanding of the status of the project can be achieved. This is then, quite clearly, an excellent monitoring system although it will be shown later that it can be much more than this.

## Blocking

It is now necessary to introduce another concept. Some components cannot be started because they are blocked by something which must be done first. To be more precise, any stage of any component may be unable to start because it is blocked by something else which must be done first.

This blocking effect needs to be investigated. In order to achieve the aims, blocking must work on all components in a similar manner. Common rules must be drafted which apply to the blocking of all stages of all components uniformly:

In order to do this, consider a set of stages which may apply to any component. Consider, for example, stages consisting of functional specification, system design, production and implementation. Initially, consider also a component in the middle of the tree (Figure 1). The functional specification of a module will be blocked by the functional specification of the father (using normal tree terminology). Not until the functionality of the father is established can that part of the functionality which is to be provided by the son be identified. A stage in the father can, therefore, block a stage in the son (Figure 2). The design of a component is blocked not only by the design of its father but also by its own functional specification. A stage can, therefore, be blocked by prior stages within itself as well stages in its father.

Figure 1 A component tree. Note: (1) no father has only one son; (2) subtree B obeys the same rules as tree A etc; (3) total system = components A, components $(B+C+D+E)$ , components $((F+G+H+I)+C+D+(J+K))$ etc; (4) eventually the leaves are components which can be tackled by one person.

These are not the only possibilities, however. Consider the implementation stage. The implementation stage may well be bottom-up, whence the implementation of the father cannot be started until the sons are finished, i.e. their implementation stage is complete. It is, therefore, possible for stages in the father to be blocked by stages in the son.

If these mechanisms are considered more closely, however, a pattern emerges. The design stages of the father block the design stages of the son, the design stages of the son block the implementation stages of the son and the implementation stages of the son block the implementation stages of the father (in bottom-up implementation). In Figure 2, therefore, the stages are split into two broad categories: 'design' which is blocked by the father and 'implementation' which is blocked by the sons (if any). Notionally, the stages have been put into order so that stages from left to right block each other.

Unfortunately, if more rigorous blocking rules are postulated it is very easy to come up with examples where they do not hold. There are, therefore, two options, namely: (1) Choose the stages to fit the blocking rules; or (2) Devise blocking rules for each project. The first of these is obvious and requires no further discussion. It may be the best approach, it may be too restrictive. Only further research will provide the answer. The second option offers much more flexibility. The blocking rules used must, of course, apply throughout the tree but it is left to the user to specify what the rules are. The rule can be specified using a blocking plan as shown in Figure 3.

Certain aspects of the overall rule are built into this plan. There is no facility, for example, for the father's implementation to block any stage in the son. However, the plan can be used to state specific blocking within the above generalized framework\*.

## Computer aided support

The basic model has now been defined and it has already been demonstrated that some aspects, namely style of management and ease of training, have benefited from a change of model. The acid test for any new model of project management is, however, the ease with which it can provide computer aided support since this is likely to produce most benefits in terms of effectiveness and efficiency. The ability to support management based on the above model must, therefore, be examined critically.

In order to propose a computer-aided project management system the minimum amount of data required to control a project must be established. The minimum data set is actually quite small. All that is required is an estimate of the effort required to complete each stage of every component and subsequently the actual effort used. If resource allocation were to be included it would also be necessary to specify a skill level for each stage, possibly of each component. Given this information and the blocking diagram a program can easily compute and save the component data shown in Figure 3. This minimum data set will then be held for each component to form a very comprehensive but uniformly processable data set for the entire project. In order to achieve uniformity, each component should be represented by an identical data structure.

The data should allow the production of the most complex of information, such as critical path analysis and resource management. It should also provide the most fundamental of management information; namely how much work has been completed and how much remains to be done at any given time. Since the minimum data set will only be held once, any updates of this data will automatically appear throughout the system. For example, estimates of the effort required to complete a stage of a component will be held in that component's minimum data set and it will be referenced at that location by whatever facility requires it, whenever it is required.

This centralized approach of storing only a minimum set of data eliminates the duplication and mismatch problems associated with using many independent packages but, since the data set is the minimum set, deduceable information will not be stored.

## Scheduling

Given the component tree as shown in Figure 1 component stages specified according to Figure 2 and either a default or a specified blocking plan, depicted in Figure 3, an activity network such as that shown in Figure 4 can be drawn. The drawing of the activity chart is entirely automatic and entirely a consequence of the previous information and the imposition of global rules. It could, therefore, easily be generated by a computer. The implications of this are far reaching. Once an activity diagram is available, critical path analysis can be performed and effort requirements can be calculated. Consequently, the health and viability of the project can be directly assessed.

However, before the activity analysis can be used for critical path and effort analysis more information is required for the system. Initially, this is in the form of estimates. The system requires an estimate of the effort required for each stage of each component of the project (see Figure 5). This may seem rather a lot, but it is becoming a generally accepted method of estimating (Pressman, 1982). It is, therefore, a worthwhile exercise in its own right. Given the effort estimates, the blocking plan and the component tree, we now have the data needed to work out the activity network and to calculate the critical path.

If timescales are not being met troublesome components can be split. These could then have, by implication, additional people working on them and consequently should reduce the time taken to execute the critical path. If the components on the critical path cannot be split, increasing effort would involve giving two people the same task. This is highly undesirable and rarely produces the required effect (Brookes, 1974).

By following the above techniques the component tree can be developed until it describes the project fully.

## Monitoring the project

It is now quite clear how the project can be monitored. The information stored for each component gives estimated times and actual times. A comparison of these will quickly determine the overall state of the component.

As actual times become available these will be used in the activity network. Critical path analysis will then give the estimated project completion date and highlight those limbs of the tree which are potentially troublesome.

## Controlling change

The system described will also cope with change. If a component requires change the fact is flagged in the appropriate parts of the component matrix. Such a change can potentially affect the entire subtree of which it is a part. In fact, a particularly nasty change could affect the entire tree. The consequences of the change must be propagated upward until an ancestor is reached which does not require modifying as a result of the change. All descendants of the last modified ancestor then require checking for change.

## Efficiency of the software support

The real impact of this system is derived from a study of the inputs required of the user. Because the structure and the rules pertain to the entire system, the user only has to provide the absolute minimum of information. The component tree must be defined, the stages must be named and if a default blocking plan is not to be used, a user-specified plan must be provided. All these are global and not data intensive inputs. The only major intensive inputs are those of the estimates for each stage of each component of the tree. But, if the project is to be undertaken with any true idea of the likely cost this must be done anyway.

Once this information is provided the computer will provide an activity plan and the results of the critical path analysis. All information, such as scheduled starts and scheduled finishes will be provided by the computer for each stage of each component. The computer can, therefore, provide much of the information from the absolute minimum amount given.

Once the project is under way the system must collect actual starts, actual finishes and actual effort figures. Provided this information is maintained the system will be able to say if the project is on schedule and meeting cost targets. It can give a revised completion date if not. It can also revise the activity network if necessary. In this way, the minimum of information is collected, used globally and the feedback maximized.

## An integrated software support tool for project management

Whether or not the project management model described above is capable of being supported by a single software tool can, ultimately, only be tested by attempting to write such a program. An initial prototype has been developed at Bradford University, written in Turbo Pascal, running on an IBM PC Compatible with extremely promising results.

The program depicts the project in the form shown in Figure 6. This form was chosen entirely for its ease of programming but, it is quite pleasant to work with once one becomes familiar with this representation of a tree. The program has facilities for both setting up and managing a project and perhaps the easiest way to describe how it works is to follow a project through these phases.

![](/api/attachments/9HH4RBFT/fulltext/images/99cf319dc40db71696850fc2d5289763ff8f132b49c4e9d24a13d418f2d0ed75.jpg)  
Figure 6 A component tree as depicted on the VDU screen

The first step in the definition of a project is to specify the stages which are going to be used, see Figure 2. For example, a simple project may only require the following stages:

(1) Design

(i) user requirement definition,

(ii) system requirement specification,

(iii) software specification,

(iv) software design;

(2) Implementation

(i) coding (self and/or integrating code of sons),

(ii) testing (self and integrated sons if any).

The states, i.e. blocked, scheduled start, actual start etc, are predefined in the program and are set automatically as the project progresses. The only other prerequisite is a blocking plan of the project, see Figure 3.

The next step is to construct a tree which represents the project. The program provides several facilities for doing this, for example, the addition of a given number of sons to a component, the deletion of a component, the wholesale movement of subtrees etc. It also has a crude zoom-in, zoom-out facility to assist with trees which are too big for the screen. At some stage during the construction of the tree every component must be given a name. The entire tree structure does not have to be completed at this stage, however, as it can be extended later.

Once a tree is defined, an estimate of the time required to work every stage of every component is required. The program's facility for doing this provides the user with a table of stages for each component, see Figure 5, and the user simply completes the table (in a free format mode).

At present, the program does not work to a calendar; it works in terms of weeks or days into the project, i.e. if the estimates were given in weeks then the output from the program must be interpreted as weeks. Thus the program talks about week 6 of the project for example. Consequently, once it has the above information it can automatically calculate a scheduled start time and scheduled finishing time for each component in terms of number of weeks into the project. Once the 'minimum data set' for the project has been defined and initialized in this way, the program can be used for its real purpose, namely that of managing the project.

Clearly, throughout the project, the minimum data set must be kept up to date. The minimum data set is stored on disc between sessions together with a representation of the tree. Every time the program is started it requests the name of the project in question and the number of weeks into the project. Component information is updated by placing the cursor on a component of the tree and selecting an option which displays the corresponding data set. Any data in this set can then be changed, for example the actual start can be given. This very simple technique is all that is required during the course of the project.

The actual management of the project is done visually. The tree is depicted in green on a black background during the clerical operations. The program itself has a series of highlighting modes which enable the manager to see the health or otherwise of the project before going deeper into the whys and wherefores of the problem.

The simplest highlighting option is for checking the initialization and each restart. If it is selected it turns any component which has an incomplete minimum data set, red. This is originally used to check completeness and also to check that data has not been accidentally corrupted at a later stage.

All the other highlighting modes split the boxes representing the components into a series of equal vertical stripes, one to represent each stage within the component. This can then be used to give a very graphical view of the state of the project.

As an example, consider Figure 7 which depicts the highlighting mode which shows whether or not the project is running on time. Any component which is entirely in the correct state, i.e. every stage is in the state it should be in, remains totally green on the screen (unshaded in Figure 7). But, any component which has a stage which is not in a correct state, e.g. should have been started but has not yet been started, has the corresponding stripe shaded red (cross hatched in Figure 7). In addition, this mode highlights, in yellow, any stripe corresponding to a stage which has not reached its scheduled start time but is currently not blocked, i.e. is ahead of schedule (dotted in Figure 7). A manager can, therefore, see at a glance which parts of the project are in difficulties and which parts are ahead of schedule. Figure 7, for example, depicts a project with serious problems in the right subtree, probably due to a design difficulty which arose in component U but which propagated a requirement for change right back to the root module. On the other hand, it is well ahead of schedule in the left subtree, i.e. ready for coding ahead of schedule.

Seeing where the problems are, is, of course, not the only thing the manager wants to do. She/he will also want to know why and by how much. To answer these questions she/he will only have to move the cursor to the offending components and request to see the data set. All should then be revealed; at least in terms of actual times versus scheduled times. The source of the problem is likely to be the component which has an unstarted stage with the earliest scheduled start.

Other management aids can be depicted in this way. One which is worthy of mention is the management of a ‘required change’. If it is discovered that a particular stage of a component requires a change in its specification, for whatever reason, this can be flagged using the ‘requires change’ state. The manager is then permitted to enter into a mode whereby the computer propagates the change backwards towards the root of the tree, i.e. the top level component. At any state on the way up the manager is able to indicate that she/he believes that the change can be contained at this level. Once this has been done the computer propagates the change forwards until all affected components have been flagged. It is then necessary to revise the estimated times for each stage in each component affected and finally reschedule the project to include the change. The highlighting modes are used to keep track of those components requiring change throughout this exercise.

Figure 7 The use of colour (or grey tones) to indicate stages which are ahead (dotted) behind (cross hatched) schedule

Because the data is stored between sessions a minor amount of file management will permit the program to be used in a 'what if' mode. The program can be started from the genuine data and the manager can try a particular scenario in order to estimate the consequences of making a particular change. Once his/her deliberations are complete, she/he can save the scenario to a different file and then try an alternative solution. Once all the alternatives have been tried, the best one is chosen and the corresponding file is used to provide the data for continuing the project.

A shrewd reader may have noticed that at no time has the maintenance stage of the software lifecycle been mentioned and certainly there has been no mention of a maintenance stage in the components. This is because the maintenance stage does not exist in this scheme of things. It becomes, what it has always been, a requirement to make changes. Nothing in the proposed method dictates that 'requires change' can only be used whilst the job is in progress. Quite the contrary. The program requires that a component be changed, even if it is complete, if it falls within the repercussions of a change. Consequently, even if the project is finished, the 'requires change' option can be used to assess the extent of the change, estimate the effort required and schedule its execution.

The effect of this pictorial representation of the project is quite dramatic. Once the project has been initialized the shape of the tree does not change. Even if the project has to be rescheduled or components have to be reworked, the basic shape stays the same. This is in stark contrast to a PERT type analysis which could change dramatically if the project is rescheduled. The project manager is, therefore, presented with a much more stable representation of his/her project.

The above software was produced quickly and easily until it became necessary to try to produce a PERT type analysis from the model. At this stage recursion cannot be used since recursion wishes to search depth first and does not model the parallel nature of the work on the project. To do this requires breadth first development of the PERT chart. It requires a simulation of the multitasking nature of a project team.

In order to prototype this part of the supporting software it was decided to adopt, at least temporarily, a more suitable language and SIMSCRIPT II.5 was chosen (Law and Larmey, 1984). A discrete event simulation language was chosen because there were many similarities between the hierarchical model of project management and discrete event simulation. Both had many concurrent processes, had to provide for one process to wait until another reached a predetermined state and had to allocate limited resources to competing processes. SIMSCRIPT II.5 was chosen because it exists as a language in its own right and provides for low level coding mixed with high level modelling all within the same code.

Once the mysteries of recursively generating concurrent processes and passing flags between them had been unravelled the SIMSCRIPT II.5 model showed great potential. It was demonstrated that a relatively simple program could map the hierarchical tree model of the project into a PERT-like analysis giving, in effect, a simulated run of the project. Moreover, the SIMSCRIPT model demonstrated that it was very easy to declare resources and calculate the effect of this on the project. In fact, by using the probabilistic functions provided in SIMSCRIPT it was clear that SIMSCRIPT II.5 could not only be used to produce a PERT-type analysis, but would easily produce a full blown simulation which could also be used to assess risk.

## Future developments

The potential for further work is clear. The original Pascal program demonstrated that by using the hierarchical model an integrated project management software tool can be achieved. The SIMSCRIPT II.5 work introduces the possibility of even greater power and the next step would be to code a second prototype in SIMSCRIPT II.5 from the beginning.

The potential shown so far has been achieved by discarding the lifecycle model in favour of a hierarchical model. This model was the only model considered. It may be that, fortuitously, this model is particularly easy to support with software. On the other hand, there could be even better models. Certainly, there would appear to be good reasons which indicate the need for a long hard look at the lifecycle model to see if it has not outlived its usefulness.

## Conclusion

It has been shown that some rather theoretical ideas can provide a concise informative tool for project management. But the theory is very idealistic and has yet to be exposed to the harsh effects of reality.

However, an idealistic model such as this is programmable. A pilot system would not be excessively large in either man or machine resources. A typical micro-computer would be adequate to develop an initial prototype.

The ideas have yet to be tested in real situations but some initial brushes with reality have been promising. There is some cause for being optimistic that a system of this type could be made to work ‘in the field’ and the author would welcome comment from interested readers on the viability of the above proposals for project management.
