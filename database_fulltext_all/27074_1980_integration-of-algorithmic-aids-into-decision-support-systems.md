# INTEGRATION OF ALGORITHMIC AIDS INTO DECISION SUPPORT SYSTEMS\*

By: L. C. Barbosa
R. G. Hirko

## Abstract

This article reports on an application for which a districting algorithm was integrated into an existing decision support system. From this experience a set of guidelines was derived which may be helpful to the system designer who has a similar task. These guidelines aim to improve the interface, feedback, flexibility, and control of the integrated system.

Keywords: Decision support systems, algorithmic aids, aids for decision making

ACM Categories: 3.50

## Introduction

In recent years much has been written regarding the usefulness of decision support systems (DSS) in solving unstructured $^{1}$ or semi-structured problems [12, 2]. One of the reasons for the effectiveness of DSS is that the user is given control of the problem solving process. Another reason is that usually in designing a DSS some consideration is given to the creation of a convenient human interface.

On the other hand it is well known that the use of complex models or algorithms by decision makers has met with mixed success $[8, 9]$ . We therefore suggest that management science techniques in general, and algorithms in particular, can be made effective by adopting some of the qualities of DSS such as flexibility, control, and use of feedback. Since many users of DSS are not algorithmically or mathematically oriented, special consideration must be given to how a user can maintain control of an algorithmic aid in a problem solving situation. Following the above suggestion, we discuss in this article the problem of integrating algorithmic aids into DSS.

## Difficulties of using algorithms

Most of the following remarks apply to models or other complex computational aids as well as algorithms. There are some well known difficulties in the use of algorithms by the non-analyst user. Most of these relate to the rigid structure imposed by the algorithm and the unsatisfactory result obtained when one tries to force the human decision maker into this framework. For example, one difficulty is that the structure of a problem is often undefined at the outset whereas algorithms require a rather rigid structure to be determined beforehand. As the user develops a further understanding of the problem, often his perception of the underlying structure of the problem changes. The conflict here is that the rigid framework in which the algorithm resides cannot be altered easily to match the user's changing perception of the problem. Another difficulty is obtaining user acceptance of the assumptions underlying the model which the algorithm supports. Furthermore the information requirements of an algorithm or model often far exceed the user's patience for entering the data. This can be a problem even if the model is a sufficiently good representation of reality that potentially useful results could be generated by the model. One way of overcoming these difficulties is to employ a better interface between the human user and the algorithm or model.

## Desirable features

Let us examine for a moment some desirable features of an algorithm which would be easy to use. First the algorithm or the system in which it is imbedded should be able to accommodate the changing structure of the problem. These structure changes are due not only to actual physical changes in the problem situation, but often they are caused by the changing perception of the problem by the user as he gains a better understanding of the problem variables and their interrelationships.

Secondly, the system should be structured so that the user can utilize subjective information during the solution generation phase. Often it is far too costly to elicit the complete problem characterization from the user even if it were known at the outset of the problem solving process.

Another desirable feature of a system employing an algorithm is to have rapid enough feedback (i.e., information flow back to the user) to enhance the problem solving process. If a large amount of information or large number of interactions is required at each step of the process, then this feedback to the user will be impaired.

## General approaches

There have been many approaches suggested to overcome the above mentioned difficulties in the use of algorithms. One is the use of the intermediary to bridge the gap between decision maker and algorithm. Keen [10] points out that with an intermediary, who is knowledgeable in mathematical tools and an interactive computer language, such as APL, and has managerial skills, it is possible to support strategic decision making with a DSS. Another method is what we may call the interactive algorithm approach [5, 13]. In this case the system designer creates a procedure by which information is elicited from the user. In a conversational mode the user may describe his problem parametrically.

The method which we would like to explore in greater detail here is what we shall call the DSS-algorithm method. In this method we not only have a sophisticated computational tool available for the user, but we also have a DSS to support many of the other aspects of decision making—such as problem finding, data verification and exploration, comparison of alternatives, and report generation. This approach may or may not include the use of an intermediary. We feel, however, the interface to the system should be suitable for the actual decision maker to become directly involved in the solution generation process. The main purpose of this work is to present some guidelines for integration of algorithmic aids into DSS. We shall introduce these guidelines by describing three examples of DSS which were designed to solve a districting problem.

## Specific Approaches

It is the aim of this article to present general guidelines to be followed by the system designer who wishes to minimize the mismatch between the system and the user. In order to understand better the meaning of the guidelines and how they can be used in developing such a system, we focus here on a specific problem and two approaches to its solution. A third approach, which involves the integrated system, will be discussed later. The specific example to be considered is a districting problem in which a geographic area is to be partitioned into a small number of territories having a balanced workload. The first approach is a DSS developed for solving an area partitioning problem. The second approach involves an algorithmic aid which was incorporated into this DSS.

## DSS-GADS

This DSS, called GADS (Geo-Data Analysis and Display System), supports several phases of the problem solving process (e.g., data exploration through graphs, tables, and maps; alternative generation; and comparison of solution alternatives). In order to give a flavor of how to use a DSS such as GADS we shall describe one of the major functional areas in GADS. A more complete description of GADS can be found elsewhere [7].

GADS employs the notion of a map in which a geographic area is divided into a number of atomic zones (non-divisible areas). Associated with each atomic zone is a numeric value which is a measure of the contribution of the zone to the total workload. This map then represents the distribution of workload over the geographic area being displayed. Figure 1 shows the general layout of the relevant frame. There is a central working area where maps being constructed are displayed. The space along the bottom and the right-hand side contains commands and other textual information. The user performs the partitioning process by aggregating the atomic zones into territories. The aggregation may be done by pointing, with cross-hairs, at the atomic zones which are to be included in a territory. At any point in the process, the map may be redrawn showing the current territory boundaries and the corresponding aggregate values of the workload. The user may modify the simple equality criterion for balancing the workload at any time to satisfy his own subjective judgment. Indeed, GADS provides a great deal of flexibility during the partitioning process in that the user could at any time make modifications to his partially constructed map and obtain an immediate indication of the resulting workload distribution. The constructed map may be stored in a map library so that several solution alternatives may be saved and further examined at a later time. GADS by itself contains none of what would traditionally be called algorithmic aids.

## A districting algorithm

A preliminary study of how an algorithm could be used in GADS was done by T. J. Lee [11]. Lee's procedure was an heuristic districting algorithm patterned after how a human might solve the problem. Briefly, the procedure is described as follows. The user specifies a measure of workload over the entire geographic area together with some starting parameters. The algorithm computes a quota for the first territory using the unassigned workload and the number of territories remaining. Aggregation consists of combining suitable adjacent zones until the quota is approximated. After each zone is added, the adjacent zones are scanned for single zone “islands.” If found, these single zone islands are added to the territory, regardless of other criteria. The starting zone for the next territory is generated by the algorithm. A new quota is computed for the next territory and aggregation proceeds as for the first district. New territories are constructed until the required number is created.

The algorithm was in itself conceptually quite simple which made it easy for the user to understand. A majority of the required input parameters were easy to understand in terms with which the user worked naturally. Another useful feature was that several alternative solutions could be generated quite rapidly. These alternatives could be perturbed or altered slightly by means of the usual GADS functions. Finally, the workload leveling by the algorithm was often better than that which was achieved by using manual operations alone.

The districting algorithm, as implemented, contained a number of shortcomings, however. The user interface to the algorithm was very awkward. There were too many interactions required of the user. He had to leave his frame of reference in order to run the algorithm. In addition, the feedback to the user was very slow. Also, the user had very little control over the solution generation process. He would just set a few initial parameters and the algorithm gave back a completely new solution. Since the solution starting point was always the basic map (i.e., the collection of atomic zones), it was not possible to work on a map upon which some aggregation had already been done. Although the user could generate many alternative solutions quickly, he could not easily examine the resulting maps. In fact, it was rather difficult to compare two or more alternatives. Since the feedback was so slow, it was difficult for the user to determine what the effect of changing an input parameter would have on the generated solution. Another point is that the solutions were not a “continuous” function of the input parameters. That is, a “small” change in one of the input parameters could generate a second solution which had little resemblance to the previous solution. In addition, a few of the parameters were defined in terms which were not natural for the user. For example, the user was required to supply a “reference zone” which had no connection to the user’s problem, but was related to the algorithm’s method of operation. These parameters forced the user to think about how the algorithm was going to use the data and what the algorithmic process was in detail. Finally, although the algorithm did a better job of equalizing the workload over the created territories, these territories did not meet subjective constraints of the users (e.g., compactness). This suggests that the human problem solver often had additional objectives in mind besides that of workload equalization. Satisfying these subjective constraints can be of utmost importance to the decision maker. If these subjective constraints cannot be satisfied, then he will have little incentive to use the system.

The above discussion has revealed several benefits and shortcomings of these two approaches to algorithmic aided decision making. In the next section we shall introduce a number of principles which should help the system designer retain the benefits and reduce the shortcomings of the algorithmic aided system.

## Design Guidelines

Analysis of existing systems has suggested to us a number of principles which may guide the system designer. These principles, grouped in categories of interface, control, flexibility, and feedback, are associated with the DSS-Algorithm combined system. More general principles relating to the DSS itself are assumed to apply in this case and have been discussed elsewhere $[1]$ .

## Interface

i) The user should be able to work in his problem solving environment without unnecessary distractions. He should not have to interrupt his process and laboriously supply some control parameters before continuing.

ii) The control parameters should be expressed in terms with which the user will be familiar. He should be able to think about only those parameters which have a direct meaning to the problem solving process.

## Control

iii) The user should be given a spectrum of control. The system should support manual operation as well as fully automatic operation, if possible.

This permits the user to select the level of algorithmic operation which suits him. It also enables the user to learn more easily by allowing him to proceed as slowly as he wishes.

iv) The control mechanism should allow the user to introduce subjective information as demanded by the problem solution process. It should not require the user to specify all constraints a priori. This direct human control of the solution process can make up for deficiencies in the algorithm and will permit the system to contain a simpler algorithm frequently resulting in a smaller information burden on the user.

## Flexibility

v) The algorithmic and manual operations should be interchangeable in the sense that the user can develop part of a solution via manual methods and then continue with the algorithm, or vice versa. The above statement implies that the range of all operations should be contained in the domain of the operations; that is, the result of one operation can be used as input to any other operation. This way operations can be cascaded in an arbitrary way. Both flexibility and control allow the user to construct a solution process which suits his problem.

This idea of interchangeability of operations is deceptively simple, but it has far reaching implications. This is the manner by which flexibility and control are achieved. That is, an arbitrary solution process can be composed of a sequence of primitive subprocesses.

## Feedback

vi) The system should provide sufficient feedback so that the user is fully cognizant of the state of the solution generation process at all times. This feedback is essential for supporting human control of the process.

vii) The design process itself should make use of feedback. Valuable information can be derived from introduction of the initial system or prototype to the users. Their feedback should be especially meaningful in the area of usability.

In the next section we describe how the previously described algorithm was integrated into the DSS consistent with the guidelines.

## Integration of Algorithm into DSS According to Guidelines

In this section we discuss how the Algorithm-DSS combination discussed above was reimplemented to form a truly integrated system. Some of the characteristics of the original system were already consistent with the guidelines and were preserved in the new implementation. For example, the majority of input parameters were easy to understand in that they were expressed in terms with which the user was familiar. Some of these parameters included the quota, number of territories, and subarea in which aggregation was to take place.

On the other hand a number of characteristics of the system required significant alteration. For example, the user interface to the algorithm had to be completely modified. In order to allow the user to run the algorithm from his normal working frame, the commands for operation of the algorithm were moved to the DSS principal working frame. In addition, the parameters which were most frequently changed could be specified at this frame. Furthermore, the interface was improved by eliminating the non-natural parameters. For example, the reference zone was computed from a starting zone which the user specified.

Another significant improvement relating to interface was the prudent use of defaults and memory. Use of default values for parameters often reduces the time and effort the user must expend in working with an interactive system. Essentially all the parameters which affected the operation of the DSS-Algorithm system had default values. This permitted the user to obtain some results without specifying any further information. Furthermore, the values of any of the parameters which the user specified could be retained across working sessions. This reduced the needless re-specification of parameter values even though a user proceeded through many working frames.

Feedback from real users was valuable in determining which of the parameters was most likely to be changed. These changes helped to promote continuity in the problem solving process. The control over the solution generation process was greatly improved. Instead of the algorithm generating a complete solution all at once, the algorithm was constrained to proceed “more slowly.” The user could build one territory at a time manually, or create one or more territories with algorithmic aid. Another change made to the system, which related to flexibility and control, was to provide the ability to restore the state of aggregation back to the user's last interaction. This required the system to remember the last state of aggregation before executing the algorithm. With the original Algorithm-DSS, the required input was a completely disaggregated atomic zone map, and the result was an aggregated map. With the integrated system, however, the user could start with a partially aggregated map and form any number of new territories. In order to accomplish this, the implementation of the algorithm had to be modified so that the domain of operation was expanded to include not only atomic zones, but also previously aggregated areas.

## An Example of Operation: A Scenario

Some of the features of the integrated DSS-Algorithm system are illustrated in the following simplified scenario. Let us assume the user wishes to partition the area shown in Figure 1 into five territories. This figure shows one of the display frames available to the user and shows a central work area together with a number of commands in the lower part of the screen. First, the user allows the algorithm to generate these five territories in one pass in order to develop a general understanding of the problem. $^{2}$ To accomplish this, he specifies the number of territories desired by entering a “5” in place of the “1” after the \*RUN command, designates a first zone by selecting the \*START ZONE command, and pointing to the zone labeled “3” in the lower right of Figure 1 and then selects the \*RUN command.

He may repeat this process many times, starting at different points, until he reaches a solution which he feels workable. One such result is shown in Figure 2. The figure shows three territories having a load of approximately 440 with one territory substantially lower and one higher. He could modify this result by transferring some basic zones $^{3}$ from the “605” territory to the “442” territory, and then transferring some zones from the latter area to the “362” territory by using the commands CREATE and EXTEND. A real user, however, may have many implicit constraints which were violated by the solution. For example, the user may have other related knowledge upon which the system cannot operate directly, such as traffic patterns or personal preferences. He may therefore wish to start again, proceed more slowly, and drive the algorithm in a way consistent with his constraints, but guided by the general shape of these territories. In our scenario the user selects the \*RESTORE command, which reestablishes the state shown in Figure 1. He then uses the algorithm to create one territory, the “605” territory, from which he then breaks off the “75” and “96” basic zones by use of the CREATE command. This result is shown in Figure 3. The user “freezes” the remaining “434” territory, indicated by the underscore, making it unavailable to the algorithm for aggregation. He chooses to create the next territory by means of the BY POLYGON $^{4}$ command; the result is shown in Figure 4. Our hypothetical user then creates one more territory by the algorithm, and then the last two by means of the CREATE command. The final result is shown in Figure 5. This scenario demonstrates some features particularly related to feedback and interchangeability of operations.

## Conclusion

We believe the principles of user oriented interface, control, flexibility, and feedback are crucial for the design of an interactive system which permits the effective use of algorithms. The user oriented interface allows the user to interact with the system in a familiar environment. The flexibility and control permits the user to develop the solution generation process dynamically and to direct it in the most appropriate manner. The feedback enhances the user's awareness and understanding of the problem and the solution generation process.

Other systems claim to have flexibility and control, but in most of them the user is restricted to a sequential solution generation process which the system designer thought was appropriate for the problem. On the other hand we believe the user should be given the flexibility and control to choose among many operations to develop the solution process which is most appropriate for him and his problem.
