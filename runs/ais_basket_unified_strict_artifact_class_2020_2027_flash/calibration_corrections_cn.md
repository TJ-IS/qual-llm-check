# 校准修订（V2；与前文冲突时以本节为准）

本节修复两个容易造成错判的边界，但不放宽三项总标准。

## 1. “最终目标客观”不等于“全文不能出现主观测量”

`all_core_success_outcomes_objective`只检查作者用来证明**最终设计目标已经实现**的主要成功结果，不检查机制链条中的所有变量。

- 如果最终目标和核心设计贡献是提升完全客观结果，而主观量表仅用于理论机制、操纵检验、proof-of-concept、过程解释或非核心补充分析，则该gate仍可为true。
- 只有当主观构念本身也是作者据以宣称制品成功的共同主要终点，或者客观结果只是次要/附加结果时，才因`MIXED_CORE_OUTCOMES`排除。
- 因此密码强度计研究应通过：其最终制品目标及proof-of-value/proof-of-use以实际生成密码的客观强度改善为准；问卷只检验信息是否按ELM预期被加工。

判断顺序必须是：先从研究问题、设计要求、主实验/现场实验的主要终点和贡献声明识别最终设计目标，再判断该终点是否完全客观；不得因为全文出现任何主观量表就自动把`metric_status`设为`mixed_objective_subjective`。

## 2. 算法组件与软件制品类别的可执行边界

算法、分类器、预测模型或优化器可以是软件制品的核心组件，但只有同时满足以下条件才是`implemented_artifact_component`：

1. 文章明确命名一个现实中可反复实例化的软件制品类别；
2. 研究问题和贡献明确面向“该类软件应如何设计”，而不是仅面向模型精度、求解方法或当前业务问题；
3. 作者把理论/需求转译为可复用的design principles、design requirements、design features、功能结构、交互、反馈、工作流或系统规则；
4. 这些设计知识在实际运行的组件中被实例化，并以最终客观指标评价；
5. 删除当前数据集、公司和案例后，仍留下关于该类软件制品的设计知识，而不是只剩算法、特征工程、方程或求解器。

因此：

- `Design Principles for Robust Fraud Detection: The Case of Stock Market Manipulations`应通过。文章明确面向fraud-detection systems，提出并映射design principles/design features，将理论指导的语言特征和ensemble机制实例化为FDS核心分类组件，并以客观分类性能及对反制的鲁棒性评价。不能仅因实例是分类器就判为“纯算法”。
- `DeepVoice`应排除：理论主要指导语音特征/深度学习模型的金融风险预测，贡献实质仍是预测模型与特征选择，并未形成某类可反复实例化软件制品的功能/交互/工作流设计知识。
- 家庭透析排班与护士路径DSS应排除：软件主要包装针对当前领域约束的MILP排班/路径求解，核心贡献是领域优化方案；“DSS”命名、GUI和可运行原型不能把它变成类级软件设计贡献。
- `Ephemeral State-Dependent Recommendation for Digital Content`应排除：核心新意是状态依赖推荐模型/策略及行为机制，不是某类推荐软件的可复用功能、交互或工作流设计贡献。

## 3. “类别可以窄”不能退化成“一种案例就是一个类别”

删除前文“居家透析排班DSS可作为窄类别”的示例。类别可以限定具体任务，但必须是可被多个独立实例反复采用的产品/软件类别，并且文章贡献的是其可复用软件机制。以下均不足：

- 只把当前医院、港口、机队、城市、生产线或数据集的问题抽象成一个带领域名称的“DSS类别”；
- 只声称优化模型、算法或框架可迁移到类似案例；
- 只有专门制作的GUI、Web App、原型壳或模块图，核心能力仍完全来自同一求解模型；
- 作者贡献声明主要面向运营方案、领域决策、算法性能或案例问题，而不是软件类别的设计知识。

反之，密码强度计、上下文感知推荐系统、社交机器人检测系统、欺诈检测系统等可以是合格类别，但仍须逐篇找到作者明确的类级设计主张与运行实例，不能仅凭名称通过。

## 4. 最终纪律

- 正例说明的是边界逻辑，不允许标题匹配式判定；负例也不得只因标题匹配排除。
- 每个gate必须引用当前全文证据重新判断。
- 严格优先于数量，但不能用“算法成分存在”或“出现主观机制变量”作为自动排除捷径。
