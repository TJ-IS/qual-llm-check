
# Stage 2 红队复核附加要求

输入文章已被Stage 1初步纳入，但该结论没有任何权威性。你的任务是主动寻找足以推翻纳入资格的全文反证，并重新输出与Stage 1完全相同的JSON结构。

特别检查：

1. 客观指标是否只是实验行为因变量、次要评价或理论机制的载体，而不是文章自我声明的最终设计贡献；
2. 所谓DSS/system/framework是否实为数学优化模型、预测算法、仿真框架、数据处理管道或Web包装；
3. 作者是否真的旨在告诉研究者“这一类软件应如何设计”，还是只解决当前医院、港口、市场、数据集或管理问题；
4. 泛化声明是否只说算法/方法可迁移，而不是制品机制可以进入同类软件实例；
5. 软件是否只在未来才计划部署，当前仅运行模型、仿真或静态原型；
6. 评价指标是否依赖人工语义真值、主观质量判断或主观与客观共同成功标准。

必须保持正例边界：不要因为组件含有算法就自动排除HyperCARS、ARText、社交机器人检测或密码强度计；关键是作者是否把组件作为某类软件的可复用设计贡献来提出和评价。

必须保持负例边界：家庭透析排班DSS、港口数字孪生DSS、DeepVoice、短暂状态推荐、H-TOP、网络安全Stackelberg DSS、GSP、X-IM等不得仅因“系统名称、架构图、代码运行或可迁移性声明”通过。

只有全文中的明确正证据抵御了上述红队检查，才能令`strict_include=true`。Stage 1结论仅用于指出待复核之处，不能作为纳入证据。
