# Coding Agent 独有重要议题：高适配文献再开发审阅

本文件是在 65 篇 `高适配` 文献基础上的二次压缩审阅。这里的目标不是把文献中的原概念照搬到 coding agent，而是寻找：哪些原概念能作为“概念原料”，帮助我们开发一个真正属于 coding agent 使用情境的新 UX 概念。

## 更严格的判断口径

一个方向只有同时满足下面三点，才值得作为主线：

- 它必须指向 coding agent 的独有重要议题，而不是一般 AI、一般 HCI、一般技术采纳都能直接使用的议题。
- 文献中的原概念不能直接搬来用，必须需要重新定义边界、维度、前因后果或测量方式。
- 这个新概念必须有现实后果：影响代码质量、安全委托、验证负担、责任归属、开发者能力、工作节奏或长期专业身份。

因此，`trust`、`explanation`、`flow`、`algorithm aversion`、`mental model`、`self-efficacy` 本身都不是我们要找的终点。它们只有在被 coding agent 的独特机制重组后，才可能成为概念原料。

## Coding Agent 的独特机制

我认为 coding agent 相比一般 AI/聊天机器人/决策支持系统，最关键的独特性有五个：

1. 它会行动：能改文件、跑命令、生成 diff、创建可提交成果。
2. 它会进入真实代码库：结果不是一次性建议，而会改变已有系统状态。
3. 它的正确性难验证：代码质量包含隐藏 bug、上下文一致性、架构影响、长期维护性。
4. 它把责任留给开发者：agent 做了很多事，但开发者仍要 review、merge、解释和背锅。
5. 它改变开发者角色：开发者从直接编码者变成任务定义者、监督者、审查者、修复者和责任承担者。

真正值得推进的概念，应当围绕这些独特机制展开。

## 为什么这些概念值得研究

这里的“重要”不能只理解为听起来很核心，而要看它在实际 coding-agent 使用中能产生什么解释和改进价值。我的判断标准是：这个概念是否能帮助我们解释开发者什么时候愿意委托、什么时候过度委托、什么时候无法验证、什么时候被打断、什么时候失去责任感或专业感；并进一步指导产品设计、团队流程、训练方式或治理机制。

| 新概念机会 | 实际场景中的价值 | 可以解释的关键现象 | 可以指导的改进 |
| --- | --- | --- | --- |
| 残余责任下的代理委托 | 解释为什么开发者明明让 agent 写了代码，却仍然感到压力、负担甚至不敢 merge | 委托后仍反复检查；不愿让 agent 做大任务；agent 提高产出速度但增加 review 焦虑；团队里“谁对 agent 代码负责”不清楚 | 设计更清晰的任务授权边界、责任提示、handoff 摘要、代码所有权标记、审查流程 |
| 代理输出的可验证性缺口 | 解释为什么 agent 产出看起来很好，但开发者仍不放心，或相反地过早相信 | 只看表面解释就接受；测试通过但仍担心隐藏 bug；跨文件 diff 难审；review 时间抵消生成节省 | 改进 diff 组织、测试证据、风险标注、变更理由、验证 checklist、可追溯命令日志 |
| 情境化能力边界感 | 解释为什么同一个 agent 对不同开发者、不同仓库、不同任务效果差异很大 | 开发者不知道哪些任务该委托；对 agent 能力过度乐观或过度保守；失败后无法更新使用策略 | 设计能力边界提示、任务适配建议、失败模式反馈、上下文充分性指示、经验学习机制 |
| 代理行动轨迹的可修复性 | 解释为什么一次小错误会让开发者放弃 agent，或为什么有些失败反而能变成顺畅协作 | agent 走偏后越改越乱；开发者难以定位从哪一步开始错；回滚成本高；修复对话很累 | 设计行动轨迹、检查点、可逆操作、失败定位、修复协议、agent 自我诊断和恢复计划 |
| 监督注意力编排 | 解释为什么 agent 有时“太吵”，有时又“太安静”，两者都会损害体验和安全 | 审批疲劳；警告被忽视；打断破坏心流；agent 静默推进导致错误累积；开发者频繁上下文切换 | 设计分级通知、低/高风险审批策略、状态可视化、批量确认、适时打断、监督节奏个性化 |
| 开发者角色与能力所有权重构 | 解释长期使用 agent 后，开发者如何重新理解自己的能力、价值和职业身份 | 新手依赖 agent 学不到东西；资深开发者觉得专业判断被削弱；开发者从“写代码”转向“审代码/管 agent” | 设计学习型解释、技能保持机制、角色分工规范、团队评价方式、agent 作为导师/助手的边界 |

## 1. 残余责任下的代理委托

这个方向不是把 `delegation` 照搬过来。传统 delegation 讨论的是把任务交给他人或系统；coding agent 的关键问题是：开发者把代码行动交给 agent，但仍然要承担产出的解释、审查、修复和后果。

可以开发的新概念：

- 残余责任下的代理委托
- responsible agentic delegation
- accountable code delegation
- agent-authored code ownership

为什么它是 coding-agent-specific：

- agent 不是只给建议，而是能直接生成和修改代码。
- 开发者可能没有逐行写代码，却要对代码质量负责。
- 责任并不会随着执行权外包而外包。
- 委托程度越高，开发者可能越需要新的 review、解释和接管能力。

不能照搬的来源概念：

- #51 的代理性 IS 委托理论可以提供“任务分配、协调、评估”的结构，但没有处理代码产物的所有权和 residual responsibility。
- #67 的 indirect IS use 很有价值，但 coding agent 不是通过另一个人间接使用系统，而是通过一个能行动的技术代理改变工件。
- #100 的 accountability UI 可以迁移，但 coding agent 中的问责不是单纯“让我更认真”，而是“我如何对一个非我亲手生成的代码产物负责”。
- #193 的 role theory 可以迁移，但需要从 end-user/developer 角色变化，改造成 developer/agent/supervisor/reviewer 的复合角色。

可能维度：

- 委托边界清晰度：我知道哪些代码任务可以交给 agent。
- 责任残留感：即使 agent 写了代码，我也觉得最终责任仍在我。
- 代码拥有感：我能否把 agent 的代码理解、认领并解释给别人。
- 接管准备度：我知道何时停止 agent、回滚或亲自处理。
- 责任-控制不对称：agent 做得越多，我却越难掌控但仍需负责。

这个概念的研究价值在于，它能把“开发者为什么不用/少用/只让 agent 做小任务”解释得更细。很多时候阻碍不是不信任 agent，而是开发者预期到自己仍要承担最终责任，却缺少足够控制权和可解释材料。研究它可以帮助产品设计者决定：什么时候应该让 agent 自动推进，什么时候必须要求开发者确认，什么时候需要生成责任转移/审查摘要。它也能帮助团队制定 agent-authored code 的 review 规范，而不是默认“谁点了 merge 谁负责”。

## 2. 代理输出的可验证性缺口

这个方向不是普通的 `trust calibration`。它更具体地指：coding agent 的输出是否能被开发者有效验证。很多时候，agent 产出看起来完整、测试也可能通过，但开发者仍无法确认它是否真正正确、安全、可维护。

可以开发的新概念：

- 代理输出可验证性缺口
- agentic code verifiability gap
- perceived verifiability of agent-authored code
- verification tractability

为什么它是 coding-agent-specific：

- 代码正确性具有隐藏性，无法只靠表面流畅度判断。
- agent 可能一次改多个文件，引入跨模块副作用。
- 开发者必须判断的不只是答案对不对，而是 diff、命令、测试、解释和架构影响是否足够可信。
- “省时间”的收益可能被“验证成本”抵消。

不能照搬的来源概念：

- #2 的专家建议评价说明用户会依赖启发式，但 coding agent 场景要把启发式依赖具体化为对 diff、测试、解释、文件范围和代理行为轨迹的判断。
- #53 的 metacognition 不能只搬成“自我监控/系统监控”，要改造成开发者在审查 agent 产物时的双重监控。
- #156、#159 的 error/deception detection 可迁移为输出验证，但 coding agent 的错误不是孤立数据错误，而是嵌入代码库和开发目标的错误。
- #175 的 user calibration 可作为基础，但我们要测的不是一般决策信心，而是“我对这段 agent-authored code 的信心是否匹配其真实质量”。
- #198 的 effort saving 很关键，但要改造成“验证努力节省是否损害代码质量”。

可能维度：

- diff 可理解性：我能快速看懂 agent 改了什么。
- 证据充分性：测试、日志和解释是否足以支持判断。
- 隐性风险感：我是否担心隐藏 bug、边界条件或架构副作用。
- 验证成本：审查 agent 产物是否接近甚至超过自己实现的成本。
- 信心-质量校准：我对 agent 产物的信心是否与真实质量一致。
- 警觉疲劳：频繁审查是否让我降低警觉。

这个概念的研究价值在于，它能解释 coding agent 的一个核心悖论：生成越快，未必交付越快，因为开发者还要验证。实际场景里，agent 可能生成一个很大的 diff、给出自信解释、跑过一部分测试，但开发者仍不知道有没有隐藏风险。研究可验证性缺口，可以指导 agent 如何呈现变更、证据和风险，而不仅是“给解释”。它还能预测什么时候 agent 会导致过度依赖、什么时候会导致弃用：前者是低可验证但高表面信心，后者是低可验证且高风险感。

## 3. 情境化能力边界感

这个方向不是普通的 `mental model`。coding agent 的能力不是一个稳定产品属性，而是由当前仓库、任务类型、上下文窗口、测试覆盖、工具权限、历史步骤和开发者提示共同决定。开发者需要形成一种情境化判断：这个 agent 此刻能否安全完成这个任务。

可以开发的新概念：

- 情境化能力边界感
- agent capability boundary sense
- delegation metaknowledge for coding agents
- task-agent fit awareness

为什么它是 coding-agent-specific：

- 同一个 agent 在不同代码库、语言、依赖、测试条件下能力差异巨大。
- 开发者不是判断“AI 好不好”，而是判断“此刻这个 agent 是否掌握足够上下文并适合继续行动”。
- 能力边界会随着对话、工具结果、失败和修复动态变化。

不能照搬的来源概念：

- #54 的 delegation metaknowledge 很关键，但要从分类任务委托改造成代码任务、仓库上下文和工具链委托。
- #56 的 know-what/know-how gap 可以说明 agent 的显性知识与开发者实践知识差距，但要转成开发者如何识别这种差距。
- #166 的 mental model 太泛，需要改造成对 agent 能力边界、失败模式和上下文充分性的模型。
- #184 的编程多问题空间很有价值，可用于解释为什么 agent 和开发者常在不同表征空间里错位。
- #18、#39、#180 可支持动态更新，但不能停留在一般 performance feedback 或 expectation realism。

可能维度：

- 任务适配判断：我知道哪些任务适合交给 agent。
- 上下文充分性感知：我能判断 agent 是否理解了足够代码上下文。
- 失败模式知识：我知道 agent 在哪些问题上容易出错。
- 动态边界更新：我会根据 agent 的近期表现调整委托策略。
- 接管阈值：我知道 agent 继续做下去何时开始危险。

这个概念的研究价值在于，它能解释为什么“同一个 coding agent”在实际使用中会出现巨大差异。高手可能知道哪些任务适合 agent、如何给上下文、何时停止；新手可能把不适合的任务交出去，或者因为一次失败就完全不用。研究能力边界感，可以帮助我们设计 agent 的任务适配提示、上下文缺口提示和失败模式反馈，也可以帮助开发者培训从“学 prompt”转向“学会判断 agent 的适用边界”。

## 4. 代理行动轨迹的可修复性

这个方向不是一般 chatbot repair。coding agent 失败后，问题不是“换个说法再答一次”，而是当前代码状态、diff、测试结果和工作路径可能已经被改变。修复包括定位错误、解释偏差、回滚、重新规划和继续协作。

可以开发的新概念：

- 代理行动轨迹可修复性
- repairability of agentic coding trajectories
- collaborative recovery from agentic code drift

为什么它是 coding-agent-specific：

- agent 的错误会沉淀在代码库状态中。
- 修复需要同时处理对话理解、代码变更、测试反馈和开发意图。
- 可修复性决定开发者是否敢让 agent 进行更长链条的自主工作。

不能照搬的来源概念：

- #10 的 collaborative repair 是强原料，但必须从对话破裂改造成代码状态破裂和任务轨迹修复。
- #25 的 machine-induced reflection 可以迁移，但要关注 agent 失败如何促发开发者重新理解问题和代码。
- #149、#162、#177 的 explanation 不能直接搬成解释质量，而要服务于“能不能修复、回滚、继续”。

可能维度：

- 偏差可定位性：我能看出 agent 从哪里开始走偏。
- 回滚可行性：我能安全撤销 agent 的错误行动。
- 修复沟通效率：我能让 agent 理解错误并有效调整。
- 状态恢复感：修复后我能重新相信当前代码状态。
- 轨迹连续性：修复不会迫使我完全放弃原来的工作路径。

这个概念的研究价值在于，它把“agent 出错”从结果问题变成过程问题。真实开发里，agent 难免会误解需求、改错文件、引入回归或走向错误方案；关键是开发者能不能低成本把它拉回来。研究可修复性，可以指导产品设计检查点、回滚机制、行动日志、错误定位和修复对话格式。它也能解释为什么某些 agent 虽然不完美但用户愿意继续用，因为失败是可恢复的；而另一些 agent 一旦走偏就让人彻底失去信心。

## 5. 监督注意力编排

这个方向不是普通中断研究。coding agent 的中断常常是监督性中断：请求权限、确认方案、汇报失败、要求补充上下文、提醒风险。太多会破坏心流，太少会让 agent 在错误方向上推进。

可以开发的新概念：

- 监督注意力编排
- supervisory attention orchestration
- agentic interruption fit
- developer attention governance

为什么它是 coding-agent-specific：

- 中断不是普通通知，而是对正在行动的 agent 的监督节点。
- 开发者需要在深度编码与监督 agent 之间切换。
- 审批和警告疲劳会直接影响安全委托。

来源概念原料：

- #20、#66、#75 可支持 flow/interruption/cognitive load，但必须重构为“监督行动中的注意力切换”。
- #30 可支持警告习惯化，但要迁移到 agent 审批、命令执行、风险提示。
- #117 的 awareness display 可改造成 agent 状态与负载显示。
- #142 的 monitor/control attention 很适合解释监督与直接控制的认知竞争。

这个概念的研究价值在于，它能解释 coding agent 体验里很具体但常被低估的问题：agent 到底应该什么时候叫我。开发者在深度思考时被打断，会丢失问题空间；但 agent 如果静默推进太久，又可能把错误扩散到更多文件。研究监督注意力编排，可以指导不同风险级别下的审批策略、通知频率、状态显示和批量确认机制。它也能解释为什么“更自动化”不一定更好，因为开发者监督注意力本身是一种稀缺资源。

## 6. 开发者角色与能力所有权重构

这个方向不是一般 AI threat 或 professional identity。coding agent 介入的是开发者最核心的专业实践：理解问题、写代码、调试、重构、解释系统。它可能改变开发者对“我是否仍然是作者/专家/工程师”的体验。

可以开发的新概念：

- 开发者能力所有权重构
- developer expertise ownership under coding agents
- agentic professional identity work
- role re-authoring in agentic programming

为什么它是 coding-agent-specific：

- agent 不是只自动化边缘任务，而是进入“写代码”这个核心身份区域。
- 开发者可能从生产者变成监督者和审查者。
- 长期使用可能带来技能增强、技能萎缩或独特知识侵蚀。

来源概念原料：

- #5 的 identity work、#59 的 face-saving dilemma、#132 的 expert technological frames 可以作为身份材料，但都要围绕 coding 这个核心专业实践重做。
- #42 的 unique knowledge erosion 很有价值，可迁移为开发者独特问题表征和代码判断能力是否被削弱。
- #138 的 mindshift learning 可支持“从编码到代理监督”的范式转换。
- #164 的 intrinsic motivation 可改造成 agent 重构任务后对开发者动机的影响。

这个概念的研究价值在于，它能解释长期使用 coding agent 的深层后果，而不只是短期效率。开发者可能更快完成任务，却逐渐失去对代码细节的掌控；新手可能通过 agent 学得更快，也可能跳过必要的困难学习；资深开发者可能把 agent 当作放大器，也可能感到自己的专业判断被替代。研究这个概念，可以帮助团队设计学习型使用规范、技能保持机制和角色评价方式，避免把开发者简单推向“只审不写”的尴尬位置。

## 最建议的主概念结构

如果我们要开发一个强概念，我建议不要把六个方向并列，而是形成一个核心结构：

核心概念：残余责任下的代理委托体验

这个总概念下面可以包含四个关键维度：

1. 能力边界感：我是否知道该把什么交给 agent。
2. 可验证性缺口：我是否能判断 agent 产出是否真的可靠。
3. 责任可拥有感：我是否能理解、解释并承担 agent 产出。
4. 轨迹可修复性：agent 失败后我是否能恢复代码状态和协作路径。

监督注意力编排可以作为影响因素或交互设计机制；开发者角色与能力所有权重构可以作为长期结果或边界条件。

这样做的好处是：它不是把 trust、explanation、flow、delegation 照搬过来，而是把这些来源概念重新组织到 coding agent 独有的现实问题中：agent 能行动，代码难验证，开发者仍负责。

## 可以怎么研究前因和后果

`残余责任下的代理委托体验` 不应被理解成一个孤立态度，而更像一个核心机制：当 coding agent 承担更多代码行动时，开发者如何感知“我把执行交出去了，但责任还留在我这里”。它可以作为中介，也可以作为被解释变量。

一个可研究模型可以是：

`agent 行动/界面/任务/团队情境` -> `残余责任下的代理委托体验` -> `验证行为、委托行为、代码结果、开发者体验`

### 可能前因

| 前因类别 | 具体前因 | 影响逻辑 | 对应文献原料 |
| --- | --- | --- | --- |
| Agent 行动范围 | agent 是只建议，还是能直接改文件、跑命令、提交 PR、跨文件重构 | 行动范围越大，开发者越可能感到“不是我写的，但我要负责” | #51 代理性 IS 委托；#199 system restrictiveness/guidance |
| 授权与控制设计 | 是否有审批点、权限边界、暂停/接管按钮、分阶段确认 | 控制越清晰，责任感可能更可承受；控制缺失会放大责任-控制不对称 | #199 restrictiveness/guidance；#157 控制-信任悖论 |
| 可验证性证据 | diff 是否清楚，测试是否充分，命令日志是否可追溯，风险是否被标注 | 证据越充分，开发者越容易把 agent 产出转化为自己能负责的代码 | #175 user calibration；#156 error detection；#159 deception detection |

| 角色规范 | 团队是否明确“agent 代码谁负责”、是否允许 agent 参与核心代码 | 角色越模糊，责任冲突越强；规范越清楚，委托更稳定 | #193 role theory；#67 indirect IS use |

| 任务风险 | 是否涉及安全、支付、数据、架构、生产系统、难回滚改动 | 任务风险越高，同样的 agent 行动会产生更强残余责任 | #95 uncertainty；#204 vigilance |
| 时间压力 | deadline 是否迫使开发者减少审查或扩大委托 | 时间压力可能增加委托，但也可能加剧“没审清楚却要负责”的压力 | #198 effort saving；#75 cognitive load |
| 过往表现 | agent 最近是否成功、是否犯过隐蔽错误、失败后是否能修回来 | 过往表现会改变开发者对委托风险和接管阈值的判断 | #39 reliance adjustment；#82 trust disconfirmation |

### 可能后果

| 后果类别 | 具体后果 | 为什么有价值 |
| --- | --- | --- |
| 委托行为 | 委托任务的范围、复杂度、自主程度、是否让 agent 连续多步推进 | 解释开发者为什么只让 agent 做小修小补，或为什么敢交给 agent 做完整 feature |
| 验证行为 | review 深度、测试补充、日志检查、手动复现、是否要求 agent 解释 | 连接到代码质量和安全，是最直接的行为后果 |
| 接管行为 | 暂停 agent、回滚、自己重写、缩小任务、改变 prompt | 解释人如何在 agent 失控前恢复控制 |
| 信任校准 | 过度依赖、过度怀疑、根据任务动态调整依赖 | 把一般 trust 改造成具体的委托和验证校准 |
| 代码结果 | bug 数量、review 返工、测试覆盖、merge 成功率、线上事故 | 让 UX 概念连接到工程结果，而不是只停留在态度 |

| 团队治理 | agent-authored code 归属、review 规范、审计日志使用、责任分配 | 帮助组织制定 coding agent 使用规则 |

### 文献里类似概念通常怎么研究

这些文献给我们的不是可直接照搬的模型，而是研究设计原料：

- 委托类文献通常研究“任务如何被分配、协调、评估”，例如 #51 提供代理性 IS 委托框架，#54 用实验研究 delegation metaknowledge 如何影响 productive delegation。迁移到 coding agent 时，我们要把任务从抽象决策任务改成代码行动，并加入残余责任、代码验证和接管。
- 问责类文献通常把界面线索或可识别性作为前因，研究其如何提高用户责任感或谨慎行为。#100 对我们有启发，但 coding agent 中的问责不是普通认真程度，而是对 agent-authored code 的责任认领。
- 校准/错误检测类文献通常研究信息可见性、警告、激励、目标如何影响检测行为和信心质量匹配。#175、#156、#159、#198 可以被改造成“开发者如何验证 agent 代码以及何时偷懒/过信”。
- 角色类文献通常研究技术引入如何改变用户、开发者、专家的角色和身份。#193、#5、#132 可迁移为“开发者从编码者到监督者/审查者/责任承担者”的角色重构。
- 中断/注意力类文献通常研究频率、相关性、时机和负载显示如何影响心流、负荷和表现。#20、#30、#75、#117、#142 可以迁移为“agent 在何时请求人类监督”。

### 针对“残余责任下的代理委托”的几个可检验研究问题

1. Agent 行动范围越大，开发者的残余责任感是否越强？
2. 可验证性证据是否会降低责任-控制不对称感，并提高委托意愿？
3. 问责显著性是否会提高验证努力，但降低委托复杂任务的意愿？
4. 能力边界感是否会让残余责任从“焦虑”转化为“可管理的责任”？
5. 可修复性是否会缓冲高风险任务对委托意愿的负面影响？
6. 时间压力是否会导致开发者扩大委托，同时降低验证深度，形成更高的事后责任压力？
7. 残余责任感是否呈倒 U 型：太低导致过度依赖，太高导致不敢委托，适中时促进认真审查和有效协作？

### 一个最清晰的起步模型

如果只做一个研究，我建议不要一开始铺太大，可以先做：

`可验证性证据` 和 `agent 行动范围` -> `责任-控制不对称感` -> `验证努力` 与 `委托意愿`

其中 `可修复性` 可以作为调节变量：当 agent 行动轨迹更可修复时，高行动范围未必显著降低委托意愿，因为开发者知道自己可以回滚、定位和纠正。

这个模型的好处是很具体：可以用实验操纵 agent 是否只给建议/直接改代码/跨文件改代码，以及是否提供清晰 diff、测试证据、行动日志和回滚点；再测开发者的责任感、控制感、验证努力、委托意愿和 merge 信心。

## 我的最终推荐：代理代码的可负责验证性

如果只能选一个最值得研究的方向，我建议不要直接选 `trust`、`explanation`、`flow`，也不要把主概念命名得过宽，比如单独叫 `残余责任下的代理委托`。最有突破和实践价值的核心概念，我会暂定为：

代理代码的可负责验证性

英文可暂定为：

- Accountable Verifiability of Agent-Authored Code
- Responsible Verifiability in Coding-Agent Use
- Accountable Verification of Agentic Code Output

### 核心定义

代理代码的可负责验证性，是指开发者在使用 coding agent 生成或修改代码后，是否能够基于足够的理解、证据、控制和修复手段，把 agent-authored code 转化为自己可以负责任接受、合并、解释和维护的代码。

它的核心问题是：

当代码不是我亲手写的，但结果仍然需要我负责时，我是否有能力把它验证到“可以负责”的程度？

### 为什么我认为它最值得做

理论贡献：

1. 它突破了一般 trust 研究。问题不再是“我信不信 AI”，而是“我能不能把 agent 产物验证到足以负责”。这把 trust 从态度问题推进到责任化验证问题。
2. 它突破了一般 explanation 研究。解释不是为了让用户觉得合理，而是为了支持开发者审查、定位风险、建立证据链和承担责任。
3. 它突破了一般 delegation 研究。coding agent 场景中出现了执行权和责任权分离：agent 执行，开发者负责。
4. 它突破了一般 HCI 可用性研究。这里的 UX 不是流畅或满意，而是能否安全地把代理产出纳入真实代码库。
5. 它能把多个文献流合并成一个新构念：委托、问责、校准、错误检测、解释、可修复性、认知努力。

实践价值：

1. 它直接解释 coding agent 的生产力悖论：生成很快，但验证不一定快；如果不能负责地验证，产出越多，风险和负担可能越大。
2. 它能指导产品设计：agent 应该如何组织 diff、展示测试证据、标注风险、记录行动轨迹、提供回滚点和生成审查摘要。
3. 它能指导团队治理：什么样的 agent 代码可以进入 PR，谁负责 review，什么证据足以 merge，哪些任务必须人工接管。
4. 它能指导开发者培训：重点不是“怎么 prompt”，而是如何判断 agent 产物是否已经达到可负责接受的标准。
5. 它能连接客观工程结果：bug 发现率、review 时间、merge 信心、返工率、线上风险，而不只是问卷态度。

### 它和其他概念的关系

| 相关概念 | 在这个主线中的位置 |
| --- | --- |
| 残余责任下的代理委托 | 是背景张力：为什么验证必须“可负责” |
| 可验证性缺口 | 是核心负向状态：开发者无法把 agent 代码验证到可负责程度 |
| 能力边界感 | 是重要前因：知道 agent 能做什么，才知道怎么验证 |
| 轨迹可修复性 | 是重要前因/调节：能修复，才更敢接受 agent 行动 |
| 监督注意力编排 | 是设计机制：让开发者在关键节点进行有效验证 |
| 角色与能力所有权 | 是长期后果：开发者是否仍觉得自己拥有代码理解和专业判断 |

### 可能维度

1. 变更可理解性：我能理解 agent 改了什么，以及为什么这样改。
2. 证据充分性：测试、日志、解释和风险标注足以支持我的判断。
3. 风险可见性：我能识别 agent 产出中可能隐藏的 bug、边界条件或架构副作用。
4. 责任可拥有感：我能向别人解释并承担这段 agent-authored code。
5. 修复可行性：如果 agent 产出有问题，我能定位、回滚、修复或让 agent 修复。

### 一个最值得起步的研究模型

`agent 行动范围` 和 `验证证据质量` -> `代理代码的可负责验证性` -> `merge 信心`、`验证努力`、`bug 发现率`、`后续委托意愿`

可加入两个调节变量：

- 任务风险：高风险任务下，可负责验证性的作用更强。
- 开发者经验：经验可能增强验证能力，但也可能提高对隐藏风险的敏感性。

### 一个可操作实验

让开发者审查 coding agent 生成的同一类代码修改，操纵两个因素：

1. agent 行动范围：只给建议、改一个文件、跨文件修改并运行命令。
2. 验证证据质量：只给最终代码、给代码加测试结果、给代码加测试结果/行动日志/风险摘要/回滚点。

测量：

- 可负责验证性感知。
- review 时间和 review 深度。
- 是否发现预先植入的 bug。
- merge 信心。
- 是否愿意让 agent 做更大任务。
- 责任压力和控制感。

这个研究能同时回答理论和实践问题：什么样的 agent 输出，不只是“看起来可信”，而是能让开发者负责任地接受。

## 再修正：更可测量的总构念

上面的 `代理代码的可负责验证性` 仍然偏向一个核心维度，而不是最好的总构念。更准确的总构念应当直接回答“到底测量什么”：

开发者对代理编码工作的可承责掌控感

英文可暂定：

- Perceived Responsible Control over Agentic Coding Work
- Perceived Accountable Control in Coding-Agent Use
- Responsible Control over Agent-Authored Code

### 这个构念到底测量什么

它测量的是：当开发者把代码任务交给 coding agent 执行时，开发者在多大程度上觉得自己仍然能够负责任地界定任务、监督过程、验证产出、修复偏差，并最终解释和承担 agent-authored code。

高水平意味着：

- 我知道哪些任务可以交给 agent，哪些不该交。
- agent 行动时，我知道它在做什么、何时需要我介入。
- agent 产出代码后，我有足够证据判断它是否可靠。
- agent 走偏后，我能定位、回滚、修复或重新接管。
- 我能向同事解释并承担这段 agent-authored code。

低水平意味着：

- 我不确定什么任务适合交给 agent，只能试试看。
- agent 改代码时，我感觉自己在失去过程掌控。
- 代码看似完成，但我不知道该如何验证。
- 出错后我不知道从哪里开始修，甚至宁愿重来。
- 我不太能把 agent 写的代码当成自己可以负责的产物。

因此，这个构念不是测量“信任 agent 的程度”，也不是测量“agent 好不好用”。它测量的是开发者是否感觉自己仍能作为一个负责任的工程主体，掌控由 agent 参与生产的代码工作。

| 文献原概念 | 摘要中的核心发现 | 为什么不能照搬 | 迁移后的构念成分 |
| --- | --- | --- | --- |
| 代理性 IS 委托（#51） | agentic IS artifacts 不再是被动工具，能主动承担任务、在不确定性下追求结果，因此 IS use 需要转向 delegation 视角 | #51 讲的是 agentic artifact 的委托关系，但没有处理开发者面对 agent-authored code 时如何继续承担代码责任 | 任务界定与委托边界：开发者是否能决定什么该交给 agent |
| 间接 IS 使用（#67） | 用户可能把 IS 使用委托给他人，但仍承担主要责任和问责 | 原文是人把系统使用委托给另一个人；coding agent 是非人代理直接改变代码工件，责任和产物所有权更模糊 | 间接执行下的责任保留：agent 做，开发者仍负责 |
| 用户参与/责任矛盾（#144） | 方法论让用户处于相对被动位置，却要求用户 sign off 并对项目结果负责 | 这个矛盾在 coding agent 中更尖锐：开发者可能没有亲手写代码，却要批准、merge、维护和解释 | 责任-控制不对称：执行权外移但责任没有外移 |

| 用户校准（#175） | DSS 设计应让用户信心与决策质量匹配，关键属性包括 expressiveness、visibility、inquirability | 校准文献关注决策信心与质量；coding agent 中要校准的是对可执行代码变更的信心和真实质量 | 可负责验证性：我是否有足够证据把 agent 代码验证到可负责 |
| 错误检测（#156） | 人类错误检测受目标、激励、信号检测等影响；人不一定天然检测差，条件设计很重要 | 数据错误检测是静态对象；agent 代码错误可能跨文件、隐藏在架构/边界条件/未来维护里 | 风险识别能力：我能否发现 agent 产出中的隐藏问题 |
| 欺骗敏感性/误报权衡（#159） | 警告和即时训练能提高检测成功率，但也增加误报，影响任务准确性和时间 | 直接搬成“警觉性”太宽；coding agent 审查中还要平衡漏掉 bug 与过度怀疑造成的低效率 | 审查警觉校准：既不过度相信，也不过度报警 |
| 决策辅助中的努力节省（#198） | 用户使用 DSS 时可能节省努力，而不是使用更多信息提升决策质量 | coding agent 更容易诱发这个问题：代码已经生成，开发者可能倾向于快速接受而非深入验证 | 验证努力保持：面对现成代码是否仍愿意认真审查 |
| AI 决策增强中的元认知（#53） | AI 建议更不透明、错误更不可预测，用户接受/拒绝建议需要自我监控和系统监控 | 医疗诊断是接受/拒绝建议；coding agent 是接受/修改/合并一个会进入代码库的工件 | 双重监控：监控 agent 产出，也监控自己是否偷懒或过信 |
| 委托元知识（#54） | 人类委托 AI 表现差，不是因为算法厌恶，而是缺乏判断自己和 AI 能力的 metaknowledge | 原文是分类任务；coding agent 的能力边界取决于仓库、任务、上下文、工具权限和测试环境 | 能力边界感：我是否知道 agent 此刻适合做什么 |
| 协同修复（#10） | 人和 chatbot 共同修复 breakdown 能提升解决率并缓解失败影响 | 对话修复只是澄清语义；coding agent 修复还要恢复代码状态、diff 轨迹和测试结果 | 轨迹可修复性：agent 走偏后我能否恢复工作路径 |
| 警告习惯化（#30） | 用户会把安全警告和普通通知混同并习惯化，导致忽视真正警告 | coding agent 中的警告可能是命令审批、风险提示、权限确认；如果泛滥，会破坏监督质量 | 监督注意力掌控：我能否在关键节点有效介入 |

### 为什么这个迁移是必要的

如果直接使用原概念，会出现几个问题：

1. 直接用 `trust` 会太宽。开发者可能信任 agent 的一般能力，却仍然不敢 merge 某个具体 diff。
2. 直接用 `delegation` 会漏掉责任问题。coding agent 不是把任务交出去就结束，开发者仍要对代码后果负责。
3. 直接用 `accountability` 会太偏问责压力。我们需要测的不只是“我会被追责”，还包括“我有没有能力负责任地接住这个结果”。
4. 直接用 `explanation` 会太偏信息呈现。解释只有在支持验证、修复和责任承接时才有核心价值。
5. 直接用 `control` 会太笼统。coding agent 的关键不是全程手动控制，而是在代理行动中保留足够的边界设定、监督、验证和接管能力。
6. 直接用 `error detection` 会太窄。开发者不是只找错，还要决定是否接受、是否合并、是否能维护和解释代码。

所以迁移后的新构念必须把这些来源概念重组起来，描述一个 coding-agent-specific 的程度变量：开发者在 agent 参与编码后，保留了多少可承责的掌控能力。

### 可能的一阶维度

| 维度 | 高水平表现 | 低水平表现 | 主要来源概念 |
| --- | --- | --- | --- |
| 委托边界掌控 | 清楚知道哪些任务、文件、风险级别适合交给 agent | 不知道该交什么，只能凭感觉试 | #51, #54, #199 |
| 过程监督掌控 | 知道 agent 正在做什么，何时该审批、暂停或接管 | agent 在后台推进时感到失控 | #30, #117, #142 |
| 产出验证掌控 | 能基于 diff、测试、日志、解释判断代码可靠性 | 代码看似完成，但不知道如何判断 | #2, #53, #156, #175, #198 |
| 偏差修复掌控 | agent 走偏后能定位、回滚、修复并恢复协作 | 出错后不知道从哪里修，只能放弃或重做 | #10, #25, #105 |
| 代码责任承接 | 能解释、维护并承担 agent-authored code | 不觉得这段代码真正属于自己，也不敢负责 | #67, #100, #144, #193 |

### 和现有构念的边界

| 相近构念 | 区别 |
| --- | --- |
| Trust in AI | trust 是相信系统；可承责掌控感是相信自己有能力监督、验证和承担 agent 工作 |
| Perceived control | control 太宽；本构念限定在 agentic coding work 中的边界、监督、验证、修复和责任承接 |
| Accountability | accountability 强调被评价/被追责；本构念强调能否实际履行责任 |
| Explainability | explainability 是信息属性；本构念关注解释是否帮助开发者形成可负责接受 |
| Delegation | delegation 是任务交付关系；本构念关注委托后开发者是否仍能掌控责任链 |
| Self-efficacy | self-efficacy 是个人能力信念；本构念是人-agent-code 情境中的责任性掌控 |

### 可测量条目方向

这些不是最终量表，只是说明这个构念的高低可以怎么测：

- 我知道哪些编码任务适合交给 coding agent，哪些任务不适合。
- 当 coding agent 修改代码时，我能判断它是否掌握了足够上下文。
- 我能在 coding agent 走偏前识别需要介入的时机。
- 我能根据 diff、测试结果和解释判断 agent 产出的代码是否可靠。
- 如果 agent 生成的代码有问题，我能定位问题来自哪一步。
- 我能安全地撤销或修复 agent 造成的不合适改动。
- 我能向同事解释 agent 生成代码的主要逻辑和风险。
- 即使代码由 agent 生成，我也能负责任地决定是否接受或合并它。

### 最简研究模型

前因可以从设计侧和任务侧来：

`行动范围清晰度`、`验证证据质量`、`回滚/日志支持`、`任务风险` -> `开发者对代理编码工作的可承责掌控感`

后果可以从行为和结果侧来：

`开发者对代理编码工作的可承责掌控感` -> `校准委托`、`验证深度`、`接管时机`、`merge 信心`、`bug 发现率`、`后续使用意愿`

这比单独测 trust 更能解释真实 coding agent 使用：一个开发者可以“相信 agent 很强”，但如果他无法验证、无法修复、无法解释和承担 agent 代码，他的可承责掌控感仍然是低的。

## 按更严格迁移标准的再次修正

这里需要更严格地区分两件事：

- 旧概念能不能用于 coding agent。
- coding agent 是否让旧概念的核心假设失效，因此必须发展新概念。

如果只是“trust 可以影响 coding agent 使用”“explanation 可以帮助 coding agent 使用”“interruption 会影响 coding agent 心流”，这不叫必须迁移。这些旧概念本来就能解释很多人机交互情境，直接拿来做情境化研究即可。真正值得做新构念的地方，应该是旧概念无法准确描述 coding agent 独有矛盾的地方。

按这个标准，我会进一步收紧：最有希望的新概念不是泛泛的“可承责掌控感”，而是一个更具体的缺口概念：

代理代码承责缺口

英文可暂定：

- Accountability-Authorship Gap in Agentic Coding
- Responsibility-Authorship Gap for Agent-Authored Code
- Accountability Gap in Agentic Code Ownership

### 这个构念测量什么

`代理代码承责缺口` 测量的是：开发者需要为 agent-authored code 负责的程度，与开发者对这段代码的作者性理解、过程控制、验证把握和修复能力之间的不匹配程度。

高缺口意味着：

- agent 实际完成了关键代码行动，但开发者仍被期待对结果负责。
- 开发者没有充分理解代码为什么这样生成。
- 开发者无法判断变更是否安全、完整、可维护。
- 开发者不确定出错时能否定位和修复。
- 开发者需要 sign off、merge 或维护一段自己没有真正“拥有”的代码。

低缺口意味着：

- 虽然代码由 agent 参与生成，但开发者理解其逻辑、证据、风险和修改路径。
- 开发者能判断是否接受、如何修复、如何向他人解释。
- 开发者承担责任时，不觉得责任超过了自己的理解和控制能力。

这个构念的高低很清楚：它不是“掌控感高不高”这种泛泛心理感受，而是责任要求和作者性掌握之间的错配程度高不高。

### 为什么旧概念在这里不够用

| 旧概念 | 为什么它可以适用 | 为什么它仍然不够 |
| --- | --- | --- |
| Trust in AI | 开发者当然会信任或不信任 coding agent | trust 关注是否依赖系统，但不描述“我必须为一段非我亲手生成的代码负责”这种作者性-责任错配。一个人可以信任 agent，但仍然有高承责缺口。 |
| Delegation | coding agent 使用显然包含委托 | delegation 通常关注任务交给谁、如何协调、如何评估；但 coding agent 中执行被外包，代码责任和维护义务却留在开发者身上。委托概念没有充分刻画这种“执行外包但作者责任未外包”的缺口。 |
| Accountability | 开发者会被要求对代码负责 | accountability 说明会被评价或追责，但不说明被追责者是否具备足够作者性理解和控制能力。coding agent 的问题不是有没有问责，而是问责是否超过了开发者实际掌握。 |
| Explainability | agent 解释可以帮助开发者理解代码 | explanation 是信息属性；承责缺口关心解释是否足以让开发者把代码转化为可负责的产物。解释可以很多，但缺口仍可能很高。 |
| Error detection | 开发者需要发现 agent 代码错误 | error detection 关注能否发现错误；承责缺口还包括作者性理解、维护责任、merge 决策、长期解释和修复能力。 |
| Perceived control | 开发者会感到控制高低 | control 太宽，不能区分一般界面控制和“我是否有足够作者性基础去承担这段代码”的责任性控制。 |
| Code review | 开发者本来就会 review 代码 | 传统 review 通常假设代码有可追溯的人类作者；agent-authored code 的问题是作者性来源不清、解释不稳定、责任仍落在人类 reviewer/merger 身上。 |

### 这个新概念具体从哪些文献迁移而来

这里不是把每篇文献直接搬过来，而是把它们暴露出的不适用之处组合起来：

| 文献原料 | 原始摘要中的关键点 | 迁移后暴露出的旧理论缺口 |
| --- | --- | --- |
| #144 用户参与/责任矛盾 | 用户在系统开发中角色相对被动，却被要求 sign off 并对项目结果负责 | 这最接近承责缺口，但原文是用户-IS人员关系；coding agent 把矛盾推进到微观代码层面：开发者可能被动接受 agent 代码，却要对每个 diff 负责。 |
| #67 间接 IS 使用 | 指定用户把部分 IS 使用委托给他人，但仍承担主要责任和问责 | 原文的委托对象是其他用户，仍有社会角色和责任主体；coding agent 是非人代理，不能真正承担组织责任，却能直接生成代码产物。 |
| #51 代理性 IS 委托 | agentic artifacts 不再是被动工具，可能承担任务和追求不确定结果 | #51 推进了 delegation 理论，但 coding agent 的代码产物让问题变成：artifact 可以行动，但 artifact 不能成为代码责任主体。 |
| #175 用户校准 | DSS 设计应使用户信心与决策质量匹配 | 校准只处理信心-质量匹配；coding agent 还需要处理责任-作者性匹配：我是否足够理解这段代码，以至于可以为它负责。 |
| #156/#159 错误检测与欺骗敏感性 | 错误检测受目标、激励、警告和误报影响 | 错误检测只覆盖“找不找得到错”；承责缺口还包括即使没找到错，我是否能维护、解释并承担这段代码。 |
| #198 决策辅助中的努力节省 | 用户可能用工具来节省努力，而非提高质量 | coding agent 中这种努力节省会制造更强缺口：越少审查越省力，但越难负责任地拥有代码。 |
| #53 AI 决策增强元认知 | AI 建议不透明且错误不可预测，用户需要监控自己和系统 | coding agent 把建议变成代码行动，元认知监控不只是接不接受建议，而是能否承担实际代码后果。 |
| #10 协同修复 | 人和 chatbot 共同修复 breakdown 可以缓解失败影响 | 对话 breakdown 修复不足以解释代码状态恢复；coding agent 需要修复的是 agent 行动留下的代码轨迹。 |

### 为什么必须迁移

这个新情境改变了旧理论的几个关键假设：

1. 从“建议”变成“代码行动”。许多 AI 决策支持概念默认系统给 advice，人类决定采纳；coding agent 会直接修改工件，开发者面对的是已经成形的代码状态。
2. 从“使用工具”变成“接收代理产物”。传统 IS use 里用户通常是操作者；coding agent 中用户可能变成 reviewer/merger/maintainer。
3. 从“责任与行动大体同源”变成“责任与行动分离”。agent 行动，但开发者负责。
4. 从“错误检测”变成“作者性承接”。开发者不仅要找 bug，还要理解、解释、维护和承担代码。
5. 从“一次性决策”变成“持续代码轨迹”。agent 的输出会进入代码库，影响未来维护、团队 review 和生产风险。

因此，旧概念不是不能用，而是不够精确。它们可以作为前因、机制或后果，但不能直接命名这个 coding-agent-specific 现象。

### 更合适的构念结构

`代理代码承责缺口` 可以由五个维度构成：

| 维度 | 高缺口表现 | 低缺口表现 |
| --- | --- | --- |
| 作者性理解缺口 | 不理解 agent 代码为什么这样写，却要负责 | 理解主要逻辑、假设和实现理由 |
| 过程控制缺口 | 不知道 agent 如何一步步得到当前代码状态 | 能追踪 agent 的行动、命令和决策路径 |
| 验证证据缺口 | 缺少足够测试、日志、风险说明来支持接受 | 有足够证据判断代码是否可接受 |
| 修复能力缺口 | 出错后难以定位、回滚或修复 | 能恢复代码状态并继续协作 |
| 责任承接缺口 | 不敢把 agent 代码视为自己可解释、可维护、可承担的产物 | 能向同事解释并承担 agent-authored code |

### 最适合的研究问题

1. 什么样的 agent 输出会扩大或缩小代理代码承责缺口？
2. 承责缺口是否解释了为什么开发者不愿意 merge agent 代码，即使他们认为 agent 能力很强？
3. 承责缺口是否导致两种相反后果：过度审查/不敢委托，或浅层审查/风险接受？
4. 测试证据、行动日志、风险摘要和回滚点是否能降低承责缺口？
5. 承责缺口是否比 trust 更能预测 bug 发现率、merge 信心和后续委托范围？

### 最小可检验模型

`agent 行动强度` 和 `代码证据链完整性` -> `代理代码承责缺口` -> `merge 信心`、`验证深度`、`后续委托范围`

调节变量：

- `任务风险`：高风险任务下，承责缺口对 merge 信心的负面影响更强。
- `开发者经验`：专家可能更能降低缺口，也可能因为更敏感而感知到更高缺口。

这样，迁移的必要性就更清楚：我们不是把 delegation、trust、accountability、error detection 换个名字放到 coding agent 里，而是指出 coding agent 让这些理论都漏掉了同一个新矛盾：**代码行动的作者性被 agent 部分拿走，但代码责任仍由开发者承接。**

## 其他核心概念的前因和后果

下面把其余五个概念也展开成类似的研究模型。重点仍然不是照搬文献里的原构念，而是看这些原构念如何在 coding agent 的独有情境里被重新开发。

## 代理输出的可验证性缺口：前因和后果

核心问题：agent 产出的代码、diff、解释、测试和命令记录，是否足以让开发者判断“这东西真的可靠吗”。这不是一般 trust，而是对 agent-authored code 的可审查性、可证据化和可承担性的判断。

### 可能前因

| 前因类别 | 具体前因 | 影响逻辑 | 对应文献原料 |
| --- | --- | --- | --- |
| 变更复杂度 | diff 大小、跨文件数量、架构影响、隐性依赖 | 变更越复杂，开发者越难判断正确性，可验证性缺口越大 | #95 product uncertainty；#184 multiple problem spaces |
| 证据丰富度 | 测试结果、覆盖信息、命令日志、失败/修复记录、风险摘要 | 证据越丰富，开发者越容易从表面接受转向有根据的接受 | #175 user calibration；#156 error detection |
| 解释可追溯性 | agent 是否解释为什么改、依据什么上下文改、替代方案是什么 | 解释如果能连接到具体代码和任务意图，可降低验证缺口；泛泛解释反而可能制造虚假信心 | #149/#162/#177 explanation |
| 测试环境可信度 | 是否有自动测试、测试是否覆盖关键路径、测试是否由 agent 生成 | 测试越可信，越能支持验证；测试薄弱时，agent 的“已通过”价值有限 | #175 calibration；#204 vigilance |
| 开发者领域熟悉度 | 开发者是否熟悉该模块、框架、业务规则 | 熟悉度高时能独立审查；熟悉度低时更依赖 agent 解释和启发式线索 | #2 patient evaluation；#53 metacognition |
| 时间压力 | 是否急于完成任务、是否有 deadline | 时间压力可能让开发者减少验证，扩大“实际可验证性”和“自以为可验证性”的差距 | #198 effort saving；#75 cognitive load |
| 警告/审批疲劳 | agent 是否频繁给出风险提示、审批请求和低价值通知 | 高频低价值提示会让开发者习惯化，降低对真正风险的警觉 | #30 warning habituation |
| agent 自信表达 | agent 是否用强确定语气、是否标注不确定性 | 过强自信可能降低验证努力，尤其在证据不足时造成过度依赖 | #12 anchoring；#44 cognitive bias |

### 可能后果

| 后果类别 | 具体后果 | 为什么有价值 |
| --- | --- | --- |
| 验证深度 | 是否逐行审查、补测试、运行场景、检查边界条件 | 是最直接的行为后果，连接代码质量 |
| merge 信心 | 是否愿意接受、合并或提交 agent 产出 | 解释为什么看似完成的代码仍不能进入主干 |
| 过度依赖 | 在证据不足时仍接受 agent 产出 | 解释 agent 带来的安全和质量风险 |
| 过度怀疑 | 即使证据充分仍不敢接受 | 解释 agent 效率收益为什么无法实现 |
| bug 发现率 | 是否能发现植入 bug、边界错误、回归风险 | 可作为实验中的客观结果 |
| 审查焦虑 | 开发者是否觉得“我可能漏掉了什么” | 解释为什么 agent 生成很快但体验仍然累 |
| 学习效果 | 开发者是否通过验证过程理解代码 | 区分 agent 是学习支架还是黑箱替代 |

### 文献里类似概念通常怎么研究

- #175 的 user calibration 研究信心是否匹配决策质量，可改造成“开发者对 agent 代码质量的信心是否匹配真实质量”。
- #156、#159 研究错误/欺骗检测、警告和误报，可改造成“开发者如何在 agent 代码中检测隐藏问题”。
- #2 说明用户评价专家建议时可能依赖启发式，可迁移为开发者依赖 agent 语气、解释流畅度、测试通过等表面线索。
- #53、#92 可支持双重监控和双过程评价：开发者既要监控自己是否偷懒，也要监控 agent 输出是否可信。
- #198 的 effort saving 提醒我们：工具可能让用户节省努力，而不是提升质量；这正是 agent 验证场景的关键风险。

### 一个最清晰的起步模型

`证据丰富度` 和 `变更复杂度` -> `可验证性缺口` -> `验证深度`、`merge 信心`、`bug 发现率`

可以让被试审查同一个 agent 生成的代码修改，操纵 diff 是否大/小、是否跨文件、是否提供测试证据和行动日志。然后测他们的可验证性感知、审查时间、发现 bug 的数量、接受意愿和信心水平。

## 情境化能力边界感：前因和后果

核心问题：开发者是否知道这个 agent 在当前仓库、任务、上下文和工具权限下能安全做什么、不能做什么、何时应该接管。它不是一般 mental model，而是面向具体 coding task 的动态边界判断。

### 可能前因

| 前因类别 | 具体前因 | 影响逻辑 | 对应文献原料 |
| --- | --- | --- | --- |
| 性能反馈 | agent 过去成功/失败记录、近期表现、错误类型 | 具体反馈帮助开发者形成边界，而不是形成笼统好感或坏印象 | #18 performance information；#39 reliance adjustment |
| 上下文充分性提示 | agent 是否显示已读文件、理解范围、未掌握信息 | 开发者能看到 agent 知道什么/不知道什么，才更容易判断边界 | #56 know-what/know-how gap |
| 任务适配提示 | agent 是否提示任务难度、风险、适合自动化程度 | 帮助开发者决定委托范围和任务拆解方式 | #54 delegation metaknowledge |
| 失败模式可见性 | agent 是否解释常见错误、局限、置信来源 | 失败模式越可见，开发者越能避免错误委托 | #166 mental model；#180 expectation realism |
| 开发者经验 | 开发者对代码库、语言、测试、架构的熟悉度 | 经验高者更容易识别 agent 的边界；经验低者更依赖系统提示 | #166 proficiency；#184 programming representation |
| 修复经历 | 开发者是否经历过 agent 走偏并成功修复 | 修复经历能让边界知识从抽象变成情境化经验 | #105 adaptive use；#10 repair |
| 输出不确定性 | 任务本身是否开放、需求是否模糊、代码状态是否复杂 | 不确定性高时，能力边界更难判断 | #45 unknowability；#95 uncertainty |

### 可能后果

| 后果类别 | 具体后果 | 为什么有价值 |
| --- | --- | --- |
| 委托校准 | 把合适任务交给 agent，不合适任务自己做或拆小 | 直接影响 agent 是否真的提高绩效 |
| 任务拆解 | 是否把大任务拆成 agent 可处理的小步骤 | 是 coding agent 使用能力的重要行为表现 |
| 上下文提供 | 是否主动给文件、测试、约束、业务规则 | 连接到 prompt/context engineering，但更有理论化空间 |
| 接管时机 | 是否能在 agent 继续走偏前暂停或纠正 | 直接影响错误扩散 |
| 信任动态 | 根据不同任务和证据调整信任，而非整体信或不信 | 把 trust 变成任务情境化判断 |
| 学习曲线 | 使用经验是否让开发者越来越会委托 | 可解释新手/专家差异 |

### 文献里类似概念通常怎么研究

- #54 研究人类是否知道哪些任务适合委托给 AI，核心是 delegation metaknowledge；迁移到 coding agent 时，任务不再是静态分类，而是仓库上下文中的多步代码行动。
- #56 的 know-what/know-how gap 提醒我们，agent 可能“知道”API 文档，却不懂团队实践和隐性约束。
- #166 的 mental model 可提供测量思路，但我们要测的是能力边界、失败模式和上下文充分性，而不是一般系统理解。
- #18、#39、#82、#180 都说明用户会根据性能反馈和期望失验调整使用，但 coding agent 里要研究的是任务级别的动态调整。

### 一个最清晰的起步模型

`上下文充分性提示` 和 `失败模式反馈` -> `情境化能力边界感` -> `委托校准` 与 `接管时机`

可以让开发者面对多个 coding tasks，操纵 agent 是否展示“已掌握上下文/未掌握上下文”和“该任务风险/常见失败模式”。观察开发者是否能正确选择委托、拆分、补充上下文或接管。

## 代理行动轨迹的可修复性：前因和后果

核心问题：当 agent 误解需求、改坏代码或沿错误方向推进时，开发者是否能定位偏差、撤销错误、让 agent 理解问题并恢复协作。这不是一般 service recovery，而是代码状态和协作路径的恢复。

### 可能前因

| 前因类别 | 具体前因 | 影响逻辑 | 对应文献原料 |
| --- | --- | --- | --- |
| 行动日志 | agent 是否记录每一步改动、命令、依据和目标 | 日志越清楚，越容易定位从哪里开始走偏 | #10 repair；#162 explanation |
| 检查点/回滚 | 是否有阶段性 checkpoint、可逆 diff、自动保存 | 可逆性降低失败成本，提高继续协作意愿 | #105 adaptive use；#10 repair |
| 解释粒度 | 解释是泛泛总结，还是对应到具体文件、函数和测试 | 粒度越细，越利于修复而不只是理解 | #149/#177 explanation type |
| 失败自诊断 | agent 是否能识别自己可能误解了什么、提出修复计划 | 自诊断能把失败从用户单方面负担变成共同修复 | #25 machine-induced reflection |
| 任务模块化 | 任务是否被拆成小步，每步结果是否可检查 | 小步推进让错误更早暴露，更容易恢复轨迹 | #54 delegation；#105 adaptive use |
| 开发环境支持 | IDE/git/test 是否支持快速查看、撤销、重跑 | 工具环境会影响可修复性，不只是 agent 语言能力 | #199 restrictiveness/guidance |
| 开发者调试能力 | 开发者是否能读懂变更、运行测试、定位问题 | 可修复性是人-agent-工具共同属性 | #166 proficiency；#184 programming problem spaces |

### 可能后果

| 后果类别 | 具体后果 | 为什么有价值 |
| --- | --- | --- |
| 失败后继续使用 | agent 犯错后是否仍愿意继续协作 | 区分“可忍受失败”和“破坏性失败” |
| 修复时间 | 从发现错误到恢复可工作状态的时间 | 可作为客观效率指标 |
| 回滚/接管行为 | 是否回滚、让 agent 修、自己修、重开任务 | 解释不同恢复策略 |
| 信任恢复 | 失败后是否能恢复对 agent 的任务级信任 | 比一次性信任更贴近真实使用 |
| 代码状态信心 | 修复后是否相信代码库处于一致状态 | coding agent 特有结果 |
| 学习和边界更新 | 失败是否帮助开发者理解 agent 的局限 | 连接可修复性和能力边界感 |

### 文献里类似概念通常怎么研究

- #10 研究 chatbot breakdown 中的 collaborative repair，但 coding agent 的 breakdown 不只是对话失败，而是代码状态偏移。
- #25 研究 AI 如何诱发专业人员反思，可迁移为 agent 失败如何促发开发者重新理解任务、代码和 agent 能力。
- #149、#162、#177 提供 explanation 设计原料，但我们关心解释是否帮助定位和恢复，而不是单纯提升接受度。
- #105 的 adaptive use 可以帮助解释用户在技术事件后如何从自动使用转向调整使用。

### 一个最清晰的起步模型

`行动日志/检查点` 和 `失败自诊断` -> `行动轨迹可修复性` -> `失败后继续使用`、`修复时间`、`信任恢复`

可以设计一个 agent 故意在中途引入可修复错误的任务，操纵是否提供行动轨迹、回滚点和自诊断。观察开发者能否定位错误、愿不愿意让 agent 继续修、以及最终是否恢复 merge 信心。

## 监督注意力编排：前因和后果

核心问题：agent 在什么时候把开发者拉回监督回路。它不是普通通知体验，因为这些打断往往涉及权限、风险、命令执行、方案确认和错误扩散。

### 可能前因

| 前因类别 | 具体前因 | 影响逻辑 | 对应文献原料 |
| --- | --- | --- | --- |
| 中断时机 | 在深度思考时、等待测试时、阶段结束时、风险出现时打断 | 时机越贴合开发节奏，越不破坏心流且能保留监督价值 | #20 flow interruption；#75 interruption timing |
| 中断相关性 | 请求是否与当前目标、风险、待决策事项相关 | 高相关中断更可能被认真处理，低相关中断导致疲劳 | #20 relevance；#66 interruption overload |
| 风险分级 | 低风险自动推进，高风险请求确认 | 分级能减少无意义审批，同时保留关键监督 | #30 warning habituation；#204 vigilance |
| 状态可视化 | agent 是否显示进度、当前步骤、风险、等待事项 | 状态可见可减少不必要打断，也让开发者知道何时介入 | #117 awareness displays |
| 批量/延迟确认 | 是否把多个低风险确认合并，或等到自然断点 | 降低上下文切换成本 | #75 cognitive load |
| 开发者负载感知 | agent 是否知道用户当前是否忙、是否在编辑/阅读/测试 | 负载感知越好，中断越像协作而非噪音 | #142 monitor/control attention |
| 审批历史 | 开发者是否长期看到大量低价值提示 | 低价值提示会习惯化，降低真正警告的效果 | #30 habituation |

### 可能后果

| 后果类别 | 具体后果 | 为什么有价值 |
| --- | --- | --- |
| 心流保持 | 是否维持问题空间和专注状态 | 连接开发者体验和生产力 |
| 审批质量 | 是否认真处理权限/风险确认 | 关系到安全委托 |
| 警告响应 | 是否忽略关键风险提示 | 解释 agent 自动化中的安全问题 |
| 监督负荷 | 开发者觉得监督 agent 是否耗神 | 解释“agent 帮忙但也很累” |
| 错误扩散 | agent 是否因太晚打断而把错误扩大 | coding agent 特有后果 |
| 委托意愿 | 开发者是否愿意让 agent 长时间自主推进 | 监督体验影响自主授权 |

### 文献里类似概念通常怎么研究

- #20、#66、#75 研究中断频率、相关性、时机和认知负荷，但我们要把中断改造成“监督节点”。
- #30 研究警告习惯化，非常适合迁移到 agent 审批疲劳。
- #117 的 awareness display 提供状态显示的原料，可转成 agent 进度和风险显示。
- #142 研究监控和控制的注意力资源竞争，适合解释开发者在自己编码和监督 agent 之间切换。

### 一个最清晰的起步模型

`中断相关性` 和 `风险分级` -> `监督注意力适配感` -> `审批质量`、`心流保持`、`委托意愿`

可以让 agent 在任务中以不同方式请求确认：固定频率打断、只在高风险处打断、阶段结束批量确认。测开发者的心流、审批准确率、风险发现率和愿意让 agent 自主推进的程度。

## 开发者角色与能力所有权重构：前因和后果

核心问题：coding agent 进入写代码、调试、重构和解释系统这些核心专业活动后，开发者如何重新理解“我还是不是作者/专家/工程师”。它不是一般 AI threat，因为它触及的是开发者的核心实践和能力所有权。

### 可能前因

| 前因类别 | 具体前因 | 影响逻辑 | 对应文献原料 |
| --- | --- | --- | --- |
| agent 接管任务类型 | agent 做样板代码、核心逻辑、架构设计、调试、review | 越接近核心专业活动，越可能触发身份和能力所有权变化 | #5 identity work；#193 role theory |
| 可学习性设计 | agent 是否解释思路、展示替代方案、教会开发者 | 学习型 agent 可能增强能力所有权；黑箱生成可能削弱 | #138 mindshift learning；#149 explanation |
| 团队评价制度 | 团队评价速度、代码量、设计判断、review 质量还是 agent 使用能力 | 评价制度决定开发者把 agent 视为增强还是威胁 | #132 technological frames；#190 fairness/resistance |
| 开发者经验水平 | 新手、熟手、专家对 agent 接管的感受不同 | 新手可能学习或依赖；专家可能增强或被削弱 | #141 novice/expert explanation use；#166 proficiency |
| 任务所有权标记 | 代码是否标注 agent-authored，review 时如何归因 | 归因方式影响作者感和责任感 | #100 accountability；#193 role |
| 长期使用强度 | agent 是否成为日常默认编码方式 | 高强度长期使用可能改变技能保持和专业身份 | #42 unique knowledge erosion；#164 intrinsic motivation |
| 组织叙事 | 组织把 agent 说成替代者、助手、同事、生产力工具还是导师 | 叙事影响身份威胁和角色重构方向 | #59 face-saving dilemma；#132 frames |

### 可能后果

| 后果类别 | 具体后果 | 为什么有价值 |
| --- | --- | --- |
| 专业身份安全感 | 开发者是否觉得自己仍有专业价值 | 解释抵制、焦虑和采纳差异 |
| 能力所有权 | 开发者是否觉得自己理解并拥有最终方案 | 连接责任、学习和代码质量 |
| 学习投入 | 是否主动理解 agent 产出，还是只接受结果 | 区分增强与依赖 |
| 技能保持/侵蚀 | 调试、架构判断、问题表征能力是否变化 | 长期后果，重要但难研究 |
| 角色转变接受度 | 是否愿意从 coder 转向 reviewer/supervisor/orchestrator | 影响团队流程和工作设计 |
| 内在动机 | 编码乐趣、控制感、成就感是否变化 | 解释为什么效率提升不必然带来更好体验 |
| 抵制/采纳 | 开发者是否避免使用、限制使用或深度整合 | 连接到实际扩散 |

### 文献里类似概念通常怎么研究

- #5、#132 研究技术引入如何触发专业身份工作和专家技术框架，可迁移到开发者如何重新解释自己的专业价值。
- #42 研究 AI 辅助导致独特知识流失，可迁移为开发者是否失去独特问题表征和判断能力。
- #138 研究 mindshift learning，可迁移为从“自己写代码”到“定义任务、监督 agent、审查结果”的认知转型。
- #164 从工作设计和内在动机看专家系统使用，可迁移为 agent 改变任务结构后如何影响动机。
- #59 的 face-saving dilemma 可解释专家为什么可能因身份威胁而抵制系统建议。

### 一个最清晰的起步模型

`agent 接管核心任务程度` 和 `可学习性设计` -> `能力所有权感` -> `学习投入`、`专业身份安全感`、`长期使用意愿`

可以比较两种 agent 体验：一种只给最终代码，一种给代码同时解释思路、显示替代方案、要求开发者做关键判断。看开发者是否更觉得自己理解方案、保持专业价值、愿意长期使用，并通过后测任务观察是否保留相关技能。

## 当前要降权的“高适配”

这些文献仍然重要，但更适合作为背景或机制，不建议直接发展成主概念：

- 算法厌恶/欣赏：#4、#15。过于通用，除非嵌入“是否愿意承担 agent 产物责任”。
- 一般 AI trust：#17、#126、#179。需要转化为“行动后果和责任残留下的信任”。
- 一般 explanation：#149、#162、#177。应服务于可验证性和可修复性，而不是单独做解释质量。
- 一般 flow/interruption：#20、#66、#75。应转化为监督注意力编排。
- 一般 expectation/habit：#82、#120、#180。适合解释变化过程，不适合作为独有主概念。
- 一般 cognitive bias：#12、#44、#74。适合作为验证失败机制，不适合作为主概念。
