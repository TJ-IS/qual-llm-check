# 严格独特构念候选：代理性代码状态脱节感

## 先放弃前一个概念

前一个候选“代理代码责任性拥有感”不够好。它确实容易被还原成：

- 间接 IS 使用；
- 用户参与/责任矛盾；
- accountability；
- trust in AI；
- code ownership。

如果一个新概念只能说“这些旧概念在 coding agent 情境中也重要”，那不够。真正值得发展新构念，必须说明：coding agent 让旧概念的核心假设不再适用，旧概念无法直接描述这个现象。

## 新候选概念

中文暂定：代理性代码状态脱节感

英文暂定：Perceived Agentic Codebase State Drift

也可以考虑：

- Perceived Agent-Induced Codebase Drift
- Agentic Implementation Drift
- Human-Codebase State Misalignment in Agentic Programming

## 定义

代理性代码状态脱节感是指：在 coding agent 自主或半自主地读取、修改、运行和迭代代码之后，开发者感到当前代码库的实际状态，已经偏离自己对任务实现路径、修改范围、代码行为和风险位置的心理表征的程度。

更简单地说，它测量的是：

agent 把代码库推进到了一个状态，但开发者是否还跟得上这个状态。

## 高低程度

高水平：

- 开发者不清楚 agent 到底改了哪些地方，以及这些修改如何相互关联。
- 开发者知道代码变了，但不清楚代码库现在处于什么状态。
- 开发者难以判断 agent 是从哪一步开始走偏的。
- 开发者需要花大量时间重新建立对代码状态的理解。
- 开发者感觉自己从“正在编程”变成了“追赶 agent 留下的状态”。

低水平：

- 开发者能持续理解 agent 每一步行动如何改变代码库。
- 开发者知道当前代码状态与原始目标之间的关系。
- 开发者能快速定位 agent 的关键修改、风险点和失败位置。
- 开发者即使没有亲手写每一行，也没有丢失对代码状态的心理表征。

## 为什么这是 coding agent 独有的重要议题

coding agent 的独特性不只是“AI 给建议”，而是它会在真实代码库里连续行动：

1. 它读代码。
2. 它改文件。
3. 它运行命令和测试。
4. 它根据结果继续修改。
5. 它可能跨多个文件、多个步骤推进任务。

这会制造一个传统概念很难准确描述的问题：代码库状态被 agent 实际推进了，但开发者的心理表征未必同步推进。

这个问题不是普通 trust，也不是普通 delegation。开发者可能非常信任 agent，但仍然跟不上 agent 改完后的代码状态。开发者也可能知道自己把任务委托出去了，但真正困难的是：agent 行动之后，代码库已经变成一个新的状态，而开发者必须重新追上它。

## 为什么不是间接 IS 使用

间接 IS 使用关注的是：用户把系统使用委托给另一个人，但自己仍承担责任。

它的问题结构是：

人 A -> 委托人 B 使用系统 -> 人 A 仍负责。

coding agent 的问题结构不同：

开发者 -> 让 agent 直接改变代码库状态 -> 开发者需要理解一个被非人代理连续改写后的代码状态。

严格区别在于：

- 间接 IS 使用中的代理者是人，可以承担社会责任、解释行动理由、稳定保留意图。
- coding agent 是非人代理，它会直接改变代码工件，但没有人类作者的持续意图和责任主体。
- 间接 IS 使用不关注“系统状态被代理连续推进后，原用户的心理表征是否跟得上”。

所以，间接 IS 使用可以解释“为什么用户委托”，但不能解释“为什么 agent 改完代码后，开发者失去对代码状态的把握”。

## 为什么不是用户责任矛盾

用户责任矛盾关注的是：用户参与有限，却被要求 sign off 并承担责任。

它确实和 coding agent 有关，但仍然不够精确。coding agent 的关键不是单纯“参与少但要负责”，而是：

agent 的连续代码行动改变了代码库状态，使开发者的心理表征和实际代码状态发生脱节。

用户责任矛盾可以解释“为什么不公平/为什么有压力”，但不能解释：

- 开发者为什么需要重新追踪 agent 的行动轨迹；
- 为什么跨文件 diff 会让人失去状态感；
- 为什么有测试和解释仍然可能跟不上；
- 为什么 agent 走偏后，开发者首先要恢复对代码状态的理解，而不只是决定是否负责。

## 为什么不是 trust in AI

Trust in AI 关注的是用户是否愿意依赖 AI。

代理性代码状态脱节感关注的是：用户是否还能理解 agent 已经造成的代码状态。

两者可以分离：

- 高 trust + 高脱节：我相信 agent 很强，但它改完后我看不懂代码库现在是什么状态。
- 低 trust + 低脱节：我不太信 agent，但它每一步改动我都看得清。
- 高 trust + 低脱节：理想情况，既相信也跟得上。
- 低 trust + 高脱节：最差情况，既不信也跟不上。

所以 trust 不是这个构念本身。trust 可能是前因、后果或调节变量，但不能替代“代码状态脱节”。

## 为什么不是 explainability

Explainability 关注 agent 是否解释了它的行为。

但 coding agent 中，即使解释很多，开发者仍然可能有高脱节感：

- 解释只覆盖局部改动，不覆盖跨文件影响。
- 解释说明了“为什么这样写”，但没有让开发者理解当前代码库状态。
- 解释是事后叙述，未必对应真实行动轨迹。
- 开发者需要的是状态同步，而不只是理由说明。

因此，解释可以降低脱节感，但解释本身不是脱节感。

## 为什么不是 code review

Code review 关注对代码变更的审查。

但传统 code review 通常有一个人类作者、一个相对稳定的变更意图，以及 reviewer 和 author 之间的责任分工。coding agent 的特殊之处是：

- 代码作者性是非人和人共同形成的；
- agent 可能在 review 前已经多步改变工作区；
- reviewer 往往就是发起者本人；
- 需要审查的不只是最终 diff，还包括 agent 的行动轨迹和当前代码状态是否仍与任务目标对齐。

因此，传统 code review 可以作为后果或行为场景，但不能直接命名这个心理状态。

## 为什么必须迁移

过去理论常常默认一个前提：用户理解、操作或审查的是一个相对可定位的系统输出。

coding agent 打破了这个前提。它不是一次性输出一个建议，而是在代码库中产生连续状态变化。开发者面对的不是单个答案，而是一个被 agent 推进后的工作区状态。

因此，真正需要新概念的地方是：

开发者的心理表征与 agent 推进后的代码库状态之间是否同步。

这不是简单的信任、责任、解释或委托，而是 agentic programming 中一种新的状态关系。

## 可能维度

| 维度 | 含义 |
| --- | --- |
| 修改范围脱节 | 开发者不清楚 agent 修改了哪些文件、函数或依赖关系 |
| 实现路径脱节 | 开发者不清楚 agent 为什么沿这个实现路径推进 |
| 行动轨迹脱节 | 开发者不清楚 agent 的关键步骤、命令、测试和修复顺序 |
| 风险位置脱节 | 开发者不清楚当前代码状态中最可能有问题的地方 |
| 目标对齐脱节 | 开发者不确定当前代码状态是否仍然服务于原始任务目标 |

## 条目方向

- coding agent 修改后，我很难说清当前代码库到底发生了哪些关键变化。
- 我能跟上 coding agent 每一步修改如何影响代码库状态。反向
- coding agent 完成任务后，我需要花很多时间重新理解当前代码状态。
- 我不清楚 coding agent 的实现路径是否仍然符合我的原始目标。
- 当 coding agent 走偏时，我很难判断它是从哪一步开始偏离的。
- 我知道 agent 修改后的代码中哪些地方最需要重点检查。反向
- 即使 agent 修改了多个文件，我仍能把这些修改整合成一个清楚的心理模型。反向

## 可能前因

- agent 自主行动程度：自动修改、自动运行命令、自动连续修复越多，脱节感可能越强。
- 变更跨度：跨文件、跨模块、跨抽象层修改越多，脱节感越强。
- 行动轨迹可见性：步骤、命令、文件读取、测试结果越可见，脱节感越低。
- 检查点密度：自然断点和阶段性确认越清楚，脱节感越低。
- 开发者代码熟悉度：越熟悉相关模块，越不容易脱节。
- 任务开放性：需求越模糊、实现路径越多，越容易脱节。

## 可能后果

- review 时间增加。
- bug 发现率下降或误报增加。
- merge 信心下降。
- 更频繁回滚或重做。
- 对后续大任务委托意愿下降。
- 责任焦虑增加。
- 对 agent 的信任可能下降，但信任是后果之一，不是构念本身。

## 最小研究模型

`agent 自主行动程度` 和 `变更跨度` -> `代理性代码状态脱节感` -> `review 时间`、`bug 发现率`、`merge 信心`、`后续委托意愿`

调节变量：

- `行动轨迹可见性`：高可见性可以削弱自主行动程度对脱节感的影响。
- `代码熟悉度`：熟悉模块的开发者较不容易产生脱节感。

这个构念比“责任性拥有感”更独特，因为它不再围绕责任、trust 或 ownership 这些旧理论打转，而是抓住 coding agent 真正特有的 UX 问题：**agent 不是只给答案，而是在代码库中推进状态；开发者需要追上这个被代理推进的代码状态。**
