# 高适配文献再复审：避开掌控感后的核心构念判断

## 这次先承认的问题

前面提出的几个方向，包括“状态脱节感”“接管可行感”“责任性拥有感”“验证可判定性”，都过于靠近 perceived control / supervisory control。它们的问题都是：只要把题项写成“我能不能理解、验证、干预、接管、放心合并”，就很容易被掌控感吸收。因此这些方向可以保留为重要机制或结果，但不适合作为我们要开发的新核心构念。

这次复审只做一件事：回到 65 篇高适配文献，找一个不靠换词、而是旧概念真的无法完整描述的 coding-agent-specific UX 对象。

## 复审规则

我用三个过滤器重新看高适配概念：

1. 旧概念可吸收性：如果可以被 trust、perceived control、explainability、algorithm aversion、cognitive load 直接吸收，就不作为主构念。
2. 掌控感反问：如果把概念改写成“我能不能控制/判断/干预/恢复”，意义基本不变，就降级为掌控感相关变量。
3. coding-agent 独特性：必须依赖 coding agent 的特殊性，即它不仅给建议，还能参与软件开发中的问题理解、实现选择、代码生成、测试解释和工作角色重构。

## 被降级的高适配簇

### 1. 委托、责任、验证、监督簇

相关文献包括 #6、#10、#18、#30、#36、#39、#51、#53、#54、#67、#76、#99、#100、#113、#117、#142、#144、#149、#156、#157、#159、#175、#177、#198、#199、#204。

这些文献非常重要，但更像在解释 coding agent 使用中的控制、监督、校准、风险沟通、错误检测和委托质量。它们适合作为前因、机制或后果，不适合作为新构念本身。原因是它们的核心问题通常可以被翻译为：

- 我是否能判断 agent 做得对不对？
- 我是否能保持合适警觉？
- 我是否能有效监督或干预？
- 我是否能校准信任和依赖？
- 我是否能承担或分配责任？

这些都离 perceived control 太近。

### 2. 信任、厌恶、期待与启发式评价簇

相关文献包括 #2、#3、#4、#12、#15、#17、#38、#44、#82、#92、#95、#126、#179、#180。

这些文献能解释开发者为什么接受、拒绝、过度依赖或错误评价 coding agent，但它们本身仍是较成熟的 AI 信任、算法厌恶、锚定、启发式评价、期望失验等概念。迁移到 coding agent 后很有用，但还不足以构成“只有 coding agent 才让旧概念不适用”的新核心。

### 3. 中断、心流与注意力调度簇

相关文献包括 #20、#30、#36、#66、#75、#117、#142。

这一簇非常有实践价值，适合做交互设计研究，例如 agent 何时打断、何时请求确认、何时提供状态更新。但它更像设计变量或体验条件。其核心仍可被 interruption、flow、attention allocation、cognitive load 吸收。

## 当前最值得发展的核心对象

我现在更倾向于把核心现象界定为：

**代理编程中的专业认知位移**

英文可暂定为：

**Perceived Epistemic Role Displacement in Agentic Programming**

这不是最终命名，重点是它指向的对象：coding agent 使开发者感到软件开发中原本属于自己的专业认知活动，被部分转移给了 agent。

## 工作定义

代理编程中的专业认知位移，是指开发者在使用 coding agent 完成软件开发任务时，感到自己在问题理解、实现假设形成、方案权衡、代码生成、错误解释和知识沉淀等专业认知活动中的角色，从“亲自推理和构造解决方案的人”转向“提示、筛选、验收、修补或旁观 agent 解决方案的人”的程度。

更短地说：

**它测量的不是开发者能不能控制 agent，而是开发者是否感到核心编程认知工作正在从自己身上转移到 agent 身上。**

## 高低程度

高专业认知位移：

- 我感觉关键实现思路主要是 agent 想出来的，而不是我形成的。
- 我更多是在筛选和验收 agent 的方案，而不是亲自构造方案。
- 完成任务后，我得到了一段可用代码，但没有明显增长自己的实现 know-how。
- 我感觉自己的角色更像 prompt / review / repair，而不是 programming。
- 我虽然能让 agent 改来改去，但核心问题解决过程并不在我这里发生。

低专业认知位移：

- agent 帮我加快了实现，但关键问题理解和方案权衡仍由我参与形成。
- 我能从 agent 的建议中发展自己的实现思路，而不是只接收结果。
- 使用 agent 后，我对相关代码、模式或调试逻辑有了可迁移的理解。
- agent 的参与没有削弱我作为开发者的专业贡献感。
- 我仍觉得自己在进行编程发现，只是多了一个能执行和反馈的协作者。

## 为什么它不是掌控感

掌控感问的是：我能否影响、约束、干预或恢复 agent 的行为与结果。

专业认知位移问的是：这次编程任务中的专业思考、实现判断和 know-how 形成，主要发生在我这里，还是被转移到了 agent 那里。

两者可以分离：

| 情形 | 掌控感 | 专业认知位移 |
| --- | --- | --- |
| 我一步步 approve agent，随时能停它，但核心实现都是 agent 提出来的，我只是验收 | 高 | 高 |
| agent 比较自主，但不断提出备选方案、解释权衡、让我形成判断，我最后学会了这类实现 | 中或低 | 低 |
| 我不能很好控制 agent，也没有参与核心推理 | 低 | 高 |
| 我能控制 agent，也深度参与问题求解 | 高 | 低 |

所以它不是“低掌控感”的反面。一个人可以很有控制权，但仍觉得自己没有参与专业认知活动；也可以控制不多，但通过高质量协作保留了专业认知角色。

## 为什么旧概念不够

### 不是 trust in AI

Trust 解释我是否愿意依赖 agent。专业认知位移解释我依赖 agent 时，自己的专业认知角色是否被迁走。开发者可以高度信任 agent，同时担心自己逐渐不再形成实现 know-how。

### 不是 perceived control

Control 解释我是否能让 agent 按我的意图行动。专业认知位移解释我是否仍然是解决方案的认知构造者。控制按钮、审批点和回滚机制可以很强，但它们不保证开发者参与了编程发现过程。

### 不是 explainability

Explainability 是 agent 提供解释的性质。专业认知位移关注解释是否让开发者重新进入问题求解过程。事后解释可能让人看懂结果，但不一定恢复开发者的专业认知角色。

### 不是 self-efficacy

Self-efficacy 问“我相信自己能不能完成任务”。专业认知位移问“在 agent 协作中，核心专业认知活动实际上由谁承担”。一个高能力开发者也可能在高性能 agent 面前产生高位移感。

### 不是专业身份威胁

身份威胁是可能后果。专业认知位移是更靠前的体验判断：开发者先感到自己的问题求解、实现判断和 know-how 形成被转移，之后才可能出现身份威胁、抵制、焦虑或动机下降。

## 为什么它对 coding agent 有独特价值

coding agent 和普通 AI 建议系统不同之处在于：它直接进入程序员最核心的专业实践。它不只是评价、推荐或预测，而是参与：

- 读代码；
- 形成实现路径；
- 写代码；
- 调试；
- 解释错误；
- 修改架构或抽象；
- 生成可合并的工作成果。

因此，coding agent 带来的关键 UX 问题不只是“我能不能控制它”，也不是“我信不信它”，而是：

**当 agent 真的替我推进开发任务时，我还是不是在进行编程意义上的专业思考？**

这个问题有现实意义，因为它会影响：

- 开发者长期技能保持；
- 新手学习质量；
- 资深开发者的专业身份和内在动机；
- 对 agent 的抵制或依赖；
- 代码风格与团队知识多样性；
- 团队是否只获得短期产出，却损失长期 know-how；
- coding agent 产品是否应该设计成“答案生成器”还是“反思与实现协作者”。

## 可能维度

1. 问题理解位移：需求澄清、约束识别和问题分解是否主要由 agent 完成。
2. 实现推理位移：关键实现假设、算法选择、架构权衡是否主要由 agent 提出。
3. 代码构造位移：开发者是否感觉自己只是编辑或验收 agent 生成的代码。
4. 错误解释位移：调试和失败解释是否主要依赖 agent，而不是开发者自己的诊断。
5. know-how 沉淀缺失：任务完成后，开发者是否没有形成可迁移的编程理解。
6. 专业角色位移：开发者是否感觉自己从 programmer 变成 prompt operator / reviewer / repairer。

这些维度共同指向一个程度：开发者是否感到自己的专业认知角色被 coding agent 转移。

## 可能前因

- agent 的答案先行程度：agent 是否在开发者形成方案前直接给出完整实现。
- 交互模式：是 solve-then-explain，还是 compare-and-reason，还是 ask-before-solve。
- 解释类型：只解释最终代码，还是解释替代方案、失败路径和权衡。
- 任务新颖性：任务越新，开发者越可能把认知工作外包给 agent，也越可能产生学习机会。
- 开发者经验：新手可能更容易产生 know-how 沉淀缺失；专家可能更容易产生专业角色位移或身份威胁。
- 团队规范：团队是否鼓励理解 agent 代码，还是只奖励快速合并。
- agent 性能表现：高性能可能降低反思需求，反而增强位移；适度冲突可能诱发反思。

## 可能后果

- 学习效果和可迁移 know-how。
- 长期独立编程能力。
- 内在动机和工作意义感。
- 专业身份威胁或身份重构。
- 对 coding agent 的依赖方式：增强型使用还是替代型使用。
- 代码理解深度和后续维护质量。
- 团队层面的知识多样性和方案多样性。

## 最小研究模型

`agent 答案先行程度` 和 `solve-then-explain 交互模式`
-> `代理编程中的专业认知位移`
-> `学习效果`、`内在动机`、`专业身份威胁`、`长期依赖方式`、`后续代码维护表现`

调节变量：

- `反思诱发设计`：要求比较方案、解释权衡、预测测试结果，可以削弱专业认知位移。
- `开发者经验`：新手和专家对位移的解释和后果可能不同。
- `任务新颖性`：新任务中位移更可能影响学习，熟悉任务中位移可能主要表现为效率提升。

## 当前判断

如果我们的目标是开发一个同时具有理论贡献和实践指导意义的新构念，我现在会把“代理编程中的专业认知位移”排在第一，而把“验证、接管、责任、控制、监督”降为围绕它的机制或边界条件。

原因是：前者真正回答了 coding agent 改变了什么人类专业经验；后者更多回答开发者如何安全地使用 agent。

## 更精确定义：这个构念到底测什么

### 构念对象

这个构念的对象不是 agent，也不是 agent 产出的代码质量，而是：

**开发者在一次 coding-agent-assisted programming 任务中的专业认知角色。**

也就是说，它关注开发者在这次任务中是否仍然作为一个程序员参与核心认知活动，还是更多退到提示、筛选、验收、修补和追随 agent 的位置。

### 被测属性

被测属性是：

**开发者感到核心编程认知活动从自己转移到 coding agent 身上的程度。**

这里的“核心编程认知活动”包括：

- 理解问题与约束；
- 拆解任务；
- 形成实现假设；
- 比较实现方案；
- 生成关键代码结构；
- 解释测试失败和错误原因；
- 抽象出可迁移的编程 know-how。

因此，这个构念不是问：

- 我能不能控制 agent；
- 我信不信 agent；
- 我能不能验证 agent；
- agent 写得好不好。

它问的是：

**这次编程任务中，原本构成“我在编程”的那些专业思考活动，主要还是发生在我这里，还是被 agent 承担了。**

### 推荐工作定义

更正式的定义可以写成：

**代理编程中的专业认知位移**是指：开发者在使用 coding agent 完成软件开发任务时，感知到问题理解、实现推理、方案权衡、代码构造、错误诊断和经验沉淀等核心编程认知活动，从自己作为程序员的专业实践中部分转移到 coding agent 身上的程度。

更口语但仍然精确的说法：

**它测量的是：开发者在 agent 帮忙写代码时，是否觉得自己仍在进行编程式的问题求解，还是变成了 agent 方案的提示者、验收者和修补者。**

## 它是不是 0-1 的

不是。它不应该被定义成 0-1 的二分变量。

它应该是一个连续构念，最好作为 task-level 或 episode-level perception 来测量。也就是说，在某一次具体使用 coding agent 完成任务之后，开发者可能有不同程度的专业认知位移。

可以理解为从低到高的连续谱：

| 程度 | 状态 |
| --- | --- |
| 很低 | agent 主要承担执行和反馈，开发者仍主导问题理解、方案形成和错误解释 |
| 较低 | agent 提供局部建议，但开发者仍能把建议纳入自己的推理过程 |
| 中等 | agent 生成了关键方案，开发者理解并调整，但部分实现推理没有亲自经历 |
| 较高 | agent 主要完成问题拆解、实现和调试，开发者主要在筛选、确认和修补 |
| 很高 | 开发者得到结果但没有形成自己的实现理解或可迁移 know-how，感觉核心编程过程发生在 agent 那里 |

它可以在问卷中用 Likert 题项测量，例如：

- 在这次任务中，关键实现思路主要由 coding agent 形成。
- 我更多是在筛选 agent 的方案，而不是形成自己的实现方案。
- 虽然任务完成了，但我没有明显形成关于这个问题的可迁移实现理解。
- coding agent 让我从直接解决编程问题的人，转向了验收和修补其方案的人。
- 在这次协作中，我仍然参与了主要的实现推理过程。反向

## 为什么不是“是否用了 agent”的 0-1

因为两个开发者都用了 coding agent，但认知位移程度可能完全不同。

低位移使用：

开发者先形成自己的方案，再让 agent 实现局部代码；或者 agent 提供多个方案，开发者比较权衡后形成自己的理解。

高位移使用：

开发者给出任务后，agent 直接生成完整方案、代码和修复；开发者只做表层审查，任务完成后也说不清为什么这样实现。

所以，关键不是“有没有 agent 参与”，而是“核心编程认知活动在谁那里发生”。

## 可能维度的更清晰版本

### 1. 问题框定位移

开发者是否感到需求澄清、约束识别、任务拆解主要由 agent 完成。

高水平表现：

- 我没有充分想清问题边界，agent 就已经替我拆解了任务。
- 我依赖 agent 来告诉我这个需求实际上要解决哪些子问题。

文献联系：

- #184 编程作为多问题空间中的科学发现，说明问题空间构建本身就是编程困难的核心。
- #51 agentic IS delegation，说明 agent 不只是被动工具，而会承担任务和目标追求。

### 2. 实现推理位移

开发者是否感到关键实现假设、方案选择、架构权衡主要由 agent 形成。

高水平表现：

## 和关键旧概念的边界

### 与掌控感的区别

掌控感的对象是 agent 行为或任务结果：我能不能影响、停止、纠正、恢复。

专业认知位移的对象是开发者自己的认知角色：编程中的关键问题求解是否还由我承担。

典型区分：

高掌控、高位移：我每一步都批准 agent，但方案、代码和修复主要是 agent 想出来的。

低掌控、低位移：agent 自主执行较多，但它促使我比较方案、预测结果、解释失败，我仍深度参与实现推理。

### 与信任的区别

信任问我是否愿意依赖 agent。

专业认知位移问我依赖 agent 时，自己的编程 know-how 和问题求解角色是否被转移。

开发者可以高度信任 agent，同时强烈感到自己的实现能力没有被锻炼；也可以不太信任 agent，但仍通过反驳和修改 agent 建议参与深层推理。

### 与专业身份威胁的区别

专业身份威胁是后果之一，不是同一个概念。

专业认知位移是更前端的体验判断：我在这次任务中是否仍然承担核心编程认知活动。

如果这种位移长期发生，才可能进一步导致身份威胁、动机下降、抵制或角色重构。

### 与 automation deskilling 的区别

deskilling 更像长期结果，关注技能是否退化。

专业认知位移是一次任务或一段使用中的主观体验，关注核心认知活动是否被转移。它可以预测 deskilling，但不等于 deskilling。

### 与学习投入的区别

学习投入问开发者是否努力学习。

专业认知位移问 agent 协作结构是否让开发者仍处在形成理解的位置。开发者可能很愿意学习，但如果 agent 直接给完整答案、只提供事后解释，仍可能发生高位移。

## 一句话版本

如果要把它压成最清楚的一句话：

**代理编程中的专业认知位移，是开发者在使用 coding agent 时，感到核心编程问题求解从自己的专业实践转移到 agent 身上的程度。**

这句话里的关键词是：

- 核心编程问题求解；
- 从自己转移到 agent；
- 程度，而不是是否发生。
