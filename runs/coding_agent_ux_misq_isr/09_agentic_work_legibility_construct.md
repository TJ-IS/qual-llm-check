# Coding Agent UX 候选构念：代理工作可读性

## 为什么重新换方向

前一个候选“代理编程中的专业认知位移”有理论味道，但它不够泛用。它更适合解释资深开发者、学习、技能保持和专业身份，不一定适合大多数 coding agent 用户的日常使用体验。

现实使用里，一个更普遍的问题是：

- 用户不爱用 CLI，因为不方便看到 agent 到底改了什么；
- agent 一直弹审批、确认和通知，用户很快疲劳；
- 用户不是一开始就说“我没有掌控感”，而是先遇到“我看不清它做了什么、哪些变化重要、哪些通知值得我停下来处理”。

这提示我们：掌控感可能是后果，不是核心构念。真正更靠前、也更 coding-agent-specific 的体验对象，可能是 agent 工作过程和工作产物是否对用户“可读”。

## 候选名称

中文暂定：**代理工作可读性**

英文暂定：**Perceived Agentic Work Legibility**

也可以考虑：

- Coding-Agent Work Legibility
- Agentic Change Legibility
- Perceived Legibility of Agentic Coding Work

目前我更推荐“代理工作可读性”，因为它比“改动可读性”更宽，能同时覆盖：

- agent 正在做什么；
- agent 已经改了什么；
- agent 为什么请求审批；
- 哪些通知真的重要；
- 当前任务推进到什么状态；
- 哪些地方需要用户注意。

## 工作定义

**代理工作可读性**是指：在使用 coding agent 完成软件开发任务时，开发者感到自己能够方便、及时、低成本地把 agent 的行动过程、代码改动、当前状态、风险位置和注意力请求理解为一个有组织的工作进展的程度。

更简单地说：

**它测量的不是用户能不能控制 agent，而是 agent 的工作是否让用户看得明白、分得清重点、知道什么时候该注意。**

## 这个构念测什么

### 构念对象

对象是 **coding agent 的工作呈现方式**，包括行动轨迹、代码 diff、状态更新、审批请求、测试结果、风险提示和任务进展。

它不是单独测 agent 能力，也不是单独测代码质量。

### 被测属性

被测属性是 **legibility / 可读性**：

用户是否能从界面和交互中形成一个清楚的、有层次的、可用于分配注意力的 agent 工作图景。

### 不是 0-1

它不是“是否可读”的二分变量，而是连续程度。

高可读性：

- 用户能快速看出 agent 改了哪些文件、为什么改、改动之间有什么关系；
- 用户能区分普通进展、需要稍后查看的变化、需要立即审批的高风险动作；
- 审批请求说明了用户要决定什么，以及这个决定的后果；
- agent 的状态更新帮助用户保持任务脉络，而不是打断脉络；
- 用户不需要从一堆终端输出、碎片日志和重复通知里重新拼 agent 的工作过程。

低可读性：

- 用户只能看到 agent 一串终端输出，很难知道实际改了什么；
- diff 分散、缺少层次，用户需要自己重建工作脉络；
- 审批请求太频繁、太相似，用户不知道哪些真正重要；
- agent 的通知像噪音，用户开始机械 approve 或直接回避使用；
- 用户最后只能通过重新 review 全部代码来理解 agent 的工作。

## 为什么它不同于掌控感

掌控感问的是：

**我能不能影响、停止、纠正或恢复 agent 的行为？**

代理工作可读性问的是：

**agent 的工作过程和改动结果是否以一种让我能看明白、分重点、安排注意力的方式呈现出来？**

二者可以分离：

| 情形 | 代理工作可读性 | 掌控感 |
| --- | --- | --- |
| CLI 连续输出很多日志，每一步都要我 approve，但我看不清到底改了什么 | 低 | 可能中等或高 |
| IDE 清楚展示计划、diff 分组、风险点和测试结果，但 agent 自动执行较多 | 高 | 可能中等 |
| agent 让我能随时 stop/rollback，但状态和改动脉络混乱 | 低 | 高 |
| agent 自主推进，但每个阶段都有清楚的工作摘要和可检查 diff | 高 | 中或高 |

所以，代理工作可读性不是掌控感本身。它更可能是掌控感的前因：

`代理工作可读性 -> 感知掌控感`

但它还会影响其他后果：

- 审批疲劳；
- 通知忽视；
- 信任校准；
- 验证成本；
- flow interruption；
- CLI/IDE 偏好；
- 后续委托意愿；
- bug 检测和 merge 信心。

## 为什么它不同于旧概念

### 不是 explainability

Explainability 主要问系统是否解释了某个输出、建议或决策。

代理工作可读性更宽。它不只包含“为什么这么做”，还包含：

- 做了什么；
- 现在做到哪一步；
- 改动分布在哪里；
- 哪些改动相互关联；
- 哪些审批请求重要；
- 哪些风险需要用户看；
- 哪些通知可以忽略或稍后处理。

一个 agent 可以给很多解释，但仍然低可读：解释很长、很碎、没有 diff 层次、没有风险排序、没有状态脉络。

### 不是 transparency

Transparency 容易理解成信息是否足够多、系统是否开放内部逻辑。

代理工作可读性强调的不是“信息越多越好”，而是信息是否被组织成用户能用来理解 agent 工作和分配注意力的形式。

CLI 的问题很典型：信息可能很多，但可读性低。

### 不是 awareness

Awareness display 文献关注用户是否知道他人状态、负载或可打断性。

代理工作可读性借鉴 awareness，但对象不同：这里不是知道同事是否忙，而是理解一个半自主 coding agent 正在如何改变代码库、什么时候需要用户注意。

### 不是 notification fatigue

审批疲劳和通知疲劳是后果。代理工作可读性低时，用户更容易疲劳；但可读性本身是对 agent 工作呈现是否清楚、分层、可区分的判断。

### 不是 verification burden

验证负担是后果或中介。可读性低会提高验证负担，因为用户需要花更多时间重建 agent 的行为轨迹和改动意义。

## 为什么这是 coding agent 独特的问题

普通聊天机器人主要产生文本回复。普通推荐系统主要给建议。传统 IDE 工具通常执行用户明确触发的局部操作。

coding agent 不同：

1. 它会读取代码；
2. 它会跨文件修改代码；
3. 它会运行命令和测试；
4. 它会根据结果继续行动；
5. 它会请求权限和审批；
6. 它可能在用户注意力之外推进任务；
7. 它的行动会沉淀为真实代码库状态。

因此，用户面对的不是单个“答案是否可信”，而是一段持续推进的 agentic work 是否能被读懂。

这就是为什么 CLI 体验会成为关键现实入口：CLI 可以给出原始过程，但很难把 agent 的工作呈现为层次化、可比较、可筛选、可审批的工作图景。

## 可能维度

### 1. 改动可见性

用户是否能方便看到 agent 改了什么。

高水平：

- diff 清楚；
- 文件、函数、模块级改动有层次；
- 用户不需要自己从终端输出中找变化。

相关现实例子：

- CLI 中用户不方便查看改动；
- IDE 集成 diff 面板可能提高这一维度。

### 2. 行动轨迹可理解性

用户是否能理解 agent 的关键行动顺序和任务推进路径。

高水平：

- 用户知道 agent 先读了什么、为什么改这些文件、测试失败后如何修复；
- agent 的行动不是一串碎片事件，而是可理解的工作轨迹。

### 3. 状态摘要清晰度

用户是否能随时知道当前任务处于什么状态。

高水平：

- 用户知道任务完成了多少；
- 当前阻塞点是什么；
- 下一步 agent 想做什么；
- 还有哪些未解决风险。

### 4. 注意力请求可区分性

用户是否能区分哪些通知或审批请求重要。

高水平：

- 低风险进展不会频繁打断；
- 高风险动作有明显区分；
- 审批请求说明决策对象和后果；
- 用户不会把所有 approval 都当成同一种噪音。

这个维度直接连接用户提到的“审批疲劳”。

### 5. 风险位置可定位性

用户是否能知道 agent 工作里最值得检查的地方在哪里。

高水平：

- agent 不只是说“我改好了”，还指出最可能影响行为、兼容性、安全或维护性的改动；
- 用户能优先 review 高风险区域。

### 6. 工作粒度匹配

agent 呈现工作的粒度是否匹配用户任务。

高水平：

- 小任务不被过度汇报；
- 大任务不被压缩成一句“完成了”；
- 阶段性 checkpoint 有意义，而不是机械通知。

## 文献联系

### 1. Agentic IS 与自主工具：为什么需要新构念

**#51 The next generation of research on IS use: A theoretical framework of delegation to and from agentic IS artifacts, 2021, MISQ**

这篇文章说明新一代 IS artifact 不再是被动工具，而是能主动承担任务、追求结果、在不确定要求下行动。它提供了 coding agent 的理论前提：用户面对的是一个会行动的 artifact。

但 delegation 理论本身不直接解释 agent 工作过程是否可读。它告诉我们为什么 agent 可以被委托；代理工作可读性解释委托发生后，用户如何理解这个 agent 正在做的工作。

**#45 The Unknowability of Autonomous Tools and the Liminal Experience of Their Use, 2021, ISR**

这篇文章说明自主工具的输入-输出关系对用户来说可能事前和事后都不可知，使用体验充满模糊性、涌现和多轨迹推进。

代理工作可读性可以看作对这种 unknowability 的 coding-agent-specific 响应：不是消灭自主性，而是让持续涌现的 agent 工作对用户更可读。

### 2. Awareness 与中断：为什么 CLI 和审批疲劳重要

**#117 Awareness displays and social motivation for coordinating communication, 2008, ISR**

该研究说明抽象的工作负载显示可以帮助协调沟通和打断时机。它启发我们：coding agent 也需要一种状态和工作负载显示，让用户知道何时该介入。

但 coding agent 的对象不是同事负载，而是代码改动、任务进展和风险位置。

**#20 What Disrupts Flow in Office Work?, 2023, MISQ**

该研究说明 IT-mediated interruptions 的频率和相关性会破坏 flow。coding agent 的通知和审批请求正是一种特殊中断，且中断通常伴随行动后果。

**#66 Life Interrupted, 2018, MISQ**

该研究提出中断过载、心理转换和任务闭合等机制。coding agent 审批疲劳可以沿这条线理解：低可读性通知会制造额外心理转换，让用户难以闭合当前编程任务。

**#75 More Harm Than Good? How Messages That Interrupt Can Make Us Vulnerable, 2016, ISR**

该研究说明中断时机影响用户是否忽略安全消息。对于 coding agent，审批和权限请求如果出现在错误时机，就可能被机械处理。

**#30 The Fog of Warnings, 2025, MISQ**

该研究说明非安全通知会导致习惯化泛化，使关键安全警告也被忽视。它非常适合解释 coding agent 中的审批疲劳：大量低价值 approval 会让用户对真正重要的 approval 也失去敏感性。

**#36 Artificial Intelligence Assistant in Online Shopping, 2025, ISR**

该研究关注 AI assistant 的主动信息提供、打断感和交互模式。它支持我们把 agent 的主动状态更新视为一个需要设计的 UX 变量，而不是单纯“多通知就更透明”。

### 3. 解释、校准、警觉：可读性影响什么

**#149 The Use and Effects of Knowledge-Based System Explanations, 1996, ISR**

**#162 Explanations from Intelligent Systems, 1999, MISQ**

**#177 The Impact of Explanation Facilities on User Acceptance of Expert Systems Advice, 1995, MISQ**

这些解释文献说明解释会影响学习、接受和判断。但代理工作可读性不等同于解释，它把解释放入更宽的工作呈现系统中：diff、日志、状态、风险、审批、测试结果都属于可读性的一部分。

**#175 A Theory of Decision Support System Design for User Calibration, 1996, ISR**

这篇文章说明系统设计应帮助用户校准信心和质量。代理工作可读性可能是 coding agent 场景下信任校准的关键前因：用户只有读得懂 agent 的工作，才更可能校准信任。

**#156 Can Humans Detect Errors in Data?, 1997, MISQ**

**#159 Inducing Sensitivity to Deception in Order to Improve Decision Making Performance, 2002, MISQ**

这些错误检测和警觉性文献说明检测绩效会受目标、激励、警告和误报影响。coding agent 中，可读性帮助用户知道“在哪里警觉”，否则警觉会变成到处怀疑或机械忽略。

**#198 The Use of Information in Decision Making, 1992, MISQ**

该研究说明决策辅助可能让用户节省努力，而不是提高质量。coding agent 如果可读性低，用户可能更倾向于省力：跳过 diff、机械 approve、只看最终结果。

### 4. 编程认知：为什么“改动可读”比普通 explainability 更关键

**#184 Why Is Programming (Sometimes) so Difficult?, 1997, ISR**

该文把编程视为规则空间、实例空间和表征空间中的发现活动。coding agent 的工作可读性之所以重要，是因为开发者需要把 agent 的行动和 diff 整合进自己的问题表征。

如果可读性低，开发者不是简单“不理解解释”，而是难以把 agent 的工作纳入编程任务的表征空间。

## 当前判断

相比“专业认知位移”，**代理工作可读性**更适合做本项目的主构念候选：

1. 它更泛用，CLI 用户、IDE 用户、新手、专家都会遇到。
2. 它能解释用户提到的现实痛点：看不到改动、审批疲劳、通知噪音。
3. 它与掌控感有关，但不重合；掌控感更像后果。
4. 它有多重后果，不只影响掌控感，还影响疲劳、信任、验证、心流和委托。
5. 它能整合高适配文献中 agentic IS、自主工具、awareness display、中断、warning fatigue、解释、校准和错误检测几条线。

现在最需要继续挑战的问题是：

- 它会不会被 transparency 或 explainability 吸收？
- “可读性”这个词会不会和 code readability 混淆？
- 是否应该改名为“代理工作可辨识性”或“代理工作态势可读性”以更精确？
- 题项是否能避免写成“我能不能控制 agent”？

## Agentic 特异性审查

### 先承认：单纯“可读性”不特有

如果“可读性”只是指信息好不好读、界面清不清楚、日志是否整洁、diff 是否容易看，那么它不是 coding agent 特有概念。它会被已有概念吸收：

- transparency；
- explainability；
- awareness；
- information presentation；
- usability；
- code readability；
- notification quality。

因此，这个构念不能叫泛泛的“可读性”。它必须限定在 coding agent 独有的问题结构上：

**用户要读懂的不是静态信息，而是一个半自主代理如何持续推进软件开发工作。**

### Agentic 具体体现在哪里

这里的 agentic 至少有六个条件。缺少这些条件，这个构念就会退化成普通透明度或普通可用性。

#### 1. 自主行动

coding agent 不只是显示信息或给建议，而是会主动采取行动，例如读文件、改文件、运行命令、根据错误继续修复。

因此，用户需要理解的是：

- agent 做了哪些行动；
- 哪些行动是它自己决定的；
- 哪些行动是用户明确要求的；
- 哪些行动改变了后续任务路径。

这和普通 explainability 不同。解释一个推荐结果，不等于读懂一个 agent 的行动序列。

#### 2. 持续轨迹

coding agent 的工作不是一次性输出，而是多步推进：

1. 读上下文；
2. 形成计划；
3. 修改代码；
4. 运行测试；
5. 看到失败；
6. 再修改；
7. 请求审批；
8. 汇报完成。

用户要读懂的是这个 trajectory，而不是单个结果。

所以更准确的测量对象不是 readability，而是：

**agentic work trajectory legibility**

也就是代理工作轨迹是否可辨识。

#### 3. 工件状态改变

coding agent 的行动会沉淀到代码库里。它不是只说了一句话，而是改变了文件、依赖、测试、配置和潜在风险。

因此，可辨识性必须包含：

- 行动和代码改动之间的映射；
- 改动之间的关系；
- 当前代码库状态和任务目标之间的关系；
- 哪些变化会影响未来维护。

如果只是“解释为什么这么写”，仍然不够 agentic。关键是：用户能否把 agent 的行动和代码库状态变化对应起来。

#### 4. 注意力请求

coding agent 会把一部分决策交回用户：审批命令、确认方案、允许改文件、接受风险、继续还是停止。

这就是用户提到的审批疲劳。它不是普通通知疲劳，因为这些通知不是信息消费，而是 **agentic handoff of attention and authorization**。

因此，一个 agentic 构念必须包含：

- 审批请求是否有风险分级；
- 用户是否知道这个审批会放行什么行动；
- 用户是否能区分例行确认和关键授权；
- 频繁审批是否让用户机械通过。

#### 5. 不确定性与涌现

coding agent 的执行路径常常不是用户预先完全知道的。它可能读到代码后改变计划，测试失败后改变方案，或者在修复中引入新问题。

这连接 #45 autonomous tools 的 unknowability 和 liminal experience。agentic 不是“系统复杂”，而是：

**行动路径在交互中持续涌现。**

可辨识性要处理的正是这种涌现路径是否能被用户跟上。

#### 6. 混合主动权

coding agent 工作中，主动权在用户和 agent 之间来回切换：

- 用户提出目标；
- agent 拆解并执行；
- agent 请求确认；
- 用户批准或修正；
- agent 继续行动；
- 用户 review 或中止。

这不是传统工具使用，也不是单纯自动化。它更像 agentic collaboration。构念必须描述这种主动权切换是否对用户可辨识。

## 更精确的构念名称建议

为了避免“可读性”太泛，我建议把名称从“代理工作可读性”改窄为：

**代理行动轨迹可辨识性**

英文：

**Perceived Legibility of Agentic Action Trajectories**

如果想保留 coding 情境，可以写成：

**Perceived Legibility of Coding-Agent Action Trajectories**

这个名字比“代理工作可读性”更能体现 agentic：

- 行动：不是静态信息；
- 轨迹：不是单次输出；
- 可辨识性：不是信息量多少，而是用户能否把行动、改动、状态和注意力请求组织起来理解。

## 修订后的定义

**代理行动轨迹可辨识性**是指：在使用 coding agent 完成软件开发任务时，开发者感到自己能够方便、及时、低成本地识别和理解 agent 的自主行动序列、这些行动造成的代码库变化、行动之间的因果关系，以及哪些行动节点需要自己注意、审批或检查的程度。

更短的定义：

**开发者能否把 coding agent 的多步自主行动读成一条清楚的、可检查的、重点分明的工作轨迹。**

## 这比“可读性”更 agentic

普通可读性：

> 这个信息好不好读？

代理行动轨迹可辨识性：

> 这个 agent 在一段时间里如何自主推进任务、如何改变代码、何时把决定交回我、哪里需要我注意，我能不能辨认出来？

## 和控制感的关系

控制感不是构念本身，而是可能后果。

机制可以是：

`代理行动轨迹可辨识性 -> 感知掌控感`

但是它也会影响其他后果：

- 审批疲劳：轨迹不可辨识时，审批请求更像噪音；
- 通知忽视：重要与不重要的 agent action 无法区分；
- 验证成本：用户要额外重建行动与改动的关系；
- 信任校准：用户无法知道哪些成功来自正确路径，哪些只是偶然通过；
- 心流中断：低价值 action handoff 频繁打断；
- 后续委托意愿：用户不愿把更大任务交给不可辨识轨迹的 agent。

## 当前更严格判断

如果叫“可读性”，这个概念不够特有。

如果改成“代理行动轨迹可辨识性”，并严格限定为：

- 半自主行动；
- 多步轨迹；
- 代码库状态改变；
- 审批和注意力交还；
- 轨迹涌现；
- 用户需要把行动、改动、风险和请求整合起来理解；

那么它才有 coding-agent-specific 的机会。

这也解释了 CLI 的问题：CLI 不是没有信息，而是很难把 agent 的行动轨迹、代码变化和注意力请求呈现成可辨识的结构。
