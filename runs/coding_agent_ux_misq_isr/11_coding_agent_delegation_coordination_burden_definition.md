# 编码代理委托协调负担：定义、边界与测量草案

## 构念名称

中文名：

**编码代理委托协调负担**

英文名：

**Perceived Coordination Burden in Coding-Agent Delegation**

缩写建议：

**CADCB**，即 coding-agent delegation coordination burden。

## 适用对象

这个构念只适用于开发者已经把一个具体编程任务部分交给 coding agent 自主推进的情境。

这里的 coding agent 指：能够接收编程目标，读取项目上下文，进行多步计划或行动，并通过工具修改代码、运行命令、执行测试或提出补丁的 AI 系统。

不包括：

- 只做代码补全的 autocomplete；
- 只在聊天窗口给建议、但不进入项目执行行动的普通聊天机器人；
- 只做静态搜索、lint、格式化或规则检查的传统开发工具。

## 核心定义

**编码代理委托协调负担**是指：开发者在把具体编程任务部分委托给 coding agent 自主推进后，为了使 agent 的行动持续符合任务目标、代码库状态和自己的最终接管责任，而感知到的额外认知与交互成本。

更操作化地说，它测量的是：

> 开发者为了让 coding agent 的自主工作保持可对齐、可追踪、可审批、可整合、可接管，需要额外操心和操作到什么程度。

## 构念水平

这是一个连续程度构念，不是 0/1 构念。

低协调负担：

- 用户能较轻松地设定任务边界；
- agent 的行动路径容易跟踪；
- 权限和审批请求少且容易判断；
- 代码变更容易验证和整合；
- 用户清楚何时需要介入、接管或修复。

高协调负担：

- 用户需要反复细化任务、边界和约束；
- 很难跟上 agent 做了什么、为什么这么做；
- 审批、通知或权限请求频繁打断判断；
- 代码变更需要大量额外验证和整合；
- 用户需要不断判断是否该停止、接管、回滚或修复 agent 的行动。

## 边界：它不是什么

它不是一般工作负荷。一般工作负荷可以来自任务本身很难，而 CADCB 必须来自“把任务委托给 coding agent 后，为协调 agent 自主行动而增加的负担”。

它不是信任。信任回答“我是否愿意依赖 agent”，CADCB 回答“即便我愿意依赖它，我为了协调它的行动还要付出多少成本”。

它不是掌控感。掌控感回答“我是否觉得事情仍在我控制之下”，CADCB 回答“我为了维持这种可控状态需要做多少协调工作”。掌控感可以是 CADCB 的后果。

它不是 verification burden。验证负担只覆盖检查结果是否正确；CADCB 还包括任务边界设定、行动追踪、审批分流、验证整合和接管修复。

它不是 warning fatigue 或 approval fatigue。审批疲劳关注频繁提示导致疲劳或习惯化；CADCB 关注用户在每次权限交还时需要判断、分流和保持任务连续性的协调成本。审批疲劳可以是其中一个后果或相邻维度，但不能等同于整体构念。

它不是可读性。代码或过程可读性是可能降低 CADCB 的前因；CADCB 本身是用户为了理解和协调 agent 行动所感受到的负担。

## 建议维度

整体 CADCB 更适合建模为形成式二阶构念。下面五个维度共同形成整体协调负担，但它们不必高度相关；用户可能审批负担高但验证负担低，也可能行动追踪负担高但接管负担低。

每个一阶维度可用反映式题项测量。

### 1. 任务边界对齐负担

用户为了让 agent 正确理解任务目标、范围、约束和不可触碰部分而感到的额外负担。

示例题项：

- 为了让 agent 按我的意图行动，我需要花很多精力把任务边界说清楚。
- 我需要额外说明哪些文件、逻辑或约束不应该被 agent 改动。
- 在 agent 工作过程中，我需要反复调整或补充任务要求。

### 2. 行动轨迹追踪负担

用户为了跟上 agent 多步行动、命令、文件修改和中间决策而感到的额外负担。

示例题项：

- 我需要花很多精力弄清楚 agent 到底做了哪些操作。
- 我需要额外追踪 agent 的代码修改与原任务之间的关系。
- agent 的中间行动让我必须不断重新理解当前任务状态。

### 3. 审批与注意力交还负担

用户为了处理 agent 的权限请求、确认提示、继续/停止判断和注意力交还而感到的额外负担。

示例题项：

- agent 的权限或确认请求需要我投入不少判断精力。
- 我需要频繁决定是否让 agent 继续、限制它或停止它。
- agent 在工作过程中交还注意力的方式打断了我的任务节奏。

### 4. 代码变更验证整合负担

用户为了判断 agent 的代码变更是否正确、是否适配现有代码库、是否会引发副作用而感到的额外负担。

示例题项：

- 我需要花很多精力判断 agent 的修改是否适配现有代码库。
- 接受 agent 的代码前，我需要额外检查它对其他模块或行为的影响。
- 我需要额外运行、解释或补充测试来确认 agent 的修改是否可以合入。

### 5. 接管与修复决策负担

用户为了判断何时介入、如何纠偏、是否回滚、是否自己完成剩余工作而感到的额外负担。

示例题项：

- 我需要花精力判断什么时候应该接管 agent 的工作。
- 当 agent 偏离任务时，我需要额外思考如何把工作拉回正确方向。
- 我需要额外规划如何修复、回滚或重做 agent 留下的问题。

## 推荐测量方式

### 参照情境

建议不要问泛泛的“你使用 coding agent 时如何”，而是使用 task-episode 测量：

> 请回想你最近一次使用 coding agent 完成一个真实编程任务的经历。这里的 coding agent 是指能够读取或修改项目代码、运行命令或测试、并进行多步行动的 AI 编程代理。请根据这次具体任务回答以下问题。

### 量表

使用 7 点李克特量表：

1 = 非常不同意，7 = 非常同意。

### 筛选题

正式测量前需要确认：

- 你是否在最近一段时间使用过 coding agent 完成真实编程任务？
- 该 agent 是否能够读取或修改项目代码、运行命令、执行测试或提出多步补丁？
- 本次任务是否不只是代码补全或普通聊天建议？

只有回答是的样本才进入 CADCB 测量。

## 区分效度建议

为了证明它不是旧概念换名，建议同时测量相邻构念并做区分效度检验：

- perceived control：应作为后果，而不是 CADCB 的题项；
- trust in AI：应作为前因或结果，而不是 CADCB 的题项；
- technostress/work overload：应作为更宽泛的压力构念；
- interruption overload：只覆盖打断，不覆盖整体委托协调；
- verification burden：只覆盖检查输出，不覆盖任务边界、行动轨迹、审批交还和接管修复；
- perceived usefulness/productivity：应作为结果变量。

可采用 HTMT、CFA、交叉载荷和已知组差异检验。已知组差异可以包括：

- 高自主 agent 应比低自主 assistant 带来更高 CADCB；
- 文件修改多、工具调用多、审批次数多的任务应带来更高 CADCB；
- diff 可视化更清晰、权限设计更好的工具应带来更低 CADCB；
- 用户对代码库越熟悉，CADCB 可能越低，但也可能因为更能发现问题而提高验证整合负担。

## 可以研究的前因与后果

可能前因：

- agent 自主性水平；
- agent 可靠性；
- agent 行动轨迹透明度；
- 权限/审批设计；
- 任务复杂度和代码库耦合度；
- 用户对代码库熟悉度；
- 用户 AI 使用经验；
- 测试和版本控制支持程度。

可能后果：

- perceived control；
- approval fatigue；
- verification fatigue；
- continued use intention；
- delegation willingness；
- task performance；
- takeover frequency；
- 对高自主 agent 的回避或降级使用。

## 当前判断

CADCB 不是一个完全脱离旧理论的新概念。它最有说服力的理论位置是：

**把 IS delegation 中较抽象的 coordination mechanism，转化为 coding agent 情境下可被用户感知、可被测量、并能解释使用体验和持续委托行为的个体层面构念。**

它的独特性不在于“协调”二字本身，而在于 coding agent 同时具有：

- 被委托执行编程任务；
- 多步自主行动；
- 直接改变共享代码库；
- 频繁权限和注意力交还；
- 用户保留最终责任；
- 需要随时接管和修复。

如果定义中缺少这些边界，它就会退化为 technostress、verification burden 或 interruption overload。
