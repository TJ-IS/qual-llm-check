# 编程智能体态势感知研究：选题背景与问题提出

> 本稿为逐句对齐版。正文中的 HTML 注释标记对应 `dong_thesis.md` 第 1.1 节的句号编号，渲染后不显示。标记仅用于检查每一句的论证来源，定稿时可以统一删除。

## 第 1 章 绪论

## 1.1 选题背景与问题提出

### 1.1.1 研究背景

作为数字产品、数字服务和组织信息基础设施的生产活动，软件开发在现代经济运行和企业价值创造中发挥着重要作用。<!-- D2.1 --> 随着生成式人工智能快速发展，软件开发正在进入人工智能广泛参与的新阶段。<!-- D2.2 --> 尤其是自大语言模型具备程序生成与工具调用能力以来，人工智能在软件开发中的应用已经由局部代码补全扩展到需求分析、缺陷修复、代码重构、测试和维护等多类活动。<!-- D2.3 --> 这一发展不仅形成了新的开发工具和服务市场，而且正在改变软件开发的任务分配方式、工程流程和开发者工作内容。<!-- D2.4 --> 麦肯锡全球研究院对 63 类生成式人工智能用例的分析表明，软件工程是生成式人工智能潜在经济价值最集中的四类企业职能之一，人工智能对软件工程生产率的直接影响可能相当于该职能年度支出的 20% 至 45%（McKinsey Global Institute, 2023）。<!-- D2.5 --> Gartner 估计，企业编程智能体市场截至 2026 年 4 月的年化规模约为 98 亿至 110 亿美元（Gartner, 2026a）。<!-- D2.6 --> OpenAI 公布的产品数据则显示，Codex 在 2026 年 6 月的每周活跃用户已超过 500 万，较同年 2 月桌面应用发布时增长六倍以上（OpenAI, 2026a）。<!-- D2.7 --> 上述咨询机构分析、市场估计和厂商使用数据虽然不能证明编程智能体必然改善所有软件开发任务，但共同说明企业和个体用户正在投入大量资源尝试将人工智能的任务执行能力转化为软件开发收益，编程智能体因而构成具有明确实践规模和潜在商业影响的研究情境。<!-- D2.8 -->

编程智能体为人工智能参与软件开发创造了新的可能，拓展了人工智能在软件工程中的作用范围，并改变了软件开发的作业方式。<!-- D3.1 --> 编程智能体是能够接受用户提出的软件开发目标，在一定权限边界内获取项目情境、规划任务步骤、调用开发工具、修改软件制品、检查执行结果并继续调整行动的能动型信息系统。<!-- D3.2 --> 它的核心特征在于将用户表达的任务目标转化为连续的软件工程行动，而不要求用户逐步指定每一个操作。<!-- D3.3 --> 随着模型推理、长上下文和工具调用能力的发展，人工智能参与软件开发的方式正在由内容生成向任务代理扩展。<!-- D3.4 --> 一方面，个体开发者开始把缺陷修复、代码重构、测试生成和项目理解等任务交给编程智能体实施。<!-- D3.5 --> 另一方面，企业开始把编程智能体纳入正式的软件开发流程，以期缩短交付周期、扩大开发产能并处理软件积压。<!-- D3.6 --> Gartner 预测，到 2027 年，在采用智能体编程的工程团队中，超过 65% 将不再把集成开发环境视为必不可少的工作入口，开发控制、治理与验证将进一步转移到自动化平台（Gartner, 2026b）。<!-- D3.7 --> 因此，编程智能体正在由个人开发者尝试的新型工具发展为企业软件生产和治理中受到关注的技术基础。<!-- D3.8 --> 对企业管理者而言，在关注系统能够执行多少任务之外，还需要关注个体用户在任务代理化后形成的使用体验，因为这是技术投入进入实际使用过程的一项用户侧条件。<!-- D3.9 -->

编程智能体突破了传统开发工具只能被动响应具体操作的限制，使用户能够通过目标委托调用连续的软件工程行动，从而改变了用户参与开发任务的方式。<!-- D4.1 --> 用户的工作由以亲自执行为主逐步转向直接操作与智能体任务委托并存，任务界定、情境提供、结果理解和后续决策由此成为新的日常活动。<!-- D4.2 --> 依托编程智能体，用户可以要求系统读取项目结构、跨文件修改、运行命令和测试，再根据执行结果继续调整。<!-- D4.3 --> 与此同时，系统行动产生的代码差异、测试结果、权限变化和未决问题也成为用户认识当前任务状态的主要信息来源。<!-- D4.4 --> 可以说，编程智能体的应用扩散正在推动软件开发由用户直接操作技术工具进入用户与能动型信息系统共同推进任务的新阶段。<!-- D5.2 --> 在这一变化中，企业可以重新安排部分开发活动，个体用户则需要在减少直接操作的同时理解由系统间接造成的任务状态。<!-- D5.3 --> 在这种背景下，编程智能体作为一种区别于被动开发工具的能动型信息系统形态应运而生。<!-- D5.4 --> 编程智能体正在改变用户与软件制品之间的行动联系；当用户无法从系统反馈中形成对任务状态的清晰认识时，便难以获得稳定的掌控感，也难以形成令人满意的使用体验。<!-- D5.5 -->

编程智能体是人工智能辅助软件开发的延伸，是通过理解开发目标、利用项目情境和开发工具采取连续行动，并与用户共同完成软件制品改变的能动型信息系统。<!-- D6.1 --> 简而言之，它是能够围绕软件开发目标自主推进多个相互关联步骤的人工智能代理。<!-- D6.2 --> 它的典型特征是支持用户把完整或相对完整的软件开发任务交给信息系统执行。<!-- D6.3 --> 传统开发工具主要通过执行用户明确指定的命令和操作提高开发效率。<!-- D6.4 --> 但是，编程智能体并非大语言模型、开发工具和自动化脚本的简单相加，因为系统在接收目标后能够自行选择行动顺序、观察执行结果并继续调整。<!-- D6.5 --> 编程智能体在行动发起、任务推进和工作空间影响等方面不同于传统开发工具，它使用户与软件变化之间的联系由直接操作部分转变为对系统行动结果的间接认识。<!-- D6.6 --> 理解这种开发方式，需要在传统信息系统使用的基础上进一步理解任务委托、自主行动和用户主观任务认识之间的关系。<!-- D6.7 --> Gartner 的市场分析显示，企业编程智能体正在吸收越来越多的软件工程支出，厂商竞争重点也由代码生成质量扩展到复杂流程协调、工程环境集成、治理和生产率提升（Gartner, 2026a）。<!-- D6.8 --> Robbes 等（2026）根据代码提交和合并请求中的可识别痕迹分析 129,134 个 GitHub 项目，估计编程智能体的项目采用率已达到 15.85% 至 22.60%，且采用范围覆盖不同成熟程度、编程语言和主题的项目。<!-- D6.9 --> 由此可见，编程智能体正在成为软件工程市场中增长迅速并具有潜在经济影响力的技术形态。<!-- D6.10 --> 因此，本研究从个体用户视角出发，旨在研究用户如何形成对编程智能体任务态势的主观感知，以及这种感知如何影响其使用体验。<!-- D6.11 -->

传统开发工具主要支持用户亲自实施软件开发操作，其行动后果通常可以结合用户自身的操作过程加以理解。<!-- D7.1 --> 编程智能体在替用户连续执行任务的同时，也使行动过程和工作空间变化不再完全来自用户的直接经历。<!-- D7.2 --> 它融合了软件制品生产属性和能动型信息系统的代理行动属性，使用户面对的不只是一个生成结果，而且是由非人行动者造成并持续演化的任务状态。<!-- D7.3 --> 在编程智能体使用过程中，用户需要借助计划、过程信息、代码变化和验证结果形成对任务当前状况的主观判断，这种判断为用户获得掌控感并形成满意的交互体验提供了认知基础。<!-- D7.4 -->

由于编程智能体植根于软件开发活动，同时又引入能动型信息系统的自主规划与行动能力，其用户体验同时受到软件任务内容和系统代理行动方式的影响。<!-- D8.1 --> 从概念层面上，对编程智能体的研究需要考察这种间接行动关系如何改变用户对任务状态的主观认识。<!-- D8.2 --> 系统提供的行动信息、变化汇总和验证结果如何帮助用户形成任务态势感知，又如何进一步影响用户的掌控感和满意度。<!-- D8.3 --> 因此，在编程智能体快速商业化和企业化的背景下，识别一种能够评价用户是否感觉自己了解任务态势的体验构念，对产品界面和交互机制设计具有现实意义。<!-- D8.4 --> 研究者需要识别这一主观体验包含哪些内容、受到哪些因素影响，以及它如何作用于后续用户体验和使用。<!-- D8.5 --> 基于上述判断，本研究把编程智能体态势感知作为核心研究对象，依次开展构念与量表开发、前因研究和后果研究。<!-- D8.6 -->

### 1.1.2 问题提出

编程智能体作为一种新兴的软件开发系统形态，已经引起研究者、开发者和企业管理者的广泛关注。<!-- D10.1 --> 然而，相关研究主要由模型能力评价、软件制品分析和产品实践推动，针对个体用户主观体验的理论积累仍然有限。<!-- D10.2 --> 不同于传统开发工具，编程智能体不仅支持用户完成操作，而且能够在一定自主程度下代替用户连续执行软件开发任务。<!-- D10.3 --> 用户要使用这种技术，既需要提出任务并利用其代理执行能力，也需要形成对任务过程与结果的主观认识。<!-- D10.4 --> 随着编程智能体行动范围和执行速度不断扩大，如何在减少直接操作的同时支持用户感觉自己仍然了解任务态势，构成这一新型开发方式的重要用户体验问题。<!-- D10.5 -->

代理技术应用于软件开发，促进了用户与开发工具关系的变化。<!-- D11.1 --> 那么，编程智能体的连续行动如何形成用户可以理解的任务状态？<!-- D11.2 --> 用户又是依靠系统提供的哪些信息，形成对智能体行动、软件变化、任务约束和后续影响的主观认识？<!-- D11.3 --> 回答这些问题，研究者需要考虑编程智能体如何使用户同时实现减少直接操作与维持主观任务定向两个目标，并重新认识代理任务所需要的用户体验条件。<!-- D11.4 --> 现有态势感知研究主要描述操作者对动态环境的感知、理解和预期，主观信息处理感知则把这一理论迁移到解释型人工智能，用于评价用户是否感觉自己能够看见系统输入、理解信息处理并预测系统输出（Taylor, 1990; Schrills et al., 2021）。<!-- D11.5 --> Chen 等（2024）关于语音交互可用性的研究表明，当研究对象、任务和交互方式发生实质变化时，成熟构念的既有维度与量表可能无法覆盖新情境；同理，一般态势感知和主观信息处理感知的现有内容也不能完整描述编程智能体用户所面对的任务态势。<!-- D11.6 --> 编程智能体不仅处理信息并给出结果，而且会自主调用工具、修改代码与配置、引入依赖、运行测试，并依据执行反馈继续行动；用户需要理解的是由智能体行动持续制造的、分布在多类软件制品和工具结果中的任务状态。<!-- D11.7 --> 基于 Taylor（1990）对主观态势感知的界定，本研究将 CASA 初步定义为用户在一次编程智能体任务中，对自己能够感知智能体关键行动、理解软件制品变化及其任务意义并预期可能后续影响的程度判断。<!-- D11.8 --> 那么，如何基于主观态势感知发展 CASA？<!-- D11.9 --> CASA 又将如何影响用户的感知控制、满意度和持续使用意愿？<!-- D11.10 --> 现有文献尚未识别编程智能体任务态势感知的具体内容与维度，也没有相应量表用于评价这一特定用户体验。<!-- D11.11 -->

CASA 是用户获得满意编程智能体体验的重要基础。<!-- D12.1 --> Schrills 等（2021）指出，当智能系统替用户处理信息时，用户需要能够感知系统使用的信息、理解处理过程并预期输出，才能形成有效的人机协作体验。<!-- D12.2 --> 事实上，研究者已经开始把主观态势感知作为评价智能系统用户体验的重要理论来源。<!-- D12.3 --> Schrills 等（2021）开发的主观信息处理感知量表与自动化信任和解释满意度存在中等至较强相关。<!-- D12.4 --> Schrills 等（2024）使用两个样本进一步发现，该量表具有良好可靠性，并与信任和感知有用性形成预期关系。<!-- D12.5 --> 在实际编程智能体使用中，用户同样希望了解智能体做了什么、为何形成当前修改、任务是否仍按预期推进以及接下来可能发生什么。<!-- D12.6 --> Dhanorkar 等（2026）访谈 17 名有经验开发者后发现，开发者需要在事前设置、共同规划、实时查看和事后审查等阶段持续理解智能体工作，同时面临难以理解和检查智能体生成代码的问题。<!-- D12.7 --> 因此，CASA 对于用户形成掌控感、评价交互过程并决定是否继续使用编程智能体具有重要意义。<!-- D12.8 --> 但是，主观信息处理感知关注的是系统收集何种信息、如何处理信息以及产生何种输出，尚未包含编程智能体主动改变外部软件制品所形成的行动态势。<!-- D12.9 --> 发展 CASA 需要把主观态势感知从对信息处理过程的体验进一步扩展到对智能体行动、软件变化、任务约束和后续影响的体验。<!-- D12.10 --> 这些内容跨越代码文件、配置、依赖、终端命令、测试和版本状态，并通过智能体连续行动发生关联。<!-- D12.11 --> 那么，这些编程智能体特有的任务态势内容能否形成具有明确结构的 CASA？<!-- D12.12 --> 目前，既有态势感知和主观信息处理感知量表均未对这些内容进行概念化和操作化。<!-- D12.13 --> 这是本研究首先需要通过用户经验材料、理论分类和量表开发解决的关键问题。<!-- D12.14 --> CASA 的形成还可能受到编程智能体特征、任务特征和用户特征的共同影响。<!-- D12.15 --> 本研究将开展以 CASA 前因为主题的子研究，识别并检验影响 CASA 的关键因素。<!-- D12.16 --> CASA 也可能进一步影响用户的感知控制、满意度和持续使用意愿。<!-- D12.17 --> 本研究将开展以 CASA 后果为主题的子研究，解释 CASA 如何作用于这些用户体验与使用结果。<!-- D12.18 -->

基于以上分析，本研究旨在解决以下研究问题：<!-- D13.1 -->

（1）编程智能体使用过程中，CASA 如何产生？<!-- D14.1 --> 影响 CASA 的关键因素有哪些？<!-- D14.2 --> 这些因素之间存在怎样的关系？<!-- D14.3 -->

（2）如何以 Taylor 的主观态势感知为基础发展 CASA 构念？<!-- D15.1 --> CASA 是否包含可识别的具体维度？<!-- D15.2 --> 如何测量 CASA 及其维度？<!-- D15.3 -->

（3）CASA 如何影响用户的感知控制、满意度和持续使用意愿？<!-- D16.1 -->

## 严格对齐说明

1. 正文逐句对应 Dong 第 1.1 节中与本研究适配的 D2.1 至 D16.1，并在第 5 点说明为何删除 D17 至 D18。
2. Dong 的 D5.1 是图示说明，本研究没有必要且有可靠数据支持的对应图，因此删除，但未改变 D5.2 之后的论证顺序。
3. Dong 的 D6.6 原本引出三类商务形态比较表。本研究不建立传统工具、人工智能编程助手和编程智能体的三分法，因此用一条边界句替代，不设置比较表。
4. Dong 的 D12.1 至 D12.18 用于证明第二类核心因素的重要性、给出现实证据并引出后续作用研究。本稿沿用这一推进形式，证明 CASA 对编程智能体用户体验的重要性，并引出 CASA 的概念开发、前因和后果三个子研究。
5. Dong 的第 17 至 18 组研究问题专门服务于买卖关系形成及其与技术可供性的联合作用。本研究没有对应的第二基础构念，因此删除这两组研究问题，不为追求数量一致而制造新的问题。
