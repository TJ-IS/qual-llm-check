# 编程智能体态势感知研究：选题背景与问题提出

> 本稿为第 7 版逐句对齐稿。正文中的 HTML 注释标记对应 `dong_thesis.md` 第 1.1 节的句子功能，渲染后不显示。本版将构念迁移的内部分析与面向读者的论文论述分开，正文只呈现研究现象、概念缺口和研究问题。

## 第 1 章 绪论

## 1.1 选题背景与问题提出

### 1.1.1 研究背景

作为数字产品、数字服务和组织信息基础设施的生产活动，软件开发已经成为现代经济运行和企业价值创造的重要基础。<!-- D2.1 --> 工业和信息化部统计显示，2025 年我国软件和信息技术服务业实现软件业务收入 154831 亿元，同比增长 13.2%，其中信息技术服务收入 106366 亿元，同比增长 14.7%（工业和信息化部，2026）。<!-- D2.2 --> 随着生成式人工智能快速发展，软件开发正在进入人工智能广泛参与需求理解、程序生成、测试、缺陷修复和软件维护的新阶段。<!-- D2.3 --> 国务院发布的深入实施人工智能+行动意见将智能化研发工具和平台推广应用列为技术研发模式创新的重要内容，并提出在软件等领域推动智能体广泛应用（国务院，2025）。<!-- D2.4 --> 麦肯锡全球研究院对 63 类生成式人工智能用例的分析表明，软件工程是生成式人工智能潜在经济价值最集中的四类企业职能之一，其直接生产率价值可能相当于软件工程年度支出的 20% 至 45%（McKinsey Global Institute, 2023）。<!-- D2.5 --> 中国信息通信研究院与华为云（2024）的调研也显示，受访者在开发阶段使用人工智能工具所报告的人效提升约为 40%，人工智能与开发工具的结合正在由代码生成逐步扩展到工具调用和工程任务执行。<!-- D2.6 --> Gartner 估计企业编程智能体市场截至 2026 年 4 月的年化规模约为 98 亿至 110 亿美元；OpenAI 公布的产品数据则表明，Codex 在 2026 年 6 月的每周活跃用户已经超过 500 万（Gartner, 2026a; OpenAI, 2026）。<!-- D2.7 --> 软件产业规模、国家政策导向、企业生产率预期和新兴产品采用共同表明，人工智能参与软件开发已经成为软件产业发展中具有重要经济影响的实践趋势。<!-- D2.8 -->

编程智能体为人工智能参与软件开发创造了新的可能，拓展了人工智能在软件工程中的作用范围，并改变了软件开发的作业方式。<!-- D3.1 --> 编程智能体是能够接受用户提出的软件开发目标，在一定权限边界内获取项目情境、规划任务步骤、调用开发工具、修改软件制品、检查执行结果并继续调整行动的能动型信息系统。<!-- D3.2 --> 它的核心特征是把用户表达的目标转化为一系列相互关联的软件工程行动，而不要求用户预先指定每一步操作。<!-- D3.3 --> 随着模型推理、长上下文和工具调用能力不断提高，人工智能参与软件开发的方式正在由生成内容向代理实施任务扩展。<!-- D3.4 --> 个体开发者开始把缺陷修复、代码重构、测试生成、项目理解和文档维护等相对完整的任务交给编程智能体执行。<!-- D3.5 --> 企业也开始把编程智能体纳入代码库、开发流水线和治理流程，以期缩短交付周期、处理软件积压并扩大研发产能。<!-- D3.6 --> Robbes 等（2026）从 129134 个 GitHub 项目的可识别痕迹中估计，编程智能体采用率已达到 15.85% 至 22.60%，且采用范围覆盖不同成熟程度、编程语言和主题的项目。<!-- D3.7 --> 因此，编程智能体正在从个人开发者尝试的新型工具发展为企业软件生产中受到关注的技术形态。<!-- D3.8 --> 如何使编程智能体的任务执行能力转化为稳定的软件开发价值，已经成为企业采用这一技术需要面对的问题。<!-- D3.9 -->

编程智能体突破了传统开发工具主要响应用户具体操作的限制，使用户能够通过目标委托调用连续的软件工程行动。<!-- D4.1 --> 用户的工作由以直接编辑和执行为主，逐步转向任务界定、情境提供、行动确认、变化理解和后续决策等活动与直接操作并存。<!-- D4.2 --> 在一次任务中，编程智能体可以读取项目结构、跨文件修改代码、更新配置或依赖、运行命令和测试，并根据执行结果继续采取行动。<!-- D4.3 --> 相应地，智能体的行动说明、软件制品变化和工具执行结果成为用户认识任务进展与当前状况的重要信息来源。<!-- D4.4 --> 编程智能体的应用由此推动软件开发从用户借助工具亲自改变软件制品，进入用户与能动型信息系统共同推进任务的新阶段。<!-- D5.2 --> 这一变化减少了用户逐项执行操作的需要，也使用户不再能够仅凭自己的操作过程了解任务状态。<!-- D5.3 --> 用户在获得任务执行便利的同时，需要根据智能体提供的信息理解它已经做了什么、软件制品发生了什么变化以及任务是否仍在按预期推进。<!-- D5.4 --> Kumar 等（2025）发现，持续与智能体迭代协作的开发者比采用一次性交付方式的开发者更容易完成真实项目任务，但开发者在信任智能体回复以及共同调试和测试时仍面临困难；Dhanorkar 等（2026）也发现，开发者需要在任务设置、共同规划、执行查看和结果审查等阶段持续了解智能体工作。<!-- D5.5 --> Stack Overflow（2025）的调查进一步显示，87% 的相关受访者担忧智能体提供信息的准确性，45.2% 的受访者认为调试人工智能生成的代码更加耗时。<!-- D5.6 --> 这些现象说明，编程智能体在减少直接操作的同时产生了一个新的使用问题，即用户如何保持对智能体任务态势的认识。<!-- D5.7 -->

本研究所称的编程智能体，是能够围绕软件开发目标自主推进多个关联步骤，并直接改变软件制品或开发环境的人工智能代理。<!-- D6.1 --> 简而言之，它是能够在软件工作空间中采取行动的任务执行者。<!-- D6.2 --> 它的典型特征是支持用户把完整或相对完整的软件开发任务作为委托单位，而不是只请求一段文本或一次代码补全。<!-- D6.3 --> 传统开发工具主要按照用户明确指定的命令、点击或编辑操作改变软件制品，用户可以把变化与自己的操作过程直接对应。<!-- D6.4 --> 编程智能体并非大语言模型、开发工具和自动化脚本的简单相加，因为系统在接收目标之后能够选择行动顺序、观察执行反馈并据此继续调整。<!-- D6.5 --> 这种自主推进使任务结果由用户行动和智能体行动共同形成，也使用户与软件变化之间的联系由直接操作扩展为对智能体行动及其结果的认识。<!-- D6.6 --> Baird 和 Maruping（2021）将这种关系概括为用户向能动型信息系统委托任务，并指出委托使信息系统从被使用的工具转变为能够代替用户采取行动的代理。<!-- D6.7 --> 随着厂商竞争重点由代码生成扩展到工程环境集成、复杂流程协调、后台任务执行和开发治理，用户需要认识的也不再只是生成内容，而是智能体介入后形成的整个软件任务状态（Gartner, 2026a）。<!-- D6.8 --> Tang 等（2026）对 1639 个代码库中的 20574 次真实编程智能体会话进行分析，发现开发者与智能体之间的偏离涉及误读用户意图、违反约束、行动越界、错误实施和不准确报告进展等多类问题。<!-- D6.9 --> 编程智能体因而不仅扩大了人工智能可以完成的软件工程任务，也改变了用户认识任务过程及其结果的方式。<!-- D6.10 --> 本研究从个体用户视角出发，关注用户在使用编程智能体时如何形成对任务态势的主观感知，以及这种感知如何影响其后续使用评价。<!-- D6.11 -->

传统开发工具主要支持用户亲自实施软件开发操作，用户通常能够借助自己的行动记忆理解任务已经进行到何处以及软件制品为何形成当前状态。<!-- D7.1 --> 编程智能体在替用户连续执行任务时，使部分关键行动和工作空间变化发生在用户的直接操作经验之外。<!-- D7.2 --> 它同时具有软件制品生产属性与能动型信息系统的代理行动属性，用户面对的因而不只是一个生成结果，而是由智能体行动持续形成和更新的任务状态。<!-- D7.3 --> 用户需要根据有限的系统反馈形成对智能体行动、软件变化、任务进展和后续影响的整体认识，这种认识构成编程智能体情境中的态势感知。<!-- D7.4 --> 当用户能够形成清晰的任务态势感知时，才更容易判断任务是否符合预期、决定是否接受当前结果并选择后续行动；当这种感知不足时，即使智能体已经完成大量工作，用户也可能难以确认当前状态并产生失去掌控的感受。<!-- D8.1 --> 因此，编程智能体态势感知是连接智能体任务执行与用户后续判断的一项重要个体感知。<!-- D8.2 --> 现有研究尚未明确这种感知由哪些内容构成，也缺少适用于编程智能体使用的测量方式。<!-- D8.3 --> 对该构念进行研究，可以帮助产品设计者判断系统所提供的信息能否支持用户认识任务状态，并为改进行动呈现、变化反馈和任务交接提供依据。<!-- D8.4 --> 研究者还需要进一步识别哪些因素影响这种感知，以及它如何影响用户的感知控制、满意度和持续使用意愿。<!-- D8.5 --> 基于上述判断，本研究把编程智能体态势感知作为核心研究对象，依次开展构念与量表开发、前因研究和后果研究。<!-- D8.6 -->

### 1.1.2 问题提出

编程智能体作为一种新兴的软件开发系统形态，已经引起研究者、开发者和企业管理者的广泛关注。<!-- D10.1 --> 然而，相关研究的进展很大程度上由模型能力评价、软件制品分析和产品实践推动，关于个体用户如何认识智能体任务状态的理论研究仍处于起步阶段。<!-- D10.2 --> 不同于传统开发工具，编程智能体不仅支持用户完成操作，而且能够在一定自主程度下替用户连续执行软件开发任务。<!-- D10.3 --> 用户需要在利用这种任务代理能力的同时，保持对任务过程和当前状态的认识。<!-- D10.4 --> 随着智能体能够承担的行动范围不断扩大，如何在减少用户直接操作的同时支持其了解任务态势，构成编程智能体发展所带来的重要研究问题。<!-- D10.5 -->

代理技术运用于软件开发，促进了用户与开发工具关系的变化。<!-- D11.1 --> 那么，编程智能体连续采取行动并改变软件制品之后，用户如何认识任务已经进行到何种状态？<!-- D11.2 --> 用户又如何理解智能体行动及软件变化对任务目标的意义，并对任务的后续发展形成判断？<!-- D11.3 --> 回答这些问题，需要重新认识用户顺利参与编程智能体任务所需要的状态信息和个体感知。<!-- D11.4 --> 现有研究已经讨论了自动化信任、系统透明、感知控制和一般可用性等因素，但这些概念分别关注用户对系统的信赖、系统信息的可见程度、用户对影响系统的感受或交互使用质量，并不直接描述用户对当前任务状态的认知程度。<!-- D11.5 --> 态势感知关注个体对动态任务情境中相关事件、因素和变量的认识与预期，为解释上述问题提供了适合的概念基础（Taylor, 1990; Endsley, 1995）。<!-- D11.6 --> 然而，传统态势感知主要形成于航空等动态操作任务，其中操作者需要持续认识环境与系统的当前状况；在编程智能体任务中，用户所要认识的状态不仅随任务推进而变化，而且由智能体代替用户采取行动而持续形成，并分布在智能体行动、软件制品变化和执行反馈之间。<!-- D11.7 --> 因此，经典态势感知的既有内容无法直接说明用户应当认识哪些编程智能体任务状态，也无法充分反映任务委托所造成的间接行动关系。<!-- D11.8 --> 如何以态势感知为基础发展适用于编程智能体的特定构念，成为本研究首先需要解决的问题。<!-- D11.9 --> 这一构念又会受到哪些因素影响，并如何作用于用户的后续判断和使用？<!-- D11.10 --> 现有文献尚未对这些问题作出系统回答。<!-- D11.11 -->

本研究将编程智能体态势感知（以下简称 CASA）初步定义为用户在一次编程智能体任务中，对自己能够感知智能体关键行动、理解这些行动所形成的任务状态及其意义，并预期任务后续发展的程度判断。<!-- D12.1 --> 较高的 CASA 表示用户感觉自己能够将智能体行动、软件变化与任务目标联系起来，较低的 CASA 则表示用户难以形成连贯的任务认识。<!-- D12.2 --> CASA 关注用户对任务状态的认识，不等同于用户对智能体能力的信任，也不等同于用户感觉自己能够影响系统的感知控制。<!-- D12.3 --> 这种区分使 CASA 可以解释编程智能体任务执行如何进一步影响用户判断，而不是重复已有的系统评价概念。<!-- D12.4 --> 编程智能体的自主行动使用户对任务状态的认识不再完全来自自己的操作过程，而需要通过系统呈现的信息重新建立。<!-- D12.5 --> 软件开发任务还具有制品相互依赖、状态持续演化和执行结果需要验证等特点，使用户需要把智能体行动及其造成的变化作为一个相互联系的任务态势加以理解。<!-- D12.6 --> 这些特征构成 CASA 区别于一般态势感知的具体情境基础。<!-- D12.7 --> 因此，识别 CASA 的内容和维度并建立相应测量方式，是研究编程智能体使用所需要的基础工作。<!-- D12.8 -->

CASA 的重要性已经得到相关实践研究的初步支持。<!-- D12.9 --> Kumar 等（2025）发现，开发者与智能体保持渐进互动有助于完成真实软件任务，说明用户参与任务推进仍然是编程智能体使用的重要组成部分。<!-- D12.10 --> Dhanorkar 等（2026）发现，开发者会在任务开始前、执行中和完成后采取不同方式了解智能体工作，并在理解和检查智能体生成代码时面临困难。<!-- D12.11 --> Tang 等（2026）进一步表明，编程智能体可能在理解项目、遵循用户意图、限定行动范围和报告任务进展等方面与用户预期发生偏离。<!-- D12.12 --> 这些研究共同说明，系统能否完成任务并不足以呈现用户与编程智能体共同推进任务的完整过程，用户是否感觉自己了解任务态势同样值得研究。<!-- D12.13 --> 目前，文献尚未形成 CASA 的清晰概念结构和测量方法。<!-- D12.14 --> CASA 的形成可能受到系统信息呈现、智能体行动方式、任务特征和用户经验等因素影响。<!-- D12.15 --> 本研究将开展 CASA 前因子研究，识别并检验影响 CASA 的关键因素。<!-- D12.16 --> CASA 还可能进一步影响用户的感知控制、满意度和持续使用意愿。<!-- D12.17 --> 本研究将开展 CASA 后果子研究，解释 CASA 对这些用户感知和使用结果的作用。<!-- D12.18 -->

基于以上分析，本研究旨在解决以下研究问题：<!-- D13.1 -->

（1）编程智能体使用过程中，CASA 如何产生？<!-- D14.1 --> 影响 CASA 的关键因素有哪些？<!-- D14.2 --> 这些因素之间存在怎样的关系？<!-- D14.3 -->

（2）如何以态势感知为基础发展 CASA 构念？<!-- D15.1 --> CASA 是否包含可识别的具体维度？<!-- D15.2 --> 如何测量 CASA 及其维度？<!-- D15.3 -->

（3）CASA 如何影响用户的感知控制、满意度和持续使用意愿？<!-- D16.1 -->

## 写作调整说明

1. 第 1.1.1 节保持 Dong 的五步推进：软件开发的重要性、编程智能体带来的技术变化、用户活动变化、新研究对象的界定，以及由对象属性导出的研究重点。
2. D7 与 D8 合并为同一段，使传统工具与编程智能体的差异直接引出 CASA 的意义，不再形成过短的过渡段。
3. 第 1.1.1 节不再反复使用用户体验价值作为论证标签，而是围绕任务委托、任务状态认识和用户后续判断展开。
4. 第 1.1.1 节末段取消从概念、作用和产品设计三个角度并列论述的写法，改为从编程智能体的双重属性自然推导 CASA、研究缺口和三个子研究。
5. 第 1.1.2 节不再向读者说明 Chen 等（2024）的迁移方法，也不展开 SART 的具体维度或主观信息处理感知量表；这些内容属于后续理论与构念开发章节。
6. CASA 的情境特殊性在开篇中只保留三个必要层次：任务由智能体代替用户执行，任务状态由智能体行动持续形成，状态分布于行动、软件制品变化和执行反馈之间。
7. Dong 的 D17 至 D18 服务于其第二核心因素及联合作用。本研究没有对应的第二基础构念，因此保留三个能够由后续子研究回答的研究问题。
