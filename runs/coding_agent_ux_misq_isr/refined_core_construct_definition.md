# 核心构念精简定义：代理代码责任性拥有感

## 构念名称

中文：代理代码责任性拥有感

英文暂定：Perceived Responsible Ownership of Agent-Authored Code

## 定义

代理代码责任性拥有感是指：开发者认为由 coding agent 生成或修改的代码，已经被自己理解和掌握到足以作为自己负责的代码来接受、合并和维护的程度。

更简单地说，它测量的是：

开发者是否觉得 agent 写出来的代码已经可以被自己负责任地当作“我的代码”来接住。

## 高低程度

高水平：

- 开发者理解 agent 代码的主要逻辑和修改理由。
- 开发者有足够证据判断这段代码是否可以接受。
- 开发者相信自己之后能维护或修复这段代码。
- 开发者愿意把这段 agent-authored code 作为自己负责的工作产物。

低水平：

- 代码虽然由 agent 生成出来了，但开发者并不真正理解它。
- 开发者不确定测试、解释或日志是否足以支持接受。
- 开发者担心未来出错时自己无法维护或解释。
- 开发者感觉自己只是被迫 approve/merge 一段不真正属于自己的代码。

## 为什么不是原来的复杂概念

之前的“可承责掌控感”“承责缺口”把太多东西揉在一起：委托、控制、验证、修复、责任、身份。那不像一个清楚构念，更像一个理论模型。

现在这个构念只保留一个核心心理判断：

我是否能够把 agent 生成的代码负责任地接纳为自己的代码产物？

委托边界、验证证据、回滚机制、agent 行动范围都可以作为前因；merge 信心、验证努力、后续委托意愿、责任焦虑都可以作为后果。它们不再塞进定义里。

## 为什么需要从文献迁移

这里的迁移不是因为旧概念完全不能用，而是因为旧概念都只能解释一部分，却无法直接解释“agent 写代码，人类负责代码”这个新矛盾。

| 文献原概念 | 原始概念能解释什么 | 到 coding agent 后为什么不够 | 迁移成什么 |
| --- | --- | --- | --- |
| 间接 IS 使用（#67） | 用户可以委托别人使用系统，但自己仍承担责任 | 原概念中的代理者是人；coding agent 是非人代理，能直接生成代码却不能承担专业责任 | 从“委托他人使用系统”迁移为“接纳非人代理生成的代码责任” |
| 用户参与/责任矛盾（#144） | 用户参与有限，却被要求 sign off 并负责 | 原文是系统开发方法中的角色矛盾；coding agent 把这种矛盾推到每个代码 diff 上 | 从“项目 sign-off 责任”迁移为“agent-authored code 的责任性拥有” |
| 代理性 IS 委托（#51） | agentic artifact 不再是被动工具，可以承担任务 | 原文强调委托关系，但没有处理 agent 产物如何被人类拥有和维护 | 从“委托 agent 做任务”迁移为“人类如何接住 agent 产物” |
| 用户校准（#175） | 用户信心应与决策质量匹配 | coding agent 中不只是信心是否匹配质量，还包括开发者是否能维护和解释代码 | 从“信心-质量校准”迁移为“代码接纳是否有足够理解和证据” |
| AI 决策增强元认知（#53） | 用户要判断 AI 建议是否正确 | 医疗诊断中的建议不会变成用户长期维护的工件；agent 代码会进入代码库 | 从“是否接受 AI 建议”迁移为“是否负责地拥有 AI 生成工件” |
| 错误检测（#156/#159） | 用户能否发现数据错误或欺骗 | 找到 bug 只是 coding agent 使用的一部分；开发者还要 merge、维护、解释和承担后果 | 从“检测错误”迁移为“接纳代码前的责任性判断” |
| 协同修复（#10） | 人和 chatbot 可以共同修复对话 breakdown | coding agent 失败不是只修复对话，而是修复代码状态和后续维护责任 | 从“对话修复”迁移为“代码产物能否被重新拥有和维护” |

## 和相近概念的边界

| 相近概念 | 区别 |
| --- | --- |
| Trust in AI | trust 问“我信不信 agent”；本构念问“我能不能把 agent 代码当作自己负责的代码来接住”。 |
| Accountability | accountability 问“我会不会被追责”；本构念问“我是否觉得自己有能力和证据来承担这段代码”。 |
| Code ownership | 传统 code ownership 通常建立在人类作者、模块维护者或团队边界上；本构念关注非人代理生成代码后，人类是否能形成责任性拥有。 |
| Explainability | explainability 是系统提供解释的程度；本构念关注解释、测试、日志等是否足以让开发者负责地接纳代码。 |
| Delegation | delegation 问任务如何交出去；本构念问任务完成后，agent 产物如何被人类接住。 |
| Error detection | error detection 问能否发现错误；本构念还包括理解、接受、维护和承担责任。 |

## 可能维度

这个构念可以先按三个清楚维度发展：

1. 理解充分性：我是否理解 agent 代码的主要逻辑、假设和修改理由。
2. 判断充分性：我是否有足够证据判断这段代码是否可靠、可接受。
3. 维护准备度：如果这段代码以后出问题，我是否能解释、维护或修复它。

这三个维度共同指向一个核心程度：开发者是否能负责任地拥有 agent-authored code。

## 条目方向

这些只是初步条目，不是最终量表：

- 我理解 coding agent 生成代码的主要逻辑。
- 我知道 coding agent 为什么做出这些修改。
- 我有足够信息判断这段 agent 代码是否可以接受。
- 我能够向同事解释这段 agent 代码的主要作用和风险。
- 如果这段 agent 代码之后出问题，我知道如何开始维护或修复。
- 我愿意把这段 agent 代码作为自己负责的工作产物。
- 反向：我觉得自己只是在批准一段并不真正理解的 agent 代码。
- 反向：如果这段 agent 代码出问题，我会觉得自己很难解释或维护它。

## 最小研究模型

前因：

- agent 行动强度：只建议、改单文件、跨文件修改、自动运行命令。
- 证据质量：是否有清晰 diff、测试结果、行动日志、风险说明。
- 任务风险：是否涉及核心逻辑、安全、数据、生产系统。
- 代码熟悉度：开发者是否熟悉该模块。

后果：

- merge 信心。
- 验证努力。
- bug 发现率。
- 后续委托范围。
- 责任焦虑。
- 对 agent 代码的长期维护意愿。

最小模型：

`agent 行动强度` 和 `证据质量` -> `代理代码责任性拥有感` -> `merge 信心`、`验证努力`、`后续委托范围`

这个模型的核心不是证明 agent 好不好，而是解释：什么情况下开发者能把 agent 写的代码真正接住。
