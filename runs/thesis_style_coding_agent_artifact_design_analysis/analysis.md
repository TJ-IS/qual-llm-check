# 从“移动文娱平台推荐与展示决策”到 Coding Agent 软件制品设计：thesis 写法与 AIS 文献映射

## 一、结论先行

认真对照三篇 thesis 后，原先把 coding-agent 研究拆成“委派、监控、干预、验收”四个并列实验的方案需要调整。它可以成为实验题库，但还不像《移动文娱平台的内容推荐与展示决策研究》那样形成一篇完整 thesis。

目标论文真正值得模仿的不是“使用机器学习预测，再使用优化算法决策”，而是下面这套论文级结构：

1. 先确定一个贯穿全文、包含内在张力的设计目标；
2. 找到两种会实质改变行为过程与设计问题的产品模式；
3. 先做一项机制研究，说明两种模式为何不同，并产出后续设计所需的状态、过程和边界条件；
4. 再为两种模式分别构建软件制品；两个制品共享一个核心架构和结果目标，但具有不可互换的模式专属设计；
5. 使用同一组客观结果分别评价两个制品，从而使各章既独立又共同回答一个总问题。

对 coding agent，最接近这一结构的总问题不是泛化的“如何提高生产力”，也不是四个彼此松散的监督准确率实验，而是：

> **如何针对前台协作与后台委托两种 coding-agent 工作模式，设计人类可治理的 coding-agent 制品，在减少人类注意投入的同时，提高经验证的自主软件进展并保持软件变更完整性？**

建议的 thesis 工作题目是：

> **Coding Agent 交互与控制制品设计研究：平衡自主软件进展与人类可治理性**  
> *Designing Human-Governable Coding Agents: Balancing Autonomous Software Progress and Human Governance*

这里的“人类可治理 coding-agent performance”不应开发成问卷构念，而应当作为多目标设计准则，由三个客观结果共同表达：

- **经验证的任务进展**：需求满足率、隐藏测试通过率、正确完成的子目标数；
- **软件变更完整性**：回归、越权操作、未验证修改、仓库约束违反和错误验收的数量或比例；
- **监督成本**：人的主动注意时间、检查步骤、打断次数和干预次数。

不要一开始把三者强行加权成一个任意指数。主分析分别报告三个结果，并用 Pareto 改善或“在完整性约束下最大化经验证进展、最小化监督成本”表达平衡关系。只有在应用方能给出明确权重时，才增加加权决策函数作为补充分析。

## 二、目标浙大 thesis 到底是怎样写成一条主线的

### 1. 它从一个矛盾开始，而不是从一种算法开始

论文的总矛盾是：推荐系统通常只促进用户使用内容，却可能忽略创作者继续生成内容；短期使用增长并不等于平台生态可持续。全文因而不是“提高预测准确率”，而是“通过推荐与展示决策平衡内容使用和内容生成”。摘要已经把这一矛盾、两种模式以及三项研究一次性闭合（目标论文第 23–31 行）。

这对 coding agent 的启示是：不能把 thesis 写成“我们做了四个 UI feature”。需要先说明 coding agent 的根本矛盾：更大的自主性可以减少人的操作，但也会增加部分可观察、长链工具调用、持久仓库修改和错误扩散；反过来，频繁审批虽然增加控制，却可能消灭 agent 的效率价值。因此研究对象应是“自主进展—人类治理”的平衡，而不是单独的信任、易用性或满意度。

### 2. “点击 vs. 滑动”不是两个方便取样的场景，而是会改变决策结构的产品模式

目标论文论证了两种模式在四方面有结构性不同：

- 用户看到信息的时点不同，导致不确定性与期望不确认不同；
- 用户行为顺序不同：先点击后互动 vs. 先滑动后互动；
- 展示决策不同：二维位置分配 vs. 序列分配；
- 时间结构不同：滑动模式存在更强的序列相关性，因此还需平衡当前与未来结果。

这些差异直接导致研究二使用多维展示和整数规划，研究三使用序列展示和动态规划。换言之，两章不是同一个模型换数据，而是“共同问题、共同模块、不同状态转移和控制方式”。研究问题部分对此写得尤其明确（目标论文第 243–263 行），滑动模式框架再次把不确定性、期望不确认和序列相关性写成专属设计依据（第 1662–1705 行）。

coding agent 中最像这种结构性模式差异的是：

- **前台协作模式**：用户持续在场，agent 以短回合推进；人的主要困难是过程信息过多、表示不透明和过度微观干预。
- **后台委托模式**：用户把任务交给长时间运行的 agent 后转移注意；人的主要困难是状态恢复、关键事件遗漏、打断成本以及何时应把决策权交还给人。

这两种模式不能互换：前台模式需要压缩和组织连续轨迹，后台模式需要事件选择、风险门、恢复上下文和控制权交接。这种不可互换性正好提供 coding agent “非它不可”的独特性。

### 3. 第一项研究负责识别机制，后两项研究负责制品设计

目标论文第三章先使用信息觅食和期望不确认等理论，识别两种模式下用户选择与互动的机制；该章的作用不是凑一篇实证论文，而是为后续设计提供关键变量和过程模型。作者在研究方法和结论中反复声明研究一是研究二、三的基础（第 279–300 行、第 2285–2299 行）。

这给 coding-agent thesis 一个很清晰的结构：

- Study 1 不急于做 feature，而是识别前台与后台模式下人的监督过程、错误类型和注意分配机制；
- Study 2 把 Study 1 发现的前台问题转译为“状态化执行工作台”；
- Study 3 把 Study 1 发现的后台问题转译为“风险触发检查点与上下文恢复制品”。

关键要求是建立可审计的追踪矩阵：`Study 1 发现 → 设计要求 → 软件特征 → 预期机制 → 客观结果`。这会比目标论文中较为松散的“机制为模型提供依据”更强。

### 4. 两个设计章节使用同一母架构，但保留真正的模式专属增量

目标论文的第 4、5 章都有三个共享模块：内容使用预测、内容生成预测、推荐与展示决策；同时又在状态变量、展示对象、时间跨度和求解方式上产生有意义差异（第 886–902 行、第 1681–1705 行）。这种“对称框架 + 非对称实现”使两个章节既像一家人，又不重复。

coding-agent thesis 可使用一个共享的 **instrumented agent-control scaffold**：

- 同一 agent、同一任务协议和工具权限；
- 同一事件日志：计划、工具调用、文件修改、测试、失败、回滚和用户动作；
- 同一仓库状态检查器和隐藏测试；
- 同一结果向量：经验证进展、变更完整性、监督成本。

在此基础上，Study 2 实现前台状态表示与逐步控制，Study 3 实现后台事件触发、风险门、恢复摘要和交还控制。这样研究修改的是可运行的软件制品，而不是预测模型的参数。

### 5. 它的评价分成“模型是否准确”和“决策是否更好”

目标论文分别评价预测表现、决策表现和稳健性，而不是只报告一种准确率（第 1335–1498 行、第 2017–2190 行）。coding-agent 研究虽然不做预测模型，也应保留这种双层评价：

- **制品内部有效性**：状态表示是否忠实、风险事件是否正确触发、日志是否覆盖关键状态、回滚是否真正恢复仓库；
- **人机任务结果**：是否完成需求、是否引入回归、用户是否在正确时点干预、需要多少主动注意。

只做后一层，会不知道 feature 为什么生效；只做前一层，又只是软件测试而不是 IS 研究。

## 三、另外两篇 thesis 告诉我们的边界

《人工智能用户抵制研究》采用“基础构念开发 → 下游效应的纵向拓展 → 多主体互动的横向延伸”。这个结构适合新构念和量表，但不适合当前目标：它会把研究拉向主观测量、组织结果和医疗多主体关系，而不是可运行 coding-agent 制品。

《信息过载视角下众筹多媒体内容与融资绩效的影响研究》围绕同一客观结果，按两阶段说服过程和不同信息维度组织三项研究。它说明“阶段可以组织 thesis”，但其研究主要解释既有内容如何影响融资绩效，并不真正构建和比较软件制品。

因此，三篇 thesis 中应采用的组合是：

- 以目标浙大论文的“机制研究 + 两个模式专属设计”作为主骨架；
- 借众筹论文的“同一结果按决策阶段拆分”来设计日志和任务；
- 不采用 AI 抵制论文的构念开发路线。

## 四、最合适的 AIS 文献：哪些能撑骨架，哪些只撑一章

需要先说明口径：你当前本地全文库中包含 MISQ、ISR、JAIS、JMIS、EJIS 等严格 AIS Senior Scholars Basket 期刊，也包含 DSS 和 I&M。下面把它们分开，避免把补充期刊误写成严格 Basket。

### A. 严格 Basket 中，可作为 thesis 骨架的三篇

#### 1. Designing Effective Mobile Health Apps（JMIS, 2021）——最适合模仿“理论变成软件 feature”的写法

这是当前最重要的方法论文。它采用 **explanatory design theorizing**：选择窄的 kernel theories，将理论自变量忠实实例化成可开关的软件特征，建立关于特征主效应与交互效应的假设，构建四个共享基线功能的 app 原型，再以五周随机田野实验和客观 trace data 比较它们。论文还发现两个单独有效的 feature 组合后反而产生负交互，而不是默认“feature 越多越好”（源文第 23、101–109、154–188 行）。

应模仿：

- 同一个基础 coding-agent scaffold；
- 每项研究只加入少量可独立开关的设计特征；
- 明确理论变量如何被 feature 忠实实例化；
- 用 2×2 或逐层消融检验 feature 组合，而不是一次性推出复杂“全功能版本”；
- 用后台日志测量真实行为。

不应模仿：把 app 使用次数当成 coding-agent 成功。我们的结果必须是任务正确性、仓库完整性与人的注意投入。

#### 2. Designing Conversational Dashboards for Effective Use in Crisis Response（JAIS, 2023）——最适合模仿“理论驱动 DSR + 客观任务评价”

该文用 Theory of Effective Use 提出理论驱动的 conversational dashboard，真正实现可运行制品，并通过任务正确率、完成时间以及实际交互路径相对最短必要路径的效率来评价 transparent interaction（源文第 53–61、91、259、298 行）。

应模仿：

- `kernel theory → design principles/requirements → artifact → controlled task evaluation`；
- 把交互日志转成客观“路径效率”，而不是只问易用性；
- 明确设计 trade-off，并通过 onboarding 或其他制品成分处理 trade-off。

它适合作为 thesis 的 DSR 评价骨架，但 TEU 太一般，不宜独自承担 coding-agent 独特性。独特性要由 coding agent 的持久仓库修改、工具执行、部分可观察和控制权交接提供。

#### 3. Cognitive Challenges in Human–AI Collaboration（ISR, 2022）——最适合支撑 coding-agent 的 agentic 核心

该文不是一般的“信任 AI”，而是比较人单独、AI 单独、人向 AI 委派以及 AI 向人交还任务（inversion），用 ground-truth accuracy 评价合作；其核心机制是 complementarity、metaknowledge 和 delegation rule。论文又通过解释/强制规则、连续反馈和任务难度形成一组递进研究（源文第 21、39–57、103–113、299–324 行）。

应模仿：

- 把控制权方向本身作为产品设计对象；
- 在 task-instance 层面交还子任务，而不是整项工作只能“全自动或全人工”；
- 使用可验证能力边界触发 handoff，而不是直接相信模型口头报告的 confidence；
- 同时比较 human-alone、agent-alone、human-delegation 和 agent-inversion 的客观表现。

这篇最能解释为什么 coding agent 不是普通 chatbot：agent 会自行执行并需要在能力边界处把决策权交还给人。

### B. 严格 Basket 中，最适合支撑具体设计章节的论文

#### 4. Skipping Class（EJIS, 2022）——前台制品最强的“不是改算法，而是改表示”范例

该文不改变底层数据，而是把 class-based representation 改为 instance-based representation；在信息等价的条件下，以两个实验比较开放式探索与封闭式查询，客观测量正确 pattern、precision、query formulation accuracy 和时间（源文第 53–77、135–179、225–253 行）。

对 Study 2 的直接启示：不要只让用户阅读 agent 的线性聊天记录；将同一底层执行事实表示为以任务实例和状态关系为中心的结构，例如：`需求 → 计划节点 → 工具调用 → 文件变更 → 测试证据 → 未解决风险`。底层信息保持一致，比较表示方式本身是否提高用户对仓库状态的理解和正确干预。

#### 5. The Fog of Warnings（MISQ, 2025）——后台风险门最强的“机制 → 界面干预 → 行为”范例

论文先证明普通通知的习惯化会泛化到安全警告，再分别改变警告的视觉外观和交互方式，并用 warning disregard 与反应时间验证干预。它的三项实验形成“现象建立 → 排除机制替代解释 → 隔离具体设计成分”的递进结构（源文第 23、45–51、65–93 行）。

对 Study 3 的直接启示：coding agent 的普通进度事件不能和高风险授权门长得一样、操作方式也不能一样。普通事件可批处理；关键风险可使用不同视觉和不同动作，例如 hold-to-approve 或 drag-to-authorize。需要同时测量漏拦危险操作与误拦安全操作。

不应模仿 fMRI；只需复制其在线 field experiment 和 feature 隔离逻辑。

#### 6. Will Humans-in-the-Loop Become Borgs?（MISQ, 2021）——总目标中“为什么必须平衡”的理论支撑

该文不仅看人机最终准确率，还看人类能否保留 AI 没有的 unique human knowledge；AI 建议可能提高个体表现，却使人们趋同并损失补充性知识。它适合支撑“进展提高不能等同于治理成功”，以及设置 `agent 错、人正确发现并纠正` 这一关键结果。

对 coding agent，应记录：agent 失败的任务上，人是否仍能发现问题、提出替代修复或拒绝错误补丁。若一种制品让平均完成率上升，却使这一能力消失，它可能不是可持续的人机协作设计。

### C. 非严格 Basket、但对制品方法很有价值的补充论文

#### 7. An Assisted Approach to Business Process Redesign（DSS, 2022）

这是最接近“论文级软件架构”的补充范例：问题识别 → design objectives → assisted redesign concept → 不同自动化等级 → reference architecture → prototype → 人工和自然情境评价（源文第 29、43–45、72–88、110–147 行）。

可借它来写共享 coding-agent control architecture 和自动化等级，但不要复制 KUKA 案例、专家访谈与长期组织项目。我们的评价可以限定为个人层面的实验任务。

#### 8. Animation as a Dynamic Visualization Technique for Improving Process Model Comprehension（I&M, 2021）

它把静态流程表示改成动画、自动播放或用户控制的逐步表示，用 cognitive theory of multimedia learning、cognitive load 和 cognitive dimensions 指导设计，并客观测量顺序、排他、并发和循环等理解以及时间。它可与 Skipping Class 合并，支撑前台执行轨迹的动态、分层、用户控制设计。

#### 9. Trust Calibration of Automated Security IT Artifacts（I&M, 2021）

它区分 performance、process、purpose calibrators，并将其与实际 reliance 和客观 phishing detection performance 联系。对 coding agent，分别对应：历史验证表现、当前执行过程证据、错误操作的后果严重性。适合指导后台恢复摘要和最终验收面板，但不宜把主观 trust 当成 thesis 的总结果。

## 五、推荐的三项核心研究

### Study 1：前台协作与后台委托模式下的人类监督机制

**研究问题**：两种模式如何改变用户对 agent 状态的理解、注意分配、干预时机和验收决策？这些差异产生哪些模式专属设计要求？

**设计**：同一 agent、同一能力、同一仓库任务，操纵前台 turn-by-turn 与后台 delegated run。记录完整的 `specify → delegate → observe/resume → intervene → verify/accept` 事件链。

**客观结果**：

- 正确干预、错误干预和漏干预；
- 正确接受/拒绝补丁；
- 状态恢复测试的事实正确率；
- 主动注意时间、被打断次数和完成时间；
- 最终隐藏测试、回归和越权事件。

**理论角色**：Cognitive Challenges 提供 delegation/inversion 与 metaknowledge；TEU 提供透明交互—忠实表示—知情行动的过程逻辑。Study 1 的产出不是新量表，而是可观测错误分类和一组设计要求。

### Study 2：前台模式的状态化执行工作台

**问题**：用户虽然持续在场，但线性聊天与原始日志使多步执行难以理解，导致不必要干预或错误放行。

**制品改造**：

- 将 agent 轨迹表示为 `需求—计划—动作—变更—证据—风险` 的状态关系图；
- 允许用户控制逐步推进、折叠常规事件和展开因果链；
- 把 diff、测试和当前仓库状态绑定到相应计划节点；
- 在关键节点提供局部暂停、回滚和继续。

**最小实验**：先比较线性 chat/log 与状态化表示；再用 2×2 检验“状态结构”和“用户控制的逐步动态表示”分别及组合的效果。所有条件显示的信息事实必须等价。

**文献链**：Skipping Class（表示结构）+ Animation（动态过程表示）+ Conversational Dashboards（客观路径效率）+ mHealth（feature factorial 和交互效应）。

### Study 3：后台模式的风险触发检查点与上下文恢复制品

**问题**：用户不持续在场，固定频率审批会制造打断和习惯化；完全自治又会错过高风险节点，且用户返回后难以恢复准确状态。

**制品改造**：

- 将常规进度事件批处理；
- 按可验证事件触发风险门，如权限越界、测试状态恶化、需求冲突、修改关键文件和不可逆动作；
- 让风险门在视觉与交互方式上区别于普通通知；
- 提供恢复 capsule：任务目标、已完成节点、当前 diff、验证证据、未解决风险和建议控制动作；
- 在 verifier 证据表明 agent 越过能力边界时，执行 inversion，把特定子任务交还给人。

**最小实验**：2×2 比较固定审批 vs. 风险触发，以及无恢复 capsule vs. 有恢复 capsule；另保留 agent-alone 或 never-interrupt 基准来衡量真正的 autonomy benefit。

**文献链**：Fog of Warnings（风险门）+ Cognitive Challenges（交还控制）+ Trust Calibration（展示哪些证据）+ Borgs（防止补充性人类知识丢失）。

## 六、三个研究如何共同回答一个 thesis 问题

| 层次 | Study 1 | Study 2 | Study 3 |
|---|---|---|---|
| 作用 | 识别模式差异与错误机制 | 设计前台制品 | 设计后台制品 |
| 用户注意状态 | 持续 vs. 间歇 | 持续在场 | 离开后返回 |
| 核心设计对象 | 过程和控制点 | 状态表示与逐步控制 | 事件选择、风险门、恢复与 handoff |
| 共同结果 | 经验证进展、变更完整性、监督成本 | 同左 | 同左 |
| 模式专属结果 | 状态理解、干预和验收错误 | 表示理解与路径效率 | 漏警、误警、恢复准确率和打断成本 |
| 对下一章的关系 | 产出设计要求 | 实例化前台要求 | 实例化后台要求 |

这个结构与目标 thesis 的对应关系是：

| 目标 thesis | Coding-agent thesis |
|---|---|
| 平衡内容生成与内容使用 | 平衡经验证的自主进展与人类治理/变更完整性 |
| 点击 vs. 滑动 | 前台协作 vs. 后台委托 |
| 模式机制研究 | 监督与注意机制研究 |
| 点击模式的推荐/展示制品 | 前台状态化执行工作台 |
| 滑动模式的序列决策制品 | 后台风险触发与恢复制品 |
| 参与者活跃度 | 经验证进展、完整性、监督成本的客观结果向量 |

## 七、为什么这条线比“四个监督阶段实验”更像 thesis

原先的 delegation、monitoring、intervention、acceptance 四阶段仍然有价值，但应降级为以下角色：

- 作为 Study 1 的过程编码框架；
- 作为 Study 2、3 中的客观事件与错误类型；
- 作为结果指标的阶段分解。

不宜再把四个阶段各自写成一个独立 feature 研究，因为那会造成四套理论、四种 artifact delta 和四个局部故事，缺少像目标 thesis 那样的“模式导致设计必然不同”的母问题。新的三研究结构中，四阶段被统一在同一个制品生命周期里，而前台/后台两种模式决定为什么需要两种不同的软件设计。

## 八、最小可行实现与论文写作顺序

1. 固定一个开源或自建 coding-agent scaffold，先实现完整事件日志、仓库快照、隐藏测试和权限规则；这些是三项研究的共同基础设施。
2. 先做小规模 Study 1，确认前台与后台确实产生不同错误结构；若差异不足，就不要强行进入两模式论文。
3. 从 Study 1 结果中选择两个最稳定、最可通过软件改变的问题，形成正式 design requirements。
4. Study 2 与 Study 3 分别只构建一个主要制品，并把内部 feature 作为 factorial/ablation，而不是把多个 feature 分散为多篇不相干论文。
5. 所有研究固定基础模型、工具能力、任务难度分层、隐藏测试和仓库规则；采用 participant × task 的交叉随机效应分析。
6. subjective trust、usefulness、cognitive load 只作为机制、操纵检验或补充解释；核心结论必须建立在日志、测试和仓库状态上。

最终，这条路线不是“把某个算法换成另一个算法”，而是研究 **怎样表示 agent 的工作、怎样安排控制权、怎样选择必须打断人的事件、怎样让人恢复并做出正确控制动作**。这些都是可运行 coding-agent 软件制品的核心设计，而且它们只在会自主调用工具、持续修改代码仓库并需要人类接管的 agentic software 情境中同时成立。
