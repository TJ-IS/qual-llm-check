# 被检索到不等于可行动：面向 Coding Agent 的依赖完备仓库上下文打包方法

**英文标题：** *Retrieved Does Not Mean Actionable: Dependency-Complete Repository Context Packing for Coding Agents*

> 稿件状态：逐段对照重写稿。所有经验结果均等待在冻结 benchmark、检索器和模型版本上真实运行。

## 摘要

在仓库级缺陷修复和功能维护中，coding agent 通常依赖检索器从大型代码库中补充与任务相关的代码片段，现有系统多按相关性分数截取排名靠前的候选。然而，在上下文预算有限时，高度相关的候选仍可能集中于同一符号，却没有同时给出修改所需的定义、调用、配置与测试证据，使 agent 能够定位局部代码却无法判断修改影响或验证修复结果。本文将能够共同支持修改定位、影响判断和结果验证的代码证据集合界定为“可行动上下文”，并把它的构造建模为依赖完备的预算打包问题。为此，本文提出依赖完备上下文打包方法 DCCP，它从任务描述与候选代码中识别待满足的证据义务，并按单位 token 新增满足的加权义务选择代码片段。已经满足的义务不再产生边际收益，因而重复证据会在同一目标函数中自然降权，而不需要另设去冗余模块。该目标形成一个带背包约束的单调次模最大化问题，使 DCCP 能够在严格 token 预算内给出可运行且可解释的近似解。本文将固定候选检索器与下游 coding agent，在 ARB、ContextBench 和 RepoBench 上比较预算内证据完备性、任务表现与推理成本，实验结果将在完成实现后报告。

**关键词：** Coding agent，仓库检索，可行动上下文，证据完备性，预算打包，次模优化

## 1. 引言

大语言模型与开发工具的结合，正在把代码智能从编辑器中的单次补全扩展为能够承担仓库级软件维护任务的 coding agent。一次典型的仓库级修复始于缺陷报告或功能请求，agent 随后搜索文件与符号、阅读项目代码、实施修改、运行测试，并根据执行结果继续调整（Jimenez et al. 2024，Yang et al. 2024）。与根据当前文件续写程序不同，完成这类任务所需的信息往往分散在接口定义、调用者、配置项和测试之中，agent 必须先决定查看什么，才能进一步决定修改什么。将这些搜索和验证活动委托给 agent，为开发者从逐步操作转向目标设定与结果监督提供了可能，同时也使错误定位、遗漏影响范围和无效工具调用成为系统部署时必须控制的结果。SWE-bench 等公开任务已经把真实 GitHub issue、可执行仓库和测试结果组织为可重复评价环境，使这种工作方式及其成败可以被系统观察。因而，coding agent 的实际价值不仅取决于语言模型能否生成代码，也取决于系统能否以可接受的上下文与推理成本提供支持修改和验证的仓库证据。

向 agent 提供仓库证据的一种直接做法，是让词法、向量或结构检索器分别为文件、符号或代码片段计算相关性分数，再选取排名最高的若干候选，或者沿排序填充到 token 上限（Shrivastava et al. 2023，Cheng et al. 2024）。这种做法隐含地把每个候选的价值视为可以单独判断，并假定排在前面的候选能够在拼接后继续保持其价值。真实仓库却包含大量内容相近而作用重叠的代码，同时把完成一次修改所需的定义、调用、配置和测试约束分散在不同位置。假设缺陷报告直接提到一个解析函数，排序靠前的片段可能反复给出该函数的实现、包装器和相似注释，而真正规定异常行为的调用者与回归测试因同 issue 的直接匹配较弱被挤出有限上下文。此时检索器已经找到了与问题高度相关的代码，交给 agent 的证据集合却仍不足以支持完整修复。语义表示、数据流和仓库图可以改善候选的发现范围，但只要最终上下文仍由单项分数直接截断，候选之间的重复与互补关系就没有进入选择决策（Ding et al. 2024，Ouyang et al. 2025）。因此，“发现相关候选”与“形成能够支持代码行动的上下文包”是两个相连但不同的问题。

仓库级修改的正确性取决于补丁是否同时符合项目的程序依赖与预期行为，而不取决于某个代码片段同 issue 的相似程度。目标符号的定义可以说明代码做了什么，调用者揭示哪些行为会受修改影响，配置项决定相关路径是否被启用，测试则表达项目希望保持或改变的结果。某一类证据即使与 issue 十分相似，也不能稳定替代其余证据，因为这些材料回答的是修改决策中的不同问题。反过来，同一问题的答案一旦已经出现，再加入表达相同关系的片段通常不会带来同等增益。本文据此把“可行动上下文”定义为一个在给定预算内共同回答当前修改所需关键问题的代码证据集合，并将每个尚待回答的问题表示为由任务触发的证据义务。这里的依赖完备性不要求收集整个仓库或枚举所有程序关系，而只要求最终上下文覆盖由 issue、候选锚点及其可验证依赖所诱发的义务。这样，代码片段的价值便不再是脱离集合的固定相关性，而是它加入当前上下文后能够满足多少仍未满足的任务义务。

IS 研究早已指出，信息质量不能被缩减为信息本身是否准确，而应当考察信息对使用者当前任务是否适用（Wang and Strong 1996）。据此推论，仓库证据是否优质也不能只看单项相关性，还要看它是否补足当前修改所需的信息，但该观点本身没有说明有限预算下应当取得哪一组代码。Mookerjee and Mannino（1997）进一步把案例检索视为有成本的信息获取，证明检索策略需要在保持任务表现的同时控制获取成本，并且与任务所依据的概念联合设计。Saar-Tsechansky and Provost（2007）则表明，即使一项信息能够改善模型的统计准确性，只要它不改变实际决策，为取得它付出的成本仍可能是浪费。把这三项认识带入 coding agent，可以得到两个相互约束的设计要求：代码证据必须针对当前修改能够支持的行动来计价，其收益又必须相对于有限的 token 和处理成本来判断。不过，既有 IS 构念并不直接给出仓库中的计算单位，因为代码片段之间的替代与互补由定义、调用、配置和测试关系产生。本文以任务诱发的证据义务表示这些关系，正是要把“适合当前任务且值得付费取得的信息”转化为可以在代码仓库中识别、组合与评价的对象。

基于上述问题，本文提出唯一的研究问题：**如何在固定 token 预算下，把检索器发现的候选代码组成一个尽可能满足当前修改证据义务的可行动上下文？** 为回答该问题，本文设计依赖完备上下文打包方法 DCCP，并把候选检索器固定在打包过程之前。DCCP 从任务输入中的路径、符号、错误、测试和可见代码位置确定初始锚点，再利用仓库索引中可追溯的定义、引用、调用、配置与测试关系生成证据义务。每个候选片段因呈现这些关系而覆盖一组义务，DCCP 在每次选择时计算该片段单位 token 能够新增满足的加权义务。由于已经满足的义务不再重复计入收益，同一规则会降低重复片段的优先级，并提高能够补齐缺失依赖的片段的优先级。由此得到的目标是带单一背包约束的加权覆盖函数，本文以惰性边际密度贪心形成实际上下文，并用小规模整数规划审计经验最优差距。整项设计围绕一个可检验主张展开：相较于直接截断相关性排序，在相同 token 预算下优先补足修改义务，能够向固定 agent 提供更有行动价值的仓库上下文。

这一主张可以在现成的公开环境中检验。核心评价场地是 Agent Retrieval Bench 和 ContextBench，前者提供真实开发信号、冻结仓库、工作流所需文件以及 token 预算评价，后者提供 1,136 个 issue 任务及经人工核验的文件、代码块和行级上下文（Qin and Xie 2026，Li et al. 2026）。两者已经提供查询、仓库、金标准与评价程序，但没有直接提供本文定义的证据义务，因而 DCCP 仍需用公开的关系抽取规则生成义务，并通过独立人工抽检报告其准确性。RepoBench 用于检验同一打包规则能否在 Python 与 Java 的跨文件补全中保持作用，其 v1.1 数据、运行脚本与评价程序已经公开（Liu et al. 2024）。CrossCodeEval 只在取得其官方说明需另行申请的原始仓库数据后作为附加复现，不进入承诺完成的主实验（Ding et al. 2023）。所有比较都固定候选池、候选相关性和下游模型，只替换预算内的打包方法，并在多个 token 预算上与排序截断、单位 token 相关性和最大边际相关性等基线比较。主要结果同时包含预算内金标准覆盖、上下文精确度和固定 agent 的任务成功，token 数与运行时间用于说明为取得这些结果支付的成本。只有当 DCCP 在相同候选与预算下补足更多外部金标准证据，并且这种改善继续传导到补全或修复结果时，本文才把它解释为可行动上下文的增量价值。

本文试图把 coding agent 检索的评价对象从彼此孤立的相关候选，推进到一个受预算约束、面向修改行动的仓库信息制品。可行动上下文把 IS 研究中的任务适用性、获取成本和决策后果落实到程序依赖关系，使信息是否有用能够由它与当前任务、已选证据和后续代码行动的共同关系来判断。DCCP 进一步把这一判断变成一条可运行的边际覆盖规则，并为每次选择保留可核查的证据理由。这些预期贡献目前仍是有公开评价条件的设计主张，最终能够成立到何种程度，将由外部金标准和下游任务结果决定。

## 2. 文献综述

### 2.1 仓库上下文从代码补全走向 Coding Agent

仓库级代码补全首先把当前文件之外的项目代码识别为一种可以独立检索和评价的模型输入。CrossCodeEval 从真实开源仓库构造必须使用跨文件依赖才能正确补全的样本，并在 Python、Java、TypeScript 和 C# 中分别评价检索与生成（Ding et al. 2023）。RepoBench 进一步把仓库级补全系统分为检索、补全和检索—补全流水线，使研究者能够区分“没有找到所需代码”与“已经找到但模型没有正确使用”两类失败（Liu et al. 2024）。RepoCoder 等方法则让当前生成结果更新下一轮查询，说明仓库上下文并非总能通过一次静态检索取得（Zhang et al. 2023）。由此，跨文件信息不仅被证明能够改变代码模型的输出，取得这些信息的过程也成为可以与生成分开评价的系统功能。不过，补全任务通常给定明确的光标位置并要求生成局部代码，而 issue 级 agent 需要从较含混的自然语言与执行反馈中自行定位修改对象、影响范围和验证条件，因此所需上下文不只是一处 API 定义。

面向 issue 修复的工作把上下文获取进一步嵌入 agent 的仓库操作。SWE-agent 通过面向软件活动设计的查看、搜索、编辑与执行接口，让模型在观察结果后继续选择工具（Yang et al. 2024）。AutoCodeRover 以抽象语法树中的类和方法为搜索单位，并在测试可用时引入故障定位信号，逐轮收集补丁生成所需的代码上下文（Zhang et al. 2024）。RepoGraph 把仓库依赖图作为可插接的导航结构，LocAgent 则让 agent 在包含文件、类、函数及其导入、调用和继承关系的异构图上执行多跳定位（Ouyang et al. 2025，Chen et al. 2025）。这些设计证明，项目结构能够帮助 agent 跨越自然语言描述与真实修改位置之间的距离，并发现查询没有直接点名的依赖实体。它们的主要决策对象仍是下一次搜索、图遍历或待定位实体，取得的内容通常随后直接交给 agent 或按单项定位结果保留。因而，结构化导航扩大了可以发现的候选范围，却没有自动回答另一个问题：当这些候选共同竞争固定 token 预算时，哪一组片段能够以最少重复补齐修改所需的不同证据。

与预算成包相邻的研究分别改变了是否检索、提示内容和集合选择。Repoformer 学习判断一次仓库检索是否会改善补全，从而在检索有害或无用时跳过整个操作，但它不负责在决定检索后组合相互补充的多个代码片段（Wu et al. 2024）。Repository-Level Prompt Generator 从仓库结构与相关文件生成任务特定的提示提案，CodePromptZip 则依据代码 token 类型压缩已经取得的示例，二者分别扩展了提示来源和可容纳内容，却没有以修改证据关系定义集合完备性（Shrivastava et al. 2023，He et al. 2026）。在通用检索中，最大边际相关性通过相关性与语义新颖性的折中减少冗余，近期一篇多跳问答预印本还直接把读者上下文构造建模为预算次模最大化，并联合优化相关性、查询覆盖、代表性和多样性（Carbonell and Goldstein 1998，Bala 2026）。这项最新工作意味着，次模优化或预算打包本身不能构成本文的独立新颖性。它也留下了一个清楚的情境差别：问答证据围绕答案跨度与文档桥接组织，仓库修改证据则由程序实体之间的依赖、受影响行为和项目测试约束组织。DCCP 因此不再叠加一组通用多样性分数，而只检验代码关系能否形成任务义务，以及覆盖这些义务能否比通用打包目标更有效地支持 agent 修改与验证。

### 2.2 任务适用性、获取成本与行动后果

信息质量研究为判断仓库上下文提供了比单项准确性更宽的起点。Wang and Strong（1996）从数据消费者的使用出发定义质量，并将 value-added、relevancy、timeliness、completeness 和 appropriate amount of data 归入情境数据质量。其中，相关性表示信息是否适用于当前任务，完备性涉及任务所需的广度、深度与范围，适量性则要求信息数量本身与使用需要相称。迁移到 coding agent，候选同 issue 的相似程度主要回答相关性，而一个上下文包是否包含修改对象、受影响依赖和验证约束，更接近任务条件化的完备性。严格 token 上限又使适量性成为实际设计约束。这个框架因而支持从“相关片段”转向“适合当前修改的有限证据集合”，但它没有给出代码关系的抽取方式、片段组合规则或客观求解目标。本文把情境数据质量作为设计依据，而不假定 coding agent 会像人类数据消费者一样主观感知质量，相关迁移最终必须由可观察的代码任务结果检验。

信息一旦需要搜索、传输和处理，适合任务并不足以决定它是否值得取得。Mookerjee and Mannino（1997）研究案例系统怎样依次收集诊断属性，并把系统表现分为信息获取成本与分类准确性。由于软件版本等属性容易取得，而远程诊断等属性成本更高，检索策略必须考虑每项信息相对于成本带来的问题区分能力。该研究还表明，先形成任务概念、再另行优化检索顺序，会弱于把概念形成与检索策略联合设计，因为同一属性的价值取决于系统最终要区分什么。coding agent 中的成本载体不再是向用户询问属性，而是代码片段占用的 token、模型处理时间和由此引起的调用成本。相应的迁移不是照搬原文的决策树，而是要求 DCCP 用修改义务定义片段收益，再用 token 长度约束取得这些收益的代价。候选索引的离线建设成本与推理时上下文成本将被分开报告，这也遵循原研究不把固定知识库建设成本混入单次信息获取成本的界定。

有成本信息获取还需要避免把易优化的中间指标误当作最终价值。Saar-Tsechansky and Provost（2007）指出，传统主动学习倾向于选择最能降低统计误差的标签，但预测模型服务于具体业务决策时，昂贵的准确率改善可能不改变甚至损害决策结果。其 decision-centric acquisition 因而优先取得更可能影响决策的信息，并以决策准确性和利润而非模型误差单独评价选择策略。coding agent 的对象有所不同，本文选择的是推理时进入上下文的代码片段，而非用于训练预测器的标签。可迁移的原则是，相关性、金标准覆盖和本文构造的义务覆盖都只是中间信号，只有固定 agent 的补全或修复结果才能判断取得这些代码是否真正改变行动。DCCP 因此用义务覆盖指导可计算的选择，却不以该内部目标自证有效，而是在相同 token 成本下检验外部证据保留能否继续提高代码任务成功。任务适用性、有成本获取和决策中心评价由此汇成同一设计要求：为尚未得到支持的修改行动选择单位成本边际证据，而不是在三个理论标签下建立三个彼此独立的模块。

### 2.3 研究缺口

现有研究已经能够用词法、语义与程序结构发现仓库候选，也已经提出选择性检索、代码压缩和通用预算打包，因此本文面对的缺口不是“coding agent 尚无检索方法”。真正缺少的是一个位于候选生成与 agent 行动之间的情境化选择规则，它能够判断若干代码片段放在一起后，是否在有限预算内共同呈现了当前修改所需的不同依赖证据。通用多样性与问答证据打包没有定义程序实体的修改义务，图导航与代码定位又没有把义务间的替代和互补写成独立的预算集合目标。IS 的任务适用性、获取成本和决策中心原则说明了为什么需要这种选择规则，却仍需被转化为可从仓库索引计算的关系和可由代码结果检验的制品。DCCP 所填补的正是这一窄缺口：以任务诱发的程序关系义务表示可行动性，在固定候选池内按单位 token 的未满足义务增益选择片段，并要求该内部目标通过外部金标准和下游 agent 结果获得验证。

## 3. 问题定义与 DCCP 设计

### 3.1 决策时点与输入输出

DCCP 位于候选检索器和 coding agent 之间，并在 agent 开始本轮修改推理之前执行一次。给定任务描述 $q$、冻结在指定提交上的仓库 $R$ 和任意检索器返回的候选片段集合 $C$，每个候选保留文件路径、起止行、所属符号、检索分数以及按目标模型 tokenizer 计算的长度。部署者同时给出可用于仓库证据的 token 预算 $B$。DCCP 只从 $C$ 中选择总长度不超过 $B$ 的子集，并把所选片段连同来源位置和选择理由交给下游 agent。它不改写任务查询、不扩展候选池，也不参与补丁生成与测试执行。这样的接口把“发现哪些候选”“保留哪些候选”和“agent 如何使用候选”分开，使打包规则的作用可以在同一检索器和同一 agent 下独立比较。

候选单位由一个对所有比较方法相同的确定性适配器生成。对可解析的源代码，适配器用 tree-sitter 将检索到的文件或长范围映射为函数、方法、类和模块头等带完整来源位置的符号片段。对配置、构建文件和无法稳定解析的文本，则采用固定长度且固定重叠率的行窗口。来自多个检索结果的相同范围按提交号、路径、起止行去重，部分重叠范围被投影到同一组规范片段，防止任何方法仅因重复计费获得不同候选。超过单片段上限的符号按照语句边界确定性拆分，超过总预算且无法拆分的项在所有方法中共同排除。候选 $c_i$ 的成本 $l_i$ 是它连同文件路径、行号和分隔标记序列化后，使用下游模型 tokenizer 得到的实际 token 数。本文不在片段内部删除或改写 token，因而所研究的是具有原始代码来源的集合选择，而不是提示压缩。

### 3.2 从任务锚点构造证据义务

DCCP 首先从推理时可见信息中确定当前任务的仓库锚点。它用语言无关的模式抽取 issue 或评审评论中显式出现的文件路径、标识符、错误类型、测试名称与命令，并把堆栈帧和编译错误中的位置解析到冻结提交上的文件和符号。对于给定编辑片段或代码补全光标的任务，锚点还包括输入中已经可见的修改位置、当前文件与光标所在符号。若这些任务信号没有任何可解析实体，系统才把冻结检索器排名最高的少量候选符号作为低置信度种子，且这一回退规则与数量上限在实验前固定。名称能够唯一解析时形成一个锚点，重名符号则保留所有可达解析并共同分配原始置信度，避免任意挑选一个同名实现。每个锚点记录其来源、解析规则、仓库位置和置信度，以便后续检查某项义务为什么被创建。锚点提取不访问修复补丁、benchmark 金标准或任务完成后的测试信息，其作用只是把自然语言、代码位置与错误信号连接到可追溯的仓库实体。

锚点随后触发与当前修改有关、且在仓库索引中真实存在的证据义务。对符号锚点，定义或声明关系回答“修改对象是什么”，入向调用、继承和引用关系回答“哪些代码会受到影响”，出向调用与数据依赖回答“该对象依赖什么”。当锚点或其模块被配置文件、构建脚本或注册表引用时，系统创建激活义务，用于回答相关行为在何种条件下生效。当测试代码直接引用锚点、覆盖相同调用路径或在 issue 中被点名时，系统创建验证义务，用于呈现项目预期保持或改变的行为。堆栈帧之间的相邻调用、错误位置到所属符号的包含关系也可以产生定位义务。DCCP 默认只展开一跳关系，并只为候选池中存在可覆盖片段的关系建立优化义务，防止不可取得的仓库内容扭曲打包选择。每项义务保存锚点、关系类型、目标实体和生成规则，因此“定义、影响、激活、验证”是对已生成义务作用的解释，而不是无条件套在每个任务上的四个模块。

设 $T_a$ 为锚点 $a$ 实际触发且包含至少一项关系的类型集合，$O_{a,t}$ 为其中关系类型 $t$ 产生的义务。若锚点置信度为 $ρ_a$，默认权重为

$$
w_o = \frac{ρ_a}{|T_a|\,|O_{a,t}|}, \qquad o \in O_{a,t}.
$$

这一分配使一个锚点的总权重不因仓库中同类关系数量增加而膨胀，并让定义、影响、激活或验证等实际出现的关系类型在该锚点内拥有相同初始份额。关系类型权重也可以只在训练划分上估计，但等权归一化作为主设定，学习权重仅用于稳健性分析。义务 $o$ 被候选 $c_i$ 覆盖，当且仅当该片段包含索引记录的证据位置，例如定义体、调用点、配置引用或测试断言，并保留足以追溯该位置的文件与行号。记候选覆盖集合为 $M_i$，一个片段可以同时覆盖多项义务，多段包含同一证据的代码也可以覆盖同一义务。关系生成器保留全仓可观察义务 $O_R$，实际优化只使用至少被一个候选覆盖的子集 $O_C$，二者之差用于评价候选生成阶段已经损失了多少证据。

### 3.3 依赖完备的预算目标

对任意已选候选集合 $S \subseteq C$，DCCP 将其义务价值定义为

$$
F(S)=\sum_{o\in O_C} w_o\min\left(1,\sum_{c_i\in S}\mathbb{I}[o\in M_i]\right).
$$

内层求和判断义务 $o$ 是否已被所选片段呈现，截断函数使该义务无论被重复呈现多少次都只获得一次权重。因而，加入覆盖已有义务的相似片段不会增加相应收益，加入覆盖新义务的互补片段则会直接提高 $F(S)$。DCCP 求解

$$
\max_{S\subseteq C} F(S) \quad \text{s.t.} \quad \sum_{c_i\in S} l_i \le B.
$$

预算约束按最终提示的真实 token 计费，使较长片段只有在带来足够新增义务时才值得进入上下文。$F(S)$ 是非负、单调的加权覆盖函数，也具有次模的边际收益递减性质。这个性质提供了可扩展的近似求解条件，但不意味着内部覆盖天然等同于下游修复价值，二者仍由经验评价连接。

### 3.4 最优性审计与理论边界

前述目标说明什么样的候选组合具有最高义务价值，却还不能衡量实用求解器离这一组合有多远。为此，本文在候选规模允许时另建一个只用于审计的整数规划。令 $x_i$ 表示候选 $c_i$ 是否入选，$y_o$ 表示义务 $o$ 是否被至少一个入选候选覆盖，精确审计问题为

$$
\max \sum_{o\in O_C}w_oy_o \quad \text{s.t.}\quad y_o\leq \sum_{i:o\in M_i}x_i,\quad \sum_i l_ix_i\leq B,\quad x_i,y_o\in\{0,1\}.
$$

在预先规定的候选数阈值和求解时限内，该模型返回最优解或仍有效的上界，使本文能够报告默认求解器的经验最优差距和运行时间。超出阈值的实例不把超时结果当作最优值。经典次模背包算法可以通过枚举可行的一至三个元素并完成贪心扩展取得 $1-1/e$ 近似保证，但其直接实现可需要 $O(|C|^5)$ 次函数值计算，不适合作为本文面向仓库任务的默认在线求解器（Sviridenko 2004）。理论算法因而只提供问题性质的参照，整数规划只校验小实例，主实验与部署仍使用下文定义的惰性求解器。

### 3.5 可运行的打包算法

即使义务价值已经给定，直接检查候选片段的全部可行组合仍会随候选数迅速增长，因而不能作为大型仓库的默认打包方式。DCCP 采用惰性边际密度贪心形成实际交给 agent 的上下文。算法从空集开始，把候选 $c_i$ 的当前优先级定义为新增义务价值 $F(S\cup\{c_i\})-F(S)$ 与 token 成本 $l_i$ 的比值，并用最大堆保存该比值的上界。候选出堆时，算法依据当前已覆盖义务重新计算其真实边际密度。若该值仍不低于堆中其余上界且加入后不超预算，算法便将候选纳入 $S$。否则，它更新候选的上界，或跳过已经无法容纳的候选。由于次模性使边际收益只会随 $S$ 扩大而下降，先前计算的数值可以安全地作为惰性上界，从而避免在每次选择后重新扫描全部候选。算法在没有正边际收益的可行候选时结束，并将所得集合与最佳可行单片段比较，返回 $F$ 值较高者。每次入选同时记录新覆盖的义务、边际价值、token 成本和当时的已覆盖集合，使最终上下文能够沿选择轨迹回溯到具体关系证据。

### 3.6 输出序列与实施边界

集合选择结束后，DCCP 还必须把无序的 $S$ 转换为下游模型实际读取的文本序列。本文保持任务描述、系统提示和工具接口不变，并按候选在冻结检索器中的原始名次排列入选片段，同名次时再按仓库路径和起始行排序。每个片段只附带已经计入 $l_i$ 的路径、行号和分隔标记，不把义务权重、边际收益或选择理由额外写入 agent 提示。相同的排序与标记规则应用于所有打包基线，使实验差异来自预算内选择了哪些片段，而不是位置提示或额外解释文本。义务倒排表、堆操作次数、实际函数求值次数和端到端打包时间作为实施日志保留，选择轨迹则只供错误分析和人工审计使用。由此，DCCP 的在线输出仍是一个普通的代码上下文包，可以直接接入现有 retriever—agent 流程，而无需改变 agent 的生成、编辑和测试机制。

## 4. 实证评价

### 4.1 研究场地与分析单位

核心评价使用两个直接观察仓库上下文取得过程的公开场地。Agent Retrieval Bench（ARB）包含 25 个开源仓库上的 427 个样本，其中 345 个正例分别要求从实现变更找到回归测试、从评审评论补足上下文、从失败轨迹定位实现，以及从已知编辑发现连带影响文件。每个子集均提供与样本匹配的冻结语料和工作流所需文件（Qin and Xie 2026）。本文只把这 345 个正例用于打包比较，82 个无金标准样本留作边界检查，因为本文研究的是检索已经发生后的预算组合，而不是是否启动检索。ContextBench 提供 66 个仓库、八种语言上的 1,136 个 issue 解决任务，并为每项任务标注经人工核验的文件、代码块和行级上下文（Li et al. 2026）。在两个场地中，一个分析单位均由任务输入、冻结提交、固定检索器产生的候选池和 token 预算共同定义。DCCP 只读取任务输入与冻结仓库来生成义务，金文件、金片段、参考补丁和测试补丁始终保留到评价阶段，因而不会参与锚点、权重或选择决策。

RepoBench 用于检查同一打包规则能否从 issue 处理迁移到已知光标位置的跨文件代码补全。该 benchmark 把评价区分为检索、补全和二者衔接的流水线任务，并公开 Python 与 Java 的 v1.1 数据、运行脚本和 Exact Match、Edit Similarity、CodeBLEU 评价程序（Liu et al. 2024）。本文使用 `cross_file_first` 与 `cross_file_random` 两种确有跨文件依赖的设置，以光标所在符号和当前文件为锚点，在数据已经提供的候选片段内重建可观察关系，再比较预算打包后的检索与补全结果。该场地只承担跨任务迁移检验，不与 ARB 和 ContextBench 合并计算总体均值。CrossCodeEval 虽然覆盖四种语言并公开推理与评价代码，但其官方复现说明仍要求另行申请原始数据。没有取得完整仓库输入并验证关系索引以前，本文不把它列入承诺完成的主实验，只保留为数据到位后的附加复现（Ding et al. 2023）。

### 4.2 比较方法

比较方法围绕“代码义务是否比已有预算规则提供额外信息”来设置。排名截断按冻结检索器的原始次序装入候选，直到下一个片段会超过预算，用于表示最常见的 top-ranked packing。相关性密度把原始检索分数除以片段 token 数后排序，用来检验仅偏好短而相关的代码是否已经足够。最大边际相关性（MMR）在每一步权衡候选同任务的相似度与候选之间的语义重复，检验通用去冗余能否替代程序关系互补。本文还实现 Bala（2026）的通用次模证据打包思路，在相同候选和预算上联合考虑相关性、查询词项覆盖、候选代表性与语义多样性，以区分“采用集合优化”与“采用代码义务”这两层作用。MMR 和通用次模方法的权重只在开发划分确定，所有方法共享候选切分、真实 token 计费和输出顺序。小实例整数规划不作为竞争方法，只给 DCCP 的目标提供最优性审计。RepoGraph、LocAgent 等改变候选发现过程的方法则在后续检索器稳健性分析中充当候选生成器，而不与打包规则混为同一比较层。

### 4.3 结果指标与识别逻辑

评价指标按照证据进入 agent 的顺序组织，而不把 DCCP 自己计算的 $F(S)$ 当成成功标准。首先，候选池金文件或金片段召回率衡量上游检索是否曾经取得所需证据，$|O_C|/|O_R|$ 则诊断程序关系在候选阶段的可达程度。其次，预算上下文用外部金标准评价证据是否存留。ARB 以各预算下的 Budgeted Context Yield 为主结果，并同时报告文件精确率与召回率。ContextBench 以金代码跨度的 token 级 F1 为主结果，并分列精确率、召回率和完整金跨度命中率。再次，在具有可执行环境的 ContextBench 子集上，固定 agent、生成模型和测试流程，报告补丁通过率，并记录初始上下文之后新增的文件读取、工具调用和推理 token。RepoBench 则使用官方 Exact Match 作为迁移主结果，以 Edit Similarity 和 CodeBLEU 辅助描述不完全匹配的补全。最后，所有场地都报告实际装入 token、打包时间和峰值内存，小实例另报相对整数规划上界的差距。义务覆盖率、各关系类型的边际贡献和重复义务 token 占比只用于解释外部结果为何变化，不作为支持主张的替代终点。

### 4.4 实验协议

主实验把 Qwen3-Embedding-8B 固定为候选检索器，在每项任务上取得排名前 200 的代码片段，再由共同适配器规范化为候选池（Zhang et al. 2025）。该开源检索器在 ARB 的官方结果中具有较高的 Recall@20，因而能减少“候选根本未出现”对打包比较的遮蔽，但本文不会用测试金标准重新排序或补入候选。所有打包方法分别在 2K、4K、8K 和 16K token 预算下运行，并共享检索器权重版本、仓库提交、tokenizer、候选上限与序列化规则。需要估计权重的基线使用按仓库分组的开发折确定参数，再在未参与调参的仓库折上产生结果，DCCP 的等权主设定不使用金上下文调参。ContextBench 的下游实验先运行只能读取给定上下文的固定修复 agent，用于观察上下文本身能否支持补丁。随后开放共同的搜索与读取工具，观察不同初始包是否减少补偿性探索。两种模式均冻结 agent 提示、模型快照、最大回合数、测试命令和生成参数。RepoBench 沿用官方测试划分和评价脚本，只替换输入提示中的跨文件候选集合。

8K token 被预先指定为确认性预算，其余三个预算用于绘制效果随约束松紧变化的曲线。检索与上下文指标在完整测试任务上计算方法间的任务内差值，再以仓库为簇进行 10,000 次 bootstrap，报告均值差和 95% 置信区间。DCCP 对四个主要打包基线的确认性比较采用双侧成对置换检验，并对同一主结果上的四个检验使用 Holm 校正。下游 agent 的成本较高，本文在查看任何方法结果前，从具有可执行环境的任务中按仓库、语言和金上下文长度分层固定 100 项，并为每种条件运行三个预先登记的随机种子。主表报告各次独立运行的补丁通过率与成本，另以任务为单位汇总至少一次通过率，防止只呈现有利种子。基础设施失败先按相同配置重试一次，仍失败的运行单独报告。主分析采用成对可用样本，稳健性分析再分别把缺失计为失败和排除。所有开发折、测试折、任务抽样、随机种子、容器镜像和模型版本在首次结果生成前写入不可变配置文件。

### 4.5 机制消融

为分离 DCCP 中三项设计的作用，本文每次只移除一个关系。`DCCP-Local` 只保留锚点自身的定义或当前位置义务，不生成调用、依赖、激活和验证义务，用来检验跨片段关系是否确实带来超出局部定位的证据。`DCCP-Flat` 保留全部关系，却令每条关系获得相同未归一化权重，用来检验按锚点和关系类型分配权重是否抑制高出度符号支配预算。`DCCP-Static` 先为每个候选独立计算其覆盖义务权重之和，再按该数值与 token 成本的比值一次排序，不随已选集合更新边际收益，用来检验重复义务不再计价这一集合机制。三个变体仍使用同一候选、预算和输出规则。本文在外部金上下文指标上比较完整 DCCP 与三个变体，并以义务类型的入选变化解释差异，不以被消融定义直接决定的内部覆盖值证明该组件有效。

### 4.6 适用边界

DCCP 的优势需要候选中已经存在互补证据，也需要预算紧到迫使片段竞争，因而本文不把它假定为所有仓库与模型上的恒定增益。候选条件分别使用 BM25、Qwen3-Embedding-8B 和结构化 RepoMap 产生，并在比较打包结果前报告各自的金证据召回，以检验 DCCP 能否在检索质量改变时保持作用。预算条件沿 2K 至 16K 展开，用来识别极紧预算下证据无法共同容纳，以及宽松预算下所有方法趋同的区间。任务条件按金上下文是否跨文件、是否包含两类以上程序关系进行预先分层，用来检验关系互补而非单点相关是否构成主要受益情境。读取条件在严格上下文模式下分别冻结一个 7B 与一个 32B 开源代码模型，检验更强读者是否会吸收打包差异。上述分析均报告 DCCP 相对排名截断和通用次模打包的交互差值，不以单个语言、仓库或模型上的最好结果替代总体结论。

### 4.7 义务构造抽检

外部 benchmark 只能说明所选上下文是否碰到金证据，不能确认 DCCP 给出的选择理由是否忠实于程序关系。本文因而在查看方法成绩前，从三个评价场地按任务类型和语言分层抽取 120 项任务，由两名具有软件开发经验、且不知道各方法结果的标注者独立审查。正式标注前，两人用另取的 20 项任务试标并修订判定手册，这些试标任务不进入抽检估计。正式审查分四步进行：锚点是否来自推理时允许看到的输入，关系是否真实存在于冻结提交，所生成义务是否回答了相应的修改问题，候选片段是否确实呈现了义务指向的证据。标注者还依据任务描述、金上下文及锚点一跳邻域补列系统遗漏的可观察义务，使义务生成不仅有精确率估计，也有受限范围内的召回估计。本文分别报告四步通过率、义务精确率与召回率、两名标注者的一致性以及仓库簇 bootstrap 区间，分歧由第三名标注者在不查看模型结果的条件下裁决。错误被归为输入解析、同名实体解析、关系抽取、义务作用判断和候选映射五类，并从每类随机选择成功与失败案例回放完整选择轨迹。

## 5. 讨论与预期贡献

实证结果必须同时穿过内部机制与外部后果两道检验，才能支持“可行动上下文”这一主张。若 DCCP 在候选金证据已经可达的任务上，相对排名截断和通用次模打包提高预算内金上下文指标，并且该差异继续表现为更高的固定-agent 补丁通过率或更少的补偿性搜索，结果才说明程序义务为 coding agent 提供了超出一般相关性与去冗余的行动价值。若改善只出现在 $F(S)$ 或义务覆盖率上，本文只能说明目标函数按其定义运行，不能声称上下文质量提高。若 DCCP 超过排名截断却不能超过 Bala（2026）的通用打包，贡献应收缩为 coding 场景对集合选择的又一验证，而不是新的代码义务表示。若优势只存在于较弱读者、中等预算或多关系任务，结论也应明确限定在这些条件内。若外部金上下文和下游结果均无稳定改善，则核心主张不成立，关系规则与权重只能作为一项经过否证的设计尝试报告。

在完整证据模式得到支持的前提下，本文对 IS 文献的首要贡献是把仓库上下文质量界定为一种面向行动的集合属性。Wang and Strong（1996）的适用性观点说明信息质量取决于使用任务，但没有规定多个信息项在硬预算下怎样共同形成可用输入。DCCP 进一步指出，一个代码片段的质量不仅取决于它同任务的关系，还取决于当前集合已经回答了哪些修改问题。由此，重复呈现同一义务的信息会失去边际价值，表面相关性较弱却补足另一项义务的信息可能变得更有价值。这个关系把任务适用性从单项判断推进为“任务—已有信息—待执行行动”共同决定的集合判断，也把可行动上下文同一般的相关文档集合区分开来。该贡献的边界仍是程序关系可观察且外部结果能够验证的仓库任务，不能被推广为所有信息产品的普遍质量定义。

第二项贡献涉及有成本的信息获取。Mookerjee and Mannino（1997）说明检索策略应把取得信息的代价同任务所需概念联系起来，Saar-Tsechansky and Provost（2007）进一步要求信息价值由它是否改善最终决策来判断。DCCP 把这两项规范落实到 coding agent 的一个具体决策点：在检索器已经给出候选以后，每个 token 的收益由它还能补足多少修改义务决定，所得信息包再由补丁与搜索行为评价。这样，token 预算不只是模型窗口的技术限制，而成为决定何种仓库证据值得交给 agent 的信息获取成本。选择轨迹也使研究者能够区分“上游没有找到”“预算内没有保留”和“agent 没有利用”三种失败。该贡献不在于首次提出成本敏感检索，而在于提供一种能在程序关系上计算、在固定 agent 上检验、并能逐项审计的信息获取规则。

对 coding-agent 系统设计者而言，DCCP 的直接用途不是替换现有搜索器或代码模型，而是在二者之间增加一个可以检查的预算决策层。团队可以利用预算曲线选择金证据存留或修复成功开始趋缓的 token 点，而不是沿用任意 top-k。若选择日志显示大量义务从未进入 $O_C$，改进重点应放在检索器或仓库索引。若义务已进入候选却未被打包，问题属于预算规则。若完整证据已经交付但 agent 仍失败，则应检查推理、编辑或验证。关系类型和来源位置还允许维护者抽查某段代码为何被加入提示，而无需解释稠密向量分数。相反，当任务主要依赖单个局部片段、预算足够容纳全部候选，或目标语言的关系抽取尚不可靠时，DCCP 增加的索引与打包成本可能没有价值，系统应保留简单排名或直接读取作为回退。

本文有四项直接限制。第一，DCCP 只在一次 agent 推理前打包固定候选，不能处理测试反馈到来以后应继续搜索还是停止的问题。该动态问题由系列研究中的前缀价值停止方法另行研究。第二，DCCP 冻结候选检索器，因而无法挽回 $O_R\setminus O_C$ 中的证据。怎样依据任务与仓库条件选择检索组合属于系列研究中的任务匹配检索组合问题。第三，一跳静态关系不能完整表达反射调用、运行时配置、生成代码和跨语言构建关系，支持语言扩展后必须重新抽检义务精确率与召回率。第四，公开 benchmark 的金上下文可能遗漏替代性有效证据，100 项下游样本也不能代表所有 agent 与软件生态，因此文件或跨度未命中不总等于信息无用，局部修复增益也不能自动推广到生产开发效率。更根本地说，本文目前仍是可执行的研究设计而非完成的经验论文，所有预期贡献都须在冻结配置上真实运行并公开失败案例以后再改写为结果性陈述。

## 6. 结论

仓库检索已经能够向 coding agent 提供与任务相似的代码，但有限上下文要求系统进一步决定哪些证据应当共同留下。本文把这一决策界定为可行动上下文构造，并提出 DCCP，用任务诱发的程序关系义务表示修改定位、影响判断与验证所需信息，再按单位 token 的未满足义务价值选择候选片段。该设计把相关性排序之后、agent 行动之前的集合选择变成一个独立、可运行且可审计的研究对象。ARB、ContextBench 与 RepoBench 提供了从文件证据、代码跨度到下游补全和修复的公开评价路径，而冻结候选与 agent 的协议使 DCCP 的作用可以同检索发现和代码生成分开判断。只有当真实运行同时支持预算内外部证据与下游后果时，本文才会把 DCCP 解释为面向 coding agent 的信息质量与获取成本方法。在此之前，它是一套已经明确数据、算法、反例和失败条件的待检验设计。
