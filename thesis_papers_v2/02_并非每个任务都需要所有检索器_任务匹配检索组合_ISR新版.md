# 并非每个任务都需要所有检索器：面向 Coding Agent 的任务匹配检索组合

**英文标题：** *Not Every Task Needs Every Retriever: Task-Matched Retrieval Portfolios for Coding Agents*

> 稿件状态：逐段对照重写稿。所有经验结果均等待在冻结 benchmark、检索器和模型版本上真实运行。

## 摘要

Coding agent 平台开始同时接入词法、稠密、仓库地图与代码关系等检索服务，但固定使用一种服务可能错过任务所需线索，无差别调用全部服务又会增加查询与候选处理成本，并使重复候选竞争有限上下文。现有选择性检索主要决定是否启动一个既定检索流程，逐实例算法选择虽然能够选择算法或并行子集，却通常假定成员独立产生任务结果，不能直接表示多路代码候选融合后的互补与挤出。本文借鉴任务—技术匹配和有成本信息取得研究，把检索前的来源集合界定为任务匹配检索组合，并提出 TMRP。该方法只使用检索前可见的任务—仓库条件，对少量可行服务组合评分，其监督次序来自统一倒数排名融合与 token 打包后的外部证据质量减实际查询成本。本文设计在 Agent Retrieval Bench 与 ContextBench 上按仓库分离训练和测试，并以 RepoBench 检查预构造候选空间下的边界，同时比较全调用、AutoFolio 和自动并行组合选择的直接迁移，再用固定 mini-SWE-agent 检验选择差异能否传递到代码行动。当前稿件不预报经验优势。只有 TMRP 在两个全仓库场地均以更低成本保持质量、超过两个选择近邻，并产生可观察的 agent 过程或代码后果，任务匹配检索组合的理论与方法主张才得到支持。

## 1. 引言

大语言模型正在把代码智能从局部补全扩展为能够处理仓库级缺陷与功能请求的 coding agent。开发者提交 issue 或修改要求以后，agent 通常要先在冻结仓库中找到定义、调用、配置与测试等任务证据，随后才形成修改并通过执行反馈验证结果（Jimenez et al. 2024, Yang et al. 2024）。为支持这种工作，agent 平台开始同时维护词法索引、稠密向量索引、仓库结构摘要和代码关系图。它们分别擅长匹配错误字面量、自然语言语义、全局文件结构与跨符号依赖，也具有不同的索引成本、查询延迟和候选规模。一次检索选择因而不只是模型前的一项技术设置。它决定哪些仓库信息有机会进入 agent 的判断，也决定平台为取得这些信息付出多少计算与处理成本。

在一个可部署的检索流程中，平台先为冻结提交建立若干可独立调用的检索服务。任务到达后，编排器把同一项 issue 或代码请求发送给被启用的服务，各服务按预先固定的配置返回文件或代码片段及其分数。平台随后规范化来源位置、去除重叠候选，并用同一个预算打包器形成初始上下文，agent 才据此开始阅读、编辑和测试。本文把一次任务中被共同启用的服务配置集合称为检索组合。组合中的配置可以是 BM25 的固定 top-k、稠密检索的固定 top-k、RepoMap 的结构候选或代码图的一跳候选，但本文不在任务到达后连续调节各服务配额。组合选择发生在读取任何检索结果之前，所能依据的只有任务文本、推理时可见的错误信号以及预先计算的仓库属性。这样，组合器控制的是一项明确的前置决策：本次任务值得为哪些信息来源支付查询与候选处理成本。

平台可以为每项任务调用全部服务，以扩大找到有用代码的机会，但每增加一种服务都会带来查询延迟、候选规范化和合并处理，其返回的大量近似候选还会竞争固定的上下文预算。平台也可以长期使用一个默认服务来控制成本，却会把该服务不擅长的任务稳定地置于不利位置。Agent Retrieval Bench 的公开结果显示，稠密检索在总体召回上较强，RepoMap 在 8K token 下取得更高的预算上下文产出，不同任务类型的最佳检索族也并不相同（Qin and Xie 2026）。这种差异具有直接的开发含义。带有精确错误字面量的失败轨迹可能只需低成本词法检索，未直接点名实现的评审意见可能依赖语义匹配，沿编辑位置寻找连带影响文件则更可能受益于结构关系。如果平台能够在检索前识别这些条件，它就可能用一个小型组合保留当前任务需要的来源，同时避免无差别调用其余服务。

在检索前完成这种匹配并不直接。任务文本能够显示路径、标识符、堆栈帧或自然语言描述，却不能揭示这些线索最终会被哪一种服务转化为有用候选。相同的错误词在命名一致的仓库中可能支持精确词法定位，在别名多、生成代码多或跨语言调用密集的仓库中则未必如此。组合价值还取决于服务之间的重复与互补。两个单独表现较好的服务可能返回近似文件，一个单独较弱的结构服务却可能为稠密检索补入唯一的依赖证据。平台因而不能只识别任务类型，再调用该类型平均得分最高的单个检索器。它需要利用检索前可见条件，估计多个可运行组合在统一上下文预算下的任务收益，并把新增收益同本次查询成本比较。

现有 coding 研究主要改变检索来源本身或决定是否启动一次既定检索。Repo-Level Prompt Generator、CoCoMIC 与 DraCo 分别利用仓库示例、静态关系和数据流构造更有效的跨文件上下文（Shrivastava et al. 2023, Ding et al. 2024, Cheng et al. 2024）。RepoGraph 与 LocAgent 进一步让代码图进入仓库导航或多跳定位，但它们的主要对象仍是怎样沿某种结构发现候选（Ouyang et al. 2025, Chen et al. 2025）。Repoformer 学习检索是否会改善补全，从而在可能有害时跳过预定的检索流程，却不在多个异质服务组合之间配置查询（Wu et al. 2024）。这些工作使平台拥有了更丰富的可选服务，也证明固定检索并非总是有益，但没有回答一个已经安装多种服务的平台应怎样在结果尚不可见时，为当前任务挑选成本可接受且彼此互补的服务集合。这个决策不能由某个新检索器的平均准确率替代，也不能由一次二元的“检索或不检索”判断替代。

IS 研究为这项选择提供了两条能够落实到算法的规范。任务—技术匹配理论认为，一项技术只有在其功能与任务要求相符并被实际使用时，才有可能改善绩效（Goodhue and Thompson 1995）。对 coding agent 而言，词法、语义与结构检索不是一般意义上性能高低不同的工具，它们提供的是对不同仓库线索的处理功能。匹配对象因而应是当前任务与仓库共同提出的信息要求，以及一个检索组合能够共同提供的功能。与此同时，案例检索研究表明，信息取得成本需要进入检索策略。即使概念表示已经给定，按照单位成本的预期损失安排信息采集仍能减少无效支出（Mookerjee and Mannino 1997）。这要求本文不能以选中金文件的概率单独定义最佳组合。组合只有在经过统一打包后改善代码任务所需证据或下游行动，并且这种改善足以抵偿服务调用成本时，才具有部署价值。

本文据此提出唯一的研究问题：**在检索结果尚不可见时，怎样依据任务与仓库条件，为 coding agent 选择一个任务收益足以抵偿调用成本的小型检索组合？** 为回答该问题，本文提出任务匹配检索组合器 TMRP。TMRP 先在训练任务上枚举由已安装服务构成的少量可行组合，让每个组合经过相同的候选合并、预算打包和外部评价，得到其可观察任务收益与运行成本。它随后学习任务—仓库特征与组合结果之间的成本敏感次序，而不是预测某个服务独立于其余服务的固定分数。新任务到达时，TMRP 只计算检索前特征，在可行组合中选择预测净收益最高的一项，再把该组合交给原有检索与 agent 流程。整个方法只有一个被检验的核心命题：相对于全调用、固定单服务和选择性启停，学习条件化的组合次序能够以更低或相当的成本保留更有用的仓库证据，并将这种优势传递到固定 agent 的代码行动。

该命题可以在现成的公开环境中直接运行。Agent Retrieval Bench 提供任务查询、冻结提交语料、金文件、词法与 RepoMap 等基线程序，并同时包含四类正检索任务和无金标准的选择性检索任务，适合训练与评价组合决策（Qin and Xie 2026）。ContextBench 进一步公开 66 个仓库、八种语言上的 1,136 个 issue 任务、人工金上下文和自动评价程序，能够检验组合选择是否迁移到更复杂的 issue 定位（Li et al. 2026）。RepoBench v1.1 则提供 Python 与 Java 的跨文件补全数据和官方指标，用于检查任务匹配能否从 issue 检索迁移到已知光标位置的代码补全（Liu et al. 2024）。本文将在每个场地内按仓库分离训练、开发与测试，固定服务版本、候选合并、打包器和下游 agent，只让组合选择发生变化。论文目前不报告任何胜出结果。只有当 TMRP 在未见仓库上改善外部金上下文或代码结果，并在预先规定的成本口径下优于全调用与固定服务，任务匹配检索组合的主张才得到支持。

## 2. 文献综述

### 2.1 仓库检索服务的形成

仓库级代码补全首先使跨文件上下文成为可以独立评价的模型输入。CrossCodeEval 和 RepoBench 构造了只有借助其他文件中的定义或用法才能正确补全的样本，并分别评价检索、补全及二者组成的流水线（Ding et al. 2023, Liu et al. 2024）。围绕这些任务，RepoCoder 用当前生成结果迭代更新相似性查询，Repository-Level Prompt Generator 则从仓库中选择任务特定的提示提案（Zhang et al. 2023, Shrivastava et al. 2023）。后续研究开始把程序结构直接做成检索功能。CoCoMIC 的 CCFinder 根据跨文件实体关系取得项目上下文，DraCo 以扩展数据流构造仓库图并返回依赖实体（Ding et al. 2024, Cheng et al. 2024）。这些研究共同证明仓库信息的来源与组织方式会改变补全结果，也留下了词法相似、生成反馈、静态关系和数据流等性质不同的可调用能力。

Issue 驱动的 coding agent 没有预先给定的补全光标，检索还要承担修改对象定位和影响范围发现。SWE-agent 让模型通过面向软件活动的接口反复查看与搜索仓库，AutoCodeRover 则以类和方法为单位进行程序结构搜索，并在测试可用时引入故障定位（Yang et al. 2024, Zhang et al. 2024）。RepoGraph 把仓库级代码图作为可插接导航，LocAgent 则让 agent 在异构图上执行多跳实体定位（Ouyang et al. 2025, Chen et al. 2025）。随着这些服务进入 agent 流程，ARB 开始直接评价下一步需要的文件，ContextBench 则用人工金上下文观察 agent 已探索和实际使用的代码（Qin and Xie 2026, Li et al. 2026）。这类过程评价使检索失败不再只能从最终补丁反推，也使不同来源的候选收益可以在调用 agent 之前比较。现有 agent 方法仍主要规定怎样使用某一种搜索接口或结构，它们没有把多个已安装服务构成的前置组合本身作为决策输出。

### 2.2 选择性检索与逐实例算法组合

选择性检索已经指出，更多仓库上下文不必然带来更好的代码结果。Repoformer 用自监督信号学习一次跨文件检索是否会改善当前补全，并在预测无益时跳过检索（Wu et al. 2024）。ARB 则把这一判断扩展到自然无金文件任务和错误仓库对照，显示从人工构造负例校准的阈值未必能迁移到真实无金任务（Qin and Xie 2026）。这两项研究说明检索调用应当依赖当前实例，也说明选择规则必须在自然任务分布上验证。它们所控制的行动仍是“执行或跳过一个已经规定的检索流程”。当平台同时提供词法、稠密、仓库地图和代码图服务时，二元启停无法判断该调用哪一种来源，也不能利用两个来源经共同打包后才产生的互补证据。

逐实例算法选择提供了更接近本文问题的成熟范式。该范式利用实例特征，从一组没有恒定赢家的算法中选择预期表现最好者。SATzilla 根据问题特征预测不同 SAT 求解器的表现，ASlib 则把实例特征、算法运行结果和评价协议组织成可复用的选择场景（Xu et al. 2008, Bischl et al. 2016）。AutoFolio 进一步自动配置选择模型及其参数，使选择器可以适应不同问题分布（Lindauer et al. 2017）。这些研究支持本文先在训练任务上取得完整的“任务—配置—结果”矩阵，再从低成本特征学习逐任务决策。传统输出通常是一个求解器，其价值由自身是否求解、得分或运行时间决定。检索服务却可以同时运行，最终价值来自候选合并与预算打包后的共同证据，因而单个服务的性能模型仍不足以表示组合结果。

并行算法组合研究已经进一步考察逐实例选择算法子集。Kashgarani and Kotthoff（2023）直接测量算法并行运行的实际表现，并表明全并行与单算法选择之间仍存在可由子集选择利用的空间。这项工作构成 TMRP 最接近的方法先例，也意味着“选择小型组合”本身不能作为本文的算法贡献。二者的差别在于组合结果怎样形成。并行求解器组合通常由最先完成的成员决定结果，代码检索组合则要把所有成员返回的候选合并、去重并压入同一个上下文预算。新增服务可能补入唯一证据，也可能只增加重复候选、合并成本和预算竞争，其价值必须在共同打包后观察。TMRP 因而把已有的子集选择范式迁移到一种输出需要融合的信息服务，并把学习标签从并行求解时间改为“外部代码证据或行动收益减取得成本”。若这种联合结果表示不能超过直接套用的并行子集选择与通用逐实例选择，本文就不能主张提出了新的检索组合方法。

### 2.3 任务匹配与信息取得成本

任务—技术匹配研究关心技术功能何时能够转化为任务绩效，而不把技术使用本身等同于收益。Goodhue and Thompson（1995）把匹配界定为技术功能对任务要求的支持程度，并指出技术被使用且具有良好匹配时才会产生绩效影响。Dennis et al.（2001）在群体支持系统中进一步区分被选择使用的系统结构与任务需要，发现匹配对决策质量等结果有效性影响更强，而使用支持对时间等过程结果影响更强。该区别对检索组合具有直接意义。词法、稠密和结构服务提供不同的信息处理功能，外部金上下文与代码结果用于判断所选功能是否适合任务，查询时间和候选处理量则描述取得这些功能的过程负担。TMRP 因而不以某项服务被频繁选中来证明其价值，而要检验特定服务结构在何种任务—仓库条件下改善了结果，又付出了何种过程成本。

有成本的信息取得研究进一步规定了这种匹配应当怎样计价。Mookerjee and Mannino（1997）在案例检索中指出，即使检索所依赖的概念已经形成，按信息取得成本安排属性采集仍能减少不必要的支出。Saar-Tsechansky and Provost（2007）则表明，以降低统计误差为目标的信息采集可能不会改善最终决策，决策中心方法应优先取得可能改变行动的信息。迁移到 coding agent 后，一个检索服务即使提高原始候选召回，只要新增证据没有进入预算上下文或没有改变代码行动，为它付出的查询与处理成本仍可能是浪费。反过来，一个平均召回较低的服务若在特定任务中补入唯一金文件或减少 agent 的补偿性搜索，也可能具有较高净价值。因此，TMRP 的监督结果必须在共同打包器之后计算，并以外部证据或下游行动的改善扣除实际取得成本，而不是用检索器自己的相关性分数生成标签。

### 2.4 研究缺口

以上文献留下的是三个相接但尚未闭合的接口。代码检索研究已经提供多种可运行来源，却主要优化每个来源内部怎样发现候选。逐实例算法选择能够学习配置决策，并行组合研究甚至能够选择算法子集，但其常用结果算子不能表示多路候选融合后在有限上下文中的重复、互补与挤出。IS 文献说明技术功能要同任务要求匹配，信息取得又要由成本和行动后果共同计价，却没有把这些关系操作化为 coding agent 的服务选择规则。TMRP 试图闭合的正是这个有限接口：用检索前的任务—仓库条件表示需求，让所有小型服务组合在相同打包与外部评价下产生净收益次序，再学习新任务上的组合选择。它不提出新的底层检索器，也不声称首次研究算法子集。它的增量是否存在，取决于融合后净收益的表示能否在未见仓库上超过选择性检索、通用算法选择和并行子集选择的直接迁移。

## 3. 任务匹配检索组合方法

### 3.1 决策对象与信息边界

设任务 $t=(q,R,s)$ 由任务文本 $q$、冻结仓库 $R$ 和推理时可见信号 $s$ 组成。平台预先安装服务配置集合 $J$，其中一个配置固定其索引版本、查询构造规则、候选单位与返回上限。服务 $j$ 只有被调用后才产生排名候选 $r_j(t)$，因而这些候选不属于组合选择的输入。给定最多同时启用 $m$ 项服务的部署约束，可行组合为

$$
\mathcal P_m(t)=\{p\subseteq J_t: |p|\leq m\},
$$

其中 $J_t$ 只包含能够处理仓库主要语言且索引状态有效的配置，空组合也被保留以处理无需外部检索的任务。TMRP 在观察任何 $r_j(t)$ 之前输出一次 $\pi(t)\in\mathcal P_m(t)$，随后不再调整成员或配额。这样，学习器面对的是一个有限、可枚举且可以实际执行的服务集合决策。底层检索器、融合规则、打包器和 agent 均位于该决策之外并在比较中冻结。

### 3.2 统一的候选融合与预算输出

每个服务返回的文件或代码范围先由共同适配器映射为带冻结提交、路径和起止行的规范候选，完全相同的范围只保留一次。由于词法、稠密和结构分数不在同一量纲，主设定使用倒数排名融合（Cormack et al. 2009）。候选 $c$ 在组合 $p$ 中的融合分数为

$$
h_p(c)=\sum_{j\in p:c\in r_j(t)}\frac{1}{k_0+\operatorname{rank}_j(c)},
$$

其中主设定取 $k_0=60$，未返回 $c$ 的服务不贡献分数。候选按 $h_p(c)$ 降序排列，同分时依次按最优原始名次、仓库路径和起始行排序，再沿该次序装入真实序列化成本不超过 $B$ token 的上下文 $S_B(t,p)$。路径、行号和分隔符都计入预算，候选内容不压缩。所有组合使用同一融合与打包规则，因此新增服务既可能让多路共同命中的候选前移，也可能让只由某一路取得的证据离开有限预算。TMRP 学习的是这种融合后输出的结果，而不是各服务原始榜单分数的平均值。

### 3.3 检索前的任务—仓库表示

任务特征只从 $q$ 与 $s$ 中确定性抽取。表示首先记录任务长度、代码块占比以及自然语言词与代码形态词的比例，用于区分叙述性需求和代码信号密集的请求。它随后统计显式文件路径、标识符、错误类型、堆栈帧、测试名称与命令，并计算其中能够在冻结仓库路径表和符号表中精确解析的比例。任务词在仓库文件名与符号词典中的逆文档频率均值和上分位数用于描述字面线索的稀有程度。已知编辑位置、评审文件和补全光标若由 benchmark 输入直接提供，也作为二元信号保留。上述特征均可在调用候选服务以前由轻量元数据取得，不运行稠密编码、图遍历或 agent。参考补丁、金上下文、完成后测试和任何服务返回的排名都不进入表示。

仓库特征用于说明相同任务信号为何会对应不同的信息需求。本文记录文件数与代码 token 数的对数、语言构成、平均路径深度、标识符重名率，以及测试、配置和构建文件占比。若平台已经为所有方法共同建立轻量符号关系表，则再记录导入与引用边密度和连通分量比例，其一次性构建时间与存储量单列报告。仓库名称、组织名称、提交哈希和可直接识别项目身份的文本不进入模型。对组合 $p$，表示 $z_p$ 包含服务成员、成员数量、成对共现和基于训练仓库估计的服务成本档位。最终排序输入为

$$
\phi(t,p)=[x_t,x_R,z_p,(x_t\oplus x_R)\otimes z_p],
$$

其中 $x_t$ 和 $x_R$ 分别是任务与仓库向量，$\oplus$ 表示拼接，最后一项使同一服务成员能够在不同任务—仓库条件下获得不同作用。成对共现允许模型区分两个来源的联合结果与各自独立效果。该表示不预先规定“堆栈必须选图”或“自然语言必须选稠密检索”，这些条件关系只能从训练仓库的外部结果中学习。

### 3.4 离线组合结果与净效用

对训练任务集合 $D_{\mathrm{tr}}$，本文先在固定硬件与容器中单独运行每项可用服务，并保存规范候选、CPU 时间、加速器时间、峰值内存和端到端查询延迟。服务版本、索引、解码参数和随机种子均被冻结，不能在固定种子下复现候选的服务不进入主目录，只进入重复运行的稳健性分析。候选输出由任务、提交和配置内容寻址，因而每项主目录服务只需执行一次，所有 $p\in\mathcal P_m(t)$ 的融合上下文都可按第 3.2 节从缓存榜单确定性重建。融合与打包时间依据各组合的实际候选量另行测量。若生产编排器并行调用服务，本文还对开发与测试中的实际选中组合重复运行三次，报告并行墙钟延迟，避免把孤立运行的最大值误当成无争用的真实响应时间。测试任务上可以在选择完成后运行其余组合以计算离线 oracle 与后悔值，但这些结果不允许回流到 TMRP 的特征、参数或当次选择。

组合 $p$ 对任务 $t$ 的质量 $Q_{tp}\in[0,1]$ 由融合榜单及其预算输出 $S_B(t,p)$ 接受 benchmark 外部评价。ARB 使用预算内文件集合相对于金文件集合的 F1，并约定预测与金集合同时为空时得 1、仅一方为空时得 0，官方 BCY@8k 与 selective success 另行报告。ContextBench 使用官方区间求交程序计算的字节加权 span F1，RepoBench-R 使用官方 Accuracy@1，RepoBench v1.1 的固定补全模型 Exact Match 和 Edit Similarity 只用于检验选择结果能否传递到代码产出。不同 benchmark 各自训练和评价选择器，$Q_{tp}$ 不跨场地混合。设 $T^{\mathrm{cpu}}_{tp}$、$T^{\mathrm{acc}}_{tp}$ 和 $T^{\mathrm{pack}}_{tp}$ 分别为组合实际消耗的 CPU、加速器和融合打包时间，令 $\omega$ 为实验硬件在冻结价格表中的加速器与 CPU 时价比，则查询资源成本及其归一化值为

$$
C_{tp}=T^{\mathrm{cpu}}_{tp}+\omega T^{\mathrm{acc}}_{tp}+T^{\mathrm{pack}}_{tp},\qquad
c_{tp}=\frac{C_{tp}}{C_{tJ_t}},
$$

其中 $C_{tJ_t}$ 是同一任务调用全部可用服务的成本。训练组合的净效用为 $U_{tp}(\lambda)=Q_{tp}-\lambda c_{tp}$。主实验预先给定平均成本上限 $\beta$，在开发仓库上从 $\{0,0.01,0.02,0.05,0.1,0.2,0.5,1\}$ 的冻结网格选择满足该上限且平均质量最高的 $\lambda$，并报告全部 $\lambda$ 的质量—成本前沿。峰值内存、索引构建与存储、三次并行墙钟延迟不并入该标量，而是分别报告并作为超限时的可行性约束。这样，$U_{tp}$ 只负责在同一场地内给组合排序，不被解释为能够跨数据集比较的通用价值。

### 3.5 成本敏感的组合排序

对给定的 $\lambda$，同一训练任务中满足 $U_{tp}>U_{tq}+\epsilon$ 的组合对形成偏好 $p\succ_t q$，效用差不超过预设容差 $\epsilon$ 的近似平局不参与学习。TMRP 以 $g_\theta(t,p)=\theta^\top\phi(t,p)$ 给组合打分，并最小化

$$
\mathcal L(\theta)=\sum_{t\in D_{\mathrm{tr}}}\sum_{p\succ_t q}w_{tpq}
\log\!\left[1+\exp\!\left(-(g_\theta(t,p)-g_\theta(t,q))\right)\right]
+\rho\lVert\theta\rVert_2^2,
$$

其中 $w_{tpq}=(U_{tp}-U_{tq})/\sum_{a\succ_t b}(U_{ta}-U_{tb})$，使每个任务的总权重相同，同时让效用差较大的错误次序受到更强惩罚。若某任务没有非平局组合对，它不进入当前 $\lambda$ 的排序损失。连续特征的标准化参数、$\epsilon$ 和正则系数 $\rho$ 只由训练仓库与内部交叉验证确定。每个冻结的 $\lambda$ 独立拟合一个排序器，开发仓库仅用于按第 3.4 节的成本上限选择最终 $\lambda$ 及其模型。线性打分是主设定，因为第 3.3 节已显式构造任务—仓库与服务成员交互，且系数可以直接审计。使用同一输入的 LambdaMART 仅作为非线性稳健性比较，不替换主方法。新任务上不需要取得任何组合结果，TMRP 计算所有 $p\in\mathcal P_m(t)$ 的 $g_\theta(t,p)$ 并选择分数最高者，空组合与其他组合在同一个排序中竞争。

### 3.6 固定服务目录与执行规模

主目录包含四项能够在本地复现且归纳偏置不同的固定配置：基于路径、标识符和代码词项精确匹配的 Lexical，基于共同代码块语料的 BM25，使用冻结 Qwen3-Embedding-8B 检查点的稠密检索（Zhang et al. 2025），以及由冻结仓库符号结构生成候选的 aider-style RepoMap。ARB 直接调用其官方实现、全文件候选过滤和发布的查询格式。ContextBench 与 RepoBench 只增加输入输出适配器，把各自公开任务字段转成同一服务的查询，并把返回对象映射为官方 evaluator 接受的区间或片段，不改变服务内部评分。适配器只读取任务推理时公开字段，金上下文、参考补全和参考补丁仅由评价器加载。所有排名服务的检查点修订、分词器、代码块边界和查询模板在训练前固定，主返回上限统一为 $K=100$，RepoMap 使用 ARB 官方基线的结构限额。需要单独付费的闭源 API 和尚未发布稳定代码的预印本检索器不进入主目录。RepoGraph 仅在其受支持语言子集上作为附加结构服务复测，不能替代四项主配置或改变主结论。

主设定取 $m=2$。当四项服务均可用时，含空组合在内只需评分 $1+4+\binom{4}{2}=11$ 个行动。离线构造结果矩阵并不运行 11 套检索，每个任务最多运行四项服务一次，其余操作只是从缓存榜单重建 11 个融合输出并调用确定性评价器。上线时，系统依次抽取任务—仓库特征、枚举可行组合、计算排序分数、并行调用被选服务，再按第 3.2 节融合和打包。每次决策保存输入特征版本、全部组合分数、选中成员、候选内容哈希、各阶段时间和最终预算输出，以便重放选择与定位成本偏差。$m=1$、3 和 4 只用于敏感性分析，其中 $m=1$ 退化为带空动作的单服务选择，$m=4$ 包含全调用。四服务目录下的最大枚举规模为 16，因此本研究的计算负担来自真实检索和外部评价，而不是组合搜索本身。

## 4. 经验评价

### 4.1 数据场地与仓库分离

ARB 是主开发场地。本文下载并锁定 `v2_code2test`、`v2_comment2context`、`v2_trace2code`、`v2_edit2ripple` 和 `v2_abstention` 五个发布包，在运行前用官方校验器检查样本、语料清单和校验和。当前发布说明包含 427 项任务、25 个仓库、六种主要语言和 271 个被样本实际引用的仓库—基准提交快照，其中 345 项为正检索任务、50 项为有维护者证据的自然无金任务、32 项为错配仓库的反事实对照。主模型由 345 项正例与 50 项自然无金任务构成，反事实对照只用于检验组合器是否利用了过于容易的仓库错配信号。25 个仓库被预先分为五个互斥折，每次使用三折训练、一折开发和一折测试，并轮换测试折，使同一仓库及其所有提交快照始终只出现在一个角色中。论文同时报告各工作流、各仓库宏平均与五个测试折合并结果。若实际下载清单与论文或网页总数不一致，本文以通过校验的冻结清单为运行对象，并在复现附录列出差异，不用文字中的预期总数替代数据核验。

ContextBench 构成独立的 issue 检索场地。其公开完整集现含 66 个仓库、八种编程语言上的 1,136 项 issue 任务，并提供人工标注金文件、金符号与金区间，另有 500 项 verified 子集。本文锁定 Hugging Face 数据修订和 ContextBench evaluator 提交，按数据中的仓库地址与基准提交检出代码，再在任何服务运行前完成可获取性检查。静态组合评价把 $S_B(t,p)$ 映射为 evaluator 的规范区间集合，直接调用官方 `coverage_precision` 与区间求交函数计算 precision、recall 和 F1，不把一次预置上下文读取伪装成 agent 的 explored 或 utilized trajectory。完整集用于五折仓库分离的组合学习与静态检索评价，verified 子集用于固定 agent 的后续行动检验，此时才由官方抽取器处理完整 agent 轨迹。无法检出提交、解析语言或通过数据校验的任务按预先公布的失败规则在所有方法运行前统一移除，并报告仓库、语言和原因。五折划分在仓库互斥的前提下平衡语言与数据来源，不与 ARB 合并训练，使 ContextBench 能检验方法在更长 issue 描述和多粒度金上下文上的独立成立性，而不是重复主场地的样本。

RepoBench 只承担候选空间受限时的边界检验。公开的 RepoBench-R 含 192,000 项 Python 与 Java 样本，覆盖 cross-file-first、cross-file-random 及难度划分，并为每项样本给出当前文件信息、候选代码片段和金片段索引。由于这些候选由数据集预先构造，它能够检验 TMRP 是否在不同补全信号下选择合适的重排服务，却不能证明组合器完成了真实全仓库定位。本文锁定 `tianyang/repobench-r` 数据修订，重新按 `repo_name` 建立五个互斥折，并以官方 Accuracy@1 和 Accuracy@3 评价 Lexical、BM25 与 Qwen3-Embedding-8B 三服务目录。RepoMap 因缺少可验证的完整仓库结构而从该场地的 $J_t$ 中移除，不以候选列表臆造关系图。RepoBench v1.1 的 Python 与 Java 公开集仅用于附加的代码补全传递实验：本文按所选组合重排数据中已有的跨文件片段，固定补全模型与提示，再调用官方脚本报告 Exact Match、Edit Similarity 和 CodeBLEU。两项 RepoBench 分析单独成表，且不与 ARB 或 ContextBench 的全仓库结果平均。

### 4.2 比较方法

第一组比较建立不含学习或不含任务匹配的参照。它包括空组合、每个单项服务、由开发仓库确定的全局最佳单服务、全局最佳双服务组合、所有可用服务全调用，以及在相同组合大小分布下随机抽取成员的策略。所有非空组合均经过同一个 RRF、稳定排序和 token 打包器，不能使用各自有利的融合规则。全局最佳配置按开发集平均净效用选择，测试集上不重新确定。随机策略以 1,000 个冻结种子运行，报告均值与 95% 分位区间。测试任务结果全部可见后取得的最高净效用组合另记为 oracle，用于计算 TMRP 的组合选择后悔值，但不作为可以部署的方法。该组比较分别回答不检索、只用一个固定来源、长期使用一个固定混合来源、调用全部来源和随机增加来源时会发生什么。

第二组比较检验 TMRP 是否超过已有选择范式的直接迁移。二元选择器使用相同的任务—仓库特征，只在空组合与开发集最佳单服务之间选择，对应选择性检索的“取或不取”。单服务选择器为每项服务拟合独立的随机森林净效用模型并选择预测值最高者，对应经典逐实例算法选择。Top-2 选择器取这组独立模型预测值最高的两项服务，用来检验简单成员排名是否已经足够。AutoFolio-combination 把每个可行组合视为一项候选算法，把训练仓库的完整组合结果矩阵交给 AutoFolio 配置选择流程，是通用算法选择对本文行动空间的直接应用。APPS 迁移则依照 Kashgarani and Kotthoff（2023），由随机森林分别预测各单服务的损失 $-U$ 及其 jackknife 不确定性，再以服务预测分布同最低预测损失服务分布的重叠概率决定是否纳入组合，重叠阈值在开发仓库选择并受 $m$ 限制。上述方法使用相同输入特征、外层仓库折、服务目录、融合器和成本上限。TMRP 只有同时超过 AutoFolio-combination 与 APPS 迁移，才能把优势归因于融合后组合结果及任务—成员交互，而不是一般意义上的实例选择或不确定性驱动的并行子集选择。

### 4.3 结果指标与检验规则

主结果表把结果有效性与取得过程分开。ARB 首先报告组合学习所用的预算文件 F1，同时报告官方 MRR、Recall@20、BCY@8k，并把 natural-only 与包含反事实对照的 mixed selective success@20 分开。ContextBench 报告文件、符号与 span 层次的 precision、recall 和 F1，主质量列为字节加权 span F1。RepoBench-R 报告 Accuracy@1 和 Accuracy@3，v1.1 的附加补全实验报告 Exact Match、Edit Similarity 和 CodeBLEU。过程指标包括相对全调用的查询资源成本 $c_{tp}$、实际并行墙钟延迟的中位数和第 95 百分位、峰值 CPU 与加速器内存、索引构建时间与存储，以及进入 agent 的真实 token 数。选择诊断另行报告平均组合大小、各服务及服务对的选择率、空组合的正负例混淆矩阵和相对 oracle 的平均后悔值。固定 agent 实验还报告测试通过或 benchmark 官方解决率、后续搜索调用数、检索 token 与总运行成本，但这些下游结果不反向参与组合器训练。

主检验以仓库而非任务为独立单位。对每项方法差，本文进行 10,000 次分层 bootstrap，先有放回抽取测试仓库，再在所抽仓库内抽取任务，以形成质量、成本、净效用和后悔值差异的 95% 置信区间。相对于全调用，TMRP 只有在主质量差异下界高于预注册的非劣界 $-0.01$，且相对成本差异上界低于 0 时，才被视为以更少资源保留质量。相对于 AutoFolio-combination 与 APPS 迁移，主检验使用仓库均值上的配对置换检验比较净效用，并对两个场地共四项优势检验作 Holm 校正。ARB 与 ContextBench 分别检验且分别报告，只有两处都满足质量非劣、成本降低和对两个近邻的净效用优势，论文才支持跨 issue 检索场地的主张。RepoBench 的结果只判断候选受限边界是否一致，不用于挽救主场地上的失败。所有阈值、折分配、检验方向与主比较在读取外层测试结果前登记，探索性切片均标为事后分析。

### 4.4 消融、敏感性与选择解释

消融实验逐项移除 TMRP 主张中的必要对象。去掉 $x_t$ 检验任务信号，去掉 $x_R$ 检验仓库条件，去掉交互项与服务对共现检验成员是否只需可加表示。将 $U_{tp}$ 替换为成员单独运行净效用之和，检验是否必须观察融合后组合结果。设 $\lambda=0$ 且不施加平均成本上限，检验质量优先选择能否自然控制资源，移除空组合则检验无检索行动对自然无金任务的作用。每个变体保留相同仓库折、服务输出、融合器和调参预算，只改变所声明的一项设计，并同时报告主质量、资源成本、净效用与组合分布。只有移除相应对象后在预期任务条件下出现稳定损失，正文才能把该对象解释为有效设计，而不能根据线性系数的正负直接声称因果作用。

敏感性分析改变部署约束而不重新定义方法。主设定为 $B=8$K token、$m=2$ 和平均相对成本上限 $\beta=0.5$，并分别在 $B\in\{4\mathrm K,16\mathrm K,32\mathrm K\}$、$m\in\{1,3,4\}$ 与 $\beta\in\{0.25,0.75\}$ 下重跑完整外层评价。融合与成本参数分别取 $k_0\in\{10,100\}$、$K\in\{50,200\}$ 和 $\omega$ 的主值乘以 0.5 或 1.5，用来检查候选深度与成本换算是否改变组合次序。模型方面以 LambdaMART 复测线性排序器，以 Qwen3-Embedding-4B 替换 8B 检查点，并在支持语言子集加入 RepoGraph。每项分析沿用原仓库折且单独报告，不能从多个参数组合中挑选最优测试结果替代主设定。若结论只在一种预算、一个价格比或单个稠密检查点上成立，论文应把它写成适用条件而不是稳健的任务匹配规律。

选择解释围绕预先定义的任务—仓库条件展开。本文按显式路径或标识符可解析率、自然语言与代码词比例、堆栈或已知编辑位置、仓库标识符重名率、仓库规模和语言形成切片，在每个切片中同时展示成员选择率、相对最佳单服务的实现质量增量和相对全调用的成本变化。标准化线性系数及其跨外层折稳定性只用于说明模型依赖了哪些输入，不作为任务特征导致服务有效的因果证据。实例分析按确定规则选择四项测试任务：与 oracle 一致且相对全调用节省最多的任务、服务对质量超过两个成员各自质量至少 $\epsilon$ 的互补任务、正确选择空组合的自然无金任务，以及净效用后悔值最大的失败任务。每个实例依次呈现输入线索、仓库条件、全部组合的预测分数与事后实现净效用、选中服务、融合前后候选位置、预算内金上下文、资源成本和固定 agent 后续行动。这样的解释用实现后的结果检查任务—技术匹配与信息取得成本是否同时出现，而不是从服务名称反推一个必然成立的故事。

### 4.5 执行与复现协议

全部实验在版本化容器中运行，并在结果表旁记录处理器、加速器、内存、驱动、检索代码提交、模型权重提交和数据修订。每个仓库的词法索引、BM25 语料、稠密向量和 RepoMap 只构建一次，构建产物按仓库—提交—配置哈希寻址，主查询成本不重复计入构建时间，但另按 100、1,000 和 10,000 次查询规模报告摊销成本。RepoBench-R 的候选片段向量按内容哈希跨样本缓存，查询向量仍逐任务生成，以使 192,000 项候选重排能够在单个研究集群上完成。ContextBench verified 的下游实验固定 mini-SWE-agent 提交与 `Qwen/Qwen3-Coder-30B-A3B-Instruct` 权重修订，使用 temperature 0.2、top-p 0.95、相同初始提示、50 步上限和同一容器测试环境，只替换 TMRP、全调用、最佳单服务、AutoFolio-combination 与 APPS 提供的初始上下文。全部 500 项 verified 任务以冻结种子 0 各运行一次，另按仓库与语言预先抽取 100 项任务用种子 1、2 和 3 重复，以估计 agent 运行波动。RepoBench v1.1 使用冻结的 `Qwen/Qwen2.5-Coder-7B` 基座权重和 greedy decoding 完成下一行。配置文件、折清单、候选缓存清单、逐任务轨迹、评价输出和失败日志全部保留，下载完成后的主实验禁用网络访问。

## 5. 讨论与预期贡献

实证结果首先决定本文能提出多强的主张。若 TMRP 在 ARB 与 ContextBench 上都以低于全调用的资源成本保持主质量，并且净效用同时超过 AutoFolio-combination 与 APPS 迁移，结果才支持“融合信息服务需要学习任务条件下的组合结果”这一核心判断。若它只超过全调用和固定服务，却不能超过两个选择近邻，实践上仍可说明检索裁剪有用，方法贡献则应收缩为已有算法选择在 coding 检索中的应用。若静态金上下文改善没有传递到固定 agent 的解决率、补偿性搜索或总成本，本文只能主张改进了上游证据取得，不能把它写成代码行动改进。若优势只出现在 ARB 而不出现在 ContextBench，任务匹配只能限定于结构化工作流信号，不能推广到一般 issue。若 RepoBench 候选重排成立而两个全仓库场地失败，结果更不能反向挽救主张。若质量非劣、成本降低和近邻优势均不满足，TMRP 就是一项被公开 benchmark 否证的设计。

在完整主条件得到支持时，本文对任务—技术匹配研究的增量是把匹配对象从单项技术扩展为受共同输出约束的信息服务结构。对 coding agent 而言，一项服务的功能价值不仅随任务线索和仓库组织变化，还会因共同调用的成员、RRF 次序和固定上下文预算而改变。因而“稠密检索适合自然语言任务”这类单项对应不足以决定部署，真正被检验的是任务—仓库要求同一个可执行组合的联合输出是否匹配。金上下文与代码行动评价这种匹配的结果有效性，查询资源、延迟和后续补偿性搜索评价取得过程，两者对应 Dennis et al.（2001）区分的结果与过程后果。空组合又使技术使用本身成为可比较行动，避免把更多使用预设为更好匹配。TMRP 对这一关系的贡献不是提出新的普遍匹配理论，而是提供一个组合可枚举、结果可观察、成本可实测的计算化检验。它的理论边界是多个服务结果必须经过共同融合并竞争同一输出预算，不能直接推广到彼此独立完成任务的工具集合。

本文对有成本信息取得与算法选择的连接也建立在融合结果上。Mookerjee and Mannino（1997）把检索属性的取得顺序同成本联系起来，Saar-Tsechansky and Provost（2007）要求信息价值由行动后果判断，TMRP 则把这两项规范落实为检索前的来源集合决策。训练标签不奖励某服务返回较高的内部相关性分数，而是观察多路候选共同打包以后留下了什么外部证据以及为此实际消耗多少资源，固定 agent 与补全实验再检验这种差异能否传递到代码结果。相对于经典单算法选择，本文允许多个来源共同提供信息。相对于 APPS，并行成员不以最快求解器独立完成任务，所有输出必须合并，新增成员可能贡献唯一证据，也可能制造重复并挤出已有证据。任务—成员交互和融合后净效用正是对这一结果算子的表示，而不是对子集选择名称的重新包装。只有它们相对 APPS 直接迁移带来未见仓库优势时，本文才为信息服务组合提供了新的算法选择工具，否则贡献应停留在成本敏感选择的场景应用。

对 coding-agent 平台维护者而言，TMRP 的用途是把“默认调用哪些检索服务”变成能够按任务审计的部署决策。质量—成本前沿可以帮助团队依据实际查询量和硬件预算选择 $\beta$，而不是长期沿用一个未经验证的全调用策略。逐任务日志还能分离四种问题：选中组合远离 oracle 属于组合器失配，所有成员都未产生金证据属于底层服务覆盖不足，成员榜单含有证据但预算输出丢失属于融合或打包失败，正确证据已经交付却未形成补丁则属于 agent 阅读、编辑或验证失败。服务选择率与实际成本偏差还可以暴露稠密索引或结构服务在特定语言上的维护负担。当平台只有一个服务、全调用成本可以忽略、任务分布高度单一或仓库元数据无法稳定抽取时，TMRP 没有足够的选择空间，应回退到固定服务。新语言、服务版本或仓库组织进入以后，平台也应先监测特征分布和选择后成本，再用新结果重训，而不能把旧组合规则当作永久配置。

本文有六项直接限制。第一，四服务目录覆盖词法、概率、稠密和仓库结构，但不代表所有 coding 检索器，CodeGrep、RANGER 和 GraphCodeAgent 等新方法只有在稳定代码与兼容数据发布后才能纳入复测（Chen et al. 2026, Shah et al. 2025, Li et al. 2025）。第二，TMRP 只在第一次检索前选择一次组合，不能依据 agent 已读内容、测试反馈或剩余预算改变服务，因而不回答动态搜索与停止问题。第三，训练阶段需要得到每项服务的完整输出，再重建所有小型组合，四服务且 $m=2$ 时可承受，服务目录扩大后仍会受到候选生成和外部评价成本约束。第四，轻量任务—仓库特征有意排除检索榜单与项目身份，减少泄漏的同时也可能遗漏需要语义编码或运行时分析才能识别的匹配条件。第五，$\omega$、索引摊销和并行延迟来自固定硬件与价格时点，生产环境的并发、缓存命中和服务定价会改变成本次序。第六，ARB 与 ContextBench 的金上下文可能遗漏替代证据，RepoBench-R 又使用预构造候选，单一 mini-SWE-agent 与开放权重模型的下游结果也不能代表所有 coding agent。更根本地说，本文仍是等待真实运行的研究设计，任何理论、方法和实践贡献都必须在公开配置上通过预注册检验后才能改写为结果性陈述。

## 6. 结论

拥有多项检索服务的 coding-agent 平台不只面对“是否检索”，还要在结果尚不可见时决定本次任务值得调用哪些信息来源。本文把这一问题界定为任务匹配检索组合，并提出 TMRP，用推理前可见的任务—仓库条件给小型服务组合排序，排序标签来自统一融合与预算打包后的外部证据质量减实际查询成本。该设计不改变底层检索器，也不在运行中继续调节配额，因此可以把组合选择同检索发现、候选打包和 agent 行动分开评价。ARB 与 ContextBench 提供两个可下载、可按仓库隔离的全仓库场地，RepoBench 提供候选受限与代码补全的边界检查，AutoFolio 和 APPS 则给出不能回避的直接选择基线。只有真实运行同时显示质量不劣于全调用、资源成本更低、净效用超过两个近邻，并在固定 agent 上产生可观察的过程或代码后果，本文才会把 TMRP 解释为融合信息服务的任务—技术匹配与成本敏感选择方法。在此之前，它是一套服务目录、数据、算法、比较对象与否证条件均已明确的可执行研究设计。
