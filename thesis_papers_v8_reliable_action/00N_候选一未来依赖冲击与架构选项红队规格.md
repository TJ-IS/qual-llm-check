## 0. 判定状态与证据边界

本文档最初记录替换原候选一的预冻结方案。两轮独立审计后的最终判定是 **NO-GO / REMOVED FROM SERIES**。两时点工程构想可以保留为 benchmark 或数据基础设施设想，但 component-granularity 路线存在构念错置，Schober 救援路线又没有通用 two-stage POMDP 无法复制的计算责任。只有将来出现实质不同的新理论机制和新行动问题，才可作为新候选从零送审，不能从本方案直接恢复。

截至 2026 年 8 月 15 日，本文档没有本研究的实验结果。文中出现的样本规模、计算量和效应方向均为 pilot 目标、设计约束或理论预期，不是已观察事实。任何结果表、效应量和显著性均须在真实实验完成后另行填写。

暂定题目为：

> 面向未来依赖冲击的安全可演化 coding agent：在当前实现中创建并行使架构选项

核心研究问题是：当 coding agent 在当前任务中引入或深度使用外部软件包时，如何在不知道具体未来冲击的条件下，联合决定当前功能实现与依赖边界，使系统既不过度支付抽象和验证成本，又能在未来安全或兼容性冲击发生后迅速升级、替换、隔离、降级或移除该依赖？

该问题与另外两个候选的责任边界不同。它研究系统与外部软件生态之间的依赖以及跨时间可靠行动。候选二研究异质 coding-agent 团队的知识协调。候选三研究升级后人类参与的可信取证。本文不以团队知识分配或真人审核为主要机制，也不以请求确认作为核心动作。

## 1. 风险、行动者与两时点决策

### 1.1 真实损害

研究中的潜在损害不是抽象的“维护性下降”，而是外部依赖冲击造成的可执行后果：

- 已披露漏洞在可达调用路径中继续暴露；
- 恶意、撤回或弃维版本无法被及时隔离或替换；
- 紧急升级或替换破坏功能、安全属性、数据约束或部署可用性；
- 依赖调用散布和架构耦合使修复范围扩大，延长 time-to-safe-remediation；
- 为追求所谓灵活性而生成过量抽象、接口和测试代码，反而增加当前缺陷、攻击面与验证负担。

主要安全结果至少包括可达漏洞暴露时长、限定时限内的安全修复成功率、修复后的安全与功能回归、冲击期间不可用时间、受影响调用面以及不可恢复失败。任务成功率、当前开发成本、人工介入、推断成本和额外代码量必须同时报告。安全改善不能由拒绝所有依赖或停止完成任务取得。

### 1.2 Coding agent 的行动时点

每个研究实例包含两个严格分离的时点。

在 \(t_0\)，coding agent 接收功能 issue、仓库快照、源码、manifest 与 lockfile，以及当时可获得的包、版本和维护信息。它必须实际完成当前功能，并在代码中选择依赖使用方式。其动作包括直接集成、创建 provider-neutral component、限制依赖能力、进程或权限隔离、实现可验证降级路径、建立契约测试，或在当前收益不足时不创建这些结构。

在 \(t_1\)，先前对 agent 隐藏的真实生态冲击被揭示，例如 CVE 披露、恶意或撤回版本、维护终止、破坏性版本变化或可替代包迁移需求。agent 接收此时才合法可见的信息，实际生成升级、替换、隔离、禁用或移除补丁，并运行验证。\(t_0\) 的边界设计和 \(t_1\) 的 option exercise 都是代码与工具动作，不是建议文本或风险分数。

### 1.3 为什么不是普通包选择或事后迁移

当前包选择只问此刻哪个包或版本更合适。事后迁移只问冲击已经发生后如何修补。本文研究的是一个跨时间的联合行动：agent 是否应在当前任务中支付可测量的 option premium，以及该结构在真实未来冲击中能否被行使。若实验最终只剩安全版本排序、CVE 评分、迁移补丁生成或固定 wrapper 规则，应立即撤题。

## 3. Subramanyam 理论的原义与迁移边界

### 3.1 原文事实

主理论来源为 Subramanyam, Ramasubbu, and Krishnan (2012), “In Search of Efficient Flexibility: Effects of Software Component Granularity on Development Effort, Defects, and Customization Effort,” *Information Systems Research*, 23(3), 787–803, DOI 10.1287/isre.1110.0392。本地全文为 `database_fulltext_all/00462_2012_in-search-of-efficient-flexibility-effects-of-software-component-granularity-on-development-effo.md`。

原研究考察一家企业软件公司的 model-driven, component-based development，分析 92 个 ERP business components。其研究单位是可部署和定制的软件组件，不是开源包、供应商或 coding agent。原文将 component granularity 概念化为 code volume、functionality 和 independence 三个设计子维度，并在具体场景中以 data elements、data-layer interfaces 和 internal interfaces 操作化。后面三个指标是该企业和方法情境中的测量，不可原样移植成通用依赖边界指标。

原研究建立的机制不是“模块化总是更好”。较粗粒度组件覆盖更大功能范围、包含更多逻辑路径并追求更高平台独立性，因而需要更多当前开发 effort，且更易产生 in-process defects。与此同时，它们在异质客户环境中可更多使用 black-box customization，因而降低 downstream customization effort。缺陷又会增加当前开发 effort 和下游 customization effort，形成部分中介。边际分析显示存在场景特定阈值；超过阈值后，新增粒度不再带来净灵活性收益。原文报告的 1–154 个 data elements 和 0–4 个 data-layer interfaces 只适用于该样本，本文不得硬编码或宣称可迁移。

因此，理论迁移必须经过三个构念检验。第一，dependency boundary 是否构成 component boundary 的合法实例。第二，新情境中的 volume、functional breadth 和 independence 是否能由代码结构和执行证据可靠测量。第三，当前缺陷与未来 remediation/customization 是否呈现相互冲突且可能反转的关系。三项中任一失败，理论迁移即不成立。

### 3.2 Supporting lens 的有限责任

Schober and Gebauer (2011), “How Much to Spend on Flexibility? Determining the Value of Information System Flexibility,” *Decision Support Systems*, DOI 10.1016/j.dss.2011.03.004，将 flexibility-to-change 界定为系统初始化时为未来修改或升级支付的附加投资，并区分初始 premium 与未来 exercise cost。原文比较确定性估值、decision-tree analysis、real-options analysis 和风险模拟，指出忽略不确定性可能低估灵活性，而 ROA 在低风险情境可能高估其价值。

该理论只负责规定两时点、初始 premium、未来 exercise 和风险分布不能被压成确定性成本。它不单独产生本文的主要算法贡献。若实现只是给通用 agent 的候选补丁加一个“option value”辅助分数，理论责任失败。real options 必须通过可行 exercise path、未来状态转移和 t0/t1 联合行动进入前向计算；主要的结构化中间状态和方向冲突仍由 component granularity 的效率—灵活性机制产生。

| 第 160–185 行以 \(F-E\) 形成 fragment disconfirmation，再聚合 cumulative satisfaction。 | 理论规定差值、符号和聚合顺序。 | policy 先比较当前 premium 与各 shock 下可行 exercise 的后果，再形成风险敏感 t0 动作；不得先汇总后解释。 |
| 第 187 行承认 \(E,F\) 无直接标签，转而使用实际 response 与理论因果方向监督。 | 缺少中间标签并不允许自我标注，而要寻找可观测外部监督。 | option value 没有人工真值，因此以同一 repo/task/shock 下的随机化 counterfactual rollout、build/test/trace 和真实 advisory 时间提供监督，禁止 LLM-as-judge 充当主标签。 |
| 第 189–195 行让 response label 改变 contrastive direction，并以 attribute/fragment sparsity 处理局部反例。 | 标签改变损失方向，理论允许局部状态与终局不完全一致。 | pairwise loss 必须在当前任务等价时，按真实未来损害改变 t0 边界排序；单一局部 shock 不得强迫所有边界维度同向。 |
| 第 199–219 行把理论生成的 \(E,F\) 继续输入 LSTM prediction，并将 cumulative satisfaction 与 black-box prediction共同优化。 | 理论状态进入最终预测，而非训练后解释。 | \(G,D^0,R^1,X^1\) 必须同时条件化 action policy 和 patch decoder；real-option state 不得只在最终 logits 上加一个手工分。 |
| 第 221–227 行把预测损失、理论差值和中间状态约束放在同一端到端目标中。 | 终局与机制证据共享训练责任。 | 当前执行、未来 exercise、反事实排序、shape、mediator 和代码生成损失需联合训练，并分别消融。 |

DSDL 给本候选的最重要约束是“中间状态不可被末端分数替代”。本候选若没有直接标签，可以像 DSDL 一样使用外部结果和理论方向形成训练信号，但不能把模型自评当作状态真值。real options 只能在以下条件下进入算法：模型显式表示可行 exercise action；不同 shock 下的 action-state transition 经真实执行监督；t0 decoder 在生成边界代码时能 cross-attend 到这些 exercise paths；删除这些状态会改变 t0 架构和 t1 修复行为。仅有 \(V_{option}\) 标量加权不满足肖老师论文的理论—算法标准。

## 5. 两时点数据构造

### 5.1 实例定义

一个实例定义为

\[
\mathcal I=(R_{t_0},q_{t_0},K_{t_0},\{b_j\}_{j=1}^{J},s_{t_1},K_{t_1},\{o_a\}_{a=1}^{A},Y),
\]

其中 \(R_{t_0}\) 是仓库快照，\(q_{t_0}\) 是当前功能任务，\(K_{t_0}\) 是严格按时间截断的生态知识，\(b_j\) 是经当前测试验证的候选边界实现，\(s_{t_1}\) 是隐藏的真实冲击，\(K_{t_1}\) 是冲击发生后才可见的信息，\(o_a\) 是 t1 可执行动作，\(Y\) 是执行结果。研究单位不是单个包，也不是一段补丁，而是同一当前任务、同一未来冲击下的一组可比设计及其后果。

### 5.2 数据源及用途

- BUMP 提供稳定、Docker 化的 Java breaking-update 冲击和前后构建命令。公开仓库为 <https://github.com/chains-project/bump>。完整镜像约需 250GB，不能在尚未下载复放前声称全部可用。
- PyMigBench 提供真实替代包迁移及其代码变更。需逐仓库恢复 pre-migration state、测试和许可证，不能只使用标注表。
- OSV 与 GitHub Security Advisory 提供披露时间、受影响版本和修复版本。\(t_0\) 输入只能使用披露日前存在的信息，不能从当前数据库页面反推未来。
- AIDev-pop/DepDec 轨迹用于识别 coding agent 实际增加、删除和更新依赖的任务形态，并可作为外部行为测试；它不直接提供 counterfactual architecture 标签。
- SWE-Chain 可补充连续维护与累积回归压力。MigrationBench、MigrationMiner、CORAL 和 ZTD-Java 只作为辅助或分布外资源，不能混称同一任务。

### 5.3 构造流程

1. **历史截断。** 为每个 repo-package pair 确定 \(t_0\) 和 \(t_1\)。保存 commit、release、registry、advisory 和工具版本的 immutable manifest。
2. **恢复当前任务。** 优先恢复引入或显著使用目标依赖前的 issue/PR 与可执行测试。若无法重建功能要求和验收测试，该样本不进入主数据。
3. **生成候选边界。** 使用同一基础 coding model、token 与工具预算生成至少 direct、适度独立边界、隔离或降级等多种候选。候选必须完成相同功能测试；失败候选保留作当前成本标签，但不能伪装成可比较 option。
4. **随机化与配对。** 在同一任务内随机候选生成顺序、decoder seed 和 shock 分配。通过结构匹配和测试等价建立配对，避免将仓库难度误当成边界效果。
5. **隐藏冲击。** 在 \(t_0\) 完成后才向 t1 agent 揭示真实 advisory、breaking release 或迁移目标。所有 future release notes、gold diff 和后见 metadata 在 \(t_0\) 隔离。
6. **行使选项。** 在相同 t1 agent、调用预算和验证环境下分别执行 upgrade、replace、quarantine、disable 或 remove。记录每一步工具与代码轨迹。
7. **结果标注。** 以 build、hidden tests、security tests、动态调用/权限/数据 reachability、修复时间、受影响面和资源成本形成标签。LLM judge 可用于定性失败分析，不能作为主要安全真值。

### 5.4 Pilot 与完整数据门槛

第一阶段 pilot 建议抽取 100–200 个可复现实例，每例至少三个 \(t_0\) 设计和一个真实 \(t_1\) 冲击，目的是估计 replay yield、设计可比性、标签方差和 effect identifiability，不用于宣称论文结果。

完整研究的暂定进入门槛为至少约 1,500 个 replayable t0→t1 配对并覆盖约 100 个 package families。该数值是深度策略学习和跨包检验的预冻结目标，最终应依据 pilot 的方差、聚类结构和功效分析修订。若许可证、容器复放或时间隔离使规模远低于此目标，不能用同一 repo 的大量合成变体虚增独立样本数。

### 5.5 划分与泄漏隔离

- 训练、验证和测试按 repo family、fork、package family 和时间联合分组，任何一个维度的近重复都不得跨集合。
- 主测试至少包含 unseen repositories、unseen package families 和 later-time shocks 三类分布外集合。
- OSV/GHSA 的修订历史按首次公开时间重建。\(t_0\) 检索索引只能包含当时可见文档。
- gold migration diff、未来 release note、隐藏测试、当前网页上的未来版本元数据和从后续 commit 推导的符号名称均不得进入 \(t_0\)。
- 所有 Docker image digest、Git commit、registry snapshot、advisory version、seed、split 和排除原因写入 manifest。

## 6. 模型张量、结构与前向计算

设 batch size 为 \(B\)，每个实例有 \(J\) 个候选边界、\(S\) 类或个真实冲击、\(A\) 个 t1 exercise actions，repo-package 图有 \(N\) 个节点，隐藏维度为 \(d\)。

### 6.1 输入图

模型构建时间异质图 \(\mathcal G_{t_0}\)。节点至少包括文件、函数、数据对象、权限/资源、boundary component、provider API、package/version、maintainer、advisory 和可替代 provider。边至少包括调用、数据流、权限可达、声明依赖、实现 capability、版本继承、维护归属、替代和 exercise path。基础节点表示为

\[
H_{t_0}\in\mathbb R^{B\times N\times d}.
\]

关系类型必须进入 message passing。把所有节点平铺成 token 的 Transformer 是强基线，不是本文理论模型。

### 6.2 理论中间状态

1. **边界粒度张量**

\[
G\in\mathbb R^{B\times J\times3},\qquad
G_{bj}=[g^{vol}_{bj},g^{fun}_{bj},g^{ind}_{bj}].
\]

`volume` 表示边界相关代码与逻辑路径规模，`functional breadth` 表示封装的业务 capability 范围，`independence` 表示 client 与 provider-specific representation、API 和运行环境的分离程度。三项由静态图、动态 trace 和 proposal code 共同估计，并用人工双标的小样本、可计算结构指标和干预变体校准。不得把三者合为一个无语义 latent score。

2. **当前效率状态**

\[
Q^0\in\mathbb R^{B\times J\times2},\qquad
Q^0_{bj}=[E^0_{bj},D^0_{bj}],
\]

其中 \(E^0\) 是当前实现/验证 effort，\(D^0\) 是当前缺陷和回归状态。\(D^0\) 同时是理论指定的 mediator，必须单独进入未来结果模型。

3. **冲击条件下的未来状态**

\[
R^1\in\mathbb R^{B\times J\times S\times K},
\]

其中 \(K\) 至少覆盖 remediation effort、可达暴露时长、功能回归、安全回归和不可用时间。它不能由静态 maintainability proxy 代替。

4. **选项可行性与动作结果张量**

\[
X^1\in[0,1]^{B\times J\times S\times A},
\]

表示在边界 \(j\) 和冲击 \(s\) 下，upgrade、replace、quarantine、disable、remove 等动作的可执行概率与结果分布。provider alternatives 和 exercise paths 的关系 embedding 直接进入 \(X^1\) 和 t1 patch decoder。

5. **策略状态**

\[
\pi_0\in\Delta^J,\qquad \pi_1(\cdot\mid j,s)\in\Delta^A.
\]

\(\pi_0\) 选择并生成 t0 边界，\(\pi_1\) 在真实冲击后行使动作。两者共享 world model，但分别输出可执行 patch。

### 6.3 结构化前向路径

推荐结构包括五个相互负责的部分：

1. temporal heterogeneous graph encoder 编码 repo、provider 和时间截断知识；
2. boundary proposal policy 与本地 code decoder 生成多个可执行 t0 方案；
3. granularity head 产生 \(G\)，current-outcome network 产生 \(E^0,D^0\)；
4. shock-conditioned world model 以 \((H_{t_0},G,D^0,s)\) 预测 \(R^1,X^1\)，显式保留 `granularity → defect → future remediation` 的中介路径；
5. hierarchical policy 先基于当前成本和未来 action-state distribution 形成 \(\pi_0\)，再在 t1 形成 \(\pi_1\)。两个 code decoder 均 cross-attend 到对应理论状态和 exercise-path embedding。

real options 不以手工 \(V_{option}\) 奖励附在末端。即使内部计算未来价值，它也必须由 \(X^1\) 中可行动作的真实状态转移导出。若删除 exercise graph 后 t0 patch 不变，说明 option state 没有进入行动，理论责任失败。

## 7. 损失函数与训练过程

总目标暂定为

\[
\mathcal L=
\mathcal L^0_{exec}
+\lambda_g\mathcal L_G
+\lambda_d\mathcal L^0_{defect}
+\lambda_w\mathcal L^1_{world}
+\lambda_x\mathcal L_{exercise}
+\lambda_{cf}\mathcal L_{counterfactual}
+\lambda_{shape}\mathcal L_{shape}
+\lambda_m\mathcal L_{mediator}
+\lambda_p\mathcal L_{policy}
+\lambda_c\mathcal L_{code}.
\]

- \(\mathcal L^0_{exec}\) 监督当前功能、构建和安全约束。
- \(\mathcal L_G\) 使三维 granularity 与结构测量、人工双标和干预变体一致。
- \(\mathcal L^0_{defect}\) 监督当前 defects、回归和 effort。
- \(\mathcal L^1_{world}\) 监督各 shock 下的 exposure、remediation、regression 和 downtime 分布，需报告校准与不确定性。
- \(\mathcal L_{exercise}\) 监督动作可执行性和 action-state transition。
- \(\mathcal L_{counterfactual}\) 在同一 repo/task/shock 内，当当前任务成功相同或落入等效界时，排序真实总损害更低的 \(t_0\) 设计。
- \(\mathcal L_{shape}\) 用 shape-constrained spline 或 monotonic lattice 表示“适度增加 granularity 可能降低未来 customization，但提高当前 effort/defect；超过经验阈值后净收益可反转”。只约束理论允许的形状，不使用原 ERP 样本的具体阈值。
- \(\mathcal L_{mediator}\) 比较保留和阻断 \(D^0\) 路径的预测，检验 defect 是否承担部分中介，而不是把理论结构画在图上。
- \(\mathcal L_{policy}\) 优化风险敏感的两时点行为，同时约束正常任务成功率和拒绝率。
- \(\mathcal L_{code}\) 监督 t0/t1 patch token、edit action 和 verifier feedback。

训练建议分四阶段。第一阶段训练并验证图表示、\(G\) 与当前状态。第二阶段使用真实 rollout 训练 shock world model 和 exercise feasibility。第三阶段以离线 counterfactual policy learning 训练 \(\pi_0,\pi_1\)。第四阶段对 7B 或 14B 开源 code model 进行 LoRA/adapter 训练，使 patch decoder 由上述状态条件化，再做受控联合微调。每阶段保留独立 checkpoint，以便定位增益来源。

## 8. 理论方向冲突和机制干预

### 8.1 预注册冲突情境

理论必须在至少四类情境中产生不同选择。

1. **低冲击、低关键性、低耦合。** 当前额外 abstraction 的 effort 和 defect premium 应超过未来收益，倾向 direct integration。
2. **高暴露、存在成熟替代。** provider-neutral boundary 或隔离结构可能降低未来暴露和替换成本，即使当前代码更多。
3. **无可行替代。** 可替换 facade 的 option 不可行，策略不应因抽象名称而支付 premium，可能改选能力限制、隔离或降级。
4. **过度粗粒度。** 当 code volume、functional breadth 或 independence investment 超过新数据学习的阈值，当前缺陷与验证负担应抵消 future customization 收益，选择应再次反转。

如果模型在四类情境中都选择同一设计，或方向只由额外测试数量解释，理论机制不成立。

### 8.2 机制干预

- 删除 \(G\)，保持参数量的 learned latent replacement；
- 在 batch 内打乱 \(G\) 与 repo/shock 的对应；
- 保留 \(G\) 但阻断 \(D^0\) mediator；
- 中和 \(\mathcal L_{shape}\)，改为无约束 MLP；
- 打乱 provider-alternative 和 exercise-path edges；
- 把 \(X^1\) 压成单一 option scalar，只在最终 logits 相加；
- 固定 always-direct、always-wrapper、always-isolate 和 always-more-tests；
- 保持层级结构但用同参数通用 state 替代所有理论命名状态。

每项干预不仅比较最终平均性能，还比较冲突情境的行为方向、状态校准、t0 代码结构和 t1 action distribution。

## 9. 等参数通用替代的反证设计

理论贡献不能以“通用模型难以理解理论”作为前提。原则上，足够数据的 Transformer、temporal GNN 或 POMDP 可能复制全部能力。因此，本候选只有通过下列等参数反证才可继续。

### 9.1 替代模型

1. raw-token/graph Transformer，看到相同源码、manifest、生态元数据和 rollouts，但没有显式 \(G,D^0,R^1,X^1\)；
2. equal-parameter temporal heterogeneous GNN，具有相同 relation inputs，但只直接预测最终损害和动作；
3. generic two-stage world model/POMDP，具有相同状态观测、动作空间、shock rollouts 和 code decoder；
4. 与理论模型相同层级和参数量的 anonymous-state model，以同维 latent tensors 替代有构念监督的状态；
5. real-option-only scalar model，用未来预期收益对通用 agent rerank，用于直接证明末端辅助分数不足。

### 9.2 公平控制

可训练参数控制在预注册误差范围内，建议不超过 ±1%。所有模型使用相同训练实例、counterfactual rollouts、基础 code model、检索索引、token/tool/test/运行时间预算和超参数搜索次数。匿名状态模型不能被故意削弱。理论模型使用的构念标注成本应计入数据与计算预算。

### 9.3 等效判定

在 pilot 后依据方差预注册主要安全结果、任务成功和冲突行为的 equivalence margin。若 generic POMDP 或 anonymous-state model 在主要结果上落入等效界，并复制四类方向冲突，理论结构没有产生不可替代新增能力，应撤销独立理论算法贡献。只在解释性图表上更好不能挽救该判定。

理论模型还必须在 unseen package family 和 later-time shock 上显示稳定增益。若优势只在训练包或通过同一 advisory template 复现，说明模型记忆了 package history，而非学习理论机制。

## 10. 基线、评价与统计

### 10.1 强基线

- 同期 frontier coding-agent 配置；
- DepDec/OSV-guided selection、PySelect、Dependabot 和 Renovate；
- PyMigTool、LLM migration agents、CORAL、BigBag、Byam、DependaFix 和 SWE-Chain 对应配置；
- ZTD-Java 或相同最小权限/隔离控制；
- 通用 architecture knowledge graph 与 architecture-aware coding agent；
- Chondamrongkul–Sun 的形式 architecture-evolution planner，以及同等输入下的 search-based architecture refactoring/planning；
- 上述所有等参数通用替代和固定策略。

### 10.2 结果层次

主要安全结果包括 reachable vulnerable exposure、限定时间内安全修复成功、安全/功能回归和不可用时间。主要任务结果包括 \(t_0\) 功能成功与 \(t_1\) 修复成功。主要成本结果包括生成与验证时间、tool calls、GPU/CPU、人工介入、diff/LOC、接口数和测试成本。

机制结果包括 \(G\) 的构念效度、\(D^0\) 中介效应、\(R^1/X^1\) 的校准、option exercise accuracy、四类冲突选择和理论干预效应。静态 smell、耦合和 maintainability index 只能作辅助指标。

统计模型应考虑 repo 与 package family 的聚类，报告效应量、置信区间和多重比较控制。主要结论同时进行 superiority 与 equivalence 检验。失败样本按无法构建、任务失败、边界无效、shock 不可达、修复失败和验证不充分分层，不得只报告成功复放的子集。

## 11. 本地算力与复现工件

### 11.1 Pilot 资源估计

资源数值尚未实测。初步估计需要至少 2–4 张 24GB GPU、256–512GB 内存、4TB NVMe 和容器运行环境。BUMP 完整镜像本身约 250GB；跨生态镜像、registry snapshot 和多设计 rollout 可能使磁盘需求超过 1TB。100–200 个实例、每例三个设计和至少一个 t1 冲击意味着约 300–600 条完整两时点执行链，实际时长须由前 20 个实例测量。

### 11.2 完整训练工件

预期本地工件包括 50M–150M 规模的 temporal graph/world model 权重、7B/14B code model 的 LoRA checkpoint、granularity calibration model、time-sliced package/advisory index、policy checkpoint、verifier 配置和 replay cache。初步训练预算可按 4 张 24GB GPU、3–7 天作为排期占位，不能在未 profiling 前写入正式论文。

复现包至少包含：代码版本、环境 lockfile、Docker digest、数据下载和排除 manifest、时间截断索引构建脚本、split manifest、配置、随机种子、模型与 optimizer checkpoint、完整 tool trajectory、失败日志、统计脚本和逐实例结果。任何因许可证不能再发布的仓库都需提供获取脚本、commit hash 和可核验排除说明。

## 12. 撤题门

出现下列任一核心情况，候选不得冻结为论文一：

1. 容器复放、许可证和时间隔离后，无法形成具有足够 package-family 覆盖的两时点数据；
2. 当前任务、未来冲击或安全结果不能通过执行获得，只能依赖 LLM 自评；
3. counterfactual boundary variants 无法在当前功能上建立等价，或生成过程系统性泄露未来冲击；
4. \(t_0\) 边界差异不实质改变 \(t_1\) 暴露、修复、回归或不可用时间；
5. 改进可由 always-wrapper、更多 LOC、更多测试或更多调用预算完全解释；
6. dependency boundary 上的 \(G\) 缺乏构念效度，三个子维度无法可靠区分或干预；
7. granularity—defect—future remediation 的中介和阈值机制没有可观察证据；
8. 等参数 generic POMDP、temporal GNN 或 anonymous-state model 在主要结果与方向冲突上进入等效界；
9. 模型不能在 unseen repository、package family 或 later-time shock 上泛化；
10. 新近直接工作已经实现相同的 prospective dependency-option construction 与 exercise 能力；
11. 工件最终退化为包排序、风险头、提示词、规则 wrapper 或普通迁移 agent；
12. C1 与候选二的知识协调或候选三的人类升级取证发生实质重合。

## 13. 当前红队结论

这个方向仍有明确损害、两个真实代码行动时点和可执行监督，但当前理论方案不合格。Subramanyam 的研究单位、构念和结果不能直接迁移为 dependency wrapper/adapter 的结构标签；把其经验形状写入损失后再用模型表现证明机制会形成循环。故本文件第 3、6、7、8 节中依赖该映射的主张均视为被否决记录，而非待润色正文。
