# 候选一架构选项理论与时间泄漏反证

> **后续终局判定（2026-08-15）：本文件提出的 Schober-centered rescue 已被终审否决。** `00U_C1依赖选项Schober救援终审.md` 证明，在相同状态、后果和效用输入下，Schober 价值关系与 two-stage Bellman recursion 可逐输入同构；公开资产也没有满足双世界和时间隔离门。以下内容只保存中间红队过程，不再构成可进入题位的 rescue 路线。

## 0. 红队结论

本文件对候选一“面向未来依赖冲击创建并行使架构选项”作独立理论责任与时间泄漏审查。审查对象包括 `00A_广义安全概念边界与系列选题论证.md`、`00B_内部选题与可行性审计.md` 和 `00N_候选一未来依赖冲击与架构选项红队规格.md`。结论分为三层。

**A. 当前以 Subramanyam、Ramasubbu 与 Krishnan 的 component granularity 为主理论，并以 granularity shape loss 强制非单调关系的方案，判定为 NO-GO。** 原研究的分析单位是面向多客户部署的 ERP business component，flexibility 的结果变量是客户现场 customization effort。dependency wrapper、provider-neutral adapter、进程隔离和降级路径不是天然的 coarse-grained component。将 boundary-related LOC、capability 数量和依赖接口直接命名为原理论的 code volume、functionality 和 independence，再把原样本的边际关系写入损失，会同时造成构念错置与循环验证。

**B. 仍存在一个不循环的救援 pilot。** 救援版应以 Schober 与 Gebauer 的 flexibility-to-change 关系为核心，显式分离当前 functionality、初始 option premium、未来未预见要求、option exercise、非行使和系统外处置，并在同一任务、同一冲击下比较 with-option 与 without-option 的真实执行后果。dependency boundary 先作为待学习和待验证的技术行动表征，不预先声称是 component granularity。Subramanyam 等人的研究只作为“当前开发负担与下游变更收益可能冲突、当前缺陷可能传导至下游”的有限经验镜头。只有新的构念、方向和中介检验成立后，才可提升其理论责任。

**C. 救援版仍不是论文级 GO。** 一般 two-stage world model 或 POMDP 可以表示相同的时间、状态、动作和成本。若等参数通用模型在 later-time、unseen-package 和行为等价冲击上复制外部安全结果、with/without 排序、行使/不行使方向与样本效率，候选必须判论文级 NO-GO。理论状态更容易解释、命名更符合管理语言或图表更美观，均不能挽救独立理论算法贡献。

因此，候选一当前状态应记为：**FORMAL FREEZE NO-GO / SCHOBER-CENTERED RESCUE PILOT ONLY**。在救援 pilot 通过构念、信息隔离、反事实和等参替代四道门前，不得进入正式论文正文。

## 2. 两篇理论原文实际允许什么

### 2.1 Schober–Gebauer 可合法负责的结构

原文的 flexibility-to-change 不是一般“代码好改”，而是一个跨时点选择。下列对应具有直接文本依据。

| 原文对象 | 对候选一可合法承担的状态或约束 | 不得越界的解释 |
| --- | --- | --- |
| 初始 functionality 与 flexibility-to-use | 当前功能任务必须独立通过，不能用未来安全收益补偿当前任务失败 | 不说明应选择哪个 package 或如何生成代码 |
| 二元决策 \(y\)，是否提供 flexibility-to-change | \(t_0\) 必须区分“option 是否真实存在”与“普通代码是否可运行” | 不证明任意 wrapper 都创建了 option |
| FCOST | 当前 option premium 必须是相对 matched no-option design 的增量实现、验证、复杂度和缺陷成本 | 不能用绝对 LOC 或模型自评代替增量成本 |
| 未预见任务份额 \(x_2,w_2\) | \(t_0\) 不可见的未来要求与当前已知功能必须分开表示 | 不允许把测试时真实 shock identity 输入 \(t_0\) forward pass |
| UCOST | option 被行使后的修改、升级和验证成本必须与初始 premium 分开 | 不负责具体 upgrade、replace、isolate 等动作集合 |
| \(w_3\)，不由焦点 IS 处理 | 候选动作必须包含不行使、禁用、降级或转由外部手段处理，option 是权利而非义务 | “系统外手工处理”与生产环境 quarantine 只可作功能类比，不能宣称构念相同 |
| \(c^*=TCNF-TCF\) | 同一环境状态下比较 without-option 与 with-option 的执行结果，形成 option value 标签 | 不能以两个不同仓库、不同任务或不同 shock 的平均差替代反事实 |
| stochastic DTA、ROA 与风险模拟 | \(t_0\) 选择必须对当时可见的未来状态分布积分，并保留收益不对称 | 原文不要求采用 ROA，也没有为安全尾部损害直接给出 CVaR 目标 |

由此可形成合法的方向冲突。稳定、低影响且替代稀缺的依赖可能不值得支付 premium。高暴露、存在成熟替代且边界确实产生可执行路径时，当前额外成本可能值得承担。冲击发生后，option 仍可能因修复成本过高而不行使。没有冲击的观察窗中，option 的 premium 仍真实存在。若数据只收集最终发生冲击的样本，这些冲突会被人为删除。

### 2.2 Schober–Gebauer 不能负责的内容

该文是面向业务流程支持系统的形式化经济模型。它没有定义 dependency boundary、API port、adapter、sandbox、fallback、contract test、权限限制或 code decoder，也没有提出软件安全损害张量。它可以规定时间分解、option/no-option 比较和估值信息需求，却不能证明某个具体架构是 option，更不能单独证明 temporal GNN 是理论必需。

因此，`00N` 中的 heterogeneous graph、provider-alternative edges、exercise-path tensor 和 patch decoder 都是本研究待验证的技术设计。它们可以受 flexibility-to-change 问题启发，但不能写成 Schober–Gebauer 原理论直接推出的唯一结构。

### 2.3 Subramanyam 等人可合法负责的有限关系

原研究有四项可迁移的设计纪律。

1. 软件灵活性需要与当前开发 effort 和 defects 同时评价，不能只报告未来改动成功。
2. 抽象的 granularity 必须分解为可测量子维度，而不是一个任意 latent score。
3. 当前缺陷可能把上游设计选择传导到下游变更成本，直接路径与缺陷中介路径需要分开。
4. 设计收益可能存在阈值或反转，不能预设“更多模块化总是更好”。

这些是待检验的迁移命题，不是已经成立的 boundary 构念。原研究的 code volume 不是简单 LOC；在其 MDCD 场景中以 data elements 操作化。functionality 以 data-layer interfaces 操作化。independence 关注组件对底层实现框架的依赖，正文用 internal interfaces 表示这一依赖，并明确“较少 internal interfaces”才对应“较高 independence”。该子维度在若干结果中的单独系数不显著。原研究的主要方向依赖三个子维度的联合检验，不能把 raw interface count 与 independence 同向编码，也不能挑选一个有利指标后宣称 granularity 已得到支持。

### 2.4 将 wrapper 直接视为 coarse granularity 为什么牵强

provider-neutral port 加若干 adapters 往往把一个直接调用拆成多个较小组件。它可能增加总 LOC 和接口数，同时缩小每个组件的功能范围，并降低核心业务组件对 provider framework 的依赖。进程隔离可能增加部署单元却不扩大业务 functionality。fallback 可能扩大功能分支，却不提高 provider independence。vendor-in 或 pinning 可能增加当前控制，却没有未来替换 option。不同子维度会朝相反方向变化，因而不存在“boundary 越多就越 coarse”的自然序。

更关键的是，原研究的 downstream flexibility 是把通用 ERP component 集成到异质客户 IT 环境的 customization effort。本候选的 \(t_1\) 结果是 CVE 修复、breaking update、替换、隔离和暴露时长。二者都涉及后续改变，但对象、触发机制、结果和行动空间不同。把 remediation effort 直接改名为 customization effort 只是术语相似，不是理论迁移。

## 3. 对 `00A`、`00B` 与 `00N` 的具体红队

### 3.1 已经合理的部分

三份文件正确地把当前任务与未来冲击分成两个时点，要求 agent 在两个时点都生成可执行 patch，并同时报告当前成本、未来安全结果和任务成功。它们也正确地设置 same-task、same-shock 反事实、通用 POMDP 反证、later-time 划分和 always-wrapper 撤题门。这些部分应保留。

### 3.2 当前必须撤销的主张

1. `00N` 第 3 节把 Subramanyam 等人设为主理论，把 Schober–Gebauer 降为 supporting lens。就当前构念证据而言，责任顺序应反转。真正直接对应研究问题的是 premium—future requirement—exercise—nonexercise 的 flexibility-to-change 结构。
2. `00N` 的 \(G=[g^{vol},g^{fun},g^{ind}]\) 可以保留为技术 architecture feature tensor，却不得在 pilot 前命名为 component granularity。三个元素需先证明与原构念的收敛、区分和干预效度。
3. `00N` 的 \(\mathcal L_{shape}\) 预先强制“适度增加 granularity 有利、超过阈值反转”。该关系来自特定企业、特定 MDCD 测量和 92 个组件的边际分析。把它写入训练损失后，再以模型呈现该方向作为理论证据，会形成循环。救援 pilot 必须删除强制 shape loss，把该方向留作独立、可失败的外部检验。
4. `00N` 的 \(\mathcal L_{mediator}\) 通过保留或阻断 \(D^0\) 路径比较预测，不能识别 causal mediation。神经路径被阻断后性能下降，只能证明模型使用了该表示。
5. `00N` 的 world model 以真实 shock \(s\) 为输入预测未来结果是合法的 \(t_1\) 训练或行使计算，但 \(\pi_0\) 不能看到测试实例的真实 \(s\)。\(t_0\) 只能对当时可得分布 \(p_0(\omega\mid I_0)\) 积分。
6. 图中可以包含 \(t_0\) 前已公开的 advisories。未来 advisory 节点、未来固定版本、未来 release note 或由 gold diff 产生的符号，即使文本被遮盖，也不得连接到 \(t_0\) 图。

### 3.3 当前最严重的数据选择偏差

若 BUMP、PyMigBench、SWE-Chain 和 advisory 数据只提供“后来确实发生 breaking change、迁移或安全披露”的正事件，训练集就条件化在 \(Shock=1\)。此时模型无法估计 \(t_0\) 面对的真实发生概率，任何 option 都会被系统性高估。Schober–Gebauer 的核心恰恰是未来状态分布和有无 option 的差异；只观察冲击样本等于把理论最重要的决策条件删掉。

主数据必须从 \(t_0\) 风险集抽样，而不是从 \(t_1\) 事件反向抽样。每个 package-family、时间和使用强度层应同时包含：

- 在预注册 horizon 内发生目标 shock 的窗口；
- 在 horizon 内保持稳定、未发生目标 shock 的右删失窗口；
- 有正常升级但没有安全或 breaking shock 的竞争风险窗口；
- 发生 shock 但依赖调用不可达、因而不需要行使的窗口；
- option 已创建但最优动作是不行使的窗口。

模型需用 survival、competing-risk 或离散时间 hazard 估计 \(p_0(\omega,\tau\mid I_0)\)，并按生态基准发生率校准。若事件样本为提高训练效率被过采样，policy 计算和评价必须用预注册权重还原总体分布。没有 stable/censored windows，救援版直接 NO-GO。

## 4. 不循环的 Schober-centered 救援版

### 4.1 研究单位和信息结构

一个决策单位是同一 \(t_0\) 仓库快照、功能任务、目标 dependency capability 和候选 provider 集合。候选 \(b\) 是实际可执行的当前实现。\(b_0\) 为 matched no-option design，其他候选只有在执行审计证明未来至少存在一条新增可行行动路径时，才被标为 with-option。

\(t_0\) 信息集写为：

\[
I_0=(R_{\leq \tau_0},q_0,M_{\leq \tau_0},L_{\leq \tau_0},A_{\leq \tau_0},D_{\leq \tau_0}),
\]

其中依次是仓库与 issue、manifest/lock、registry metadata、公开 advisory 和文档。任何时间戳晚于 \(\tau_0\) 的内容均不属于 forward input。

候选的当前 premium 是相对于 matched no-option design 的增量：

\[
C_0(b)=Cost_{t_0}(b)-Cost_{t_0}(b_0).
\]

其中必须同时包含 wall-clock、tool calls、diff、验证成本、当前缺陷与部署复杂度，不能只以 LOC 表示。

### 4.2 option 必须由可执行反事实定义

对未来状态 \(\omega\)，边界 \(b\) 的可行行动集为 \(\mathcal A_b(\omega)\)，其中始终包含 no-exercise，并可包含 upgrade、replace、quarantine、disable、degrade 或 remove。一个候选只有满足以下条件才被称为架构选项：

1. 当前功能与 matched no-option design 落入预注册等效界；
2. \(C_0(b)\) 可测且通常非负；
3. 至少在一个 \(t_0\) 未知的未来状态中，\(b\) 新增一条经执行验证的行动路径，或显著降低相同行动的成本和损害；
4. 至少在一个状态中不行使仍可成为最优动作，避免把预定迁移误称 option；
5. 新路径不是因为给予更多 \(t_1\) token、测试、人工提示或外部信息。

### 4.3 theory-owned value relation

救援模型的核心不是一个手工“灵活性分数”，而是两个共享参数的 potential-outcome branches：

\[
\widehat Y^{NF}(I_0,\omega),\qquad
\widehat Y^{F}(I_0,b,\omega,a).
\]

第一支估计 without-option 的实际成本和损害，第二支估计 with-option 在不同行使动作下的后果。\(t_0\) 选择只对当时可见分布积分：

\[
\widehat V_0(b\mid I_0)
=-C_0(b)+
\rho_{p_0}\left[
\max_{a\in\mathcal A_b(\omega)}
U\!\left(\widehat Y^{F}(I_0,b,\omega,a)\right)
-U\!\left(\widehat Y^{NF}(I_0,\omega)\right)
\right].
\]

\(\rho_{p_0}\) 是对经 stable/censored windows 校准的未来状态分布所作的预注册聚合。可以报告期望、分位数和尾部损害，但不能声称 Schober–Gebauer 唯一规定某一种风险函数。实际 \(t_0\) policy 在当前任务成功约束下选择 \(b\)，实际 \(t_1\) policy 看到已公开 shock 后才选择 \(a\)。

这套关系比 `00N` 当前的 granularity shape 更接近原理论，因为它保留了 initial premium、future unknown state、exercise/no-exercise 与 with/without difference。boundary encoder、temporal graph 和 code decoder 仍是学习这些量和执行行动的技术工件。

### 4.4 可训练状态与损失

建议将理论状态与技术状态分开命名：

- 理论状态：option-existence \(y_b\)、premium \(C_0\)、\(t_0\) shock distribution \(p_0\)、exercise feasibility mask \(F_{b\omega a}\)、with/without outcomes、exercise/no-exercise。
- 技术状态：boundary graph embedding \(Z_b\)、provider capability graph、调用/数据/权限可达性、代码 edit representation。
- 待验证机制：当前 defects \(D_0\) 与未来 exercise outcome 的中介。

总损失可包含当前任务执行、premium 回归、hazard calibration、exercise feasibility、twin outcome、same-task same-shock ranking、\(t_1\) action policy 和两时点代码生成。不得在主训练中强制 Subramanyam shape。构念方向与中介应在冻结模型后用独立干预数据检验，否则训练目标和理论证据来源相同。

训练可以使用历史 \(t_1\) 后果作为监督标签，这本身不构成泄漏。必要条件是标签构建器与 \(t_0\) feature builder 物理分离，测试 forward graph 中不存在由标签、未来文档或 gold patch 派生的任何字段。

## 5. \(t_0\) 时间泄漏隔离协议

### 5.1 不是用 advisory 日期简单切一刀

一个 shock 往往有多个公开信号：问题或 PR、修复 commit、release candidate、changelog、package yank、维护者公告、GHSA、OSV、NVD 和下游 issue。对每个事件定义：

\[
\tau_{leak}=\min(\tau_{issue},\tau_{PR},\tau_{patch},\tau_{release},\tau_{registry},
\tau_{maintainer},\tau_{GHSA},\tau_{OSV},\tau_{NVD}).
\]

\(\tau_0\) 必须早于最早可观察信号并留出预注册 buffer。Git author date 可被重写，优先使用 committer date、registry immutable timestamp、公开归档和多个来源的最早值。无法确定最早公开信号的历史事件不能进入 primary test。

### 5.2 \(I_0\) 白名单

- commit hash 固定且所有文件最后修改不晚于 \(\tau_0\) 的仓库快照；
- \(\tau_0\) 前真实存在的 issue、当前功能验收条件和文档；
- 当时可获得的 package releases、download/maintenance history、已公开历史 advisories；
- \(\tau_0\) 时真实可解析的 manifest、lockfile、transitive graph；
- 仅由上述材料运行得到的静态、动态、数据流和权限 trace。

### 5.3 \(I_0\) 黑名单

- future advisory ID、fixed version、future release number、gold migration diff；
- 当前 OSV/GHSA 页面中后来补写的 affected range、references 或修复信息；
- 由 future patch 生成的测试名称、API symbol、exception text、comment 或 fixture；
- 后续 commit 才出现的替代 provider 名称、issue 链接和迁移文档；
- 数据构造脚本根据 shock 类型写入的 variant name、目录名、prompt 或 seed；
- 真实 test shock 的 one-hot、family ID 或与其一一对应的占位节点。

信息流单元测试应对每个 \(t_0\) batch 递归检查时间戳、字符串、对象 provenance 和 feature lineage。人工抽查不能替代自动 provenance manifest。

### 5.4 基础模型预训练记忆

历史事件即使从输入中删除，基础 code model 仍可能记住 package、CVE、migration diff 或 benchmark。主评价按证据强度分为三层。

**Tier A，prospective post-freeze shocks。** 固定基础权重 hash、adapter 数据截止、检索索引 hash 和 \(t_0\) manifest 后，使用此后才公开的真实 shock。这是最强证据。必须以明确 checkpoint 和数据 cutoff 证明权重冻结；不断更新、训练截止不透明的云端模型不能承担 primary 结果。

**Tier B，sealed behavior-equivalent post-cutoff shocks。** 在 \(t_0\) patch 和模型冻结后，由独立构造器在隔离 fork 中注入先前不存在但行为真实的 shock，例如 API contract 改变、异常/返回类型变化、provider capability 撤除、权限扩大、恶意 transitive behavior、维护终止与替代 provider 出现。shock 模板预注册，具体参数、symbol 和 package fork 在封存后采样。它必须产生真实 build、security 和 runtime 后果，并对所有候选边界施加同一行为变化。

**Tier C，historical identity-masked replay。** 重命名 package、API 和版本，删除 advisory 文本并扰动路径，只能作为诊断性结果。模型仍可能从代码结构、常见 patch 和调用模式识别历史事件，因此 Tier C 单独不能支持无泄漏主结论。

若不能获得足量 Tier A，primary test 至少需 Tier B，且 Tier C 只作外部现实性补充。

### 5.5 behavior-equivalent shock 不能退化成随意合成

合成 shock 必须来自公开事件类型的机制抽象，而不是为某个 boundary 量身定做。构造器在不知道候选来源和模型分数的条件下，为同一 package capability 采样变化。每类 shock 需由独立开发者核验现实性，并在至少一个真实历史事件上验证其 build/runtime signature 相似。variant 生成与 shock 生成使用不同人员或进程、不同密钥和不可互读 manifest。

必须包含 null/benign releases 和 stable windows。若所有 synthetic episodes 都含严重 shock，仍会把发生率设为一。安全攻击类 shock 只在授权容器和无外网研究环境运行。

### 5.6 训练、调参与测试隔离

- repo lineage、fork、package family、provider family、shock mechanism、calendar time 联合分组；
- 训练集可用历史未来标签，验证集负责所有超参数与 equivalence margin，测试 shock manifest 在冻结后才解封；
- test harness 持有 shock identity 和 hidden tests；\(t_0\) agent 进程只获得 \(I_0\)；
- \(t_1\) agent 在 shock 公开后可以看到 advisory 或 release note，但不能看到 gold diff；
- 检索索引按 event-time 构建，不得用当前网页加 timestamp filter 假装历史快照；
- 报告 exact model hash、LoRA hash、retrieval corpus hash、container digest、feature provenance、seed 和所有排除原因。

### 5.7 泄漏反证实验

1. 用 \(I_0\) 训练 probe 预测 test shock identity。若在 package-family 和 time 分组后仍远超基准，先排查泄漏，不能把它解释为“风险预测强”。
2. 将 future metadata 随机置换或插入 sentinel，确认任何 sentinel 不出现在 \(t_0\) embedding、attention log 或 tool trace。
3. 比较 unmasked、identity-masked 和 behavior-equivalent 三组。只有前两组高而第三组消失，说明主要收益来自记忆。
4. 对 base model 做 closed-book known-event probe，检测其是否能从 package/版本复述未来 CVE 或 migration。
5. 将 \(\tau_0\) 向前移动多个 buffer，检查性能是否随可见信息合理下降。异常稳定可能表示参数记忆。
6. 对 stable/censored windows 检查模型是否仍系统性创建昂贵 option。若是，说明发生率或 utility 校准失败。

## 6. 构念、中介和反事实识别门

### 6.1 flexibility-to-change 构念门

option-existence 不能由模型自评。对每个 boundary，独立 executor 在多类 shock 上枚举或搜索 action path，验证是否较 matched no-option 新增可行路径或降低后果。构念还需与 maintainability、robustness、redundancy、testability 和静态 modularity 区分：

- 不需要改变即可承受 shock 是 robustness，不自动等于 flexibility-to-change；
- 更多测试提高检错能力，不自动创建 exercise path；
- pinning 或 vendoring 可能延迟暴露，却未必支持升级或替换；
- 一条为已知特定 shock 预写的 patch 是 contingency plan，若 \(t_0\) 已知其身份则不是本研究要求的未知状态 option。

### 6.2 boundary architecture 表征门

在救援 pilot 中，boundary 表征先使用中性名称 \(Z_b\)。如果要重新引入 component granularity，必须同时满足：

1. unit-of-analysis 审核证明每个被测对象是可独立部署或集成、具有明确边界的 component；
2. volume、functional breadth、independence 有独立操作化，专家双标一致性达到预注册门；
3. confirmatory factor 或多特质多方法检验支持三维结构，并在语言和生态间至少达到必要的测量不变性；
4. 受控 refactoring 能主要改变一个维度而非全部一起改变；
5. 三维度对当前 effort/defects 和未来 exercise outcome 的方向在冻结模型之外可复现。

任一条件失败，\(Z_b\) 仍可作为技术表示，但正文不得声称 Subramanyam 理论产生了该张量。

### 6.3 defect mediator 门

仅回归 \(D_0\) 或阻断神经支路不够。需要 paired randomized proposal 或受控 refactoring，使同一任务在多种 boundary 下可比较。随后对同一 architecture 构造：

- repair-mediator intervention：修复已检测的 \(t_0\) defects，同时尽量保持 boundary structure；
- seeded-mediator intervention：注入预注册、与 shock 无关的缺陷，同时保持 structure；
- direct-path intervention：保留 defect 水平，改变 provider substitution/isolation path。

以 interventional direct/indirect effects、sequential g-computation 或适合的中介估计报告结果，并显式处理测试覆盖、代码规模、模型 seed 与当前开发 effort 等 mediator–outcome confounders。若只能做 Baron–Kenny 式回归或模型内 path blocking，Subramanyam mediator 责任判 NO-GO。

### 6.4 same-task same-shock 反事实门

- 同一 \(R_{t_0}\)、issue、package/version、功能验收测试和生成预算；
- 候选生成顺序和 seed 随机化，且 shock 构造器对候选盲；
- 每个候选先通过 \(t_0\) 功能等效门，再承受完全相同的 \(t_1\) shock；
- 用固定 \(t_1\) exercise agent 隔离 \(t_0\) architecture effect，再用 learned \(t_1\) policy 测整体系统；
- LOC、测试数量、tool calls、wall-clock 和 verifier budget 匹配或进入设计控制；
- 主要真值来自 build、hidden functional/security tests、runtime trace、可达暴露与 downtime，不来自 LLM judge；
- 不成功复放、不可达 shock 和修复失败均保留在 denominator，不能只分析成功案例。

若 boundary choice 与 dependency choice同时变化，主分析无法辨别收益来自包更好还是架构更好。主反事实应固定 package capability 与 \(t_0\) 版本，另设探索性研究再允许 joint selection。

## 7. 等参数通用替代为什么仍可能复制

Schober-centered factorization提供清晰的设计关系，但它并未证明通用序贯模型无法学习这些关系。一般 POMDP 可以把 \(I_0\) 作为 belief state，把 boundary patch 当作 \(t_0\) action，把 shock 当作 observation，把 exercise 当作 \(t_1\) action，并用相同真实损害作 reward。temporal GNN 也可从同一异质图直接预测后果。

因此，必须设置四级反证，而不是只比较一个弱 raw Transformer。

1. **Raw generic model。** 相同原始输入、rollouts、code model 和预算，无显式 option states。
2. **Generic two-stage world model/POMDP。** 相同两个时点、动作、hazard 输入和 outcome labels，但直接学习 value 与 policy。
3. **Anonymous factorized model。** 具有与理论模型等维、等层次的 latent tensors 和 twin branches，但没有 option 构念监督或固定关系。
4. **Matched-state generic model。** 也获得 \(C_0,p_0,F,Y^{F},Y^{NF}\) 的监督，却用通用 cross-attention/POMDP 组合它们，不采用理论指定的 with/without 和 exercise/no-exercise关系。

所有模型的可训练参数、基础模型、数据、构念标注、检索、tool/test budget、超参数搜索和 wall-clock 需在预注册范围内公平控制。结论必须同时检查：

- \(t_0\) task success 与真实安全–成本前沿；
- with/without outcome calibration；
- stable windows 中不创建昂贵 option；
- 高冲击且存在替代时创建 option；
- option 已存在但行使不划算时选择 no-exercise；
- unseen package、provider、shock mechanism 和 later-time 泛化；
- 低数据量学习曲线和构念干预后的行为。

若第 2 或第 3 类模型在主要结果和方向冲突上进入等效界，理论专用 factorization 没有独立能力。若第 4 类也复制结果，则连理论关系的专门计算都没有新增价值。此时可以保留两时点 benchmark 或工程系统，但本候选作为 ISR 理论驱动算法论文必须 NO-GO。

## 8. 预注册方向冲突

| 情境 | Schober-centered 预期 | 可证伪点 |
| --- | --- | --- |
| 稳定、低损害、低 hazard、直接调用简单 | direct/no-option 可胜出，因为 premium 无法回收 | 若仍总建 wrapper，风险分布或 policy 失真 |
| hazard 较高、损害大、成熟替代存在 | 可替换或可隔离 boundary 可能胜出 | 必须由真实 \(t_1\) path 与后果支持，不能由名称支持 |
| 冲击发生但替代不存在 | replace option 价值低，isolate/degrade/disable 可能优于 facade | 若策略只会 replace，option graph 没有真实作用 |
| option 已创建但 shock 轻微或升级代价大 | no-exercise 可能最优 | 若 option 一有就必行使，研究退化为迁移规划 |
| null/benign release | 当前功能继续运行，premium 仍计入 | 若 null episode 不进入评价，option value 上偏 |
| boundary 引入大量当前 defects | future direct benefit 可能被当前和下游缺陷损害抵消 | 这是待识别机制，不能由 shape loss强制 |
| robust design 无需改动即可承受 shock | 可能安全但不是 exercise-based flexibility | 需分开报告 robustness 与 option exercise |

Schober–Gebauer关于确定性估值与 ROA 的结果只给出测量警示。新研究应比较基于总体发生率的 expected、distributional 和 tail-sensitive policy，但不能把“随机模型一定更好”写成不可失败假设。

## 9. 按肖帅勇老师两篇 ISR 的理论—算法论证链

### 9.1 引言应承担的句段功能

候选通过 pilot 后，引言可采用下列功能链。它不是固定段数，也不复制 ACAA 或 DSDL 的句式。

1. 先建立外部依赖已成为 coding agent 完成功能任务的重要资源，并用直接文献说明生态冲击对个人、团队和组织系统造成的真实后果。
2. 再说明 coding agent 不只推荐 package，而会生成 manifest、调用路径、权限和架构边界，因此当前快速实现会改变未来可行动空间。
3. 以一个完整 \(t_0\rightarrow t_1\) 工作流程解释管理困境：当前 premium 可见，具体未来 shock 不可见，未来暴露和修复成本却由当前结构共同决定。
4. 承认 dependency selection、upgrade、migration、vulnerability remediation 和 architecture planning 已分别解决哪些有效问题，再精确指出它们没有在同一当前任务上评价 prospective option construction。
5. 引入 flexibility-to-change，只负责从经济和决策角度分解 known functionality、premium、future requirement、exercise 与 external/no-use path。相邻引用不得被用来支持具体 boundary。
6. 说明普通 current-task optimizer 或直接损害预测把 with/without option、发生分布和行使/不行使压成一个末端分数，因而在哪些冲突情境中可能系统性误选。
7. 提出研究问题：如何从严格 \(I_0\) 学习 option construction，如何在 shock 后行使，以及 theory-owned factorization 是否改善真实安全–成本前沿。
8. 最后才命名算法工件，简述 twin outcome、hazard-calibrated option state、hierarchical policy 和两个 executable decoders，并预告待运行的评价体系。

每段只承担一个主推进。引用的责任必须局部记录：生态研究支持后果，agent 研究支持行动范围，Schober–Gebauer支持时间和估值关系，Subramanyam等人仅支持可能存在的开发–下游权衡。任何引用都不能替本研究承担构念效度、性能或因果中介。

### 9.2 理论部分到算法部分的逐项闭合

学习 ACAA 的关键不是命名多个指标，而是先指出通用相容函数在哪个方向上系统失配，再改写计算关系。救援版对应的失配是：current-fit optimizer天然偏好即时成本低的实现；只在已发生 shock 数据上训练的模型又会天然高估 option。理论因此要求把当前 premium、总体 hazard、with/without outcome 与可行 exercise 分开。

学习 DSDL 的关键不是增设 latent heads，而是让理论生成不可交换的中间状态和有方向运算。救援版的方法顺序应与理论顺序一致：

1. 构建严格 \(I_0\) 和稳定/删失 hazard state；
2. 生成 matched no-option 与 candidate option patches；
3. 从真实当前执行得到 \(C_0\)；
4. 预测并校准 \(p_0(\omega,\tau\mid I_0)\)；
5. 预测 with/without twin outcomes 和 action feasibility；
6. 先形成 \(t_0\) option construction policy，再在 \(t_1\) 形成 exercise/no-exercise policy；
7. 两个 code decoder 分别输出可执行 patch。

任何算法组件都必须能回答“删除后哪一项理论困难重新出现”。boundary GNN、LoRA 或 verifier 若只是提高一般代码能力，应作为技术组件说明，不能冒充理论贡献。

### 9.3 证据节奏

参考 ACAA 的实证责任分层和 DSDL 的中间状态回译，结果部分至少需依次报告：

1. 数据时间隔离、stable/censored base rate 和反事实可执行率；
2. \(t_0\) 与 \(t_1\) 终局安全、任务和成本前沿；
3. hazard、premium、feasibility 与 twin outcomes 的独立校准；
4. 七类方向冲突，而非只报告总体均值；
5. option-state shuffle、with/without pair break、no-exercise removal、hazard replacement 和 theory-relation neutralization；
6. 等参数 generic、anonymous 和 matched-state POMDP；
7. prospective 或 behavior-equivalent post-cutoff 泛化；
8. 失败类型、适用边界和未被支持的机制。

贡献段只有在上述证据存在后，才能分别回收：新决策对象是什么，理论关系怎样改变工件，真实执行产生了什么新知识。未运行实验时只能写设计、预注册方向和结果占位，不能使用“结果表明”。

## 10. 救援 pilot 的四道进入门

### 门一：信息与发生率

- 至少形成同时含 shock、stable、right-censored 和 benign-upgrade 的风险集；
- 每例 \(I_0\) 通过 feature-lineage 自动审计；
- primary test 有 Tier A prospective 或 Tier B sealed behavior-equivalent shocks；
- base-model known-event probe 与 shock-identity probe 不显示可解释为记忆的异常优势。

任一失败：NO-GO。

### 门二：真实 option

- matched no-option 与 candidate option 在当前功能上等效；
- option 至少新增一条真实可执行 action path，并保留 no-exercise；
- premium 与 exercise cost 可独立测量；
- boundary 差异实际改变 exposure、remediation、regression 或 downtime，而非静态 smell。

任一失败：NO-GO。

### 门三：非循环机制

- 主训练不强制 Subramanyam shape；
- granularity 若被重新引入，先通过独立构念与干预效度；
- defect 中介由外部 intervention 和适当因果估计支持；
- 理论方向在冻结模型后的冲突集上出现，不由训练标签直接编码。

任一失败：撤销 Subramanyam 理论责任。若 Schober-centered 主关系仍成立，可继续进入门四；若只剩一般 architecture predictor，则整题 NO-GO。

### 门四：通用替代

- theory model 在预注册主要安全–任务–成本前沿上优于等参数 generic two-stage POMDP；
- 同时改善 with/without calibration、stable-window abstention、exercise/no-exercise 冲突和 later-time OOD；
- 优势不能由更多参数、rollouts、构念标注、检索、tests 或 code-model budget解释。

generic 或 anonymous model 落入等效界：**论文级 NO-GO**。

## 11. 最终判定与对现有文件的影响

`00N` 是有价值的预冻结工程规格，但其当前理论层次顺序和两项损失设计不能直接进入论文。应将其视为待修订的 candidate blueprint，而非理论已闭合的证据。

当前可保留的研究核心是：coding agent 在当前功能实现中是否创建一个真实可行使的 future-change option，以及这个选择在当时可见风险分布下是否改善未来安全损害与当前成本的联合前沿。当前必须撤销的是：dependency boundary 已经等同 component granularity、原 ERP 阈值可约束新模型、模型内阻断已经识别 defect mediation。

本文件在中间审查时曾把四道门作为重新送审条件。后续 `00U` 已完成门四的解析反证：在相同输入与效用下，等参数 two-stage POMDP 可逐输入复制该关系。因此，最终状态是撤销该题的 ISR 理论算法论文资格；两时点 benchmark、数据和工程系统只能作为独立基础设施另行保留。
