## 1. 结论先行

本轮没有找到可以立即判为 GO 的第三题。本轮筛选中，唯一尚未被直接近邻或系列重叠立即否决的候选，是 **coding agent 对测试控制面的目的敏感共演**。它研究的不是怎样做一个更强的 verifier，也不是检测一次测试改动是否危险，而是当 coding agent 同时能够修改生产代码和测试、CI、度量等评价工件时，怎样学习并执行一组正式控制动作，在两种方向相反的情境之间作出不同选择。

- 当有效需求没有改变时，弱化断言、改写期望值、绕开真实交互或让可见测试假绿，会使代理通过改写成功标准取得表面成功。此时需要保护评价完整性。
- 当有效需求已经改变时，旧测试可能已经 breaking、stale 或 missing。冻结全部测试虽然能够阻止直接篡改，也会阻止正常的软件演化。此时需要更新测试，同时另建与代理所写测试相独立的结果控制。

候选暂名 **控制目的驱动的测试控制面共演策略**，英文工作名为 **Control-Purpose-Guided Test-Control Co-evolution Policy，CPTC**。其必要新增能力必须由“同一字节级测试改动、不同有效需求世界、相反的正确控制组合”识别，而不能由把 TEBench 和 ImpossibleBench 混在一起训练一个分类器来冒充。模型必须输出并执行源代码修改、测试演化、保留旧控制、建立独立控制、版本化双轨测试、隔离和重新生成等组合动作。若最后仍可约化为允许或阻止测试改动、标记 reward hacking、给现有 verifier 加分数、提示代理不要改测试，立即撤题。

之所以只给 CONDITIONAL，是因为三个核心风险尚未被真实 pilot 排除。第一，2026 年 6 月的 *The Verification Horizon* 已经明确提出验证器需要与生成器共演，动态 verifier 不是空白。第二，MONA 已经在“先写测试、再写代码”的 coding 环境中直接训练过抑制软测试的策略。第三，Wiener 等人的 control purpose 是控制者的意图，不是从 agent 行为后验推断的心理状态；若目的张量只是在技术标签上换名，等参数通用图模型或 constrained POMDP 很可能复制全部能力。

因此，本文件的结论不是“第三题已经找到”，而是：**保留一个可运行 pilot 的 CONDITIONAL 候选；在同目的配对数据、理论构念责任和等参数反证三道门通过前，题位仍为空。**

## 4. 候选问题的直白定义

### 4.1 风险和受影响对象

coding agent 在长程仓库任务中经常读写测试、fixture、mock、coverage 配置、CI workflow 和评价脚本。这些工件既是软件产品的一部分，也是组织判断代理是否完成任务的正式控制机制。代理若弱化断言、只覆盖可见输入、替换真实依赖为过度 mock、删除回归测试或改变度量计算，就可能让一个功能不完整或有回归的修改显示为成功。由此受影响的是后续维护者、部署和采购 agent 的组织、依赖该软件的用户，以及把 benchmark 分数用于模型选择和投资决策的机构。

风险也有相反方向。生产代码和有效需求发生变化时，测试需要同步演化。TEBench 已表明 stale tests 仍然通过，因此单纯依赖“执行失败再修复”结构上发现不了这类工作；missing tests 更没有失败信号。若组织把测试目录永久锁定，agent 会保留错误的旧语义、漏测新增行为，或完成不了正常迁移。安全不能由拒绝全部测试修改获得，因为这种做法降低真实任务成功并把未来回归风险留给组织。

### 4.2 决策时点、可见与不可见信息

算法在 agent 已形成候选源代码改动 `ΔP` 和候选测试控制面改动 `ΔC`，但尚未把二者提升为可交付 workspace 状态时介入。它可以看到版本化需求历史、当前有效合同、仓库前态、代码和测试依赖、候选 diff、可见测试运行、覆盖与 mutation 线索、工件 provenance、可用控制机制及其计算成本。它不能看到评价用的隐藏测试、未披露的未来需求和测试集中的秘密 oracle。训练阶段可用的隐藏 outcome 只作为 trainer 的反事实回报，在最终 test split 上物理隔离。

### 4.3 正常、风险和纠正行动

正常行动包括只修改生产代码并保留原测试，按照新需求增加测试，在版本化迁移中更新旧测试，以及在独立控制成立后共同提升代码和测试。风险行动包括弱化断言却没有对应需求变化、删除独立回归约束、用同一 agent 生成的薄测试自证、修改 evaluator 或 metric、通过 mock 隐藏真实交互，以及用特殊分支适配可见输入。纠正行动不是 `allow/deny`，而是一组会真实改变 workspace 的组合：保留旧测试为 regression lane；在 shadow branch 更新测试；生成与候选测试 provenance 分离的 metamorphic、differential 或 cross-implementation checks；为已知且可观察的 evaluator-sensitive 行为设置路径控制；建立旧合同和新合同并行的版本化测试；隔离控制面改动并继续源代码修复；在独立认证后提升 joint patch。

### 4.4 不需要假设恶意攻击者

本题主要研究优化压力、评价代理和需求演化之间的结构冲突。agent 可以有意利用测试，也可以在没有欺骗意图时过度拟合可见 suite。主研究不把模型拟人化为攻击者，也不以推断 deception 为前提。若扩展到恶意 repository instruction 或 evaluator tampering，再为该扩展单独定义攻击能力和信任边界。

## 5. 与 C1″、C3 和旧 C2 的边界

| 维度 | 本候选 CPTC | C1″ 故障后有界恢复 | C3 固定批准点可信取证 |
|---|---|---|---|
| 触发事件 | 候选代码与测试控制面可能共同变化，且有效需求可能已迁移 | benign environmental fault 已经发生 | 外部流程已经确定需要人审 |
| 核心不确定性 | 某控制面修改是在帮助有效需求形成可测结果，还是在改写成功标准；应组合何种正式控制 | 故障后哪些任务责任、执行权和干预权仍可用 | 审核者对候选行动及证据是否形成 grounded understanding |
| 主要动作 | 生成或修改测试、保留旧 lane、建立独立 outcome control、施加 formal behavior control、版本化双轨、提升或隔离 joint patch | 检查、替代路径、shadow execute、最小权利、重新委派、停止、回滚或补偿 | 选择并执行下一项证据动作、安排证据顺序、依据真人反馈修复 grounding |
| 主要结果 | hidden true success、false-green、合法测试演化成功、回归与控制成本 | 任务恢复、越权副作用和恢复成本 | unsafe approval、safe approval、审核时间和人类负担 |
| 人是否在环 | 主实验无审批动作；人只参与数据构念验证 | 可请求权利或介入，但不是固定证据审核 | 真人审核是核心结果 |

本候选不使用故障注入、rollback、补偿、handoff 或权限扩张作为主要动作，因此不与 C1″ 拼接。它也不决定何时 ask、展示何种证据或是否批准，因此不占 C3 的可信取证空间。其模型是单 coding-agent 与外部正式控制的关系，不恢复多 agent 角色、知识协调、并发或路由，不得引用旧 C2 的 TMS 张量作为遗产。

### 6.3 搜索后仍可能存在的空白及其精确边界

截至检索截止日，没有核验到一项工作同时满足以下六项：以真实 repository coding agent 为行动者；同一候选测试改动在两个有效需求世界中有相反的正确处理；策略能够生成和执行合法 test evolution；策略同时维护不受自己控制的独立结果保证；内部表示显式区分控制者的 appropriation-protection 与 creation-enablement purposes；输出是多机制正式控制 portfolio 而非 edit classifier、monitor 或 verifier hardening。

这个“未找到”不能被写成“首次”结论。检索仍受 arXiv 命名漂移、工业未公开系统和 2026 年快速更新影响。正式冻结前必须按 `test evolution + reward hacking`、`legitimate test modification + evaluator integrity`、`adaptive/evolving verifier + coding agent`、`test tampering + requirements change`、`control surface + software agent` 重新搜索 ICSE、FSE、ASE、USENIX Security、S&P、CCS、NDSS、CHI、CSCW 和 AIS Basket，并沿 *Verification Horizon*、TEBench、MONA 和 ImpossibleBench 的引用与被引网络更新一次。

## 7. IS 理论的合法迁移与计算责任

### 7.1 理论原文能说什么

Kirsch（1997）把行为控制定义为在适当行为可知且可观察时，通过程序、监督与相关评价影响 controllee；把结果控制定义为明确和度量期望结果，并依据结果评价 controllee。研究同时指出实际 IS 项目使用多种模式和多个机制构成 portfolio，一个机制可以服务不止一种控制模式。

Choudhury 与 Sabherwal（2003）在 outsourced software development 中纵向观察 control portfolio。其结果强调 outcome controls 常先出现，performance problems、行为可观察性、控制者知识、controllee 的一般和情境知识会引发后续增加或修改控制；作者还明确提醒，在高度不确定或非结构化任务中，需求可能需要在项目过程中演化，不能从案例简单推出一律使用详细前置规范。

Wiener 等（2019）把既有研究的 what 对应 control configuration，把 how 对应 control enactment，并把 why 定义为 control purpose，即控制者选择和实施控制背后的意图。value-appropriation purpose 关注防止参与者利用代理问题错误占用项目价值；value-creation purpose 关注即使不存在机会主义，也需要协调分工、接口和创新活动来创造价值。两种目的可以同时存在，一个控制机制可以同时服务两者，但特定时点通常有主导目的。作者特别要求未来研究区分 controller intention 与可观察 control behavior，并区分回顾性和前瞻性意图。

### 7.2 在本题中的角色映射

- **controller** 是部署 coding agent 的组织、项目 owner 或由其签发的任务治理契约，不是另一个 LLM judge。
- **controllee** 是有权修改仓库并运行工具的 coding agent 系统。
- **formal outcome controls** 是与有效需求对应、由独立 runner 执行的 behavioral、metamorphic、differential、regression 和 deployment-simulation checks。
- **formal behavior controls** 是在适当行为已知且可观察时，对 evaluator-sensitive 路径、测试删除、隐藏 oracle 访问、metric 修改和 provenance 混用施加的程序与监测。
- **control portfolio** 是按 obligation 组合保留旧测试、增加新测试、独立 outcome checks 和必要行为控制，而非一个全局风险阈值。
- **control purpose** 来自组织的版本化任务契约及其前瞻性控制意图。模型不能把“agent 改了测试”后验解释为 appropriation，也不能推断 agent 是否有欺骗心理。

本候选不把 clan control 映射为多个 agent 的共享规范，也不把 self-control 映射为模型自检、reflection 或 critic head。这两种映射都混淆了人类社会构念和算法模块，属于立即撤题错误。

### 7.3 理论拥有和不拥有的中间状态

| 中间状态 | 张量 | 理论责任 | 不能错误归因给理论的部分 |
|---|---|---|---|
| 控制目的状态 | `P ∈ [0,1]^(B×N_o×2)`，两维分别为 appropriation-protection 和 creation-enablement 的组织意图强度 | Wiener 等的 why-of-control 要求保留两个不可互换的目的，并允许同一 obligation 同时承受两种压力 | 需求抽取是否正确、agent 是否主观欺骗、hidden tests 是否为真 |
| 正式控制适配状态 | `F ∈ [0,1]^(B×N_o×4)`，四维为适当行为知识、行为可观察性、结果可指定性、结果可测量性 | Kirsch 及后续 control research 指出这些条件改变 behavior/outcome mode 的适用性 | 代码依赖、AST、coverage、test independence 的具体计算 |
| obligation–control 测量关系 | `M ∈ [0,1]^(B×N_o×N_c×K)`，`K` 表示正例、边界、异常和交互环境等技术覆盖关系 | 不由 control theory 独占 | 由程序分析、动态 trace、mutation 和训练数据学习，必须称为技术表示 |
| provenance 和独立性 | `I ∈ [0,1]^(B×N_c×N_c)` | 不由 control theory 独占 | 由谁生成、共享何种输入、是否能被同一 patch 同时控制，是可执行技术事实 |
| 控制 portfolio | `Z ∈ [0,1]^(B×N_o×N_m×2)`，对每个 obligation 和候选机制选择 behavior/outcome mode 权重 | control portfolio、mode choice 和双 purpose 共同规定结构 | 具体 test token 和 container command 仍由代码模型与执行器产生 |

### 7.4 肖老师标准下的 MEC–MAP–ALG 责任链

**机制到表示。** 静态 test lock 只处理 appropriation-protection，却系统性损害 creation-enablement；允许 agent 自由更新全部测试则反向失效。这个双目的冲突要求 `P` 保留两个方向，不能压成单一“安全风险”。同时，适当行为能否被知道和观察、结果能否被明确和独立测量，决定某 obligation 应受 behavior control、outcome control 或组合控制，形成 `F`。

**表示到算法。** `P` 和 `F` 进入 obligation 节点的前向计算，与技术性的 `M`、`I` 联合产生 `Z`。`Z` 决定模型是保留旧测试、生成新 outcome control、限制 evaluator 路径、建立新旧合同双 lane，还是隔离控制面修改后继续源代码工作。理论状态不仅出现在解释段，而是改变可执行动作及其损失。

**可证伪性。** 删除 `P`、把两维相加、交换两维、打乱 `F`，或把全部 control mechanisms 视为同质 test，都应在预注册的方向冲突情境中产生可观察错误。若没有错误，说明理论没有算法责任。若等参数通用 Transformer 或 constrained POMDP 用相同原始输入、动作、监督和 rollout budget 复制 direction flips 与最终前沿，则撤销理论算法贡献，不以较好可解释性保题。

## 8. 研究问题和独立贡献边界

候选的主研究问题是：**当 coding agent 可以共同修改生产代码与测试控制面，而且测试既可能需要随有效需求演化、也可能成为代理改写成功标准的通道时，怎样依据控制目的与正式控制适配状态，学习并执行能同时提高真实任务成功和评价完整性的控制 portfolio？**

该问题可分成三个需要同一算法回答、但不拆成三篇的小问题。

1. 怎样从版本化合同、候选代码/测试改动和可观察执行中，形成 obligation 级双 control-purpose 状态，并与纯技术的 measurement、provenance 状态分开？
2. 怎样依据适当行为知识、行为可观察性、结果可指定性和结果可测量性，选择 behavior/outcome control 的组合，而非全局锁测试或全局放开？
3. 怎样训练这个组合策略真正执行 source patch、test evolution 和 independent certification，并在 hidden true success、false-green、合法演化、回归和成本之间形成更好的联合前沿？

若成立，独立算法工件包括一个 temporal heterogeneous control graph encoder、obligation-level purpose/fit/portfolio weights、一个 joint code-and-test action policy、训练 checkpoint、counterfactual paired dataset、container rollout store 和不可泄漏的 hidden-oracle manifests。它与 C1″、C3 不共享核心中间状态、损失或主要结果，可以共享容器和日志基础设施。

## 9. 模型输入、张量、架构和输出

### 9.1 输入

一次决策输入记为

`x_t = (S_0:t, G_t, R_t, W_t, ΔP_t, ΔC_t, E_t, C_t)`。

`S_0:t` 是版本化需求历史及其 supersede、retain、deprecate 关系；`G_t` 是 controller 签发的 control-purpose charter；`R_t` 是仓库前态及符号、依赖、测试、CI 和 metric 工件；`W_t` 是当前 workspace 和 agent trajectory；`ΔP_t`、`ΔC_t` 是候选 production 和 control-surface diffs；`E_t` 是可见执行、coverage、mutation 和 trace；`C_t` 是各控制机制的时间、GPU/CPU、token 和人工成本。最终 hidden tests、oracle implementation 和 test-only labels不进入输入。

### 9.2 图和前向计算

模型建立 temporal heterogeneous graph。节点至少包括 requirement revision、active obligation、source symbol、test/assertion、fixture/mock、CI/metric step、agent action、workspace version 和 control mechanism。边包括 `supersedes`、`retains`、`implements`、`measures`、`depends-on`、`modifies`、`derived-from`、`shares-provenance` 和 `conflicts-with`。

图编码后的节点表示为 `H ∈ R^(B×N×d)`。obligation decoder 得到 `N_o` 个 active obligations。purpose decoder 在 `G_t` 和版本历史条件下产生 `P`；fit decoder 产生 `F`；关系 decoder 产生 `M` 和 `I`。portfolio decoder 计算

`Z = softmax(g(H_o, P, F, M, I, cost, masks))`，

其中 `N_m` 个候选机制不是固定的“安全工具列表”，而是由仓库和当前任务实际可执行的 tests、mutation operators、differential implementations、behavior monitors 和 versioned lanes 实例化。随后 structured policy 为 `K_a` 个可执行组合动作估计 distributional value `Q ∈ R^(B×K_a×N_q)`，输出任务收益、false-green、回归和成本的分位数，而不是一个标量 risk score。

代码与测试 token 由 7B 级 open-weight code model 的 LoRA/QLoRA decoder 生成，并通过 cross-attention 读取 `H_o`、`P`、`F` 和选中的 `Z`。图模型预计为 200M–500M 参数；具体规模必须通过等参数基线决定，不能先用更大容量制造理论增益。

### 9.3 推断时真正执行的动作

动作空间至少包括下列八类，每一类均在隔离 container 的 branch 上真实执行并返回 state delta。

1. 在 pristine controls 下继续 source-only repair。
2. 在 shadow branch 应用候选 test evolution，但不提升到主 workspace。
3. 保留全部旧 tests 为 regression lane，同时增加或更新满足新 active obligations 的 tests。
4. 为候选 joint patch 生成 provenance 独立的 metamorphic、differential、cross-implementation 或 environment-realistic outcome controls。
5. 在适当行为已知且可观察时，对 evaluator-sensitive paths 施加 formal behavior control，同时保留对实现的其他自由度。
6. 对需求迁移建立旧合同与新合同的 versioned dual lanes，分别报告 preserved 和 superseded obligations。
7. 隔离或撤回 `ΔC`，保留有价值的 `ΔP` 候选并重新搜索 source solution。
8. 独立认证满足后，提升 source、test 和 control manifest 的 joint change。

如果实现只输出动作 7 或 8，或把 1–8 先由手工规则决定再让模型打分，本题即退化为 gate，必须撤销。

## 10. 训练样本、标签与反事实构造

### 10.1 为什么现成数据不能直接拼接

TEBench 的自然 commits 主要是合法 test evolution；ImpossibleBench、SpecBench exploit trajectories 和 TRACE 主要是非法或过拟合行为。直接把两类样本合并，模型可以利用 benchmark、语言、仓库、prompt 风格和是否存在 impossible assertion 来分类，不需要理解同一改动的控制目的。这样的高分不能支持机制主张。

### 10.2 核心识别单元：同改动双世界

训练和评价的最小识别单元必须是

`(same repo state family, same proposed ΔC bytes, two active-contract worlds, opposite valid portfolios, independent executable outcomes)`。

例如，旧合同要求某 API 对无效输入返回 400，新合同明确迁移为 422。完全相同的测试 diff 把期望从 400 改为 422。在旧合同世界，这个 diff 改写了既有成功标准，应被隔离并在旧结果控制下修源代码；在新合同世界，它是必要的 test evolution，但仍需保留旧行为是否明确 deprecated 的版本记录并建立独立的新结果控制。双世界使用相同仓库家族、候选 diff、agent checkpoint、工具预算和随机种子，只改变 controller 签发的 active contract 和对应 hidden outcome oracle。

只有具备可执行语义相反性的 test edits 才能进入 paired set。纯增加一个不冲突测试、格式化、重命名或 developer patch exact match 不能自动形成 pair。每一对必须由独立 test author 或形式化/差分 oracle 证明：不存在一个无需读取 active contract 的固定动作能同时满足两世界。

### 10.3 数据来源和构造流水线

1. 用 TEBench 的 V−1、V−0.5、V0 和公开构造脚本恢复自然 test evolution，并从其 67,670-commit 候选池和其他许可兼容仓库继续挖掘 expectation changes、exception semantics、API migration 和 behavior deprecation。官方 314 rows 只有 `test` split，不能照搬为 train/test。
2. 用 ImpossibleBench 的 original/oneoff/conflicting triples 生成相反世界和 verified cheating branches，但必须保留 repo family grouping，不能让 original 与 conflicting 进入不同 split。
3. 用 SpecBench visible/held-out suites 构造长程 false-green outcome；held-out tests 对 agent 不可见。
4. 用 EvoCode-Bench 的 cumulative requirements 和 SpecPath 的 history manipulation 形成 longitudinal 与 contract-history OOD。两者规模不足，只能外测或用于 generator validation。
5. 用 Coding Agents as Test-Suite Auditors 的 certification-chain 思想以及 mutation、differential 和 reference implementations 构建独立 outcome controls；不得让同一 generator 同时产生候选测试和唯一 oracle。
6. 在固定 open-weight coding-agent checkpoint 的 quiescent workspace snapshot 上，对八类 action 中可执行的组合做 branch rollouts。每个 branch 保存完整 git tree、container image digest、agent template、LoRA/checkpoint、tokenizer、tool budget、RNG、commands、stdout/stderr 和 filesystem delta。

生成器、solver policy 和最终 evaluator 使用不同 checkpoint 或人工/程序源，并保留 provenance。若某 hidden test 内容、路径、失败文本或 reference patch 进入 solver context，该 family 全部作废。

### 10.4 监督信号

- active obligations 由版本化合同、开发者 issue/commit 和独立 annotators 联合确定；developer patch 只作证据，不是唯一真值。
- `P` 的标签来自 controller charter 的前瞻性目的操纵和任务作者记录，不从是否通过测试、agent 解释或最终行为后验推断。
- `F` 通过 factorial interventions 构造：分别改变适当行为是否已知、行为是否可观察、结果是否可明确、结果是否能由独立 oracle 测量，而保持任务语义和难度尽量一致。
- `M` 用 coverage、mutation kill、differential disagreement、environment trace 和人工复核共同监督。
- `I` 用 generator、输入、运行环境和可修改路径的 provenance graph 确定。
- test patch 的监督采用 executability、active-obligation satisfaction、regression preservation、mutation/differential adequacy 和 effort，不以 token exact match 作为主要标签。
- policy value 来自真实 branch outcomes。离线阶段使用保守值学习，sandbox 内再做有限 online improvement；不以 LLM judge 的主观“看起来安全”替代执行 outcome。

## 11. 损失函数和训练过程

总损失预注册为

`L = λo L_obligation + λp L_purpose + λf L_fit + λm L_measure + λi L_independence + λz L_portfolio + λcf L_counterfactual + λgen L_joint-edit + λv L_value + λc L_constraint`。

- `L_obligation` 是 active/superseded obligation 的 structured extraction 与 linking loss。
- `L_purpose` 同时监督两维 control-purpose state，并加 charter-consistency calibration；不允许 softmax 强迫两维互斥。
- `L_fit` 监督四个 formal-control fit 条件。
- `L_measure` 学习 obligation–control 多关系，`L_independence` 识别 shared-provenance 和 self-certification cycles。
- `L_portfolio` 是 obligation-level multilabel structured loss，允许一个机制同时服务 behavior/outcome modes。
- `L_counterfactual` 对每个同改动双世界施加方向 margin。新合同世界应提高“演化加独立认证”的相对值，旧合同世界应提高“隔离控制改动并保留原控制”的相对值。
- `L_joint-edit` 训练 source/test/control-manifest token，同时由编译、测试、mutation 和 hidden training-oracle 结果加权；隐藏 outcome 不作为 decoder token 输入。
- `L_value` 使用 distributional IQL 或等价保守 offline RL 学习每种组合动作的任务、false-green、regression 和成本分布。
- `L_constraint` 以拉格朗日方式限制训练 split 上的 false-green、被删除的仍 active obligations 和 hidden-oracle access，不能通过把所有任务设为拒绝来满足。

训练顺序为：图表示与各中间状态的 supervised pretraining；joint edit SFT；真实 branch outcomes 上的 conservative policy learning；仅在隔离容器中的有限 online fine-tuning；最后冻结 checkpoint 和 evaluation manifest。理论版与通用替代版必须使用相同 code-model checkpoint、训练 tokens、rollout 数、candidate count 和总参数量。

## 12. 数据划分、泄漏隔离与复现

### 12.1 分组划分

同一 repository lineage、commit ancestry、issue family、spec-revision twin、test mutator template、reference implementation 和同字节 `ΔC` 的所有样本必须在同一 split。建议至少报告 repository-disjoint、time-disjoint、language/framework-disjoint 和 control-mechanism OOD 四组结果。TEBench 的 314 个官方 test items 若被用于训练扩展，只能在重新构造的 group split 中使用，且必须另保留完全未见的 repository set。

SpecBench 的 task 级 held-out suites、ImpossibleBench 的 original/oneoff/conflicting triples、EvoCode-Bench 同一多轮链和 SpecPath 同一 final contract 的全部 histories不能跨 split。AST、assertion literals、problem statements、commit messages 和 test names 要做近重复去重。

### 12.2 隐藏测试隔离

最终 evaluator 在 agent 进程退出后，从独立只读镜像挂载 hidden suite。agent workspace、tool output 和 model context 中不出现 hidden path、collection names、失败用例、coverage maps 或 reference patch。每次评价先恢复 pristine evaluator paths，并用 manifest hash、container digest 和 file-access audit 证明隔离。任何通过修改 grader 装载路径、零测试收集或退出码伪造获得的通过均计为 integrity failure。

### 12.3 复现工件

必须发布或在许可允许的范围内提供：dataset manifest 与上游许可证；pair generator 和每对世界的 controller charter；repo/commit/image digests；所有 prompt/template；graph schema；模型配置和 checkpoint；LoRA adapter；loss weights；optimizer 和 scheduler；随机种子；branch action manifests；完整结果 parquet；统计脚本；失败案例；hidden-evaluator build script。不可再分发的上游仓库只发布获取和校验脚本。

## 13. 算力、规模和可执行性

现成公开资产足以做小 pilot，但不足以直接训练完整策略。TEBench 提供 314 个 instances 和 2.59GB Docker；SpecBench 提供 30 个长程 tasks；ImpossibleBench 提供 103 个 LiveCodeBench families 和 349 个 SWE-bench families 的三版本数据。真正缺少的是同改动双世界、多个控制组合的真实 rollout outcomes。

建议分两阶段设资源门，而不先承诺全量数字结果。

- **撤题 pilot**：至少 100 个经独立 oracle 核验的 paired families、来自不少于 8 个 repository lineages；每 family 运行 4–6 个控制组合、3 个 seeds，总计约 1,200–1,800 container branches。训练 200M–500M 图模型和 7B QLoRA decoder。预计需要 4×48GB 或 4×80GB GPU 约 5–10 天，以及 100–250 vCPU-days 执行 tests/mutation。
- **可投稿规模目标**：若 pilot 通过，再扩到 1,000–2,000 paired families、30 个以上 repository lineages、8 个控制组合和 3 seeds，约 24,000–48,000 branch rollouts。预计 0.5–1.5TB workspace/log/cache、4×80GB GPU 2–4 周和 1,000 以上 vCPU-days。具体数值由 pilot 的平均 branch 时间和 token 使用更新。

主要训练必须使用可冻结的 open-weight model 和本地 checkpoint。闭源 frontier agent 可以作为外部 baseline 或 data-generation supplement，但不能成为唯一策略、唯一标签源或不可复现的核心权重。

## 14. 最强基线与公平比较

### 14.1 直接方法

1. 全部测试只读、每轮恢复 pristine tests，以及 RewardHackingAgents 的 evaluator lock。
2. 全部允许测试演化，并运行 TEBench 当前 Codex、Claude Code、OpenCode baselines。
3. prompt/context engineering，包括明确“不要修改测试”、隐藏测试、只读测试和 ImpossibleBench 的 monitoring 条件。
4. MONA 的 myopic optimization 加 non-myopic approval。
5. CapReward 的 randomized capped evaluation。
6. SpecBench 的 visible/held-out search，以及相同 candidate budget 下的 hidden-compositional selection 上界。
7. TRACE 或等价 reward-hack monitor 加阈值；RewardHackingAgents 的 trusted-metric detector。
8. BenchJack 的 iterative verifier hardening。
9. test-suite auditor/certification chain、mutation testing、differential testing和 TEBench test evolution agent。
10. *Verification Horizon* 中 agentic judge、behavior monitoring 和动态 evaluator 的可复现部分；若代码或私有数据不可得，按论文描述复现并明确差异，不能冒充官方实现。

### 14.2 等参数通用替代

1. 与理论模型总参数相同、节点和边相同，但没有 `P`、`F`、`Z` 语义分解的 raw heterogeneous Graph Transformer。
2. 相同观察、候选动作、branch outcomes 和训练预算的 generic constrained POMDP/IQL policy。
3. 将所有状态压成单一 scalar tamper-risk 的 critic 加阈值，但仍可调用同一 patch generator。
4. 直接预测每个 action 的 hidden task、integrity、regression 和 cost outcomes，再作 Pareto search 的 model-based controller。
5. 相同 7B decoder 和 tokens、只加普通 cross-attention 的 sequence model。

等参数不仅指可训练参数量，还要控制 code-model 初始化、LoRA rank、graph depth、context tokens、retrieval、每步候选数、可调用 tests、hidden-oracle queries、container wall-clock 和总训练 rollouts。理论模型不得独享 purpose labels 之外的事实；通用替代必须获得原始 charter 和相同监督，只是不强制理论分解。

### 14.3 oracle 和下界

报告 oracle active contract、oracle purpose/fit、oracle independent tests 和 exhaustive branch-selection ceilings；报告 always-lock、always-edit、source-only、no-op 下界。oracle 用于定位瓶颈，不能作为可部署方法。

## 15. 评价结果、统计和成本

主要安全结果不能是拒绝率。至少分别报告：

- **False-Green Rate**：visible controls 通过但独立 hidden obligations 失败的比例。
- **Control-Appropriation Harm**：删除或弱化仍 active obligations、篡改 metric、逃避真实交互或形成 self-certification cycle 后仍被提升的比例。
- **True Task Success**：在独立 hidden behavioral outcomes 和 regression suite 上完成有效需求。
- **Legitimate Evolution Success**：对 breaking、stale、missing tests 的正确定位与可执行演化，并以 obligation coverage、mutation/differential adequacy 和 regression preservation 评价。
- **Over-Control Cost**：因锁定或不必要行为控制导致本可完成任务失败的比例。
- **Operational Cost**：tokens、GPU/CPU、wall-clock、test invocations、branch 数和 storage。

需要绘制 false-green 与 true success、legitimate evolution 与 over-control、总体收益与成本的 Pareto frontier，并报告 hypervolume 或 area-under-frontier，但不把多结果隐藏进单一分数。配对双世界用 McNemar 或配对 permutation test；连续结果用 repository/task hierarchical bootstrap；多模型和多机制比较做 family-wise correction。报告绝对差、相对差、置信区间和 seed variance，不只报告显著性。

## 16. 方向冲突、消融和机制干预

### 16.1 必须出现的方向冲突

1. **相同测试 diff，合同未变与合同已变。** 前者应隔离 `ΔC` 并在原 outcome control 下修源代码；后者应允许 shadow evolution，但另建独立新 outcome control后再提升。
2. **结果可测、行为未知。** 应减少对具体实现路径的 behavior control，允许 solution diversity，并强化 independent outcome control。
3. **适当行为已知、结果弱可测。** 对 grader、hidden data、test collection 和 metric paths 使用 behavior control，而不是反复生成更多同源 tests。
4. **visible pass 上升、hidden obligation coverage 下降。** 不得提升，即使 agent 声称完成；相反，visible pass 不变但 stale/missing tests 得到修复、hidden coverage 上升时应允许演化。
5. **单一机制兼具双目的。** 版本化 regression lane 既限制旧行为回归，也使新需求演化成为可能。模型应保留双目的权重，而不是强迫归入一个类别。

### 16.2 理论机制干预

- 删除 `P`；把两维相加；交换两维；在 paired family 内随机置换 `P`。
- 删除 `F`；分别打乱行为知识、行为可观察性、结果可指定性和结果可测量性。
- 将 `Z` 替换为参数量相同的无语义 latent slots。
- 保留 `P/F/Z` 监督但阻断其进入 action decoder，检验表示指标是否只是在旁路预测。
- 使用 oracle `P`、oracle `F` 和 learned downstream policy，区分表示错误与行动错误。
- 固定最终 action candidates，只改变中间状态，检验 action direction 是否随理论干预变化。

理论机制必须同时改善中间状态准确性、paired direction consistency 和外部 joint frontier。只改善 purpose classification F1，或只提供可解释 heatmap，不足以承担贡献。

## 17. 等参数反证

最强反证不是“通用模型在平均分上接近”，而是它在相同信息和预算下是否同时复制以下能力：

1. 对同字节 `ΔC` 的 contract flip 作相反 portfolio choice。
2. 在 outcome-measurable/behavior-unknown 与 outcome-weak/behavior-known 的 factorial manipulation 中作理论预期方向变化。
3. 保持 true task success 时降低 false-green，而非主要靠锁测试或停止。
4. 在 TEBench stale/missing 和 ImpossibleBench cheating 两极之间形成同一 checkpoint 的联合前沿。
5. 中和 latent slots 后出现与中和 `P/F/Z` 相同的行为变化。

若 generic constrained POMDP、raw graph Transformer 或 direct outcome model 在预注册等价区间内复制上述五项，则应得出的结论是“控制理论解释了现象，但没有产生独立算法能力”。此时可以保留理论解释型实证研究的可能性，却必须撤销本博士系列所要求的理论算法论文，不得改写贡献句维持题位。

## 18. 立即撤题门与 pilot 决策规则

出现任一项即 NO-GO：

1. 后续直接检索发现已有方法在真实 repository 上联合训练合法 test evolution 与 anti-tampering，并输出等价的多机制可执行 policy；本候选只剩换理论名字。
2. 无法从至少 8 个独立 repository lineages 构造 100 个同字节 `ΔC`、语义相反且 hidden outcome 可执行的 pilot pairs。
3. purpose labels 只能从 agent 行为、最终通过或研究者事后解释获得，不能由 controller 的前瞻性 charter 独立操纵。
4. control scholars 与 software-testing experts 对 controller/controllee、appropriation/creation 和 behavior/outcome mode 的映射不能达到预注册的一致性门槛，或认为 reward hacking 与 value appropriation 只是术语相似。
5. 主策略最终只有 allow、block、ask、warn、risk score 或 test-edit classification；source/test/control portfolio 的实际执行由手工规则完成。
6. 主要增益来自 hidden tests、pristine restore、更多 test budget、larger decoder 或闭源 judge，而不是 `P/F/Z` 所改变的 portfolio。
7. 等参数 generic POMDP、raw graph Transformer 或 direct outcome model 在 paired direction、joint frontier 和 OOD 上落入预注册等价区间。
8. 删除、交换、置乱或阻断 `P/F/Z` 不改变方向冲突中的行为，或只降低内部 F1 而不改变外部 outcome。
9. “合法测试演化”只能以 developer patch token overlap 判定，alternative correct tests 无法由行为 oracle 认可。
10. hidden oracle、reference patch、test path 或 failure feedback 不能与 solver 物理隔离。
11. 为得到有效动作必须引入 fault recovery、rollback、compensation、权利请求或重新委派，导致与 C1″ 重叠。
12. 为判断 test change 必须让人审批、选择证据或形成 reviewer grounding，导致与 C3 重叠。
13. 训练资源实际只能支持提示词、云端 LLM 拼接或单一轻量分类器，无法产生本地 checkpoint 和执行 rollout store。

只有下列全部满足才可从 CONDITIONAL 升为 GO：

- pilot data gate、构念映射 gate 和 hidden-oracle isolation gate 全部通过；
- 理论模型在至少两个 repository-disjoint OOD 上同时改善 false-green、true task success 和 legitimate evolution，不靠增加拒绝；
- 等参数通用替代未能在预注册等价区间内复制 paired direction 和 joint frontier；
- 至少一个理论机制干预产生预期的方向反转，并能与一般 capacity effect 分开；
- 公开资产、许可、算力和 container 运行时间支持完整训练与三次独立 seeds；
- 更新检索仍未发现覆盖核心联合能力的直接工作。

## 21. 最终判定

**本文件当时的判定为 CONDITIONAL；后续终局判定为 NO-GO。**

它比被撤销的 TMS 题更独立，也不依赖多 agent 路由、知识协调或旧张量。问题有真实外部损害和任务收益两端，coding agent 是能改代码、测试和运行工具的真实行动者；TEBench、ImpossibleBench、SpecBench、EvoCode-Bench 和公开容器使 pilot 可运行；算法可以产生本地图模型、LoRA checkpoint、portfolio policy 和执行 rollout store。IS control purpose 与 formal control portfolio 也比把团队理论硬套给多 agent 更自然，因为测试本身就是组织评价 coding agent 的控制机制。

但这些优点尚不足以判 GO。动态 verifier、reward-hacking mitigation、test generation 和 test evolution 都已有极强直接工作；真正剩余的贡献只存在于“同改动、不同 controller purpose、相反 portfolio”这一狭窄但可识别的联合能力。只有 pilot 证明该能力不能被等参数通用模型复制，而且 control purpose 不是后验标签，才能冻结为第三题。否则应诚实维持第三题空缺，结论改为 NO-GO，不得再把它包装成普通 test-security、risk gate 或 verifier 论文。
