# 执行者—验证者分离候选终审

## 0. 终审结论

**终局判定：NO-GO，不冻结为三篇论文中的独立一篇。置信度：高。证据截止：2026 年 8 月 15 日。**

本候选试图在 coding agent 形成 patch 之后，让一个学习型策略在异构模型、测试生成器、静态分析器、动态执行工具与安全验证器之间序贯取证，随后自主决定提交 patch 或将其退回继续修复。它瞄准的真实损害是“可见测试已经通过，隐藏功能回归、后门或漏洞却仍被放行”，因而问题本身属于 coding agent 的广义安全，而非在普通代码排序任务上附加安全标签。问题重要性不构成独立贡献的充分条件。现有工作已经分别占据了这项候选的关键算法动作、机制与结果空间：

1. Hua 等已经把“下一步调用哪个尚未调用的监控器、何时干预、何时终止以及如何受平均成本约束”写成具有相同动作语义的 POMDP，并在 BigCodeBench 后门代码上评价低成本条件下的干预召回率。[Hua et al. 2025](https://arxiv.org/html/2507.15886)
2. Koran 等已经以监控器质量和攻击样本上的低残差相关性选择组合，在公开 APPS ControlArena 与 BCB-S 数据上测量固定低误报率下的后门检出，并公开代码与数据。[Koran et al. 2026](https://arxiv.org/html/2605.15377)
3. RETRACE 已经把独立 patch 核验连接到 Submit、Revise-Patch、Revisit-Reasoning 与 Revise-Both 等机器动作；Scaling Agentic Verifier 已经训练会主动生成区分性测试的验证 agent；Agentic Rubrics 与 SWT-Bench 已经把仓库上下文、独立测试或情境化 rubric 用于 patch 核验。[Li et al. 2026](https://arxiv.org/html/2608.08950) [Ma et al. 2026](https://arxiv.org/html/2602.04254) [Raghavendra et al. 2026](https://arxiv.org/html/2601.04171) [Mündler et al. 2025](https://arxiv.org/html/2406.12952)
4. Warranting theory 与 separation of duties 能推出“证据不应由被评价的执行者自由操纵”和“执行与批准不得由同一责任主体完成”，却不能推出模型家族之间的统计误差独立性、下一验证器的最优次序或成本预算下的停止边界。把理论状态实现为 source-id、provider-id 或一个禁止自审的掩码之后，剩余能力仍由 Hua 式序贯控制和 Koran 式经验相关结构承担。

因此，候选目前剩余的新意是把若干已有验证能力接入同一仓库级流水线并建立新的交叉运行数据。该工作可以成为其他论文的实验基础设施、数据资产或重要基线，但尚不足以承担 ISR 级独立论文的理论—算法贡献。这里的 NO-GO 不是基于“通用 Transformer 在无限数据下可以表达任何函数”这一空泛反证。判定依据是：在相同输入、相同训练样本、相同参数规模与相同验证预算下，直接近邻已经覆盖核心行动；IS 理论当前只能提供硬约束或来源可操纵性字段，尚未给出能够在有限样本和分布外情境中产生独特方向选择的结构归纳偏置。

本文件没有报告任何已经运行的实验。所有模型设计、样本规模与算力数字均为终审所需的预冻结规格或规划估算，不能写成经验结果。

## 1. 候选的精确定义与范围冻结

### 1.1 决策单元

审计后保留的最窄、最可识别单元是一次**仓库级 patch 的提交前验证**。任务输入包括问题描述或变更请求、冻结的仓库快照、coding agent 的轨迹与候选 diff；算法在每一步观察已经获得的验证证据和剩余预算，选择新的验证动作，最终选择提交当前 patch 或退回 coding agent 继续修复。所谓执行者是产生当前 patch 的模型和工具链，验证者是没有参与该 patch 生成且能够产生新证据的模型、测试生成器或确定性工具。

本候选不同时研究任意 shell command。命令的安全结果可能是文件删除、凭据泄露、部署事故或权限越界，其反事实结果、可逆性和验证器集合与 patch 的隐藏回归并不共用同一标签空间。把 patch 与 command 合并只会以一个抽象的“风险分数”掩盖两种不同的决策过程。若将来研究命令，应当另建带隔离沙箱、状态快照、权限边界与恢复成本的行动环境。

### 1.2 风险时点、受影响对象与可见信息

风险发生在 coding agent 已经生成可应用的 diff、尚未向目标分支提交或部署的时点。直接受影响对象包括仓库所有者、后续开发者、依赖该软件的用户以及承担事故责任的组织。算法能够观察任务文本、仓库代码与依赖图、diff、agent 轨迹、公开测试、已调用工具的原始输出、每类验证器的版本、成本、权限与 provenance。算法不能观察隔离的隐藏测试、未触发的安全 PoC、未来依赖版本、生产流量以及模型训练语料重叠造成的共同盲点。

主要风险结果必须是下列外部结果之一，而不能是验证者同意率或静态警告数：

- 在公开测试通过的条件下，patch 仍在封存隐藏测试上失败却被提交；
- 修复已知 CVE 的 patch 仍可被隔离 PoC 利用却被提交；
- 含后门或触发器的实现逃过监控而被提交；
- 原本正确且安全的 patch 因过度保守而被持续退回，导致任务失败、延迟或人工负担增加。

相应的主要评价是固定正常任务成功率或固定低误报率下的有害 patch 接受率，而不是通过拒绝所有 patch 获得表面安全。

### 1.3 机器自主验证与 C3 的边界

本候选的推断动作完全由机器执行，输出是 invoke-next-verifier、submit 或 return-to-repair。人可以在数据构造阶段标注结果，也可以在实验治理层监督隔离环境，但人类是否相信证据、如何阅读证据、是否批准行动以及证据展示如何影响信任校准均不属于研究结果。C3 若研究人类可信取证与审批，其分析单位、理论状态、因变量和实验参与者均不同。本候选不能用人类审核质量来补足机器策略缺少的贡献。

### 2.2 “跨模型分离”已是显性命题

Futsu 2026 的 position paper 明确主张由一个 agent 生成、另一个 agent 核验，强调独立上下文、独立目标并优先使用不同基础模型。[Futsu Research 2026](https://futsu.cloud/research/generator-verifier-separation) 该材料没有专有 benchmark 数字，也没有证明跨 provider 一定带来增量，因而证据权重远低于正式实证论文。它仍有一项有限作用：跨模型 generator–verifier separation 已经是公开、显性的设计主张，不能作为本研究单独的概念创新。

### 2.3 “proof-carrying action”也不能自动救援

Proof-Carrying Agent Actions 与 CAVA 一类工作已讨论把 action identity、审批绑定、执行 receipt、attestation 与证据闭包封装为可机器检查的行动证据。[Wang 2026a](https://arxiv.org/abs/2606.04104) [Wang 2026b](https://arxiv.org/abs/2607.13716) 这类工作说明 provenance 与不可抵赖证据可以构成基础设施，却没有学习下一验证器或 patch 修复策略。若候选只增加证据 envelope，贡献会转成协议设计；若仍以学习策略为中心，证据 envelope 应作为输入控制，不是算法新意。

## 3. 本地 AIS 理论回读：理论能负责什么

### 3.1 Warranting theory

Lausen、Clapham、Siering 与 Gomber 在金融中介不当行为识别中使用 warranting theory，核心区分是信息是否容易被被评价者操纵。作者把受监管机构 FINRA 的外部核验信息视为比未知用户确认更可靠的 warrant，并将经过核验的特征加入分类器。[本地全文](../database_fulltext_all/00790_2020_who-is-the-next-wolf-of-wall-street-detection-of-financial-intermediary-misconduct.md) 这一理论可以为 coding agent 验证导出“执行者对证据生成、证据内容和验证环境的可操纵性”状态。它不能从 provider 名称推出两个 verifier 的条件误差独立，也不能决定先跑静态分析、测试生成还是 PoC。

可承担的算法责任是构造执行者—证据控制关系 C，并限制执行者不能修改 verifier、隐藏测试、完成工件或验证日志。不可承担的责任是把 C 当作经验残差相关矩阵 R，或把“来源不同”直接写成更高权重。

### 3.2 Separation of duties 与内部控制

Basu 与 Kumar 对 workflow separation of duties 的定义是同一流程中的两项任务不能由同一个人执行，典型例子包括不得自我批准与需要两人签名。[本地全文](../database_fulltext_all/26434_2002_research-commentary-workflow-management-issues-in-e-business.md) Li、Peters、Richardson 与 Watson 的控制弱点研究进一步指出，不受限制的访问以及在缺少独立监控、复核或授权时由同一主体创建、审查和处理信息，会威胁系统及其安全。[本地全文](../database_fulltext_all/00258_2012_the-consequences-of-information-technology-control-weaknesses-on-management-information-systems.md)

这两项文献可以导出硬约束：当前 patch 的生成主体不得成为唯一终端核验主体；执行者不能改写封存 oracle 或验证日志。它们没有提供“两个独立 verifier 之间何者先调用”的排序函数。只要等参数通用策略也接受同一硬掩码，separation of duties 便不再是模型结构的独占来源。

### 3.3 Control portfolio、可观测性与成本

Tiwana 区分 outcome control 与 behavior control，并说明有效控制取决于偏差能否被准确核验和评价信息是否可靠；不同控制具有不同的信息要求，增加控制数量也未必总能改善结果，因为可测性、可观测性与成本必须共同考虑。[本地全文](../database_fulltext_all/02830_2010_systems-development-ambidexterity-explaining-the-complementary-and-substitutive-roles-of-formal.md) 这为“验证器组合不能只求数量，必须考虑证据内容和成本”提供组织控制依据。然而，论文没有给出 verifier 残差图、贝叶斯更新、调用次序或停止规则。把成本、可观测性和工具类别编码为特征之后，核心控制问题仍与 Hua 的成本约束监控策略重合。

### 3.4 Substantive assurance

Spears、Barki 与 Barton 区分象征性与实质性 assurance，并强调成熟 assurance 需要客观、定量的控制指标、结果比较与纠正。[本地全文](../database_fulltext_all/00286_2013_theorizing-the-concept-and-role-of-assurance-in-information-systems-security.md) 这一理论直接约束评价：静态警告数量、judge 自信度或解释流畅性不能替代封存隐藏测试、PoC、后门检出与正常 patch 接受率。它能改变标签与结果测量，却仍不唯一决定序贯策略的神经计算。

### 3.5 理论责任边界表

| 理论命题 | 可进入的不可替代状态或约束 | 不得越权解释的能力 | 当前判定 |
|---|---|---|---|
| 难以被被评价者操纵的信息具有更强 warrant | 细粒度控制关系 C：谁能写 verifier、测试、日志、环境和证据内容 | 统计误差独立、模型家族多样性、最优次序 | 可形成硬结构，但不足以独立成篇 |
| 职责分离防止同一主体自我批准 | generator 与 terminal verifier 的身份不相交掩码；不可变 oracle | 哪个独立 verifier 更准确，多个独立 verifier 是否共同失误 | 可作为必要约束，可由所有基线共享 |
| 控制组合受可观测性、可测性与成本约束 | verifier 能观测的对象、成本与延迟字段；预算约束 | 联合误差分布与调用策略 | 直接落入既有成本约束组合问题 |
| 实质 assurance 依赖客观指标与纠正 | hidden test、PoC、后门逃逸、错误拒绝与成本的联合结果 | 学习架构 | 强化评价有效性，不产生独占算法 |

理论审计的关键结果是：C 表示**谁能操纵证据**，R 表示**验证器在真实结果上如何共同犯错**。两者既不等价，也没有确定的单调关系。跨 provider 的 verifier 可能因共同训练语料和解题范式而高度相关；同一组织维护的编译器和测试执行器虽非组织独立主体，却可能提供难以由 coding agent 操纵且高度互补的证据。若算法真正依赖 R，性能来源是经验联合误差学习；若只依赖 C，它无法处理相关盲点。当前候选尚未证明 IS 理论如何独特地连接 C 与 R。

## 4. 按肖老师 MEC→MAP→ALG 标准作最强救援推导

本节不是建议保留候选，而是把它推到最强可实现形态后再审查。推导遵循肖老师两篇 ISR 论文的责任链：先说明一般模型系统性遗漏的机制 MEC，再把机制变成模型中不可替代的状态 MAP，最后让该状态改变前向计算、损失与行动 ALG。仅在引言中出现“独立验证”不计入理论贡献。

### 4.1 MEC：共同来源依赖会制造虚假证据增量

同一 coding agent 产生 patch、解释、自写测试与修复说明时，这些证据受到共同目标和共同上下文控制。即使另换一个模型充当 judge，两个模型仍可能因共享训练语料、基础架构、公开测试和问题表述而产生相关错误。Kim 等在 350 余个 LLM 上发现模型错误存在显著重合，且共同 provider 或架构只是相关性的部分来源。[Kim et al. 2025](https://proceedings.mlr.press/v267/kim25e.html) 因此，证据数量不是有效信息量，模型身份差异也不是条件独立的充分证据。

一般的平均投票或独立 risk head 系统性忽略两类关系。第一类是执行者对证据形成过程的控制关系；第二类是各验证器在真实隐藏结果条件下的残差相关关系。前者属于 warranting 与职责分离，后者必须由联合运行数据识别。只有当两类关系共同进入决策，才能区分“来源独立但共同盲目”和“组织来源相近但证据机制互补”。

### 4.2 MAP：双图状态而非 source-id

最强映射需要两个可审计图。

- 控制图 C 的节点包括 patch generator、测试生成器、verifier、仓库快照、隐藏 oracle、执行容器、日志与提交动作；有向边表示主体是否可以创建、修改、筛选或隐藏某项证据。边值至少区分可控制、不可控制与未知，不能只记录 provider-id。
- 残差图 R_t 的节点是候选验证器；边表示在任务、patch 类型与已经观察证据条件下，两验证器错误事件的后验依赖及其不确定性。R_t 必须来自历史交叉执行和当前证据更新，不能由“不同模型家族”手工赋值。

理论只直接产生 C 的语义和硬约束。R_t 是为了使风险问题可解而加入的统计状态，不应伪称由 warranting theory 推出。候选要获得理论算法贡献，必须证明 C 在相同数据与预算下带来有限样本或分布外增益，而且该增益不能由把 C 当作普通元数据的等参数通用策略复制。

### 4.3 ALG：最强但尚未通过反证的工件

一个可被严肃检验的候选工件暂称 Dependency-Aware Verification Policy。批量大小为 B，候选 verifier 数为 M，仓库图节点数为 N，已取得证据长度为 t。其输入与中间张量至少为：

- 仓库—任务表示 H ∈ R^(B×N×d_h)，节点覆盖问题约束、AST、调用与依赖关系、diff hunk、测试和 agent 轨迹，带节点类型与可见性掩码；
- verifier 集合表示 V ∈ R^(B×M×d_v)，包含工具类型、模型与版本、证据通道、延迟、货币或算力成本、权限和生成祖先；
- 控制关系 C ∈ {0,1,?}^(B×M×K)，描述每个 verifier 输出的 K 个证据组成部分是否可被执行者影响；
- 残差依赖 R_t ∈ R^(B×M×M×d_r)，同时表示方向性依赖、样本量和后验不确定性；
- 已观察证据 Y_t ∈ R^(B×t×d_y)、已调用掩码 U_t ∈ {0,1}^(B×M)、剩余预算 b_t ∈ R^B。

前向计算可以由仓库异质图编码器、verifier set encoder、控制图 message passing、残差图更新器与 pointer action decoder 组成。硬职责分离掩码先阻止生成者成为唯一终端 verifier；decoder 再在 invoke verifier m、invoke independent test generator、run static/dynamic/fuzz/PoC、submit 和 return-to-repair 中选择动作。若模型只输出一个终端风险分数，候选会退化为 LEVER 式 learned verifier；若只对 verifier 排序，候选会退化为普通 portfolio routing。

设 z_i 表示封存 oracle 判定的有害 patch，e_im 表示 verifier m 在 patch i 上的完整证据，a_it 表示策略动作。最小训练目标应同时包含：

L = λ_joint L_joint(e_i1:M, z_i) + λ_cal L_cal(p_i, z_i) + λ_policy L_policy(a_i1:T) + λ_cost E[cost_i] + λ_safe L_constraint。

其中 L_joint 学习条件联合错误而非独立分数，L_cal 约束终端有害接受概率的校准，L_policy 通过具有完整或随机化反事实覆盖的离线策略数据学习下一动作，L_cost 计入真实时延与计算成本，L_constraint 使正常 patch 接受率或任务成功率不低于预注册阈值。C 通过图计算和硬掩码进入前向路径，不能只在损失末端增加一个小权重。R_t 必须随新证据更新，并携带稀疏任务上的不确定性。

推断时的真正动作是运行一个尚未运行的工具或验证 agent、把原始结果写入不可变证据日志、更新双图状态，并在预算耗尽前决定提交或退回。返回修复若只是“拒绝并让原 agent 自行再试”，它与 Hua 的 intervention 在决策层等价。若论文声称学习如何继续修复，就必须进一步定义传给修复 agent 的反馈内容、修复动作与新 patch 的转移分布；这会产生指数增长的分支数据，也会进入 RETRACE 已覆盖的 patch/reasoning 修订空间。当前候选没有一个同时可识别且独立于近邻的修复机制。

### 4.4 冲突情境中的理论方向

理论机制至少应在下列预注册冲突集中产生方向明确且可观察的不同选择：

1. verifier A 与执行者完全隔离，但其历史错误与已调用 verifier 高度相关；verifier B 的组织来源较近，却通过不可写的编译器或 PoC 给出互补证据。纯职责分离偏好 A，经验残差策略可能偏好 B。
2. 两个不同 provider 的 LLM judge 对某类依赖更新共同漏判，一个同 provider 维护的动态测试工具能够触发真实回归。source-id 多样性会选错，证据机制多样性应选后者。
3. 廉价 rubric judge 给出高置信通过，昂贵 PoC 或封存回归测试尚未执行。substantive assurance 要求在高影响 patch 上支付可核验结果的成本，但低影响文档 patch 不应一律执行昂贵工具。

这些冲突也揭示救援困难。理论之间可能给出相反排序，却没有提供解决冲突的定量规则；最后仍需由经验结果和成本函数裁决。若所谓理论模块的收益只来自向模型提供 C、R 与成本这些额外信息，公平通用基线也必须获得同样信息。

## 5. 公开数据、标签与策略识别

### 5.1 可用资源及其缺口

| 资源 | 分析单元与真实标签 | 可支持的部分 | 不能直接支持的部分 |
|---|---|---|---|
| SWE-bench Verified | 真实仓库 issue、候选 patch 与测试结果 | 仓库级功能修复、跨仓库划分、候选 agent patch | 安全 PoC、多 verifier 全交叉输出、调用成本 |
| SWT-Bench | 真实 bug-fix、gold patch、gold test 及 fail-before/pass-after | 独立测试生成、隐藏功能回归 | 恶意后门、权限风险、序贯政策日志 |
| PatchEval-Verified | 230 个 CVE，Docker 环境与 PoC 式 exploitability 检查；公开[仓库](https://github.com/bytedance/PatchEval) | 已知漏洞修复的真实安全结果；不是 exact-match gold patch | 规模较小；没有自然形成的多 verifier 轨迹；patch_url 等元数据需隔离 |
| APPS ControlArena / BCB-S | 正常与攻击代码、监控分数、低 FPR 后门结果 | 监控器相关性、恶意代码逃逸、分布外攻击类型 | 非真实仓库 patch；缺少仓库依赖与修复循环 |
| CodeMonitorBench | 公开测试已通过但隐藏测试失败的候选 | false-green 结果与低 FPR 评价 | 数据下载状态未核验；不是仓库 diff |
| RuVerBench | 人工 rubric satisfaction | judge 可靠性和错误重合 | 不能替代隐藏测试、PoC 或实际回归 |
| Terminal Wrench | verifier exploit 与 hardening 轨迹 | reward hacking、验证器薄弱点 | 验证的是 benchmark harness，不是提交前 patch |
| Defects4J/RGT patch corpora | 多修复工具 patch 与大规模随机测试结果 | 过拟合 patch assessment、历史基线 | 新型 agent 轨迹、安全漏洞和异构 verifier 元数据不足 |

不存在一个已核验的公开数据集同时提供以下五项：仓库级 coding-agent patch、每个异构 verifier 对每个 patch 的原始输出、每次调用的真实成本、序贯选择的反事实结果，以及封存功能与安全损害标签。因此，数据工程不是下载后训练，而是必须建立新的全交叉运行矩阵。

### 5.2 训练样本构造

可识别的训练样本应以 task–repository–patch 为主键。候选 patch 必须由多个 agent 家族、不同时间版本与多随机种子生成，并保留完整 provenance。对一部分分层抽样 patch，应执行全部候选 verifier，形成 e_i1:M 的近完整矩阵；对其余 patch，应以已知概率随机调用 verifier，记录 propensity，避免“只在看起来危险时才跑昂贵工具”造成 missing-not-at-random。LLM verifier 的随机输出需要固定温度、采样数和随机种子并重复运行，确定性工具也要冻结容器、规则版本和 timeout。

封存标签来自独立维护的隐藏功能测试、隔离 PoC、后门触发器和人工复核后的真实回归，不得由正在学习的 verifier 自己生成。SWE-bench 的 gold patch、SWT-Bench 的 golden tests、PatchEval 的 patch_url、fix function 提示和 CodeMonitorBench 的隐藏测试不能进入模型输入、检索索引或 agent 轨迹。若先用隐藏测试筛选候选再训练 verifier，也会形成标签选择泄漏。

### 5.3 return-to-repair 的识别断点

一次 verifier 调用的反事实可以通过全交叉执行或随机化估计；一次 return-to-repair 会改变后续 patch，因而需要对“反馈内容—修复 agent—新 patch—后续 verifier”整条转移进行采样。仅有历史日志时，未选择的修复反馈和未生成的新 patch 不可观察。候选有两个选择：

- 把 return-to-repair 当作终端拒绝，不学习修复转移。这样数据可识别，但动作层与 Hua 的 intervention 基本相同。
- 学习修复反馈与转移。这样可能形成新问题，却必须构造分支轨迹、处理策略依赖的选择偏差，并与 RETRACE 的修订动作直接比较；当前公开数据不支持这一完整反事实树。

这个断点是 NO-GO 的实质原因之一。候选目前在表述上同时索取“简单终端决策的可行性”和“学习修复循环的新颖性”，两者不能由同一份数据规格免费获得。

### 5.4 划分与隐藏测试隔离

最低限度需要五类互不替代的分布外划分：

- repository split，测试仓库与训练仓库完全不重合；
- chronological split，测试 issue、依赖版本与 agent 版本晚于训练期；
- generator split，保留一个 patch 生成模型家族只用于测试；
- verifier-family split，检验策略能否接入未见过的工具或模型家族，而不是记忆 verifier-id；
- risk-family split，把一种回归或 CWE 家族只留作分布外测试。

所有划分应在生成 patch 和测试之前冻结 manifest。仓库 fork、重复 issue、相同 CVE 的不同镜像、代码克隆与测试模板都要跨 split 去重。性能报告应分别给出 benign、非恶意功能错误、公开测试过拟合、后门与漏洞修复，不能把容易的正常样本稀释真实风险。

## 6. 同输入、等参数、等数据、等预算的公平反证

### 6.1 反证原则

本审计不采用“通用网络在无限数据下能够逼近同一函数”作为撤题理由。理论算法是否有价值，应在有限样本、固定容量和固定行动预算下比较。所有主要替代模型必须看到完全相同的任务、仓库、diff、verifier 元数据、控制图 C、经验残差图 R_t、历史证据和剩余预算；必须用相同 patch、相同标签、相同优化步数和相同超参数搜索预算训练；推断时必须遵守相同的 verifier 调用、token、GPU、CPU 与 wall-clock 上限。若理论模型独占 C 或 provenance，而通用模型只收到 verifier 分数，任何增益都不能归于理论结构。

### 6.2 必须纳入的公平替代

| 代号 | 替代模型 | 公平控制 | 被反驳的贡献宣称 |
|---|---|---|---|
| B0 | Hua 式条件分数 POMDP / likelihood-ratio 策略 | 同一 verifier 输出、成本、预算和终端标签 | 序贯调用与停止本身是否新增 |
| B1 | 等参数 set/graph Transformer policy | 获得 H、V、C、R_t、Y_t、U_t、b_t 全部输入；相同参数量与训练样本 | 理论专用计算是否优于一般关系编码 |
| B2 | 结构中和模型 | 与理论模型同架构、同参数；随机打乱 C 的边但保留度分布，或把控制关系替换为可学习 relation id | 收益是否真来自理论关系而非额外容量 |
| B3 | hard-SoD + 通用策略 | 与候选共享禁止自审、不可写 oracle 和日志约束，序贯部分使用普通 POMDP/Transformer | 职责分离是否只是一条可共享的工程约束 |
| B4 | Koran quality–diversity ensemble | 同一监控器池、相同校准集和总调用成本 | 复杂策略是否胜过低相关高质量组合 |
| B5 | cheap-first、best-single、random、all-tools、平均、多数票 | 相同调用次数或真实成本 | 是否只因多花成本或多拿证据获益 |
| B6 | RETRACE | 相同 patch、backbone/API 预算与最大修订轮数 | 独立重建核验和修订动作是否已足够 |
| B7 | Agentic Rubrics、SWT/CodeRM test generator 与 tests+rubric 混合 | 相同模型调用、执行时长和候选 patch | 情境 rubric 或主动测试是否解释全部增益 |
| B8 | LEVER 式 learned verifier / terminal risk head | 相同编码器规模、执行信号和标签 | 序贯状态是否真正必要 |

参数公平不应只比较名义参数量。若理论模型调用一个额外大型 LLM 生成控制图或 rubric，该调用的 token、时延和生成误差必须计入预算；若通用模型直接收到人工构造的 C，理论模型也不能把这一人工信息宣称为端到端学习贡献。对确定性工具，成本要包括容器启动和测试执行；对模型 verifier，至少报告调用数、输入输出 token、采样数和模型版本。

### 6.3 有限样本与分布外的理论增益门

理论结构只有同时满足下列三项才可能通过：

1. **有限样本效率。** 在相同的 10%、25%、50% 与 100% 训练数据曲线上，理论模型在小样本区显著降低有害 patch 接受率，且正常 patch 接受率与成本不恶化；优势不能只在更多人工 provenance 字段下出现。
2. **关系分布外。** 在未见 generator、未见 verifier family 与未见 risk family 上，理论模型仍优于 B1 和 B3；若只记忆 provider-id，verifier-family split 会使优势消失。
3. **冲突方向。** 在第 4.4 节预注册情境中，模型行为应随可操纵关系和实质证据价值发生可解释改变。打乱 C 后，这种定向行为和外部风险结果应同时下降，而不只是注意力权重改变。

若 B1 在相同 C 与 R_t 下复制结果，说明一般关系模型已经吸收能力；若 B3 复制结果，说明职责分离只是硬约束；若只在去掉 C 的不公平基线上获胜，说明实验没有识别理论贡献。理论模型不能以统计显著但实践微小的单一平均分提升过门，还应报告簇级置信区间、效应量与风险—成功—成本 Pareto 前沿。

### 6.4 当前为什么已经足以 NO-GO

候选尚未运行上述对照，原则上未运行实验不等于必然撤题。本案能够作 NO-GO，是因为待验证的主要算法宣称已经被直接近邻分解占据：B0 与候选具有相同的序贯调用、成本和终端干预语义；B4 已使用真实残差相关性选择监控器；B6 已给出独立 patch 验证与机器修订动作；主动生成测试也已有可训练实现。理论新增部分在当前规格中只剩 C 和 hard mask。C 若作为输入供 B1 使用，尚无理论理由预测候选一定作出不同决策；若不供 B1 使用，比较不公平。换言之，本候选首先需要一个成功的等参机制试点才有资格进入论文冻结，而不应先冻结后再期待实验创造机制。

## 7. 若重开，实验必须测量什么

### 7.1 主要结果

首要结果是 matched benign acceptance 或 matched task success 条件下的 harmful acceptance rate。功能场景以封存回归测试失败定义 harm；安全场景以 PoC 仍成功、触发器仍可达或后门被放行定义 harm。恶意代码场景还应报告固定 0.5%、1% 与 5% 正常误报率下的 true-positive rate 或 partial AUC，具体阈值须在验证集冻结，不能在测试攻击集选择组合或阈值。

次要结果包括正确 patch 接受率、最终修复成功率、平均修订轮数、误拒绝率、wall-clock、token、CPU/GPU 小时、容器执行次数和峰值权限。安全收益必须与任务完成和成本同时报告。静态分析告警数、verifier 平均分、模型自信度和多数意见只能作为过程变量。

### 7.2 机制干预

最低限度的消融与中和实验包括：

- 删除控制图 C，但保留相同参数；
- 保留 C 的节点与度分布，跨任务打乱边；
- 只保留 source/provider id，删除谁能修改何种证据的细粒度边；
- 删除 R_t，假设 verifier 条件独立；
- 以模型家族差异替代真实残差相关；
- 共享 hard-SoD 掩码后比较理论计算与通用计算；
- 中和成本或设置等成本，检验策略是否只是 cheap-first；
- 删除历史证据更新，只做一次性 portfolio；
- 将所有工具输出压成标量，检验原始证据内容是否必要；
- 用相同调用预算运行 majority vote、Koran 组合与 Hua 策略。

机制结果必须落到真实 harmful acceptance，而不是只显示 C 的 attention 较高。若打乱 C 不改变风险—成功—成本前沿，理论机制没有行为责任。若删除 R_t 才造成主要下降，核心贡献属于相关误差建模而非 IS 理论，应重新定位而不是以理论命名。

### 7.3 统计分析

任务是簇，重复 patch、随机种子和同一仓库 issue 不是独立样本。应按 repository 和 task 做 cluster bootstrap，报告差值置信区间，并对风险率使用合适的二项或分层模型。多种风险家族的比较需预注册主要终点并控制多重检验。成本前沿可报告在固定预算点上的配对差值和前沿支配比例。对正常任务能力应设置非劣界，而不是看到 p 值不显著便宣称“没有代价”。所有 threshold、模型选择、verifier 子集选择和早停规则都只能使用训练与验证数据。

### 7.4 威胁模型与隔离边界

非恶意功能回归无需套用攻击术语。对后门、prompt injection 或 verifier gaming 场景，则需明确攻击者能否控制仓库文本、测试、patch、agent 消息和 verifier 输入，能否知道监控器池与阈值，以及能否跨轮适应策略。所有 PoC、后门和破坏性命令只能在公开、授权的容器或虚拟机中运行，网络默认关闭，凭据为合成值，宿主文件系统只读挂载。评价不应攻击真实生产系统。

## 8. 算力、训练工件与复现要求

### 8.1 规划估算

真正昂贵的部分不是策略网络，而是产生交叉验证矩阵。假设预试验有 250 个任务、每任务 4 个 agent patch、6 类 verifier、每类至少 2 次随机运行，仅 verifier 层就有约 12,000 次执行；动态测试、fuzz、PoC 和容器冷启动会进一步增加时长。这个数字只是内部量级估算，不是已经构建的数据。PatchEval 官方仓库建议 16 CPU 核与约 500 GB 磁盘；跨 SWE、SWT、PatchEval 和容器缓存的完整环境应预留约 0.5–2 TB，本范围需要在下载 manifest 后实测。

若策略使用冻结的 7B–14B 代码编码器加 LoRA，规划上可在 2–4 张 48–80 GB GPU 上训练；若使用较小的图编码器和离线策略头，1–2 张 24–48 GB GPU 可能足够。Agentic Rubrics 的开放权重 32B 训练报告使用 32 张 H100，说明直接复现该规模超出普通本地训练条件，应该使用其已发布权重或选定更小的公平骨干。这些数字均是可行性规划，必须由小样本 profile 替换后才能写入正式方法。

### 8.2 必须产出的工件

若重开，独立算法工件不能只是 prompt 与 API 编排。至少应发布：

- 仓库与任务编码器权重；
- verifier catalog 与版本化工具 manifest；
- 控制图构造器及逐边 provenance；
- 联合残差模型和校准参数；
- 序贯 policy checkpoint；
- 完整训练、验证、测试主键与去重报告；
- 每次 verifier 调用的原始证据、成本、容器摘要和随机种子；
- 隐藏 oracle 的隔离哈希与仅在评测侧可见的运行脚本；
- 等参基线配置、参数量核算、预算核算与统计脚本。

复现 manifest 还应记录仓库 commit、patch 生成模型和版本、系统提示、采样参数、测试工具版本、网络策略、timeout、CPU/GPU 型号、Docker image digest 与失败重试规则。任何模型升级或 verifier 规则更新都需要新版本数据，不能静默混合。

## 9. 终局撤题门与唯一重开路径

### 9.1 立即撤题条件

出现任一项即维持 NO-GO，不再通过包装扩写：

- 主要算法是平均、多数票、top-k、简单 rerank、一个终端 risk head 或静态 source-id 权重；
- “独立”只由不同 provider、模型名称或 prompt 声明，没有任务条件下的联合错误测量；
- 职责分离只实现为一条 if-rule 或 hard mask，却被宣称为完整理论算法；
- 通用等参模型没有获得相同 C、R_t、成本与 provenance；
- 安全结果只测静态警告、judge 分数、拒绝率或公开测试，不测隐藏回归、PoC 或后门逃逸；
- 提升来自更多 verifier 调用、更大模型或更高 token/执行预算；
- hidden test、gold patch、patch_url、PoC 或测试模板泄漏进训练和检索；
- return-to-repair 没有学习的转移与反馈，只是把 reject 改名；
- 理论边打乱、中和或删除后，外部行为与结果没有可观察变化；
- 在已知正确 patch 上用普遍拒绝换取安全；
- 数据只有政策选择后的稀疏日志，无法识别未调用 verifier 或未选择修复动作的反事实。

### 9.2 重开所需先验试点

只有完成并同时通过下列预试验，才可重新讨论 CONDITIONAL-GO。这些数量是内部预注册建议，不是文献事实：

1. 先冻结一个 patch 域，不再混入任意 command；覆盖至少 200–300 个任务、20 个以上仓库、多个功能与安全风险家族。
2. 至少运行 5 类机制真正不同的 verifier，例如独立模型 judge、仓库情境 rubric、静态分析、动态回归测试和 PoC/fuzz，而不是五个相似 prompt。
3. 对分层子样本形成近完整 verifier 交叉矩阵，并随机化其余调用，以便估计条件相关和反事实收益。
4. 在相同输入、参数、数据与真实成本下同时运行 B0、B1、B3、B4、B6 和简单基线。
5. 理论双图模型必须在有限样本、未见 generator、未见 verifier family 或未见 risk family 中至少一个预注册主要终点上稳定优于 B1 与 B3，并在冲突情境产生理论方向的行为。
6. 改善必须体现为 matched task success 下更低的隐藏回归、PoC 失败或后门逃逸，不能由提高拒绝率解释。
7. 机制增益不得消失于把同一 C 和 provenance 提供给等参通用模型之后。

即使试点通过，也要重新评估独立贡献究竟来自 IS 控制结构、联合误差学习，还是新数据资产。若主要增益来自 R_t，论文应诚实转为“相关验证错误下的序贯 patch assurance”，理论责任需要重建；不能继续声称 warranting theory 直接推出相关性。

### 9.3 当前最合理的归宿

在当前系列中，本候选最适合作为公共验证基础设施或其他论文的强评价层：它可以统一封存测试、PoC、静态与动态工具，记录 provenance 和真实成本，并用 Hua、Koran、RETRACE 等工作构成基线。将其降为基础设施并不否认问题重要，而是防止把系统集成误写成第三个独立理论算法。除非第 9.2 节试点推翻本终审，不应为它撰写正式摘要、引言或理论假设。

## 13. 可同步终审摘要

**直接覆盖。** Hua 已覆盖“调用哪个 verifier、何时停止或干预、如何满足成本预算”的同构序贯动作；Koran 已覆盖质量—残差相关组合和低 FPR 后门结果；RETRACE 已覆盖独立 patch 验证及提交或修订动作；Scaling Agentic Verifier、Agentic Rubrics 和 SWT-Bench 已覆盖主动测试、情境验证与仓库 patch。候选剩余主要是跨工具集成与新交叉运行数据。

**理论责任。** Warranting theory 只能产生执行者对证据的可操纵关系 C，separation of duties 只能产生禁止自审和不可写 oracle 的硬约束，control portfolio 与 substantive assurance 约束成本和真实结果。它们不产生统计残差图 R_t、下一 verifier 次序或停止边界。若理论只剩 source-id 或 hard mask，则不构成独立算法。

**可识别数据。** 现有公开资源分别覆盖仓库功能修复、独立测试、CVE PoC、后门监控或隐藏失败，却没有一个同时包含每个 patch 对每个异构 verifier 的输出、成本、序贯反事实与封存安全标签。必须对分层 patch 全交叉执行 verifier，并对其余调用随机化；return-to-repair 若要成为学习动作，还需要反馈—新 patch 的分支转移数据，否则只是 terminal reject。

**等参公平反证。** 等参数 set/graph Transformer、hard-SoD 通用策略和 Hua 式 POMDP 必须获得与理论模型完全相同的 H、V、C、R_t、证据历史、训练数据和预算。只有理论结构在有限样本、未见 generator/verifier/risk family 和预注册冲突情境中仍优于这些替代，且降低 matched task success 下的隐藏回归或 PoC/后门放行，才可能重开。当前没有这项证据，而直接工作已覆盖主要动作与结果，故终局为 **NO-GO**。
