# 跨所有权边界的可靠变更：候选终审

## 0. 终局裁决

**判定：NO-GO。该候选不得进入三篇论文的独立题位，也不得以“所有权感知 patch 重构”“边界契约代理”或近义名称恢复。**

本判定冻结于 2026 年 8 月 15 日。跨模块、跨仓库或跨团队变更确实会放大协调负担，缺少局部知识的 coding agent 也可能造成回归、错误传播和责任不清。终审否决的不是问题重要性，而是当前候选无法同时建立可识别的安全结果、方向一致的理论机制和不被合理通用替代吸收的算法责任。

决定性理由有五项。第一，“越过 owner 边界”不是损害。现有 ownership 研究主要报告作者或评审经验与缺陷、失败及评审过程之间的关联，不能据此把保持局部、拆分补丁或移交 owner 识别为同一任务状态下避免回归的因果行动。第二，最自然的 IS 理论并不共同推出“边界越强，agent 越应缩小行动或移交”。集体所有权会在部分情境中解除单点 owner 瓶颈，结构镜像与跨团队同步互为替代，artifact-based coordination 甚至可能比权威式协调形成更低的传播成本。第三，知识边界理论指出语义和实用边界的跨越依赖情境化、互惠式实践。agent 单方面生成一份可执行契约不能等同于完成知识转换；若把真人 owner 的理解、协商和采纳纳入核心处理，该题便回到人类取证与监督研究。第四，双图、patch 拆分、传播成本、owner 定位和契约测试均已有直接工作；2026 年的 AtomicCommitBench 尤其已经把 coding agent 的 hunk 分组、可回放提交序列和选择性回退隔离放入同一可运行任务。第五，公开资源无法在同一决策状态上同时提供真实团队边界、可用领域知识、多个可选行动以及各行动的后续损害。把 AIDev、CODEOWNERS、AtomicCommitBench、BeyondSWE 和 Pact 仓库拼接起来，只会制造跨总体伪标签。

以下保留候选的最强算法版本，是为了完成 steelman 和可证伪终审。它不表示该版本已获准实施。本文件属于内部选题审计；没有运行实验、训练 checkpoint 或观察到任何算法改善。模型规模、样本量与算力均为条件性工程估计。

## 2. 研究对象与广义安全边界

### 2.1 候选的最强研究问题

研究单位不是 PR 是否需要 reviewer，而是 coding agent 在已形成候选修改、尚未把修改提交或部署之前的行动决策。设任务为 $q_t$，当前代码与配置为 $W_t$，候选 hunks 为 $H_t$，可见测试为 $T_t^{vis}$，工具与权限状态为 $P_t$。修改可能触及多个组件、仓库或团队责任域。agent 需要选择如何重写实际工作，而非只输出一个人名：

\[
a_t \in \{\text{局部执行},\text{重构为可回放工作包},\text{生成并验证边界契约后执行},\text{把外部工作包交给责任团队},\text{停止并保留可恢复状态}\}.
\]

“交给责任团队”若只等同于添加 reviewer，候选立即退化为 reviewer recommendation。最强版本要求 agent 真正拆分 patch、构造依赖有向图、只应用获准的本地工作包，并把外部工作包连同前置状态、可执行测试、接口假设和回滚条件交付给另一责任域。候选因此具有序贯行动，而非简单路由。

### 2.2 风险、受影响者与外部结果

候选可能涉及的真实损害包括：缺乏领域约束的修改造成隐藏功能回归；跨服务契约被破坏并使错误传播到依赖方；多个仓库的版本组合失配；未经责任团队确认的部署造成停机或数据错误；宽补丁无法选择性回退；责任不清增加事故恢复时间。受影响对象是依赖组件、服务团队、组织交付流程、业务数据和最终用户。

但 ownership crossing 只是状态描述，不是安全结果。下表给出必须保持的证据边界。

| 观察量 | 可承担的角色 | 能否单独证明安全改善 |
|---|---|---|
| 是否触及 CODEOWNERS 路径、文件 owner 数、跨团队边数 | 边界代理 | 否。名义 owner 不等于当前掌握必要知识的人，跨边界修改也可能是正常的集体所有权。 |
| PR 是否 merge、merge 用时、评论数、bot 评论比例 | 流程结果或负担 | 否。merge 由任务价值、维护者容量、项目政策和作者身份共同决定。 |
| owner 请求缩小范围、要求按惯例修改或直接改代码 | 监督需求的观察信号 | 否。它只记录实际分支上的干预，未观察没有干预时的损害。 |
| 可见测试和 CI 是否通过 | 当前任务结果 | 有限。它不能覆盖 owner 的隐含约束、下游组合或生产后果。 |
| 隐藏跨仓库测试、契约验证、版本组合测试 | 技术回归结果 | 可以，但主要识别语法与行为兼容，不自动识别组织知识边界。 |
| 生产事故、回退、SZZ 缺陷引入、下游故障 | 潜在外部损害 | 有条件。需解决归因、遗漏事故与行动选择混杂。 |
| 工作包成功率、端到端任务成功、交付时长、owner 工时 | 效率与负担结果 | 必须联合报告，防止以拒绝所有跨边界行动获得表面安全。 |

安全主张至少要同时改善真实回归或事故结果、端到端任务成功和成本结果。若模型只是减少跨边界文件数或提高 owner 接受率，它仍是变更范围控制或流程优化，不是广义安全算法。

## 3. 理论 MEC→MAP→ALG 终审

### 3.1 结构镜像与 socio-technical congruence

最自然的机制是：技术依赖产生所需协调关系，团队或知识关系表示已经具备的协调能力，两者不一致时，跨边界行动更容易遗漏相互依赖。可将技术图记为 $G_T$，人员、团队与代码责任图记为 $G_E$，并以两图之间的缺口形成边界状态。这个 MEC 可以映射为异质双图和 cross-incidence tensor，再指导拆分、同步或委派。

这一映射没有留下独立理论空间。Hahn 等人已经在 ISR 2026 中区分问题空间和解决方案空间两种分解，比较 feature teams 与 component teams，检验复杂性、同步频率和责任宽度，并揭示结构镜像与同步的替代关系。其理论并不支持一个单调的“失配越大越应委派”规则：复杂系统有时需要更宽责任域；适度同步可能优于持续同步；问题空间镜像与解决方案空间镜像的相对优势会反转。Portillo-Rodríguez 等人又已把 STC 测量和 software-agent 协调架构直接结合。候选若只计算两图缺口并触发协调，属于已知 STC 工具逻辑；若增加问题空间图、同步成本和责任宽度，则进入 Hahn 等人的现有理论计算。

### 3.2 知识边界与 boundary objects

Carlile 路径可将差异、依赖和新颖性产生的边界分为 syntactic、semantic 和 pragmatic 三类。最强 MAP 会为每个跨边界工作包产生隐状态 $b_k\in\{syn,sem,prag\}$，并根据边界类型选择广播式契约、经纪式求助或桥接式共同工作。若成立，这确实可能使相同技术 blast radius 下产生相反行动。

问题在于公开仓库轨迹不能识别该隐状态。语法边界可从接口、构建和测试中部分观测；语义边界涉及不同群体对同一表述的理解；实用边界还包含利益、策略和后果取向。Foerderer 等人的四平台研究明确没有估计每类 knowledge boundary resources 的因果有效性。Huber 等人对 46 次虚拟会议的分析进一步表明，原型的边界作用由 exemplifying、contrasting、relating 和 framing 等实际使用实践实现，物件属性也会在互动中改变。由 agent 单向生成静态契约，然后把“契约存在”当作边界已经跨越，是把群体互动层机制错误地下沉为代码工件属性。

若训练标签来自真人 owner 对“这是什么边界”的判断和协作后的共同结果，候选将成为人类取证、协商与监督研究，并与 C3 重叠。若不引入真人过程，$b_k$ 只能由规则或 LLM 伪标注产生，理论在损失函数中没有外部锚点。

### 3.3 expertise coordination、知者编码与 collective ownership

Kotlarsky 等人说明，知识编码可以为结构化任务提供行动指南，而“知者编码”只是把特定知识与可联系的人连接起来，以便非结构化问题通过互惠互动解决。把 git blame、review history 或 CODEOWNERS 映射为“谁知道”并向该人移交，实质上是 expertise location 或 reviewer recommendation。它没有把知识真正带入 agent 的前向计算，也没有形成独立于 C2 TMS 的算法机制。

Maruping 等人的结果构成更强反证。其团队层研究发现，集体所有权提高技术质量，并削弱“知道专家位置”与技术质量的关系，因为具有所需能力的成员可以自然介入全部代码。Fitzgerald 等人的 Intel Shannon 案例同时显示这种做法在单团队内有价值，但未扩展到跨团队。两者共同支持的是条件性边界：某些团队应当保持 owner 专属责任，另一些团队以集体所有权和统一编码标准降低瓶颈。仅凭提交历史无法得知当前项目处于哪一种制度与能力状态。因此，ownership theory 不能提供稳定的 action sign。

### 3.4 协调理论与传播成本

协调理论把协调界定为管理活动间依赖。Lindberg 等人已经展示模块化和自包含任务如何减弱开发相互依赖，直接实现与知识整合如何处理剩余依赖。把宽 patch 切成自包含工作包并在 owner 之间整合，概念空间已被这一研究覆盖。

Zaggl 的模型更直接。该文以 design structure matrix 形式化软件架构，比较 artifact-based 与 authority-based coordination 如何从相互依赖贡献形成 propagation costs，并发现前者通常形成较低传播成本；authority-based coordination 虽能利用 predictive knowledge 处理更广的相互依赖，却可能形成更紧密的层和更高传播成本。候选假定“把跨边界部分交给权威 owner”天然减少 blast radius，与这一机制并不一致。Zaggl 也明确指出低传播成本并非唯一目标，authority coordination 可能支持更广的可实现系统。理论再次要求多结果权衡，而非 owner gate。

### 3.5 闭环判定

| 理论视角 | MEC | 候选 MAP | 候选 ALG | 终审结果 |
|---|---|---|---|---|
| 镜像与 STC | 技术依赖与组织协调能力失配 | $G_T$、$G_E$ 与 congruence gap | 拆分、同步、移交 | 双图和行动方向已被直接研究，且复杂性与同步使方向反转。 |
| 知识边界 | 差异、依赖、新颖性形成三类边界 | 边界类型隐状态与 boundary-object 表征 | 契约、经纪、桥接 | semantic/pragmatic 状态无法从公开 trace 识别；静态契约不能替代互惠实践。 |
| expertise coordination | 识别所需知识、专家位置并使其发挥作用 | 人—团队—代码知识图 | 找 owner、委派 | 退化为 TMS 或 reviewer recommendation；“位置”不等于知识已被使用。 |
| collective ownership | 责任流动可调动全队知识并消除瓶颈 | ownership regime 状态 | 允许跨域行动或 owner gate | 理论给出反向条件，但公开数据不能识别适用制度。 |
| coordination/propagation | 相互依赖贡献及协调方式塑造架构传播成本 | DSM、预测知识与可见性 | 延迟、局部实施或权威协调 | 直接近邻已占据；权威协调并不单调降低传播成本。 |

没有一个视角同时通过三道门：形成 coding-agent 特有 MEC；产生可观测或可监督的 MAP；推出在冲突情境中方向稳定且未被现有工作占据的 ALG。将这些理论并列输入模型只会形成丰富 feature set，不会自动形成理论算法。

## 4. 直接工作对贡献空间的挤压

### 4.1 双图、组织边界与传播

Bird 等人早已报告低经验作者、top owner 集中度与 pre-release faults、post-release failures 的关联。Pinzger 等人以 developer-module network 预测失败。Thongtanunam 等人进一步说明，许多未写代码的开发者通过 review 获得模块经验，review-aware ownership 与 post-release defects 相关。这些研究支持组织信号有预测价值，但也说明 `git author = owner` 过于粗糙。

Hahn 等人 2026 年 ISR 论文和 Zaggl 2025 年 MISQ 论文分别占据“团队结构—双设计空间—跨团队同步—开发绩效”与“协调方式—相互依赖贡献—传播成本”的主理论链。候选不能再次把双图对齐、责任域宽度或 blast radius 作为首次理论化。Portillo-Rodríguez 等人的 agent architecture 则占据了“software agents 管理 STC”的基本工件主张。

### 4.2 owner 定位与 reviewer recommendation

HGRec 用超图表示 PR、贡献者和多 reviewer 高阶关系，在 12 个 OSS 项目的 87,000 余 PR 和 680,000 余评论上推荐 reviewer。CODEOWNERS 大规模研究覆盖 844,000 余 PR、190 万评论和 200 万余 review，并用 regression discontinuity 分析采纳前后的评审动态。若候选输出的是“应找谁”“是否需要 owner 审批”或 owner 排名，它直接落入这一成熟领域。把 reviewer 排名接到 coding agent 后面不会产生新的安全行动。

### 4.3 patch decomposition 与 failure containment

AtomicCommitBench 是最致命的技术近邻。它把完成后的 squashed patch 分成 ordered hunk groups，要求形成可回放提交序列，并以 PPAR、ARI 和用于选择性回退的 TCR 评价。数据包含 10 个 Python 项目的 800 个真实连续提交 episode。非随机方法几乎都能回放，但真实分组 ARI 仍只有 0.03–0.46；DACE 的依赖与 hunk-role 证据能改善较弱设置。这一任务已经同时覆盖 coding agent、patch 重构、依赖证据和失败隔离。

Tangling Pull Requests 进一步利用 merged PR 构造大规模 untangling 数据，把理想原子 PR 比例从 9.5% 提升到 55%，并扩展到 Python。DISPATCH 在 USENIX Security 2025 中用 PatchGraph 和两阶段依赖分析，从混合修改中分离安全补丁，在四个大型项目上报告超过 91.9% recall。di Biase 等人的控制实验还显示，拆分 change set 减少误报并改变 context-seeking，却没有提高发现缺陷数或变更理由理解。候选不能把“较小 patch 更安全”当作已建立因果规律。

### 4.4 multi-repo 与 contract testing

BeyondSWE 提供 500 个任务、246 个仓库和 Docker/测试环境。其 CrossRepo 有 200 个任务、67 个目标仓库，但“跨仓库”指从外部仓库获取知识，实际修改仍落在一个目标仓库；DepMigrate 的 178 个任务、120 个仓库则是在目标仓库内完成全局迁移。它们可测跨仓库推理和大范围编辑，不能测多个真实 owner 对工作包的替代行动及组织后果。

Pact 等开源工具能执行 consumer-driven contracts。2022 年 SEAA 研究分析 16 个微服务仓库，其中 4 个采用 CDCT；2025 年 STVR 研究把 CDCT 的理论责任明确限定为微服务间 syntactic interoperability，并用行动研究补充。契约测试是有价值的 verifier，却主要验证可枚举接口交互。它不能证明 owner 的语义假设、路线图、利益或操作惯例已经被 agent 获得。若候选只训练契约生成器，它是测试生成研究；若宣称契约代表知识边界，它发生理论层级错误。

### 5.2 为什么 merge、review 与干预不是安全标签

设状态为 $s$，候选行动为 $a\in\{local,split,contract,delegate,stop\}$，外部损害为 $Y(a)$。公开 PR 只给出实际选择的 $a^{obs}$ 和 $Y(a^{obs})$ 的不完整代理；其余 $Y(a)$ 均不可见。更重要的是，维护者会依据不可公开的严重度、熟悉度、人员容量和项目优先级选择是否介入。因而 $a^{obs}$ 与 $Y$ 受到共同原因影响，merge/review trace 不满足离线策略学习所需的可忽略性或充分重叠。

“owner 要求缩小 patch”可能表示原 patch 有风险，也可能只是维护者偏好；“owner 没有介入”可能表示修改安全，也可能表示没有时间；“PR 被拒绝”可能源于重复、任务无价值或作者沟通，而非回归。Njoku 等人的正式研究和 Ehsani 等人的分类研究只能作为现象证据，不能充当 action label。把这些观察信号训练成风险分数会把既有治理选择复制成模型政策。

### 5.3 不能通过跨数据集拼接补真值

一个可训练的 owner-boundary policy 需要在同一实例上同时拥有：时点 $t_0$ 的代码和任务；技术依赖；实际组织与知识状态；agent 的多个可执行 patch 分支；每个分支的隐藏跨仓库测试、生产代理、交付成本与真人负担。现有资源分别覆盖这些字段的一小部分，且仓库总体、时间窗、语言与采样机制不同。用 AtomicCommitBench 的 partition label、CODEOWNERS 的 owner、AIDev 的 merge 和 Pact 的 contract test 进行外键式拼接没有共同支持集，不能产生联合训练样本。

SZZ、revert、incident issue 或后续 bug 可作为噪声 outcome，但仍只对应历史上采取的一个行动。名义 CODEOWNERS 也经常落后于团队重组；review-aware ownership 只能改善经验代理，不能观察 tacit knowledge 或利益冲突。公开 OSS 很少提供真实 team roster、跨仓库责任矩阵和未公开事故。由此，候选所需的核心 boundary state 与 policy value 在现有公开数据下不可识别。

## 6. 最强反事实算法工件

### 6.1 输入、张量、输出与真实动作

若忽略上述真值问题，最强工件应是“跨边界工作包构造与行动策略”，而不是 owner risk head。一次输入包含：任务 $q$、基础快照 $W_0$、agent 候选 hunks $H=\{h_i\}_{i=1}^{n}$、可见测试与执行轨迹、技术依赖图 $G_T$、时间截断的知识—责任图 $G_E$ 及接口资料。

关键张量至少包括：

- $X_H\in\mathbb{R}^{n\times d}$，编码每个 hunk 的语义、角色、文件位置、可逆性和测试覆盖。
- $A_T^{(r)}\in\{0,1\}^{|V_T|\times|V_T|}$，表示 call、data、build、runtime、API 与 deployment 等 typed technical edges。
- $A_E^{(r)}$，表示 author、review、formal ownership、communication 和 team membership 等时间截断的关系。
- $M_{HT}\in\{0,1\}^{n\times |V_T|}$ 与 $M_{HO}\in\{0,1\}^{n\times m}$，把 hunk 对齐到技术节点与责任域。
- $B\in\mathbb{R}^{n\times m\times d_b}$，候选理论瓶颈，试图表示每个 hunk 对每个责任域的 required coordination、available expertise、authority、novelty 与 boundary type。

输出不是标量，而是 hunk-to-package 软分配 $Z\in[0,1]^{n\times K}$、工作包依赖 DAG $Q\in[0,1]^{K\times K}$、每个工作包的动作分布 $\pi(a_k\mid s_k)$、可执行契约或测试 $C_k$，以及 task success、regression、delivery time 和 human load 的校准联合分布。

推断时，模型必须真的重写 git 历史或工作树，生成可回放工作包，依序运行构建和契约 verifier，只应用被选中的本地包；对于外部包，应生成可执行 manifest、前置版本、测试、失败证据和回滚条件。所有破坏性试验限于容器和临时仓库，不触碰未经授权的真实系统。

### 6.2 架构

steelman 架构可由五部分组成：typed heterogeneous graph encoders 分别编码 $G_T$ 与 $G_E$；cross-graph alignment 形成 $B$；带 Sinkhorn 或 pointer decoder 的约束分区器产生 $Z$ 和 $Q$；条件生成器与 verifier 产生 $C_k$；最后由 constrained sequential policy 在任务成功、损害和成本之间选动作。模型参数可以集中在 100M–500M 的图与分区模块，契约生成器使用 1B–7B 本地代码模型或受控 frontier model，避免把全部贡献藏在云端 API。

理论若真正负责算法，$B$ 必须成为低维有限样本瓶颈，而不是把 ownership feature 拼到 HGT 后。它还必须在固定 $G_T$ 时因 $G_E$ 或 boundary type 的变化产生可预注册的相反动作，并在 OOD 组织上改善校准或样本效率。

### 6.3 训练样本与损失

理想损失可写为：

\[
\mathcal{L}=\lambda_p\mathcal{L}_{part}+\lambda_e\mathcal{L}_{replay}+\lambda_c\mathcal{L}_{contract}+\lambda_y\mathcal{L}_{outcome}+\lambda_\pi\mathcal{L}_{policy}+\lambda_b\mathcal{L}_{boundary}+\lambda_{cal}\mathcal{L}_{calibration}.
\]

$\mathcal{L}_{part}$ 监督 $Z$ 与工作包顺序；$\mathcal{L}_{replay}$ 保证每个前缀可应用、最终树一致且前置依赖满足；$\mathcal{L}_{contract}$ 使用 consumer/provider execution、mutation 和隐藏组合测试监督契约；$\mathcal{L}_{outcome}$ 联合预测真实回归、任务成功、时长和人工负担；$\mathcal{L}_{policy}$ 需要 logged propensity 或随机化行动才能进行 off-policy 学习；$\mathcal{L}_{boundary}$ 必须由独立标注的协调需求与实际可用知识监督；$\mathcal{L}_{calibration}$ 控制高风险尾部的不确定性。

当前只有前两项可由 AtomicCommitBench 稳定提供，契约项可在 CDCT 项目上局部构造。outcome、policy 与 boundary 三项没有同一总体真值。若用 merge imitation 替代 $\mathcal{L}_{policy}$，模型学习的是历史审批；若用 $G_T$ 与 $G_E$ 的矩阵差替代 $\mathcal{L}_{boundary}$，理论状态成为手工定义的 STC score；若用 LLM 标注 boundary type，损失只蒸馏标注模型偏好。最重要的三项因而无法训练。

## 7. 训练、划分、算力与复现的条件性规格

### 7.1 若未来获得真实数据，最低训练情境

唯一可辨识的方案需要与拥有多团队、多仓库系统的组织合作，在隔离环境中对真实任务产生多个语义可接受候选分支。每个分支应经过相同隐藏跨仓库测试、故障注入、契约 mutation 和固定下游 agent 或团队处理；owner 知识状态在行动前独立测量；部分低风险实例使用随机化或 encouragement design 比较 local、split、contract 与 delegate。高风险分支不得进入生产。

这不是现有公开 benchmark 的轻量扩展。它要求组织 roster、责任变更、沟通、事故和人力成本，且需要真人 owner 参与。数据采集一旦把核心结果定义为 owner 的证据理解和审批质量，研究设计将与 C3 合并。

### 7.2 划分与泄漏隔离

条件性切分必须以组织为最高隔离单位，其次为仓库族和时间：训练、验证、测试组织互斥；同一多仓库产品的所有仓库只进入一个 split；test period 晚于 train period；在 $t_0$ 后产生的 commit、review、CODEOWNERS 修改、事故 issue 和 owner 变化均不得进入输入；gold patch、隐藏测试和下游失败在推断结束前隔离。AtomicCommitBench episode 还需按 repository 和 chronology 隔离，不能把同一连续历史切进不同集合。

### 7.3 算力与工件

在 1,000–2,000 个可执行仓库上抽取 typed code/build/runtime graphs，预计需要 64–128 vCPU、0.5–2 TB 本地存储和数周离线构建；100M–500M 双图模型与分区器可在 4 张 A100/H100 80GB 上训练约 3–10 天；若本地微调 7B 契约生成器，需 8 张 80GB GPU 或 QLoRA 降配，另计大量容器执行时间。最终工件应包括 graph schema、time-censored manifest、checkpoint、分区与策略配置、容器镜像 digest、隐藏测试哈希、随机种子、数据 lineage 和每次动作的可回放 trace。

这些资源足以表明候选可以做成“硬”系统，却不能修复监督不可识别或理论重复。算力规模不是 GO 证据。

## 8. 强基线、公平比较与机制干预

### 8.1 必须包含的直接基线

1. CODEOWNERS exact match、review-aware ownership、RevFinder 与 HGRec，检验是否只是找 owner。
2. file split、dependency component split、AtomicCommitBench 的规则基线、DACE 与同预算 frontier coding agent，检验是否只是 patch untangling。
3. PatchGraph/DISPATCH 类依赖分解和普通 change-impact GNN，检验 blast-radius 计算。
4. Pact/CDCT verifier 和同预算 test-generation agent，检验契约贡献。
5. BeyondSWE 的 OpenHands、SearchSWE 与 Codex 设置，检验跨仓库知识和大范围编辑。
6. 具有完全相同 typed nodes、edges、历史、任务和动作 decoder 的 union-graph HGT，以及具有相同 observation/action/outcome heads 的 constrained POMDP。
7. 不含学习的 constrained optimizer，直接以可回放性、依赖闭包、CODEOWNERS 和成本求解工作包，检验复杂系统是否只是把已知约束组合起来。

### 8.2 公平控制

理论模型与通用替代必须获得完全相同的代码、owner/review 历史、问题空间资料、contract tests 和候选行动；参数量、训练样本、检索调用、LLM token、执行次数与 wall-clock budget 对齐；二者使用同一受约束 partition decoder。不能把理论模型获得的 boundary type、owner regime 或 DSM 指标从通用模型输入中删除。理论优势必须来自结构性偏置在有限样本下的实际作用，而非额外信息。

### 8.3 机制中和与冲突实验

最低机制实验包括：在保持技术度分布时打乱 owner/team edges；固定组织图而打乱技术依赖；交换 problem-space 与 solution-space partition；打乱 syntactic/semantic/pragmatic 标签；中和 collective-ownership regime；删除 contract 的可执行部分，只保留文字；保持参数量不变地用普通 cross-attention 替换 boundary bottleneck。

还应预注册至少三类同状态冲突对：技术范围小但涉及 owner 未公开的语义或利益时，知识边界机制应选择桥接或移交；技术范围大但接口稳定、标准充分且实行集体所有权时，机制应允许更宽局部行动；传播半径大但 authority coordination 预计形成紧密依赖时，artifact-based 机制可能选择延迟或局部实现，而非追求权威承诺。只有这些动作方向被独立真值确认，理论才承担行为责任。

当前数据无法构造这些冲突对的结果真值。用 reviewer 评论回填“语义边界”，或用 CODEOWNERS 回填“应移交”，会使实验循环证明自己的标签定义。

## 9. 同信息、同预算通用替代的有限样本反证

本候选不能仅因 Graph Transformer 或 POMDP 在原则上具有通用表达能力而撤题。公平问题是：在同参数、同数据和同计算预算下，理论瓶颈是否提供非平庸的有限样本归纳偏置、可干预的冲突方向和真实不同动作。

在当前候选中，答案仍为否。一个 union-graph HGT 可以读取同样的 typed technical edges、author/review/owner edges、hunk 表征和 contract execution，再使用同一个 constrained partition decoder 输出 $Z$、$Q$ 和行动。可从公开数据学习的标签只有历史 commit grouping、replay、测试和实际 review/merge；这些标签不要求模型显式区分 STC gap、语义边界或 collective-ownership regime。理论模型的 $B$ 若无独立监督，只是由同一输入计算的中间压缩；HGT 可以在相同 decoder 上经验复制其映射，且现有 DACE、HGRec、Portillo agent architecture 和 dependency partition 已提供合理直接替代，而非抽象的万能函数类。

理论仍可能通过有限样本证据获救，但最低要求是：独立标注的 boundary state；同状态替代行动后果；在组织 OOD 和稀少高损害类型上显著更好的校准或 regret；机制打乱造成符合预注册方向的行为崩塌；等预算 HGT/POMDP 不能以相同样本恢复；优势不是来自拒绝率、owner 信息或 decoder 约束差异。现有公开资源无法运行这组检验。因此，撤题依据是经验可复制性与真值缺失，不是“神经网络什么都能表达”的空泛论断。

## 10. 与 C2、C3、C10 的区分终审

### 10.1 与 C2 TMS

C2 的中心是分布式专长如何被识别、请求和调动。当前候选一旦用 author/review history 估计真实 owner，再把外部工作包交给该人，本质上就是 expertise location、codification of the knower 与 bringing expertise to bear。patch 只是触发专长协调的载体，不能形成新的理论对象。若删去人员定位，只保留技术分解，则又退化为 AtomicCommitBench 或 change-impact analysis。因此无法与 C2 保持干净独立。

### 10.2 与 C3 人类取证

C3 研究 agent 何时取得什么证据并支持真人判断。知识边界理论要求对象在真人的 exemplifying、contrasting、relating、framing 和协商中被使用。把 owner 是否理解、补充、接受或修改契约作为结果，当前候选就成为证据质量与真人监督；把真人拿掉，契约又只能证明 syntactic interoperability，无法承担知识边界。两条路径分别重叠 C3 或失去理论有效性。

### 10.3 与 C10 结构侵蚀

C10 面向多轮修改造成的长期架构退化和后续故障。当前候选原本可聚焦一次任务的责任边界与短期工作包。然而 blast radius、propagation cost、分解与选择性回退已经被 Zaggl、AtomicCommitBench 和 DISPATCH 直接覆盖；若加入长期跨团队错误累积，便向 C10 回流。时间尺度差异不足以支撑独立贡献。

|---|---|---|
| coding agent 是关键行动者 | 通过 | 最强版本会真实拆分、应用、验证、停止和交付工作包。 |
| 存在实际外部损害 | 概念通过、数据失败 | 回归与传播是真实损害，但公开数据主要给流程代理。 |
| 公开 benchmark 可运行 | 局部通过、联合失败 | 分解、跨仓库推理与契约可分别运行，没有 owner-policy 联合环境。 |
| 训练标签可识别 | 不通过 | 未观测替代行动；merge、review、干预和 CODEOWNERS 都不能充当安全真值。 |
| 理论产生不可替代状态 | 不通过 | 语义/实用边界不可观测；STC 与 ownership regime 可由同特征通用模型吸收。 |
| 理论推出稳定冲突方向 | 不通过 | collective ownership、mirroring、同步与 authority coordination 给出反向条件。 |
| 相对直接近邻仍有足够空间 | 不通过 | Hahn、Zaggl、Lindberg、Portillo、AtomicCommitBench、HGRec 和 CDCT 分别占据核心组成。 |
| 同预算合理替代不能复制 | 不通过 | union HGT + constrained partition decoder 在现有可学标签上是直接经验替代。 |
| 不退化为评分、路由或 reviewer 推荐 | 仅 steelman 通过 | 完整工件足够丰富，但可监督部分一拆开即退化。 |
| 与系列其他论文独立 | 不通过 | 人的部分重叠 C2/C3，结构与传播部分重叠 C10。 |

五项核心门同时失败：训练真值、理论状态、动作方向、直接近邻和系列独立性。该判定不应因可以实现一个复杂系统而放宽。

## 12. 最终处置与未来重审条件

本候选终止。不得降格为以下独立论文：CODEOWNERS reviewer recommender、跨 owner 风险分数、change-impact GNN、prompt 驱动的 patch 拆分器、普通契约测试生成器、owner escalation UI，或把上述模块串联后的系统论文。AtomicCommitBench、BeyondSWE、AIDev、Pact 和 ownership graph 可作为其他候选的基线、压力测试或数据资源，但不构成当前题目的组合式训练集。

未来只有同时满足以下条件才可重新送审：获得同一组织内时间截断的技术图、责任图和知识状态；在隔离环境中观察同一任务的多个真实可执行行动；以隐藏跨仓库回归、事故代理、任务成功和 owner 成本联合评价；知识边界类型由独立过程数据而非 repo heuristic 识别；理论瓶颈在组织 OOD 上以同预算、同信息和同 decoder 稳定击败 union HGT/POMDP；冲突实验确认 collective ownership、复杂性与协调条件下的相反动作。即便这些条件满足，仍需提出超出 Hahn、Zaggl、Lindberg、Portillo 和 AtomicCommitBench 的新机制。

终局理由可以压缩为一句话：**跨所有权边界的 coding-agent 修改是真实的组织与可靠性问题，但“owner boundary”既不是可直接观测的安全真值，也不产生单调的理论行动；在公开数据上，可训练的部分已被 patch decomposition、reviewer recommendation、STC 和 contract testing 直接覆盖，剩余的语义与实用边界又必须通过真人互动才能识别。**

### 13.5 观察性结果的使用限制

Njoku 等人的 40,214 PR 比较、Ehsani 等人的未合并 PR taxonomy 以及 Khelifi 等人的 58.02% guidance-level intervention 均只用于建立 coding-agent 协作现象与监督负担。本文没有把较低 merge、较多 bot comments、较少社会互动、较大 churn 或 owner intervention 解释为未经 owner 知识支持的回归，也没有把这些观察结果当作训练政策的因果安全标签。
