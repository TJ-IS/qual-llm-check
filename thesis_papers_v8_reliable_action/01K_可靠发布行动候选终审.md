# 可靠发布行动候选终审

> 审查对象：coding agent 将代码、配置或依赖变更推进 CI、预发布、灰度、正式发布或回退时，依据仓库语义、真实服务状态、变更耦合、可观测性和风险暴露选择后续行动。  
> 检索与核验截止：2026-08-15。  
> 终局状态：**NO-GO**。  
> 本文件是内部选题终审，不是论文正文。尚未运行候选算法实验，全文不报告性能结果，也不以“实验尚未运行”作为否决理由。

## 1. 终审结论

这个问题所指向的损害是真实的。错误发布可以造成服务中断、错误数据写入、版本间不一致、权限或依赖安全回归，并使局部错误沿服务依赖和用户流量扩散。coding agent 还能同时修改代码、调用 CI/CD 工具和操作运行环境，使原本由不同角色分担的变更与发布决策集中到同一个自主行动者手中。任务重要性因此成立。

然而，当前候选不能冻结为一篇独立的 ISR 级理论驱动算法论文。否决不是因为发布控制没有工程价值，也不是因为缺少可堆叠的模型模块，而是因为最强救援版本同时触发三个结构性失败。

第一，若输出限于选择 canary、流量比例、等待、推进和回退，研究对象就是 deployment 或 AIOps controller。Google Canary Analysis Service、sequential regression detection、multiobjective reinforcement-learning rollout、CloudCanary、ARBITER 和 Safe Remediation 已分别覆盖指标判定、序贯证据、分阶段行动、变更前相关故障审计、受约束补救和风险预算。trace-economic underwriting 还已把 bounded-role traces 映射到经济损失、CVaR 与 pre-loss controls。把 repository embedding 接到这些控制器之前，不会自动把行动者变成 coding agent。

第二，若为保留 coding-agent 身份而允许模型在发布过程中继续拆分变更、加入兼容层、修改配置、增加观测点或修复代码，问题会变成无界的“代码综合加运行控制”。Ghaleb（2026）证明 agents 已经真实修改 CI/CD 配置；UnderSpecBench 已评价 DevOps action boundaries；LoopsBench 已把 dependency-ready frontier 和持续 regression obligations 做成公开长程执行合同。它们仍未提供同一仓库状态下多种代码改写和多条生产发布路径的独立反事实真值。研究者可以在隔离集群中构造执行数据，但这只能解决训练数据问题，不能消除贡献边界。此时主要新增能力仍是通用代码生成、world model 与 rollout policy 的组合，无法形成一个由 IS 理论独有地产生的行动结构。

第三，也是决定性原因，全文检索到的自然 IS 理论都无法通过同信息、等参数替代检验。Jiang、Sarkar 与 Jacob（2012）已经在软件发布领域精确区分发布时点和停止测试时点，并建模测试者与用户的不同缺陷发现过程；把这两个时钟写进神经策略是对既有发布模型的学习化扩展。Choudhary 与 Zhang（2015）的 SaaS 成本分担只改变奖励参数。Salovaara、Lyytinen 与 Penttinen（2019）的 mindful/mindless 分层会导出未知状态下的人类升级，但该动作等价于不确定性门控，并与 C3 的人审取证及 Safe Remediation 的带宽约束人机协作重叠。软件项目协调、风险响应与 release-cycle entrainment 的理论对象分别是团队协调、管理者意向和组织时间节律，下推到单次 agent action 会造成分析层次错置。最强候选中的理论状态要么是现有输入的确定性变换，要么是行动时钟、奖励系数或认识不确定性；同输入、同动作、同监督和同参数预算的 generic distributional SMDP/POMDP 或 temporal heterogeneous graph 可以复制全部前向计算。

因此，候选即使经过最强救援，也只能成为一项有价值的系统集成或 autonomous DevOps 研究，不能满足本系列对“理论改变不可替代中间状态、损失或行动”的标准。它还会在动作上覆盖数据库迁移候选的 staged commitment，在人类升级和证据获取上覆盖 C3。当前题目应停止，不进入 pilot、正文或 thesis 主线。

## 2. 研究对象和损害边界

### 2.1 候选试图处理的真实决策链

一个严格的 episode 应从固定 repository snapshot 和 change intent 开始，经过代码或配置修改、CI、artifact build、预发布、有限生产暴露、正式推进、持续验证、暂停或回退，直至外部 verifier 判定目标状态安全完成或 episode 终止。风险不是抽象的“低置信度”，而是在以下决策时点形成的可执行后果。

| 决策时点 | agent 当时可见 | 仍然不可见或不确定 | 可造成的损害 | 正常、风险与纠正行动 |
|---|---|---|---|---|
| 提交 CI 前 | diff、依赖图、静态检查、历史测试和变更意图 | 隐藏测试、真实负载、跨服务调用与配置组合 | 编译或功能破坏、安全回归进入共享分支 | 修改、拆分、补测试、运行检查、停止 |
| CI 后进入预发布 | 构建结果、测试轨迹、artifact provenance | 生产数据形状、资源竞争、真实调用分布 | 表面过测的变更进入运行环境 | 重做 patch、加兼容层或观测、部署 staging、暂停 |
| 预发布进入 canary | 预发布 telemetry、依赖和配置状态 | 稀有流量、延迟故障、用户侧失败、污染观测 | 小比例用户受损，错误状态写入下游 | 选择 cohort 与暴露、继续观察、回退、修复 |
| canary 推进或正式发布 | cohort 差异、SLO、日志、trace、业务和安全信号 | 长尾影响、跨版本交互、后续依赖变化 | 服务中断、数据不一致、权限泄漏、错误扩散 | 推进、暂停、缩小暴露、回退、补丁 |
| 发布后停止验证或回退 | 发布后测试与用户反馈、rollback 状态 | 延迟回归、不可逆外部副作用 | 过早停止测试或不完整回退留下潜在故障 | 继续验证、隔离、补偿、回退、升级人工 |

安全改善必须同时报告损害、任务和成本。把所有变更拒绝、永远停留在 canary 或频繁回退都可能降低观测到的事故，却没有完成软件交付。最低结果集应包含 SLO burn 或中断时长、错误或不一致写入、违反安全 invariant 的次数与暴露量、受影响服务和请求规模、恢复完整性、目标变更成功率、time-to-safe-release、人工介入、测试和流量成本。

### 2.2 coding agent 身份的二分检验

候选存在两个互斥版本。

**控制器版本。** 输入是 diff 特征、服务图和 telemetry，输出是 `stage`、`observe`、`promote`、`pause` 或 `rollback`。模型不读取和修改 repository，不生成代码、配置或依赖变更，也不根据运行反馈改变变更本身。这个版本有丰富的序贯决策，但关键行动者是 release controller；称其为 coding agent 只是对象改名。

**联合改写版本。** agent 可以在 rollout 中拆分 commit、加入 backward-compatible adapter、feature flag 或 instrumentation，调整资源与部署配置，修补依赖和代码，再选择下一发布阶段。这个版本保留了 repository-level agency，却把代码综合、变更分解、验证生成、运行诊断、发布控制和恢复全部并入一个策略。不同变更类型没有共同的可枚举改写空间，执行标签取决于项目特定编译器、测试、数据和服务语义。若把改写动作限制成少量模板，策略会蒸馏静态 runbook；若不限制，行动真值与公平比较难以定义。

不存在一个中间版本可以同时绕过两个问题。把自然语言 patch 先交给固定 coding agent、再由 learned rollout head 决策，主要可训练工件仍是 controller；让 controller 反过来调用任意 coding agent，则新增结果混合了 patch generator 和发布策略能力。这个对象检验已经足以排除“普通 canary controller 加上 coding-agent 标签”的方案。

## 3. 最直接工作对研究空间的挤压

### 3.1 canary、rollout、regression 与 rollback

| 直接工作 | 原工作已经执行的动作或学习对象 | 对候选的约束 |
|---|---|---|
| Beyer 与 Davidovic（2018），[Canary Analysis Service](https://research.google/pubs/canary-analysis-service/) | 将 canary 明确定义为部分、限时的生产变更暴露，分析关键指标后 roll forward、roll back、提醒人类或采取其他动作；Google CAS 同时用于 binary、configuration 和 dataset changes | “观察 canary 指标后推进或回退”已是成熟生产控制对象，不能作为新 headline |
| Lindon、Sanden 与 Shirikian（2022），[Rapid Regression Detection in Software Deployments through Sequential Testing](https://doi.org/10.1145/3534678.3539099) | 为 Netflix 部署给出 anytime-valid 的序贯 stochastic-order/equality tests，在持续观测时控制 false detection | 等待更多证据和提前发现回归已有严格统计基线；简单风险阈值或固定窗口明显不足 |
| Pritchard、Nagaraju 与 Fiondella（2022），[Automating Staged Rollout with Reinforcement Learning](https://doi.org/10.1145/3510455.3512782) | 将 nonstationary staged rollout 表成多目标 MDP，以 Q-learning 权衡 downtime 与 delivery time，并包含 transition/observe 等动作 | “学习 rollout 策略并权衡可靠性与速度”已被直接提出；只换深度网络或 telemetry encoder 不构成足够增量 |
| Zhai et al.（2020），[CloudCanary](https://www.usenix.org/conference/nsdi20/presentation/zhai) | 在服务更新前以增量 SAT 审计 correlated failures，并给出 improvement plans | change coupling 与 correlated failure 在发布前检查已有直接系统；一般依赖图风险分数不能声称独有 |
| Henderson et al.（2024），[SafeRevert](https://research.google/pubs/saferevert-when-can-breaking-changes-be-automatically-reverted/) | 研究 CI 何时已经积累足够证据自动回退 breaking change，并在 Google 34,000 个真实 breaking changes 上评价 | “何时证据足够回退”不是空白；候选不能把 CI 证据阈值重新包装为可靠行动 |
| Kayenta、Argo Rollouts、Flagger 等公开工具 | baseline/canary 比较、progressive delivery、analysis gate、promotion 和 rollback | 可运行 substrate 与强规则基线已经存在；新策略必须在相同流量和观测预算上公平比较 |

这些工作没有单篇完成“agent 修改代码再发布”的全部链条，但它们分别封闭了候选最容易声称的核心增量。把多个已有动作置于一个大 action space，只证明系统覆盖范围更广，不证明产生了新的决策能力。

### 3.2 autonomous DevOps、AIOps 与真实服务环境

| 工作或环境 | 已核验范围 | 可复用资产 | 为什么不能直接支持该候选 |
|---|---|---|---|
| [DevOps-Gym](https://openreview.net/forum?id=bP48r4dt7Z)，ICLR 2026，arXiv:2601.20882 | 704 个来自 30 余 Java/Go 项目的任务，覆盖 build/configuration、monitoring、issue resolution 和 test generation，并提供动态 terminal environment | repository、container、terminal interaction 和 end-to-end DevOps task 评测 | 任务不是同一产品变更从 CI 到 canary 和 production 的多阶段反事实发布；没有用户暴露、发布后 SLO 与回退真值 |
| Ghaleb（2026），[When AI Agents Touch CI/CD Configurations](https://arxiv.org/abs/2601.17413)，MSR 2026 | 分析 8,031 个 agentic PR、1,605 个 GitHub repositories、711,923 个 file changes 和 99,930 个 completed GitHub Actions runs；CI/CD change 高度集中于 GitHub Actions | replication package、agentic PR、YAML/CI platform 分类与 workflow-run outcome | 证明 coding agents 实际会改 CI/CD，也提供 configuration-change encoder 的历史语料；merge/build success 是选择性观察和近端 proxy，不是 staging、canary、生产损害或反事实 release outcome |
| Ji et al.（2026），[UnderSpecBench](https://arxiv.org/abs/2607.02294) | 69 个 incident/CVE/tool-behavior grounded DevOps task families，四个 capability domains、九个 control surfaces；以 intent clarity、target certainty 和 blast radius 形成 2,208 个 prompt variants | 可重置 runtime、shadowed CLI、agent-invisible harness 与 deterministic side-effect oracles，区分 Safe Success、Wrong Target 和 OverScope | 是 coding-agent DevOps 安全的强直接 benchmark；每个 task 固定一个 ground-truth safe action，作者也承认可能漏掉可辩护替代，因此不提供多阶段 release policy 的多行动结果分布 |
| Li et al.（2026），[LoopsBench](https://arxiv.org/abs/2608.00267) | 112 个 long-horizon tasks、八种语言、九个 domains、5,300 余 development units；以 source-evidenced prerequisite DAG 释放 ready-frontier tests，并把已完成节点保留为 regression obligations | 开源 task/code、dependency DAG、flow-aware runtime、checkpoint test-state matrix 与 loop traces | 可支撑持续 coding-loop、依赖顺序和回归义务评价；其 `release` 是 evaluator 对 tests 的释放，不是产品发布，仍没有 service exposure、SLO、canary 或 rollback outcome |
| [AIOpsLab](https://arxiv.org/abs/2501.06706)，MLSys 2025 | 可部署 microservices、注入故障、生成 workload 和 OpenTelemetry，并评价 detection、localization、RCA 与 mitigation | Microsoft 公开实现、DeathStarBench/Online Boutique 类服务、可重复 fault injection | 主要对象是 incident-management/AIOps agent；输入输出可以完全绕过 repository code change |
| ITBench | 公开 Kubernetes 场景涵盖 SRE、FinOps 和 CISO 类运维任务 | 集群状态、incident remediation 和执行 oracle | 不是 repository change rollout；最自然行动者是运维控制器 |
| DeployBench，arXiv:2606.05238 | 评价 agent 部署研究 artifact 的能力 | 可重建软件 artifact 和 deployment tasks | 部署目标是让 artifact 运行，不是承担真实产品用户流量的 progressive release |
| DeathStarBench、Online Boutique、Train Ticket | 开源微服务、workload 和部分可观测性，可与 Kubernetes、Chaos Mesh 结合 | 构造服务依赖、故障、SLO 和恢复实验 | 没有天然的 code/config/dependency change histories、gold rollout alternatives 或组织发布结果；需要研究者另造变更和真值 |

这些环境说明执行实验可以构造，所以“完全没有可运行环境”不是否决理由。它们同时暴露了身份问题：AIOpsLab 和 ITBench 的最自然 policy 处理已经发生的运行故障；DevOps-Gym、UnderSpecBench 和 LoopsBench 的 agent 处理 repository 或 DevOps action，却没有 production rollout lifecycle。Ghaleb（2026）又证明真实 agentic PR 确会改 CI/CD，因此“coding agent 不会碰发布配置”也不是可用缺口。剩余工作是把真实 coding traces、长期 regression obligations 和 production controller 焊接起来；这有工程价值，但焊接本身不产生 ISR 理论机制。

### 3.3 受约束补救、事务与恢复近邻

| 工作 | 已覆盖能力 | 候选必须让出的能力 |
|---|---|---|
| [ARBITER](https://arxiv.org/abs/2607.19182) | 以 OpenTelemetry 构造 causal resource graph 和 bounded DiagnosisContext；在 typed finite actions 上使用 deterministic validator、policy gate、resource/disruption budgets、approval 和 bounded execution；在 DeathStarBench 与 Online Boutique 处理 bad-image regression 等场景 | causal service graph、target selection、`rollback_canary`、预算和 action gate 不能重新命名为本题算法 |
| [Safe Remediation for Autonomous Cloud Operations](https://arxiv.org/abs/2607.20005) | 以 CMDP 最大化 repair success，同时限制 false remediation；显式考虑 blast radius、reversibility、epistemic uncertainty 和带宽受限 HITL | 风险约束、可逆性、不确定性和请求人类都已有最直接技术近邻 |
| [Cordon](https://arxiv.org/abs/2606.17573) | 在 intent、result lineage、shadow state、staged effects、delegated authority 和 audit 上建立 task-scoped semantic transaction，支持 commit、abort 与 recovery | staged external effect、任务提交边界和授权审计不是新能力 |
| [DART](https://arxiv.org/abs/2605.23311) | failed-instance localization、admissible restore boundary、instance-aligned checkpoint 和保留已提交下游工作 | 依赖感知恢复和部分回退已被直接处理 |
| Atomix，arXiv:2602.14849 | transactional tool use、buffered effects 和 compensation | 在工具外面增加 transaction wrapper 或补偿对不是新贡献 |
| [Agent Meltdowns](https://arxiv.org/abs/2605.19149) | 以含良性失败的交互环境显示 agent 为完成任务会触发不安全恢复和连锁副作用 | 可用于风险动机和失败案例，但不提供发布策略的 theory-specific supervision |

ARBITER 与 Safe Remediation 尤其重要。候选若只增加 learned risk score 或 learned action head，就落入它们已经界定的受约束运维补救。若增加 transaction 和 recovery 层，又落入 Cordon、DART 和 Atomix。可复用这些系统作为 executor，不等于可以把它们的能力累计成新的学术贡献。

### 3.4 change-risk prediction、经济风险控制和交付过程研究

“Learning from Change: Data-Driven Deployment Risk Prediction at Scale”（ICSE-SEIP 2026，DOI [10.1145/3786583.3786876](https://doi.org/10.1145/3786583.3786876)）使用银行一年部署数据与 LightGBM/SHAP 分析 change 和 team features；“Deployment Risk Assessment Using Diff-Aware Features: A Case Study at Prime Video”（arXiv:2607.06766）使用 diff-aware 和结构特征，并结合 private data 与 ApacheJIT。它们说明从 diff 预测 deployment risk 已是直接对象，同时也说明高价值部署 outcome 多为组织私有。候选不能以“把 risk prediction 接在 rollout 前”为主要工件，因为这仍是标量预估加既有控制器。

软件交付领域还长期研究 continuous deployment、release cadence、testing 和 field failure。对本候选最具约束力的不是某个未覆盖的模型名称，而是现有工作已经分别拥有风险预测、证据积累、流量控制、回退、受约束补救与恢复。要构成独立论文，必须证明一个理论要求的联合状态会让 coding agent 产生这些系统都无法表达的 code-and-release action；本次检索没有找到该状态。

Xu et al.（2026）的 [trace-economic underwriting](https://arxiv.org/abs/2606.16465) 进一步封闭了“把发布 trace 映射为经济风险，再以 CVaR 决定介入”的救援方向。该文把 monitored customer–task–trace episode 作为风险单位，以 defined role 固定任务类别、权限和可比 histories，再将 trace、customer exposure、asset value、claimability、deductible、limit 和 intervention cost 映射到 expected claimable loss。其 pre-loss control 已包含 `allow/review/sandbox/stop`，并在 1,000 条 SWE-smith traces 上报告 trace-conditioned control 的 CVaR95 结果；其代码、标签和 audit sheets 对外提供。该文还给出明确的 scope condition：unrestricted general-purpose agent 不是有限样本可识别的 underwriting object，只有受监控且有界的 role 才产生可比 episode。

这个近邻对本候选有双重约束。若把 outage、data/security regression 换算为 dollars、premium 或 claimable loss，论文对象会变成风险定价与控制，而不是可靠发布；若只借用 irreversibility、blast radius、uncertainty、temporal position 和 CVaR，它们又是可由相同 trace 和 customer profile 计算的风险特征与目标，不能承担独有 IS 理论状态。发布论文应以真实服务损害和 safe-release outcome 为主结果，并把 trace-economic model 作为直接基线或排除项，不能把它吸收后声称“首次考虑经济风险”。

## 4. 公开数据、执行真值和训练可识别性

### 4.1 公开资产实际提供什么

| 资产 | 可形成的监督 | 缺少的关键真值 | 结论 |
|---|---|---|---|
| DevOps-Gym repository tasks | build、test、issue resolution 与 terminal execution success | production exposure、SLO、canary、promotion 与 rollback outcome | 只适合前半段 coding action |
| Ghaleb（2026）CI/CD replication data | agentic PR、CI/CD YAML、merge status 和 GitHub Actions run outcome | 未提交建议、人工选择过程、staging/production state、用户损害和替代 release path | 可预训练 CI/config encoder或作描述性事实；不能把 merge/build proxy 当 safe release label |
| UnderSpecBench | intent/target/blast-radius manipulation，以及 Safe Success、Wrong Target、OverScope 的 side-effect truth | 每个 task 只有一个 intended safe action，没有 canary time series 或多条可接受 release trajectories | 适合测试 action boundary；不能训练丰富的 release policy |
| LoopsBench | prerequisite DAG、ready-frontier test release、持续 regression obligations、checkpoint state matrix | 运行服务图、真实暴露、release-stage action 和事故损害 | 适合持续 coding-loop 与 regression-retention 子评价；不是 deployment benchmark |
| AIOpsLab、DeathStarBench、Online Boutique、Train Ticket | fault injection、telemetry、service graph、mitigation 和恢复结果 | 真实 repository changes 及同一变更的多条 release trajectories | 只适合后半段运行控制 |
| ApacheJIT 与公开 defect/change histories | diff、commit、issue 和缺陷标签 | 部署时服务状态、用户暴露、回退完整性、发布成本 | 可预训练 change encoder，不能训练端到端 policy |
| CAS/Kayenta、Argo Rollouts、Flagger | progressive-delivery executor 与规则结果 | counterfactual code rewrite、组织发布 outcome 和隐藏安全语义 | 可作为基础设施与基线 |
| trace-economic underwriting artifact | customer–task–trace schema、deterministic economic labels、claimable loss、pricing/control evaluation | 不是实际 release execution truth；经济 labels 依赖 profile、contract 与规则，且主要 actions 为 review/sandbox/stop | 适合风险估值基线，不可替代 outage/data/security oracle |
| 私有 Google、Netflix、银行与 Prime Video 数据 | 真实 CI 或 deployment outcome 的论文证据 | 数据不能作为公开 benchmark 重跑，跨组织字段也不一致 | 只能界定近邻，不能充当本题训练集 |

截至截止日，没有核验到同时包含 repository diff、CI 结果、预发布状态、canary telemetry、用户暴露、promote/rollback action、发布后损害和替代行动结果的公开生命周期数据集。这个缺口可以通过隔离执行构造部分弥补，因此单独看不是 NO-GO；但它会使“联合改写版本”的标签主要由研究者设计的 fault templates 和 action templates 决定。

### 4.2 最强可接受的数据构造方案

若暂不考虑终审结论，最严谨的构造应按以下方式进行。

1. 从明确许可的 Java、Go 和云原生 repositories 抽取独立 code、configuration 与 dependency changes，固定 source commit、target intent、build image、dependency lock 和许可 manifest。
2. 将每个项目编译为可重置的 Kubernetes episode，持续运行公开 workload，并将 hidden functional tests、SLO、data invariant、authorization checks、dependency/security scans 和 rollback replay 放在 agent 无法修改的 verifier 容器中。
3. 对同一初始 snapshot、workload seed 和 fault seed，克隆多个隔离分支，执行不同 patch decomposition、instrumentation、canary cohort、exposure、wait、promotion 和 rollback 轨迹。counterfactual sibling branches 只用于训练标签，不进入 policy 输入。
4. 行动轨迹混合 fixed progressive-delivery tools、sequential tests、human-authored plans、通用 coding agents、safe randomized exploration 和 model-based search。若轨迹全部来自单个手写 FSM，learned policy 只是规则蒸馏。
5. execution truth 由容器退出状态、hidden tests、trace-derived request correctness、SLO burn、data checksum/invariant、安全扫描、受影响请求数、recovery replay 和最终 repository target verifier共同产生。LLM judge 不得产生主要安全标签。
6. 每个 step 保存 repository commit、container digest、cluster manifest、observability schema、visible state cutoff、action、patch、pre/post state hash、workload/fault seed、oracle version 和 reset result。

即便完成上述构造，样本也更接近“研究者控制的微服务 release simulator”。它可以评价系统能力，却不能自动赋予 IS 理论效度。不同项目的有效 code rewrite 空间还会由编程语言、框架、数据语义和部署工具决定，统一 policy 很容易学习 fault-template ID 或 environment fingerprint。

### 4.3 必须采用的 split 与泄漏隔离

- repository、organization surrogate 和 service family 全部分组留出，禁止同一项目的相邻 commit 跨 train/test。
- 按日历时间先后切分 dependency versions、base images 和 vulnerabilities，训练不得看到未来发布结果或未来 CVE 修复 patch。
- code、config、dependency、API compatibility、resource contention、security regression 和 data-consistency fault family 分组做 OOD；同一 injection template 的参数变体不得跨集合。
- workload、fault 和 canary assignment seeds 只供 environment 使用。policy 只能看到决策时已经产生的 telemetry，不能看到 rollout 结束后的聚合特征。
- hidden tests、SLO threshold、data/security invariant 与 gold target 放在只读 evaluator；agent 不得修改测试、监控查询或 oracle。
- paired sibling rollouts 可以共享随机种子以降低反事实方差，但 split manifest 必须按 episode family 先冻结，不能按 rollout 分支随机切分。
- change-risk 预训练语料与下游 test repositories 做 commit、fork 和内容近重复排查；dependency graph 与 artifact digest 也要检查跨集重合。

这些要求能够阻止明显泄漏，但不能解决下文的理论可约化性。

## 5. AIS Basket 理论终审

### 5.1 逐项检验

| 理论或 IS 工作 | 与发布行动的自然联系 | 若进入算法会产生什么 | 终审 |
|---|---|---|---|
| Jiang、Sarkar 与 Jacob（2012），postrelease testing and software release policy | 对象就是 enterprise software release；分开 release time `τ` 与 testing-stop time `T`，并区分 tester 和 user defect-detection process、opportunity/testing/field-failure costs | 两个时钟、渠道别缺陷负担与成本函数 | **对象自然，但直接工作已经拥有机制；状态也是 generic SMDP 的普通行动历史与 reward** |
| Choudhary 与 Zhang（2015），SaaS patching | SaaS 改变 vendor 与 users 承担 patch cost 的比例，并影响 patch/release timing | cost-share 参数 `α`、provider/user harm 权重 | **只改 reward coefficient，不产生新表示或动作语法** |
| Salovaara、Lyytinen 与 Penttinen（2019），high reliability in digital organizing | frame problem 说明 digital algorithm 无法穷尽未被框定状态；可靠数字组织把快速、可扩展的 mindless digital operations 与较慢、情境化的 mindful human operations 分层 | novelty/frame state 与 human escalation lane | **自然但等价于 epistemic-uncertainty/HITL gate；与 C3 和 Safe Remediation 重叠** |
| Andres 与 Zmud（2002），software-project coordination fit | task interdependence 与 coordination approach 的匹配可能解释跨服务耦合 | pooled/sequential/reciprocal relation labels 或 coordination cost | **理论单位是团队/项目协调；把服务依赖边当组织协调构念是层次错置** |
| Moeini 与 Rivard（2019），IT-project risk response | 解释项目管理者是否响应风险的态度、规范压力与 perceived control | manager-response propensity 或干预阈值 | **人类意向模型，不是机器 action policy；不能规范哪项代码或发布动作正确** |
| Lindberg et al.（2024），release-cycle entrainment | OSS task allocation 与 release cycles 的时间耦合 | cadence phase 或 temporal rhythm | **组织过程解释，不给单次 rollout 的安全方向** |
| Benaroch（2018），proactive uncertainty-reducing mitigation real options | 发布前可等待、取得信息或采取保护措施，再作更难逆转的 commitment | learning/prevention/coping impact、顺序交互与 option value | **已是数据库迁移候选的核心理论；在一般发布中又退化为已有 stage/observe/rollback action，破坏系列独立性** |

### 5.2 Jiang、Sarkar 与 Jacob（2012）为什么仍不能救题

本地 AIS 全文 `database_fulltext_all/04228_2012_postrelease-testing-and-software-release-policy-for-enterprise-level-systems.md` 显示，这篇 ISR 工作并非仅提供“测试很重要”的背景。它把软件 release policy 写成两个可区分的决策时点，明确 postrelease testing 使产品可以在测试停止前发布，并让 tester 与 users 在不同路径上发现 defect；目标函数同时容纳机会成本、测试成本和 field-failure cost（Information Systems Research 23(3-part-1):635–657，DOI [10.1287/isre.1110.0379](https://doi.org/10.1287/isre.1110.0379)）。这正是本候选能找到的最自然理论邻居。

如果据此设计模型，前向计算必须保留残余缺陷负担 `u_t`、测试者发现率 `λ_test,t`、用户暴露发现率 `λ_user,t`、发布时钟 `τ_t`、停止测试时钟 `T_t` 以及三类成本。冲突情境也很清楚：机会成本较高时，可能先向有限用户发布，同时继续测试；用户暴露信号和测试证据不能被一个“是否发布”分数吞并。

问题在于，这些计算责任已经是该文的核心理论结果，不是从 coding-agent 情境新发现的机制。`τ_t` 和 `T_t` 是 action history 中的两个显式时钟，`λ_test,t` 和 `λ_user,t` 是观测 channel 的 hazard，三类成本是 reward。给相同 state、actions 和 labels 的 constrained SMDP 可以无损表示它们。若 neural factorization 优于 generic model，能够成立的是有限样本 inductive-bias 贡献；它并没有创造通用模型无法复制的 intermediate state。按本项目明确的理论责任标准，这不足以冻结。

### 5.3 high reliability in digital organizing 为什么会滑入 C3

Salovaara、Lyytinen 与 Penttinen（2019）的全文 `database_fulltext_all/12734_2019_high-reliability-in-digital-organizing-mindlessness-the-frame-problem-and-digital-operations1.md` 说明，数字算法在已经框定的状态中可以快速、稳定和可扩展地运行，却无法穷尽开放世界中的 unframed circumstances；高可靠组织通过较慢、具有认识和实践情境能力的人类行动补足这一限制（MIS Quarterly，DOI [10.25300/misq/2019/14577](https://doi.org/10.25300/misq/2019/14577)）。将这个机制映射到发布并不牵强：常规兼容变更可走 automated lane，观测模式超出已知 frame 时转给 human lane。

然而，这个映射只会得到 novelty detection、abstention 和 evidence package。generic uncertainty estimator 可以复制前两项；要让人类作出更好判断又必须选择、组织和呈现证据，这正是 C3 的取证与共同理解问题。Safe Remediation 还已经把 epistemic uncertainty、blast radius、可逆性和受限人类带宽纳入 cloud-operation policy。保留该理论会让候选要么成为普通 HITL gate，要么与 C3 争夺同一研究对象。

### 5.4 其余理论的层次和计算责任失败

Choudhary 与 Zhang（2015）的本地全文 `database_fulltext_all/09066_2015_research-notepatching-the-cloud-the-impact-of-saas-on-patching-strategy-and-the-timing-of-softwa.md` 讨论 SaaS 如何改变 vendor 与 users 的 patching cost allocation（ISR 26(4):845–858，DOI [10.1287/isre.2015.0601](https://doi.org/10.1287/isre.2015.0601)）。这个关系可以提醒评价不要把 provider downtime 和 user harm 合成一个无解释标量，却不能决定 agent 应拆哪个 commit、加何种兼容层或选择哪个 cohort。

Andres 与 Zmud（2002）的 contingency coordination 研究位于人类 software team 和 project 层次（JMIS，DOI [10.1080/07421222.2002.11045695](https://doi.org/10.1080/07421222.2002.11045695)）。把 reciprocal interdependence 直接编码为 microservice edge type，看似为图网络提供理论标签，实际混同了组织协调依赖和运行时技术依赖。Moeini 与 Rivard（2019）的 risk-response model 同样解释 manager 的态度、压力和控制感（MISQ，DOI [10.25300/misq/2019/14505](https://doi.org/10.25300/misq/2019/14505)），不能作为机器采取 rollout action 的规范。Lindberg et al.（2024）研究 open-source task allocation 与 release-cycle entrainment（MISQ，DOI [10.25300/misq/2023/16789](https://doi.org/10.25300/misq/2023/16789)），也没有给单个变更的发布安全策略。

结论不是“IS 理论与发布无关”。相反，Jiang et al. 与 Choudhary and Zhang 已证明 release policy 能够与 IS 发生直接对话。失败点在于本候选需要一个尚未被直接研究、并会改变 coding agent 内部计算的机制；当前自然理论要么已经是发布领域的直接模型，要么只提供 reward、gate 或组织层解释。

## 6. 最强救援算法规格

本节故意把候选强化到不再是风险分数、allow/block 或提示工程，用以检验它是否仍然可约化。以下均是设计，不是已经实现或取得结果的陈述。

### 6.1 研究问题和输出工件

最强可辩护的研究问题是：在目标 repository change 已给定、运行环境持续变化、部分后果只有暴露后才可见的条件下，coding agent 能否联合学习变更重构、信息取得和 staged-release 行动，使多维损害的尾部风险受控，同时保持 safe completion 和 release latency？

训练完成后需要产生三个独立 checkpoint，而不是云端 LLM 调用脚本。

1. `release_state_encoder.ckpt`：把 repository change、typed dependency/resource graph 和 telemetry history 编成可校准 belief state。
2. `release_outcome_model.ckpt`：预测每个候选 code-and-release action 的 next-state、任务结果、成本及多维损害分布。
3. `release_policy.ckpt`：在外部 hard invariants、风险预算和行动权限下选择 patch、实验、暴露、推进或恢复动作。

如果最终工件只有 `risk_score.ckpt`，或 policy 只把 score 与阈值比较，本题直接撤销。

### 6.2 输入、张量与输出

设 batch size 为 `B`，repository token 上限为 `L`，异构图节点数为 `N`，关系类型为 `K`，telemetry 窗口为 `H`，指标数为 `M`，候选行动数为 `A`，hidden width 为 `d`。

- change tokens：`D ∈ R^{B×L×d}`，由 diff、相邻函数、配置、lockfile、build/deploy manifests 与 change intent 编码，并保留 file/symbol/token masks。
- heterogeneous state graph：`X_t ∈ R^{B×N×d}`，节点类型至少包含 symbol、file、package、artifact、config key、service、database/invariant、SLO、metric、cohort 与 rollout stage。稀疏关系 `E_t^{(k)}` 区分 call、dataflow、build、dependency、deploy、traffic、writes-to、observes 和 rollback-dependency。
- telemetry：`W_t ∈ R^{B×H×M}`，另有 missing mask、sampling interval 和 cohort/source tags；禁止把 rollout 结束后的 summary 回填到较早时点。
- action/history：`A_{<t} ∈ N^{B×t}`、连续 action parameters、patch embeddings、stage clocks、traffic exposure、budget usage 和 executor return codes。
- candidate-action tensor：`C_t ∈ R^{B×A×d}`，每项包含 typed action、作用对象、patch pointer、预期权限、资源和 disruption envelope。
- 可检验但最终未通过终审的 postrelease-testing 因子：`z_t^{PT}=[u_t,λ_test,t,λ_user,t,τ_t,T_t,c_op,c_test,c_field]`。这些量必须由独立 heads 或已知成本输入产生，不能只在变量命名中出现。

outcome model 对每个 `a` 输出 `Q` 个 quantiles 或 mixture parameters：任务成功、time-to-release、SLO burn、错误请求/数据写入、安全 invariant violation、blast radius、人工与计算成本、rollback completeness，以及 next-state distribution。policy 输出分层 action distribution 和连续参数，不输出单一 allow/block。

### 6.3 架构

1. repository transformer 编码 diff 与跨文件上下文；relational graph transformer 在 typed edges 上传播 code-to-service-to-metric 影响；masked temporal transformer 编码 telemetry 与 action history。
2. cross-attention 将每个 candidate action 查询 repository、graph 和 telemetry state，形成 action-conditioned belief。单纯 embedding top-k 不可充当 learned decision capability。
3. distributional world model 预测 `p_θ(s_{t+1}, y_harm, y_task, y_cost | s_t,a_t)`；对不可见 runtime state 使用 ensemble 或 latent belief，而非把缺失值设为零。
4. patch branch 在允许的代码行动中生成或选择 structured edits，并由 compiler、static analysis、hidden test proxy 和 typed executor 验证。发布 branch 决定 stage、cohort、exposure、observe、promote、pause 或 rollback。
5. conservative offline RL 或 model-based constrained policy 使用 CVaR/chance constraints 控制每类损害，不把损害先压成一个 score。hard permission/invariant 由外部 substrate 强制，不能让 learned verifier覆盖强约束。

这是一个有实质训练量的算法，而非提示工程。它的问题不在“太简单”，而在理论专属性和对象边界。

### 6.4 训练样本和监督

每个 step 的监督必须来自上节隔离 branch execution。

- `L_next`：next-state continuous variables 的 likelihood/Huber loss 与 discrete state transitions 的 cross-entropy。
- `L_harm`：各损害结果的 distributional quantile/mixture NLL，另外训练 calibrated exceedance probabilities。
- `L_task`：外部 target verifier、hidden tests 和 safe completion 的监督；不得把 agent 自己修改的测试当 gold。
- `L_patch`：compiler、type checker、static analysis、dependency resolver 和 execution reward；自然语言相似度不作为 correctness label。
- `L_CQL` 或其他 conservative offline objective：约束未充分支持的 action value，另用 importance 或 doubly robust estimator 做离线检查。
- `L_constraint`：对 SLO、data、security 和 permission 每类 chance constraint 的 Lagrangian violation。
- `L_cal`：time-sliced calibration，防止 telemetry drift 下置信度失真。
- `L_PT`：只在 Jiang 模型的预注册参数区间内，要求 release 与 testing-stop 两个 hazard 不被绑成同一输出，并保持 tester/user evidence channels 的独立更新。

总目标可写为

`L = L_next + λ_h L_harm + λ_t L_task + λ_p L_patch + λ_q L_CQL + λ_c L_constraint + λ_cal L_cal + λ_PT L_PT`。

权重、约束阈值和 Lagrange 更新必须仅用 training/validation episodes。test 环境中不能根据失败类型重新调阈值。

### 6.5 推断时实际动作

允许动作必须是 executor 可执行且可审计的 typed actions。

- repository actions：拆分或重排 change、加入兼容 adapter/feature flag、修复代码或配置、调整 dependency、增加 instrumentation、重新 build。
- evidence actions：运行 targeted CI、integration test、shadow workload、staging replay、扩大某个 telemetry window；不能只向 LLM 提问。
- exposure actions：选择 canary cohort、流量比例、持续时间和资源隔离，或缩小暴露。
- release actions：推进、保持、暂停、abort、回退到已验证 artifact、在允许时执行预注册 compensation。
- governance action：把 episode 和最小证据包交给人类。若这一行动成为主要创新或主要结果，立即判为与 C3 重叠。

每次行动前由外部 validator 检查 authority、target identity、resource/disruption budget 和不可修改 invariant。policy 不得通过编辑 manifest 给自己扩权。

### 6.6 算力、checkpoint 与复现

一个足以检验而非证明可行的预算估计是 4 张 48–80GB GPU、64–256 个 CPU cores 或 Kubernetes workers、20,000–100,000 条可重置 branch executions、5–20TB 压缩 telemetry，以及 7–21 天的分阶段训练。具体值必须由 pilot 的平均 episode 时长和存储测量更新，不能写成已经消耗的资源。

复现包至少需要 `repositories.manifest.jsonl`、`episodes.manifest.jsonl`、`splits.yaml`、container digests、cluster manifests、observability schema、fault/workload/action seeds、oracle images、训练配置、所有 threshold/Lagrange histories、三个 checkpoint、baseline adapters 和逐 episode 原始结果。每个实验重复至少保存预注册随机种子；统计单位是 repository/change episode，不是高度相关的 telemetry row。

## 7. 最强基线、公平比较与冲突检验

### 7.1 基线矩阵

| 基线 | 必须给它的相同信息和能力 | 负责排除的平庸解释 |
|---|---|---|
| CAS/Kayenta、Argo Rollouts、Flagger | 相同 metrics、cohort、traffic 和 rollout budget | 规则或现成 progressive delivery 已足够 |
| Lindon et al. sequential tests | 相同逐时 observations 和 false-alarm target | 候选优势只是更早停止或更宽松误报 |
| Pritchard et al. multiobjective rollout RL | 相同 stage/action space、training episodes 和 reward components | 深度策略只是复刻 staged-rollout RL |
| CloudCanary | 相同 service-update graph、failure assumptions 和预检查预算 | 候选优势来自已有 correlated-failure audit |
| SafeRevert | 相同 CI evidence、culprit candidates 和 revert authority | 自动回退只是现有证据充分性算法 |
| UnderSpecBench action-boundary harness | 相同 task instruction、target candidates、authority、blast-radius cues 和 side-effect oracle | 候选安全改善只是更少 Wrong Target/OverScope 或更频繁 clarification |
| LoopsBench flow-aware loop | 相同 prerequisite DAG、ready frontier、active regression obligations 和 test budget | 长期可靠性只是持续保留已过测试与按依赖推进 |
| ARBITER 与 Safe Remediation | 相同 telemetry/resource graph、typed actions、budgets、approval 和 executor | learned graph policy只是受约束 AIOps remediation |
| Cordon、DART、Atomix | 相同 staged-effect、checkpoint、compensation 和 recovery substrate | 成功来自 transaction/recovery wrapper |
| change-risk predictors | 相同 diff/history/team-surrogate features | world model 只是更复杂的风险分数 |
| trace-economic underwriting control | 相同 customer/role、trace、asset exposure、claimability、intervention cost 和 contract terms | CVaR 或介入收益来自现成 trace-to-loss 表示而非 release mechanism |
| coding agent + deterministic guarded release substrate | 相同 base coding model、token/tool budget、tests 和 release tools | 增益来自更强 patch generator 或更多工具 |
| equal-parameter generic distributional SMDP/POMDP | 完全相同 raw inputs、actions、loss labels、compute 与参数量；删除 theory factor names | 理论 factorization 只是可重命名 latent slots |
| equal-parameter temporal heterogeneous graph policy | 相同 node/edge/telemetry tensors，以通用 cross-attention 替代理论时钟或 gate | typed graph 已能复制所谓 theory mechanism |

若某个 baseline 不支持 code rewrite，比较必须分成固定 patch 的 rollout stratum 和共享同一个 patch generator 的 policy stratum。不能让 proposed model 同时获得更强代码模型和更大 rollout budget，再把差异归给理论。

### 7.2 理论方向冲突

即使候选已经被终审否决，若未来有实质新理论试图重开，至少要通过以下冲突情境。

1. **发布与停止测试冲突。** 机会成本高、当前证据允许有限暴露但残余测试价值仍高时，应出现 `release now` 与 `continue testing` 同时成立，而不是把 `τ` 和 `T` 绑成一个 gate。这是 Jiang et al. 的已有方向，不是候选的新理论贡献。
2. **测试者与用户证据冲突。** tester channel 持续发现内部问题而用户指标暂稳，或反向发生长尾用户失败时，policy 必须按 channel 更新 belief，不能只看总 anomaly score。
3. **提供者与用户成本冲突。** provider 为加速交付承担低成本，但用户侧 failure cost 高时，Choudhary–Zhang cost sharing 会改变 release timing；这仍只是 reward sensitivity。
4. **已框定与未框定状态冲突。** 指标正常但依赖拓扑或行为模式超出训练 frame 时，high-reliability 视角预期转入 mindful human lane；generic epistemic uncertainty 也给出同一动作。
5. **改写与流量控制冲突。** 相同风险可以通过拆分 patch、加入 adapter 或降低 exposure 处理时，policy 应依据后果分布选择作用层；当前没有 IS 理论规定两类手段的条件顺序。

### 7.3 机制中和与撤销检验

- 将 `τ` 与 `T` 强制相等，检验两时钟是否有独立行为价值。
- 打乱 tester/user channel 标签，同时保留总 evidence 和参数量。
- 将 provider/user cost weights 替换为同维可学习 reward weights。
- 将 novelty/frame head 替换为等参数 ensemble uncertainty 或 conformal abstention。
- 用同维 latent slots 替换 `z_t^{PT}`，允许 generic model 接受完全相同监督。
- 对 typed relation 做边类型打乱、仅保留 topology 和同参数 message passing。
- 固定同一个 patch generator，分别比较 theory policy 与 generic policy；再固定同一个 policy 比较 patch generator，隔离能力来源。

若 equal-parameter generic model 在预注册容差内复制 harm、task、cost、OOD 与 conflict behavior，理论算法贡献必须撤销。这里不是等待实验才发现一个潜在风险；下一节给出为何这种复制在当前候选中已经由状态定义成立。

## 8. 同信息、等参数通用替代的可约化性

令可见原始状态为

`s_t=(D,G_t,W_{≤t},a_{<t},stage_t,exposure_t,budget_t)`，

行动集合为 repository edit、evidence acquisition、stage/exposure、promotion、rollback 和 escalation 的并集 `A(s_t)`。当前找到的理论状态可以写成

`z_t=f(s_t,c)`，

其中 `c` 是已知的 opportunity/testing/field-failure costs、provider/user cost share 或组织设置。`τ_t`、`T_t` 和 exposure 是行动历史的确定函数；tester/user evidence 是 `W_{≤t}` 的 source partition；cost share 是 reward 参数；novelty 是对 `p(s_t|train)` 或 world-model disagreement 的函数。若再加入 trace-economic underwriting，customer profile、asset value、deductible、limit、claimability 和 intervention cost 只是扩展后的已知上下文 `c_econ`，claimable loss 是 trace 和 `c_econ` 的规则或学习映射。没有一个 `z_t` 引入 raw state 中不存在且能由独立观测或理论约束识别的新信息。

候选的 theory-factored policy 是

`π_θ(a_t|s_t,z_t)=π_θ(a_t|s_t,f(s_t,c))`。

把 `f` 作为 generic encoder 的一部分，或给等宽 latent slots 和相同辅助 labels，便得到只依赖 `s_t,c` 的策略 `π_φ(a_t|s_t,c)`。两者有相同 action feasibility、执行监督与外部 verifier。增加 relation-aware graph、distributional heads、CVaR 或 POMDP belief 不改变这个结论，因为它们都是通用方法而非理论专属运算。

更强的反证来自监督来源。所有方向约束最终都由 branch execution 的 task、harm、cost 和 next-state labels验证。只要 generic model获得同一标签，它就可以直接学习哪个时点发布、继续测试、回退或加观测。Jiang 因子可能提高有限样本效率或可解释性，但它既没有额外信息，也没有禁止 generic model 的某类错误计算；相反，Jiang et al. 已经直接定义这些时钟。按照本项目“若等参数通用替代能够复制，则撤销独立理论算法贡献”的明确标准，本候选不能冻结。

这个论证不依赖 universal approximator 的空泛说法。否决成立于更具体的三点：理论量都是同一输入的可计算分区；理论行动已经包含在 generic action space；训练 truth 对二者完全相同。除非未来理论产生一个由发布情境独立测量、具有不可交换结构和反常方向的中间状态，否则扩模型或多跑数据不会改变结论。

## 9. 与数据库迁移候选和 C3 的边界冲突

### 9.1 数据库迁移候选

数据库迁移具有一般 release 不具备的专门语义：旧、新应用版本同时读写持久状态，expand、dual-write、backfill、validation、cutover 和 contract 改变的是数据真值、兼容窗口和可恢复边界。`01H_主动缓解期权格设计冻结规格.md` 已把该题冻结得更窄也更强：episode 从 `READY_COMPATIBLE` 开始，`pgroll start`、必要 backfill 和 old/new write propagation 已由固定 substrate 完成；agent 在 pre-cutover 状态选择 `shadow_replay`、`semantic_validate`、`failback_drill`、`temporary_write_cap`、`defer`、`pgroll complete` 或 `pgroll rollback`，并以数据损坏、语义不一致、SLO 和恢复 oracle 判定结局。其最强理论救援还把 learning、prevention 和 coping mitigation 的条件价值绑定到 `defer–mitigate–exercise–abandon` lattice。

这意味着本候选不能再把“发布前取得证据、主动保护、保留 rollback、决定何时 cutover”作为一般 release 的新增能力，数据库 pre-cutover 已被 01H 精确占用。若本候选保留代码/配置/依赖的所有 rollout action，它会把该迁移 episode 当作一个 change type并共享观察、推进、回退和 real-options 控制，导致两个题在算法行动和理论上互相吞并。

若为保持独立而排除 stateful/data-semantic changes，可靠发布候选又只剩普通 stateless rollout，直接落入 CAS、rollout RL、ARBITER 和 Safe Remediation。这个冲突不是用“论文一研究迁移、论文二研究发布”两个名词即可解决。

### 9.2 C3 人审取证

high-reliability 理论的唯一明显特殊行动是当当前 frame 不足时转入 mindful human operations。要评价这个动作是否提高安全，系统必须决定何时升级、向谁升级、选择哪些 logs/traces/diffs/counterfactuals、怎样呈现不确定性，以及人类是否据此作出更好的判断。这些正是 C3 的监督、证据取得、共同理解和人工负担结果。

若本候选只输出 `ask_human` 而不研究证据内容，它就是普通 abstention action；若研究 evidence package 和审批质量，就与 C3 重叠。移除人类行动后，Salovaara et al. 的理论计算责任也随之消失。因此不存在可同时保留该理论与 C3 独立性的版本。

### 9.3 风险估值与经济控制候选

trace-economic underwriting 已将 agent trace、customer exposure、asset value、claimability、intervention cost 与 contract terms 组合成 pricing、pre-loss control 和 risk transfer。其 defined-role scope condition 还说明，一般化 agent 只有被限制为权限和 trace 可比较的 monitored role 后，经济风险估计才是有限样本可识别对象。若可靠发布候选把主要中间状态改为 expected loss、premium、CVaR 或 review/sandbox intervention value，它会从“哪个 code-and-release action降低真实服务损害”转成“怎样估值和转移 agent trace 风险”。

两者应严格分工。发布候选的 verifier 必须直接测 outage、错误请求/数据、安全 invariant、blast radius、rollback completeness 与 safe completion；经济金额最多是外部敏感性分析。风险估值研究则可使用多任务 trace 和客户合同，但不应声称其 allow/review/sandbox/stop policy等于 learned release planner。当前候选借用经济风险层既不能修复 coding-agent 身份，也不能产生对 rollout action 的独特理论方向。

最关键的对照不是句长、连接词或标点，而是理论对计算的定向责任。ACAA 不是给普通 attention 增加“顾客注意”标签：其直接工作诊断明确指出 affinity matching 会偏好相似 key，而语义多样性要求突出与 query 互补且在 keys 之间不冗余的对象；时间、投票和图文权重还产生可观察的相反作用。DSDL 也不是给通用序列模型增加满意度 head：`E` 与 `F` 必须分开，`S=F-E` 的方向进入对比损失，属性与片段的双向稀疏又有独立中间状态评价。

本候选没有达到这个标准。它能列出很多真实信号和行动，却没有证明通用 controller 会沿哪个由 IS 理论特定指出的方向系统性算错，也没有产生不从该理论出发就难以想到的张量或损失。按照肖老师论文的句段逻辑，缺口无法从直接近邻自然推进到理论机制，方法段再完整也不能反向补救引言和理论段的责任断裂。

### 11.2 证据强度限制

- SafeRevert 的 34,000 个 breaking changes 是 Google 原研究的样本规模，只支持其自动回退证据问题已经被真实评价，不能外推本候选的发布事故率。
- CAS 的生产规模说明该工作不是概念性 toy system，不证明其在本文件构造的公开 benchmark 上表现如何。
- private bank、Prime Video、Google 与 Netflix 数据只用来证明直接工作和公开数据缺口并存，不把其内部字段或效果当成可复现实验资产。
- Ghaleb（2026）的 workflow success 只证明一个 GitHub Actions run 的近端执行状态，不等于 change 的语义正确、安全或生产发布成功；作者自己的 construct/external-validity 段也限制这种解释。
- UnderSpecBench 的主要 action-boundary 结果来自固定 safe action 和 deterministic side-effect oracle；作者明确记录这一设计可能不计入可辩护替代动作，所以不能把它当多策略 release gold policy。
- LoopsBench 中的 ready-frontier `release` 是 evaluator-side test activation。它支持 prerequisite、state continuity 和 regression-obligation 评价，不支持把测试释放偷换为生产 rollout。
- trace-economic underwriting 报告的 CVaR95 是该文在其 trace/profile/contract 表示与控制规则下的原结果，只用于界定强近邻；本文件不把该数字外推为 release policy 的可实现收益。
- 2026 年 arXiv 工作以截止日可得版本为准；其系统边界可用于近邻审查，未经同行评审的主张不用于证明候选一定失败或一定有效。
- 本文件没有实验结果。第 6–7 节的模型、预算、指标和冲突均为反证性设计规格。

| G3 直接近邻增量 | 相比 canary、MORL rollout、sequential tests、ARBITER、Safe Remediation 等仍有不可替代能力 | 剩余能力是多模块集成 | **FAIL** |
| G4 公开运行环境 | 有许可清楚、可重置、能产生外部 outcome 的环境 | 可拼接 DevOps-Gym 与开源微服务环境 | PARTIAL/PASS |
| G5 执行监督 | 标签来自独立 execution truth，不是 LLM judge 或手写 risk score | 可严谨构造，但成本高且模板依赖明显 | CONDITIONAL，不是终局否决原因 |
| G6 非平庸算法 | 有结构化 state、world model、policy、checkpoint 和真实动作 | 最强救援可达到 | PASS |
| G7 理论改变计算 | 理论产生不可交换状态、方向约束和可中和机制 | 仅有既有两时钟、reward weights、uncertainty gate | **FAIL** |
| G8 等参数通用替代 | generic SMDP/POMDP/temporal graph 不能以相同信息复制 | 已给出状态级无损约化 | **FAIL** |
| G9 系列独立性 | 不吞并数据库迁移，不与 C3 人审取证共享中心行动与结果 | rollout/commitment 与 HITL/evidence 两端均重叠 | **FAIL** |
| G10 结果证据边界 | 未运行结果不得写成已发生 | 本文件全程保持设计和事实区分 | PASS |

G2、G3、G7、G8 和 G9 都是构念、理论与贡献边界失败，不会因增加 GPU、扩大 synthetic episodes 或换更强 LLM 自动消失。特别是 G7–G8 已经违反用户设定的硬门。继续做 pilot 只能测试一个 generic autonomous-release system 的工程效果，不能回答当前 thesis 所需的理论驱动研究问题。

未来只有出现以下任一类实质新证据时才值得从头另立候选，而不是恢复本题：一项可独立测量并产生非交换行动方向的 IS 机制；一个公开 benchmark 同时提供 repository rewrite 与 rollout 的多路径执行真值；或一种 coding-agent 专属行动，使现有 rollout/AIOps controller 在相同输入和预算下原则上不能执行。单纯加入新 encoder、更多 telemetry、一个风险 head、一个 human gate 或更大模型不构成重开依据。

## 13. 终局

这个候选有重要问题、有可执行环境，也能设计出计算量充足的算法。它被否决，是因为最强版本仍不能同时证明 coding agent 的不可删除性、相对直接工作的独立能力、IS 理论的不可替代计算责任，以及与数据库迁移和 C3 的系列边界。依据截至 2026-08-15 的全文与直接工作核验，不应把 autonomous release controller 写成第三篇论文，也不应以尚待实验的口吻保留一个已经在理论和对象层失效的题目。

**终审结论：NO-GO**
