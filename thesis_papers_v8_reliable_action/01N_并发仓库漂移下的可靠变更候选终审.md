# 并发仓库漂移下的可靠变更：候选终审

> 候选情境：coding agent 在较长任务中依据旧快照读取、规划和修改代码，而人类、其他 agent、CI 自动修复、依赖升级或安全补丁同期改变 upstream、branch 或 worktree。  
> 检索、版本与证据冻结日：2026-08-15。  
> 终局判定：**NO-GO**。  
> 结果边界：本文件没有训练模型、运行新 benchmark 或取得任何候选方法结果。下文出现的模型、损失、算力和实验均为 steelman 审计对象，不是已完成研究。2026 年预印本按冻结日可见版本使用，并与正式同行评审论文分开标识。

## 0. 终局裁决

**本候选不得进入三篇论文的独立题位，也不得以“仓库漂移感知 agent”“时间协调式语义调和”“陈旧上下文 world model”“可靠并发 patch 控制器”或近义名称恢复。**

终审否决的不是现象。长时间运行的 coding agent 确实可能依据已经失效的函数签名、依赖版本、安全约束或测试结论继续行动。一次文本上无冲突的合并也可能覆盖较新的修复、复活已消除的漏洞、破坏他人有效工作，或把已经过时的契约假设重新写回系统。这些都是明确的广义安全损害，且 agent 的长推理事务、广泛而隐含的读取集、工具调用和自动提交能力使问题比普通代码补全更突出。

终局 NO-GO 由四项共同证据决定。

第一，最强技术机制已经被直接工作占据。Claim Plane 在写入前绑定精确 base commit、资源、依赖和意图版本，并对依赖失效、动态扩域、worktree 锁和集成证据实施确定性控制。CoAgent 把陈旧视图明确立为中心问题，在执行中通知受影响 reader，由 LLM 判断新写入是否破坏其计划前提，并只修补依赖于旧值的操作；框架同时执行撤销和重排。STORM 在共享代码库的写入时管理一致状态。CodeCtx 又把 agent 已观察的符号显式化为依赖，在并发编辑后定向传播失效通知。EA-Graph 则把验证主张绑定到具体 artifact 内容，并把证据强度、新鲜度与不可证明状态分离。加上成熟的语义冲突检测和学习型 merge resolution，本候选的 refresh、inspect delta、reconcile、replay、rerun、quarantine、abort/commit 动作并没有形成一项未被占据的核心能力，而是把已有控制面、陈旧前提修复、证据新鲜度和语义合并串成一个总控层。

第二，最自然的 AIS Basket 理论不能产生不可替代的算法责任。temporal coordination 在原文中处理分布式成员的工作时段重叠和协调延迟；task interdependence/coordination fit 处理信息处理需求与协调容量的匹配；team awareness 处理人类成员对任务、队友和在场状态的知识；artifact-based coordination、coordination artifacts 与 digital artefact practices 处理开发者如何通过共同工件、信息丰富度、可变性和生产—再生产实践协调。把这些构念下推到 coding agent 后，留下的分别是时间延迟、依赖边、状态通知、可见性掩码、artifact 表征和动作成本。它们都是等参 temporal graph/world model、SMDP 或 POMDP 可以在同样输入和监督下直接表示的状态，不产生像 DSDL 的有方向差值或 ACAA 的反亲和计算那样不可中和的理论运算。

第三，没有一个公开资源同时提供本题所需的决策轨迹和反事实行动真值。AgenticFlict 大规模证明 agent PR 的文本冲突并提供可重放 OID，但公开数据不存原始源码，且标签只覆盖 Git 三方合并的文本冲突。CooperBench 提供成对协作任务和可执行测试，却研究两个受控 agent 同时实现功能。Merge-Bench、ConflictBench、SAM 和 sMerge 提供 merge hunk、开发者 resolution 或语义冲突测试，却不包含长任务中哪些已读前提失效，以及 refresh、rebase、split、quarantine、handoff、abort 等多个行动的后果。LoopsBench 和 SWE-CI 提供长时演化及测试义务，但没有外生并发写入。AtomicCommitBench 固定最终 squashed diff，只评价历史重构。EA-Graph 与 StateShiftBench 可以控制漂移真值，但前者只评价主张撤回，后者是仅 100 个合成跨域案例。将这些资源拼接不会自然产生一个联合总体。

第四，最强 steelman 工件在匿名后就是一个通用的部分可观察序贯控制器。其输入是 base/current/local tree、agent read/tool trajectory、upstream delta、local patch、测试义务与动作可逆性；其内部是时序异构图和 belief state；其输出是各行动的任务成功、损害和成本分布以及结构化行动策略。若 equal-parameter temporal graph world model、SMDP/POMDP 和直接 model-predictive controller 获得完全相同的输入、动作、执行标签、候选 patch generator、预算和 action mask，它们可以复制全部计算。所谓理论变量只是在节点、边、掩码或 reward 中重新命名已有量。当前没有独立理论标签、方向约束或冲突预测能够说明理论模型在有限样本下为何应作出不同动作。

因此，本题可以成为有价值的系统集成、benchmark 构建或 coding-agent runtime 工程，但在 2026 年 8 月 15 日的证据条件下，不能成为一篇以 IS 理论驱动新算法为核心、足以独立投稿 ISR 的博士论文子研究。

## 1. 研究对象、安全边界与决策时点

### 1.1 最强研究问题

候选的最强表述不是“预测是否会 merge conflict”，而是：

> 当 coding agent 的本地计划和修改形成于快照 $B_0$，而当前仓库在 agent 行动期间变为 $B_t$ 时，如何依据 agent 实际读取过的前提、local patch 与 upstream delta 的语义关系、仍需履行的验证义务以及各行动的可逆性，学习一个序贯策略，在保留任务完成能力的同时选择刷新、隔离、重放、语义调和、拆分、复验、隔离待审、移交、终止或提交？

这一定义要求 coding agent 仍在任务轨迹内。若输入只是一个已经完成的 patch、base、ours 和 theirs，研究对象就是学习型 merge 或 patch integration；若输出只是在 merge 前给出 conflict/no-conflict，则退化为分类器；若控制器只按文件重叠、branch age 或测试失败触发动作，则退化为 VCS 规则。

### 1.2 状态、事件和损害

令 $B_0$ 为 agent 开始任务时不可变的 base commit，$B_t$ 为决策时 upstream tip，$L_t$ 为 agent 的本地树，$P_t=\operatorname{diff}(B_0,L_t)$ 为本地修改，$D_t=\operatorname{diff}(B_0,B_t)$ 为同期到达的 upstream delta，$\tau_t$ 为 agent 在 $t$ 前的读取、测试、命令、计划和写入轨迹。仓库漂移事件可以来自人类提交、其他 agent、CI autofix、bot dependency update 或安全 hotfix。需要区分三类情形。

1. **受控并发写入**。所有 writer 均在同一 admission、middleware 或 shared-state runtime 下，系统可追踪读写 footprint 和版本顺序。这正是 Claim Plane、CoAgent、STORM、S-Bus 等工作的主场。
2. **外生但可观测漂移**。人类或 bot 绕过 agent runtime 写入仓库，但新 commit、diff 和 CI 结果可在行动前读取。这是本候选尚可声称的最窄剩余情境。
3. **行动前不可观测的隐藏漂移**。agent 在 commit、push 或 destructive tool call 后才发现状态改变。若系统没有任何 version/lease/fencing signal，算法无法凭空识别；研究必须转向权限、原子提交或外部事务控制，而非代码语义策略。

外部损害不能用“发生冲突”替代。最低结果集应包括：较新修复或他人有效 hunk 被删除的 `lost_valid_work`；安全修复、权限检查或依赖约束被复活的 `security_resurrection`；文本 clean merge 之后的隐藏行为、API、schema 或 build 契约失败 `semantic_regression`；任务隐藏测试和目标功能 `task_success`；以及 wall-clock、tool calls、token、人工审批与中止造成的机会成本。安全改善只有在这些损害下降、任务成功没有被简单拒绝策略摧毁时才成立。

### 1.3 合法动作及其真实执行含义

最强动作空间至少是一个可参数化的程序，而非十分类标签。

| 动作族 | 推断时必须真实执行的操作 | 主要代价或风险 |
|---|---|---|
| `REFRESH_INSPECT(S)` | fetch 当前 tip，读取选定 delta、受影响符号和新 CI 证据 | 时间、token；过度刷新引入噪声 |
| `ISOLATE(B_t)` | 在绑定当前 base 的 branch/worktree 中保留本地修改 | 只隔离写入，不能消除旧读取前提 |
| `REBASE_REPLAY(q)` | 以选定 commit/hunk 顺序重放本地变更 | 文本可应用不等于语义正确 |
| `SEMANTIC_RECONCILE(H)` | 针对受影响 hunks 生成新 patch，并运行相同 verifier | 可能错误融合两个意图 |
| `SPLIT_CHERRYPICK(Z)` | 预测 hunk-to-unit 分区，选择性应用仍成立的单元 | 依赖断裂、历史重构错误 |
| `RERUN_OBLIGATIONS(Q')` | 运行受 delta 影响的测试、静态检查、security/property checks | 计算成本；测试仅是部分规格 |
| `QUARANTINE/HANDOFF(e)` | 保存证据、限制写入并把未决语义交给人或其他 agent | 人工负担、等待时间 |
| `ABORT` | 保留可审计工件但不合入本地 patch | 任务失败或重做成本 |
| `COMMIT` | 在当前 tree 上形成可回放 commit/PR，记录 base 和 verifier digest | 错误动作会把失效前提固化 |

真正的策略必须能组合这些动作，例如先定向刷新，再拆分本地 patch，只调和被影响单元，重跑对应义务，最后 commit；输出单个 router label 不足以承担这一任务。

## 2. 直接工作占位审计

### 2.1 预写入、执行中和验证后的三层近邻

| 决策层 | 已核验直接工作 | 已提供能力 | 对本候选的挤压 |
|---|---|---|---|
| 写入前 | [Claim Plane](https://arxiv.org/abs/2607.21909) | versioned `ChangeIntent` 记录精确 base commit、typed resources、dependencies、committed/contingent operations；原子 admission、动态 scope promotion、依赖失效、worktree locks、fencing tokens、Git-tree provenance 和集成证据 | 已占据 base freshness、dependency invalidation、隔离、串行化、fail-closed 与 integration verification。30-pair confirmatory study还显示静态可靠性收益主要来自近乎串行化，动态版本受 scope undercoverage 限制，直接暴露本题的可靠性—并发权衡。 |
| 执行中 | [CoAgent](https://arxiv.org/abs/2606.15376) | 运行时追踪 declared read/write footprints，通知 reader 新写入；LLM 判断是否破坏计划前提，只修补依赖于陈旧值的操作；框架用 inverse 撤销并按 MTPO 重排 | 与本候选最核心的“premise invalidation→selective repair”同输入、同中间状态和同动作语义。其 10 个 contention workloads 与 71 个 AIOpsLab tasks 已评价正确性、速度和成本。 |
| 执行中 | [STORM](https://arxiv.org/abs/2605.20563) | 介入 shared workspace，在 write time 检测和解决并发编辑造成的不一致视图；与 git-worktree isolation 基线比较 | 已占据“worktree 只延迟冲突、显式 state management 应前移到写入时”的主张。 |
| 执行中 | [CodeCtx](https://rybkr.com/papers/context-synchronization-for-multi-agent-workflows.pdf) | 构建 Python symbol dependency graph，把每个 agent 的 observations 显式化，并在文件改变后计算 transitive impact 和 targeted invalidation | 已占据“哪些 agent 所持代码上下文因 concurrent edit 变 stale”的定向通知能力。该工作证据规模有限，但问题和机制与候选直接重合。 |
| 执行中 | [S-Bus](https://arxiv.org/abs/2605.17076) | 由 HTTP GET 自动重构 read set，以 Observable-Read Isolation 阻止共享自然语言状态的 structural races | 虽非代码仓库专用，却进一步占据自动读取集、commit-time conflict 和一致性控制。 |
| 工具副作用 | [Atomix](https://arxiv.org/abs/2602.14849) | epoch、resource frontier、progress-aware commit、buffer/compensate 与 transactional retry | 若候选扩展到不可逆工具、push 或部署，它会进入已有 transactional tool-use 空间。 |
| 跨会话验证 | [EA-Graph](https://arxiv.org/abs/2608.04278) | artifact sub-path identity、alias-to-leaf resolution、content anchor、evidence/freshness 分离和 `UNPROVABLE`；在 upstream drift 后撤回不再有依据的主张 | 已占据“旧验证结论是否仍成立”的细粒度表示。其实现没有覆盖 write/kill 和 repair，留下的是行动集成，不是独立理论机制。 |
| 写入后 | [ConflictBench](https://doi.org/10.1016/j.jss.2024.112084)、[SAM](https://doi.org/10.1016/j.jss.2024.112070)、[sMerge](https://doi.org/10.1145/3691620.3694993)、[Merge-Bench](https://arxiv.org/abs/2605.25890) | 文本冲突 benchmark、测试生成式 semantic conflict detection、行为语义式 resolution，以及用 7,938 个真实 hunks 训练 GRPO merge model | 已占据文本/语义冲突检测与学习型调和。把 verifier 接到 rebase 后面不构成新算法。 |

CoAgent 尤其构成决定性近邻。其论文并非只做 lock 或 merge。它明确说明长 LLM transaction 的 read set 广而隐含，OCC 的整体 abort 会丢弃数分钟工作；新的 runtime 因而通知 agent，由 agent判断写入是否真正使其计划前提失效，并只重写受影响的操作。候选若把 writer 从“另一个受控 agent”改为“人类、CI bot 或安全更新”，只改变事件来源。只要该写入最终可被 fetch/observe，premise invalidation 和 selective repair 的计算问题没有改变。

### 2.2 多 agent coding 与并发现象证据

[CooperBench](https://arxiv.org/abs/2601.13295) 含 12 个库、4 种语言和 600 余个成对任务。两个 agent 分别实现可以独立完成但组合后可能冲突的 feature，并由专家测试和 ground-truth code 评价。论文报告协作平均成功率低于单独完成，失败涉及含糊或迟到的通信、偏离承诺和对他人计划的错误预期。它证明了多 agent 协作需要独立研究，但同时把共同计划、通信和并发 feature integration 置于直接 benchmark 中。

[AgenticFlict](https://arxiv.org/abs/2604.03551) 从 59,412 个仓库识别 142,652 个 agent PR，对 107,026 个成功执行确定性 merge simulation，其中 29,609 个出现文本冲突，报告冲突率 27.67%。其 [GitHub/Zenodo 工件](https://github.com/unlv-evol/AgenticFlict) 提供 base/head OID、PR/file/region 表和复现 pipeline。为遵守 GitHub 条款，公开表不存原始源码，只保存 SHA-256 和可选短预览；作者也明确限定为 Git 三方合并文本冲突，没有语义冲突和匹配人类基线。它是现象与 textual-risk 数据，不是本题的可执行序贯 policy 数据。

[AI Agent Pull Requests on GitHub](https://arxiv.org/abs/2607.04697) 又在 33,596 个 agent PR、2,807 个仓库上报告 co-active PR 的普遍性，并重放 747 对共时 PR；跨 agent pair 的文本冲突率高于同 agent pair。该结果再次证明问题存在，也再次只观察文本层，不能给出最佳调和行动。

[CodeTeam](https://arxiv.org/abs/2606.22082) 已用 machine-checkable contract 指定 file ownership、public interfaces 和 dependency constraints，并用 dependency-aware scheduler 与 Git coordination 完成 repository generation。它与 Claim Plane 共同挤压“先声明 scope/interface/dependency 就能解决并行修改”的贡献空间。若候选转向协调协议而不是 exogenous drift，它会直接落入这一组工作。

### 2.3 CRDT、隔离和 merge queue 的边界

[CodeCRDT](https://arxiv.org/abs/2510.18893) 用共享可观测状态和 CRDT convergence 支持 lock-free concurrent code generation，报告其任务上的速度权衡与 semantic conflict。CRDT 的价值是确定性收敛；它不能保证非交换代码变更满足业务 invariant。[CoVSCode](https://doi.org/10.3390/app9214642) 等实时协作编程环境又使用 operational transformation 使并发编辑操作相对于当前文档状态转换和传播。OT 同样解决副本收敛、操作次序和编辑意图保持，不提供跨文件程序契约、旧计划前提或安全 regression 的真值。CoAgent 也据此把 fork-and-merge 与 CRDT 的局限列为动机。候选可以把 CRDT/OT 作为 deterministic baseline，不能把“收敛不等于程序语义正确”本身当作新 gap。

Git 的 [worktree 官方文档](https://git-scm.com/docs/git-worktree) 明确允许同一 repository 同时 checkout 多个 branch，并为各 worktree 保留独立 HEAD/index 等元数据；这提供写入隔离，不维护 agent 已形成的语义前提。GitHub [merge queue](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/merging-a-pull-request-with-a-merge-queue) 以 merge group 在最新 base 上重跑 required checks，并在 queue check 失败时移出 PR；它控制集成顺序和 CI，不理解局部 patch 是否复活安全缺陷。两者是必须纳入的强确定性基线，却不是候选的理论来源。

### 2.4 仅剩的窄空白为何仍不足以立题

现有直接系统通常假定所有 writer 经过 control plane 或 middleware。人类直接 push、CI autofix 和 dependency/security bot 可以绕过这一假定，因此“**未被共同协议媒介、但在 agent commit 前可观察的外生仓库漂移**”仍是一个真实残差。它没有救回候选，原因是：

1. 观察外生 delta 后，CodeCtx/CoAgent 的 read-dependency invalidation、EA-Graph 的 evidence freshness、语义 merge 的 behavior checking 和 Git 的 replay/isolation 可以直接组合。
2. writer 身份从 peer agent 改为 human/bot 不会产生新的算法状态。真正决定行动的是 changed artifact、read premise、semantic dependency、uncertainty、reversibility 和 obligations。
3. 如果外生写入完全不可观察，则缺少 version、lease 或 notification 的系统只能阻断 commit 或要求重新读取；这属于并发控制基础设施，不是可学习语义策略。
4. 若以“组合后形成端到端控制器”为贡献，论文必须证明组合产生了单个近邻和等参通用模型都没有的能力。当前 IS 理论没有提供这种新增运算，公开数据也没有相应行动真值。

## 3. 公开 benchmark、训练样本与执行 oracle

### 3.1 资源适配矩阵

| 资源 | 公开且可运行的内容 | 可承担的监督 | 本题缺失字段 |
|---|---|---|---|
| AgenticFlict | base/head OID、merge simulation pipeline、PR/file/region labels | 文本 conflict 与规模/活跃度特征 | 原始公开 code content、semantic outcome、agent read history、多个行动后果 |
| CooperBench | 成对 feature、12 libraries、4 languages、expert tests/ground truth | pair success、integration tests、通信/承诺轨迹 | 非受控 human/CI drift、长单 agent snapshot、refresh/rebase/abort counterfactuals |
| ConflictBench | 180 个 Java merge scenarios，136 true/44 false conflicts，developer strategies | textual conflict truth、tool applicability/detection/resolution | agent 轨迹和 semantic clean-conflict truth |
| SAM dataset | 85 个含/不含 semantic conflicts 的 change pairs，测试生成 harness | 部分行为冲突检测 | 序贯控制动作；生成测试只是部分规格 |
| Merge-Bench | 1,439 repos、7,938 hunks、developer resolution；LLMergeJ training | hunk resolution imitation/RL reward | resolution 并非唯一真值，缺少 task trajectory 和 upstream event timing |
| AtomicCommitBench | 10 个 Python projects、800 个 consecutive-commit episodes、base+squashed diff、PPAR/ARI/TCR | patch split、ordered replay、selective-revert containment | fixed final diff，不生成漂移，不提供外部 writer 或 action policy |
| LoopsBench | 112 tasks、8 languages、9 domains、5,300 余 development units、dependency DAG 和 executable tests | ready-frontier success、累计 regression obligations | 没有 concurrent upstream intervention，也没有漂移后替代动作标签 |
| SWE-CI | 100 tasks、平均 233 天/71 commits 的真实演化、Docker/CI loop | 长期 maintainability 与连续正确性 | sequential target evolution，不是 agent 行动期间的 exogenous branch race |
| EA-Graph | 7 个生成 world、42 sessions、artifact-to-behavior ground truth、value/logic/withheld drift | prior claim 的 unaffected/affected/unprovable | 不评价 repair、write/kill、效率或 action policy；生成 worlds 和 hidden answers 受控释放 |
| StateShiftBench | 100 个合成任务、10 domains、hidden drift 与 oracle/gold traces | recheck、bad commit、safe/unsafe dynamic invalidation | software repository 仅为一域，规模小且由合成规则定义 |

长时 benchmark 仍有实际用途。[LoopsBench](https://arxiv.org/abs/2608.00267) 的 dependency DAG、ready-frontier tests 和 retained regression obligations 可以提供 `Q_t`。[SWE-CI](https://arxiv.org/abs/2603.03823) 可以提供仓库演化和连续 CI。 [AtomicCommitBench](https://arxiv.org/abs/2607.03332) 可以训练可回放的 split/cherry-pick unit。但三者组合后仍不知道某一时点 agent 已实际依赖哪些旧前提，也不知道多个安全行动的反事实结果。

### 3.2 最强可构造 episode

若不顾终局判定，最严谨的 episode builder 会执行以下过程。

1. 在 repository family 和时间切分内选择 base $B_0$、目标任务 $q$ 与一个在未来到达的真实或合成 upstream change $U$。
2. 让 coding agent 在 $B_0$ 上工作，并完整记录 file/symbol reads、commands、tests、plans、local writes 与 timestamps，得到 $\tau_t$ 和 $P_t$。
3. 在预注册触发点把 $U$ 应用到另一个 current tree，隐藏其 future diff，直到 agent 下一次合法 observation。
4. 从完全相同的 checkpoint fork 多个 siblings，分别执行 refresh、rebase、semantic reconcile、split、obligation rerun、quarantine、handoff、abort 和 commit 组合。
5. 每个 sibling 在容器中运行 task hidden tests、upstream regression/security tests、build/API/schema contracts，并测量覆盖较新代码、复活缺陷、任务成功、人工调用和 wall-clock。
6. 只把 outcome vector 和可见 prefix 用于训练；future commits、gold developer resolution、hidden tests、sibling outcomes 和 oracle implementation 不入模型。

这会产生真实的 coding-agent action trajectories，也能形成可训练 checkpoint。它仍不能自然解决三项识别问题。

第一，真实 Git 历史只观察开发者最终选择的一次 integration，其他 sibling 必须由实验系统生成。若 candidate action generator、semantic resolver 或 continuation agent 不同，outcome 同时反映 policy 和 generator 能力。第二，公开测试是不完备规格。开发者 resolution 也不是无误差 gold，sMerge 的研究恰好指出行为式分析可以发现开发者 ground truth 的错误。第三，若漂移事件、风险类型和 hidden tests 由 builder 规则产生，训练策略可能只学习 generator 的判定边界；若用 LLM judge 贴“前提是否失效”标签，则工件蒸馏 judge 偏好而非学习外部安全结果。

### 3.3 划分和泄漏最低要求

任何未来实验至少需要以下隔离；本节只说明可执行门，不表示候选获准复活。

- repository family 为最高 split 单位。同一 fork、monorepo 子项目、包生态 sibling 和共享 template 不得跨 train/test。
- chronology 必须严格前向。$t_0$ 之后的 issue comment、review、commit message、security advisory、dependency release note 和 developer resolution 均不得进入输入。
- 同一 $(B_0,q,U)$ 的所有 sibling actions、fault seeds、hidden tests 和 agent trajectories 进入同一 split；不能按 action 行拆分。
- AgenticFlict 的 open-PR label 随 extraction 时点改变，必须保存 anchor time、base/head OID 和 clone manifest。
- Merge-Bench/AtomicCommitBench 的原始 developer history、commit message、hunk boundary 和 gold order 在推断前隔离；相邻 commit windows 不得跨 split。
- benchmark hidden tests、security regression tests、oracle code 和 future upstream tree 必须处于 policy 的写边界之外，并以 digest/manifest 固定。
- 所有模型共享相同 candidate action programs、semantic patch generator、tool permissions、test budget 和 timeout。否则“理论策略”可能只因获得更强 resolver 获胜。

这些规则可以防止显见泄漏，却不能补出理论中间状态或自然反事实标签。

### 4.3 理论六问的逐项答案

1. **通用算法系统性忽略了什么机制？** 当前理论能指出依赖、延迟、可见性和共享知识不足，却没有指出通用 temporal world model 在相同 delta、read history 和 outcome supervision 下会朝哪个错误方向计算。CoAgent 已把最重要的“写入触及 read set 但未必破坏计划前提”写成直接机制。
2. **理论产生什么不可替代的中间状态？** 可构造 coordination demand、visibility、awareness 或 artifact mutability，但都能分别改写为 graph degree、observation mask、freshness flag 和 input revision count。没有独立理论标签。
3. **该状态如何进入前向或损失？** 最多作为 node/edge feature、attention mask、duration 或 reward cost。删除理论名称后计算不变。
4. **理论在何种冲突情境中应作出不同选择？** 高 interdependence 可要求更多协调，低 visibility 可要求 refresh；然而 Zaggl 的长期传播机制又可能偏好延迟可见。不同理论对安全行动没有共同稳定方向，具体选择仍由执行 outcome 决定。
5. **中和机制后能否观察变化？** 打乱依赖边、时间戳或 visibility 当然会损害任何 repository model。这证明输入有用，不证明 AIS 构念带来特殊计算。需要在保留相同技术信息时只中和理论关系，但当前没有剩余可中和量。
6. **等参数通用替代能否复制？** 能。给它相同 typed temporal graph、belief update、action programs、outcome labels 和 constraints，即可执行同一状态估计和 MPC。有限样本优势也无法归因，因为理论变量没有独立观测或预注册方向。

按照用户规定的撤销原则，第六问成立且前三问没有独立答案时，应撤销理论算法贡献，而不是把 theory embedding、coordination head 或 visibility loss 留作装饰。

### 4.4 五个理论冲突案例

| 固定技术情境 | 理论若真有责任应改变什么 | 实际可复制的通用计算 |
|---|---|---|
| upstream security hotfix 改了 agent 已读但未编辑的 authorization helper；local patch 文本 clean | awareness/依赖机制应阻止直接 commit | read-dependency graph + changed symbol + hidden security obligation 已足够；CoAgent/CodeCtx 直接覆盖 |
| peer 只追加无关文档，触及 agent 曾浏览的文件 | 理论应避免因“有变化”而全量 abort | premise relevance predictor 或 semantic dependency model；CoAgent 正以此为例区分 footprint conflict 与 premise conflict |
| upstream API contract 改变，local adapter patch 可文本合并且公开测试通过 | artifact/knowledge translation 可能要求 reconcile 或 handoff | behavior contract tests、semantic merge agent 和 calibrated uncertainty；无需团队实践标签 |
| 高依赖模块发生多个交错写入 | coordination fit 可能偏向串行化 | graph contention、failure probability 与 cost 进入普通 SMDP；Claim Plane 的 static/dynamic admission 已直接评价 |
| 低风险、可逆 patch 在低 visibility 状态等待新信息 | temporal/artifact theory可能支持延期 | value of information、duration 和 reversible action 是标准 POMDP/SMDP；没有特殊理论运算 |

这些案例证明理论术语能够解释为什么状态重要，却不能规定一个不由通用状态—后果学习得到的行动差异。

## 5. 最强 steelman 算法及其可约化性

### 5.1 输入、张量、输出与工件

为了避免用弱实现制造 NO-GO，终审采用下列最强反事实工件。模型不是 conflict classifier，而是 `Drift-Reconciliation World Policy`。

输入包括任务 $q$、$B_0$、$B_t$、$L_t$、完整可见轨迹 $\tau_t$、upstream/local hunks、code/build/test/dependency graph、当前 CI、权限与可逆性、剩余时间和验证义务。所有 source content 只能来自决策时已可见 revision。

关键张量至少包括：

- $X_C\in\mathbb{R}^{n_c\times d}$：symbol/file/package 节点的代码、接口、版本、security role 与静态/动态摘要。
- $X_L\in\mathbb{R}^{n_l\times d}$、$X_U\in\mathbb{R}^{n_u\times d}$：local 与 upstream hunk embeddings，含 base position、intent evidence、author/bot type 和可逆性。
- $A^{(r)}\in\{0,1\}^{N\times N}$：call、data、build、test、API、read、write、co-change 等 typed edges。
- $R\in\{0,1\}^{T\times N}$：agent 在每一步实际观察过的 artifact incidence；未读 artifact 不得伪装成 plan premise。
- $E\in\mathbb{R}^{T\times m\times d_e}$：按绝对时间排序的 commit、CI、tool 和 notification events。
- $O\in\{0,1\}^{k\times N}$：可见 obligations 到代码/依赖节点的覆盖；hidden verifier 不进入该张量。
- $b_t=q_\phi(z_t\mid X,A,R,E,O)$：对 premise validity、semantic compatibility、damage severity 和 future evidence 的 calibrated belief。

输出不是一个分数，而是：各参数化 action program 的联合 outcome distribution $p_\psi(y^{task},y^{lost},y^{sec},y^{sem},c^{time},c^{human}\mid b_t,a)$；结构化策略 $\pi_\theta(a,\xi\mid b_t)$，其中 $\xi$ 给出 refresh scope、hunk partition、replay order、tests 和 reconciliation targets；以及 content-addressed checkpoint、patch sequence、verifier receipt 和 audit trace。

### 5.2 架构、训练样本和损失

最强架构可以由 temporal heterogeneous graph encoder、trajectory-conditioned belief model、action-conditioned world model、constrained model-predictive policy、hunk partitioner 和 semantic patch generator 组成。generator 与 policy 必须分开计账，避免把 frontier LLM 能力归给理论控制器。

训练样本由第 3.2 节的 sibling forks 产生。每条样本至少包含决策前 observation manifest、action program、执行后的 tree hash、测试/contract vector、lost-work provenance、安全 regression、任务结果、human call 与时间成本。若同一状态没有两个以上可执行 action outcomes，该样本只能训练 outcome predictor，不能识别 policy regret。

候选损失可写为：

\[
\mathcal{L}=\lambda_{tr}\mathcal{L}_{transition}+\lambda_y\mathcal{L}_{joint\ outcome}+\lambda_p\mathcal{L}_{patch}+\lambda_o\mathcal{L}_{obligation}+\lambda_\pi\mathcal{L}_{offline\ policy}+\lambda_{cal}\mathcal{L}_{calibration}+\lambda_c\mathcal{L}_{constraint}.
\]

$\mathcal{L}_{transition}$ 预测 action 后的 graph/tree state；$\mathcal{L}_{joint\ outcome}$ 联合监督任务、覆盖、漏洞复活和语义 regression；$\mathcal{L}_{patch}$ 监督 reconciliation hunk 与 replay validity；$\mathcal{L}_{obligation}$ 预测哪些 visible obligations 需重跑；$\mathcal{L}_{offline\ policy}$ 只能使用真实 sibling outcomes、保守 offline RL 或 model-based planning，不能把维护者选择当 gold；$\mathcal{L}_{calibration}$ 评价高损害尾部；$\mathcal{L}_{constraint}$ 保证 action mask、权限和不可恢复操作边界。

推断时模型必须在隔离仓库实际执行动作，直到 `COMMIT`、`HANDOFF` 或 `ABORT`。只生成一段“建议先 rebase”的文本不算算法行动。

### 5.3 为什么 steelman 仍是已有模块加通用控制器

把上一节所有名称匿名化后：

- $R$ 与 changed nodes 是 CodeCtx/CoAgent 的 observation/read dependency。
- base/version/action authority 是 Claim Plane 的 intent/provenance/admission substrate。
- content anchor、freshness、unprovable 和 obligation withdrawal 是 EA-Graph 的状态。
- patch generation、semantic tests 和 resolution 是 SAM/sMerge/Merge-Bench 的能力。
- split/replay/failure containment 是 AtomicCommitBench 的任务。
- belief、transition、outcome 和 action sequence 是标准 temporal graph world model 与 SMDP/POMDP。

唯一新增物是把这些状态和动作放在同一个 policy 中。系统集成可能改善端到端结果，但理论没有改变 encoder 的消息方向、产生新的 relational operator、规定不可交换的聚合或创建独立监督。理论 loss 若被删除，全部训练标签和动作仍然存在；把理论标签换成 `state_age`、`dependency`、`visibility`、`info_cost` 和 `artifact_revision` 后，前向计算完全相同。这是决定性的可约化性失败。

## 6. 强基线、公平比较和匿名替代检验

### 6.1 必须同时进入的基线

1. **确定性 VCS/CI**：fresh fetch、isolated worktree、`merge-tree`/rebase、path-based test selection、required checks 和 merge queue；不得用故意不检查 branch 的弱脚本。
2. **直接语义 merge agent**：同一 backbone 获得 base/local/upstream code、同一 tests 和 token/tool budget，允许生成 resolution patch。
3. **Claim Plane/CoAgent/STORM-style runtime**：在其假定适用的 controlled-writer subset 上运行；外生 writer 场景明确报告 assumption violation，不得把“不支持”统一计为算法失败。
4. **equal-parameter temporal heterograph world model**：完全相同节点、边、轨迹、actions、labels、constraints 和 generator，只去掉 AIS 名称及专设 parameter tying。
5. **equal-parameter SMDP/POMDP**：相同 belief dimension、duration、reward、action mask、offline data 与 MPC horizon。
6. **direct outcome + constrained MPC**：对每个 action 直接预测多结果和成本，再在同一约束下优化，用来检验复杂理论状态是否必要。
7. **frontier coding agent with full refresh budget**：允许在每个 decision epoch 重读完整 current repository，衡量结构化状态是否只是节省 context，而非新增可靠性。

### 6.2 公平控制

所有 learned baselines 共享 training episodes、repo/time splits、source tokens、read logs、delta、visible obligations、hidden evaluator、action programs、semantic generator、parameters、context window、tool calls、wall-clock 与 human-call budget。理论模型不能独占 dependency graph、freshness flag、reversibility、action mask、candidate patch 或 counterfactual sibling labels。

主结果必须联合报告 `task_success`、四类实际损害、commit/abort/handoff 比例、wall-clock、token/tool cost 和 human burden。只降低 conflict rate、只提高 abstention 或只减少 commit 数都不构成安全改善。统计分析应在 repository family 和 episode 两层 cluster，报告 paired effects、confidence interval、effect size 和风险—效率 Pareto frontier。

### 6.3 理论匿名检验

将模型文档中的 temporal coordination、awareness、artifact visibility、coordination fit 全部替换为时间戳、通知、掩码和依赖强度，并给通用模型相同 inductive bias。如果输出、损失和训练数据不变，则论文没有理论算法。当前 steelman 正好满足这一等价。

这不是以 universal approximation 作空泛否决。有限样本归纳偏置本可救题，但需要：独立测量的理论状态；理论预注册的 action sign；在保留所有技术信息时只打乱理论关系；等参模型无法以同样样本恢复；优势出现在 repository/risk OOD 而非 action mask。现有理论映射和公开数据没有任何一项能运行这组识别。

## 8. 与既有撤销候选和一般 release 的边界

### 8.1 与 C2 TMS

C2 关注成员“谁知道什么”、知识可信度和 transactive memory。仓库漂移候选的必要状态是 artifact/version truth 与 agent 实际 read premise，不需要预测 peer expertise。若加入 teammate memory 来判断应听谁的 commit，该题会重回 C2；若不加入，team knowledge 理论只剩通知 channel，无法承担新算法。

### 8.2 与 C14A ownership/authority

本题不以 CODEOWNERS、修改权或责任归属定义风险。同一 owner 的两次并发提交也会形成 stale read，文件完全不重叠也可能有语义依赖。Claim Plane 中的 authority/fail-closed 是强近邻基础设施，但把 ownership 变成主理论会回到 C14A，且不能解释无权限争议的 semantic drift。

### 8.3 与 C10 structure erosion

C10 的主要结果是架构结构长期恶化与传播。这里的损害是一次事件相对 base 和 current tree 的前提失效。二者可区分。然而，若用 Zaggl 的 artifact visibility 和 propagation cost 救理论，结果会从安全 integration 转成 architecture formation，候选随即进入 C10 的结构空间。

### 8.4 与 C17 obligations

验证义务在本题中只是 action scope 与执行 oracle，回答“哪些测试或约束因 upstream delta 需要重跑”。若论文的主要新状态变成 obligation accumulation、coverage 与 discharge，它就是 C17；若只把 obligations 当 feature，本候选仍缺理论独立性。

### 8.5 与一般 reliable release

本题的终点是 local commit、PR 或 pre-merge integration，不包含流量切换、部署、canary、SLO、运行时 rollback 或 release investment。若把 commit 后 production effects 加入主行动和结果，则会扩张成一般可靠发布或故障后恢复，并与现有 Atomix、release/migration 候选重叠。

这些边界说明候选不是旧题的简单改名，却不能抵消直接技术近邻、理论可约化和数据真值缺失。

| IS 理论自然对应 | 相关理论能解释协调，却下推为状态 channel、mask、dependency 或 cost | **FAIL，终局门** |
| 理论改变内部计算 | 删除理论名后输入、前向、loss 和 actions 均不变 | **FAIL，终局门** |
| 等参通用替代 | equal-input/action/label/budget world model、SMDP/POMDP 可复制 | **FAIL，终局门** |
| 反事实行动标签 | 需新建大规模 sibling execution，历史数据本身不给出 | **FAIL/PARTIAL** |
| 相对已撤题候选有边界 | 与 C2/C14A/C10/C17/release 均可区分 | **PASS，但不救题** |
| ISR 级独立论文规模 | 工程规模大，但理论与独立算法贡献不足 | **NO-GO** |

任一终局门失败都不能靠增加 GNN 层数、扩大 action catalog、构造更多 synthetic drift 或引入 frontier model 修补。当前三项终局门同时失败。

## 11. 最终处置与有限重审条件

本候选终局撤题。可以保留的成果只有三类基础设施用途：为其他入选论文增加“base/current/local tree 与 concurrent writer”扰动；把 deterministic refresh/rebase/merge-queue 作为可靠行动基线；把 lost-work/security-resurrection/semantic-regression 指标加入通用评测。不得把这些复用项重新宣称为第四篇论文或理论机制。

未来只有同时出现以下新证据才值得重新开启独立审计，而不是直接恢复题位：

1. 一项与 coding-agent 仓库漂移自然对应的 IS 理论，能够产生独立可测状态和不由同信息 world model 自动复制的计算约束；
2. 一个公开或正式合作的可执行环境，记录 agent read/tool trajectory、外生 upstream events，并在同一状态上提供多个 action programs 的执行后果；
3. 与 CoAgent、Claim Plane、STORM、CodeCtx、EA-Graph、direct semantic merge、deterministic VCS 和 equal-param POMDP 的同预算比较；
4. 理论中和实验显示方向预注册且在 repository/risk OOD 上仍存在的有限样本优势，同时任务成功、实际损害和人工成本形成实质 Pareto 改善。

在这些条件同时满足前，本题的正确状态是 **NO-GO**，不是 `CONDITIONAL`。
