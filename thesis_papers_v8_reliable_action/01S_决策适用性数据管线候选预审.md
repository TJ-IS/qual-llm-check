# 上游数据语义变化下的决策适用性维护：候选预审

> **状态：PRE-AUDIT / NOT FROZEN / NO RESULTS。**  
> **证据截止：2026 年 8 月 16 日。**  
> 本文件只建立一个可供独立红队否证的候选，不占据三篇论文题位。文中模型、数据规模、损失函数和实验均为待审研究设计；尚未生成数据、训练模型或得到性能结果。

## 0. 为什么重新审这个问题

该候选研究的不是一般 schema drift，也不是“发现字段改名后让 LLM 修 SQL”。风险发生在上游数据的业务含义、时间语义、计量单位、实体身份或有效性规则发生变化，而现有 pipeline 仍能运行、常规 schema test 仍可能通过的时点。coding agent 若只恢复编译和表结构一致性，可能把一个技术上有效的变更传播成下游库存补货、收入确认、资格筛选、风险预警或资源配置中的系统性错误。

这里的潜在损害由下游决策执行结果界定。示例包括错误补货产生的库存或现金损失，错误收入口径导致的报表偏差，遗漏高风险对象导致的安全暴露，以及过度隔离正常数据造成的业务停摆。仅有 SQL 执行失败、dbt test 失败、字段映射错误或模型内部风险分数都不是最终安全结果。

这个问题曾在旧版项目中以“数据流水线语义连续性”出现过，但旧方案把三个研究都放在同一狭窄流水线上，依赖尚未闭合的任务规模，并且没有经受 2026 年新 benchmark 和最强直接工作的重新审查。本文件不恢复旧三篇，也不继承旧题位。它只检验一个更窄的独立问题：**coding agent 能否在可执行的数据制造过程与多个下游使用任务之间学习任务相对的质量传播，并生成和实施保持决策适用性的修复程序。**

## 1. 研究单位、风险时点与可删除性检查

### 1.1 研究 episode

一个 episode 包含以下对象：

1. 一个可运行的 dbt、SQL 或 Python 数据仓库项目，及其源表、转换 DAG、materialization、测试和版本化快照。
2. 至少两个有明确输入和可执行结果函数的下游消费任务，例如补货、风险筛选、收入汇总或服务资格判断。
3. 一个在输入格式上可能保持有效、却改变数据业务语义的上游事件。
4. coding agent 在固定仓库与数据快照中真实读取、修改、运行、验证和提交的轨迹。
5. 一个对 agent 隐藏的事件账本和消费任务 oracle，用于判定每项决策在干净世界与变化世界中的差异。

风险决策点位于上游事件发生后、受影响产物进入共享消费状态前。agent 可以观察代码、manifest、lineage、可公开的合同和样本数据，但看不到隐藏消费 oracle、gold repair 或测试答案。必要信息可能散布在 commit history、字段描述、下游查询、单位变换、事件时间规则和业务决策函数中，也可能存在相互冲突的消费者要求。

### 1.2 coding agent 不能被删除

候选只有在 agent 必须完成下列真实代码行动时才成立：定位受影响的数据制造路径，提出并执行源适配或转换 patch，必要时创建 consumer-specific view、旧新双轨、backfill、quarantine 或兼容层，运行不同证据程序，并决定何时把哪个信息产品提升到哪个消费任务。若把 agent 替换成固定 schema-migration script 后研究问题与核心动作保持不变，该题应撤销。

同样，模型不能只输出 drift 类别、质量分数、allow/block 或 repair hint。主要工件必须生成可执行仓库变更并在隔离环境改变真实输出表和下游决策结果。

## 2. 直接近邻与当前仍待证明的空位

### 2.1 已经被占据的能力

ADE-bench 已经提供公开的 agent 数据分析与 analytics-engineering sandbox。其官方仓库用临时隔离环境复制 dbt 项目和数据库，保存前后快照，并以 task-specific dbt tests 与 solution seeds 评价结果。因此不能再声称缺少 coding agent 的数据工程 benchmark，也不能把搭建 dbt 容器当作贡献。[官方仓库](https://github.com/dbt-labs/ade-bench)

DataFlow-Harness 已让 coding agent 通过 typed incremental mutations 构造持久、可编辑的数据处理 DAG，并公开平台代码。它占据了“把自然语言要求变成平台原生 pipeline artifact”与 live registry/state grounding；普通 DAG 构造和工具接地不能构成本候选的新能力。[论文](https://arxiv.org/html/2607.16617) [代码](https://github.com/OpenDCAI/DataFlow-WebUI)

kRAIG、Drift-Aware Agentic ETL、自动数据合同生成和一般 self-healing pipeline 已分别覆盖意图澄清、pipeline 生成、schema drift 检测、合同约束、LLM repair 和执行验证。证据质量不等，但它们共同排除了“检测 drift 后生成一个修复”的宽泛空白。尤其是只比较 rule-based、detection-only 和 unconstrained LLM 的设计不足以支撑本文。

SARC-DQ 已经把数据缺陷传播到 agent 实际经济行动的链条作为研究对象，并区分 payload-visible 与 metadata-borne defect；其 priced replenishment 环境和 metadata-aware pre-action gate 说明不能再把“数据质量会造成 agent 行动损失”声称为首次发现。它也提供必须纳入的 model-free decision-geometry 和下游损失基线。[论文与代码](https://arxiv.org/html/2607.26313)

传统信息质量研究已经提供更直接的理论和计算前件。Wang 与 Strong 将数据质量从准确性扩展为 intrinsic、contextual、representational 和 accessibility 四类，并明确 contextual quality 取决于使用任务。本地全文为 `database_fulltext_all/24796_1996_beyond-accuracy-what-data-quality-means-to-data-consumers.md`。Shankaranarayanan 与 Cai 的 IPMAP/IPView 已把信息产品的制造阶段建成图，区分 context-independent 与 decision-task-dependent completeness，并支持 traceability、reachability 和质量元数据传播。本地全文为 `database_fulltext_all/13168_2006_supporting-data-quality-management-in-decision-making.md`。Ballou 与 Pazer 已在 ISR 中形式化 accuracy–timeliness utility、信息改进路径、行动时点与系统重设计策略，本地全文为 `database_fulltext_all/26689_1995_designing-information-systems-to-optimize-the-accuracy-timeliness-tradeoff.md`。

### 2.2 只可能存活的交集

候选不得依赖任何一个已占能力。唯一仍值得独立检验的交集是：

- 输入不是单个坏记录或显式 schema error，而是同一可执行 pipeline 在上游语义变化后对多个消费任务形成不同质量后果。
- 中间状态不是全局 data-quality score，而是信息制造路径、真实事件对应关系、消费任务需要和决策损害的联合结构。
- 动作不是 gate 或单 patch，而是在共享转换、consumer-specific view、旧新双轨、backfill、quarantine、延迟提升和合同更新之间生成并执行一个程序。
- 监督来自同一事件和数据种子下不同 repair program 的真实 SQL 输出与下游决策 oracle，而不是 LLM 对“是否语义正确”的评价。
- 主要结果同时包含静默错误决策、正常决策保持、恢复时延、pipeline 成本、数据滞后和 agent 任务成功。

若独立检索发现已有方法同时实现上述五项，候选立即 NO-GO。若最后只剩“在现有 self-healing ETL 上加 consumer loss”，也应撤销。

## 3. 理论责任：信息产品的任务相对适用性

### 3.1 理论能合法承担什么

Wang–Strong 的合法责任是反对把可运行、准确或 schema-consistent 当作所有用途下的统一质量。它要求将 intrinsic correspondence/conformance 与 consumer-task-relative relevance、completeness、timeliness 和 appropriate amount 分开。相同数据状态在两个消费任务中可以有不同的适用性，因此模型需要显式的 consumer–information-product 关系，而不是一个全局风险头。

IPMAP 的合法责任是把质量问题放在信息制造路径上。数据源、处理、存储、检查、系统边界和数据汇构成有向制造图；traceability 指向造成当前质量问题的上游阶段，reachability 指向会被某阶段变化影响的下游产品。该结构可以产生 repair scope、影响传播和 consumer-specific intervention position，但不自动产生正确 patch。

Ballou–Pazer 的合法责任只限于准确性或完整性随时间改进而决策价值又随延迟下降的冲突。它提供 error path、time、utility surface 与 redesign cost 的结构，要求模型区分“先提供有界的暂时产物”“等待或 backfill 以提高质量”“重写制造过程使高质量更早出现”。它不负责所有质量维度，也不能把任意风险成本重新命名为 accuracy–timeliness utility。

### 3.2 理论不能承担什么

这些文献不能提供语义漂移真值、字段含义、code patch、consumer decision program、神经图边、hidden oracle 或安全标签。上述对象必须由版本化仓库、数据生成器、执行轨迹和独立 oracle 构造。数据质量维度也不能由同一个 LLM 自标后再作为理论状态的证据。

理论不能独占一般图传播、world model 或 POMDP。公平的通用替代必须获得相同原始代码、lineage、任务定义、时间、数据、候选动作、执行标签和预算。候选可主张的只是一个可检验的结构偏置：把制造路径与消费任务分成两个有语义约束的图，并限制质量传播和时效效用只能沿理论允许的接口进入行动策略。若匿名关系图或 raw-history POMDP 在未见消费任务和漂移组合上复制风险—效用前沿及方向冲突，该理论算法贡献撤销。

### 3.3 必须出现的相反选择

候选至少要构造四类冲突：

1. 低时延补货可以使用有界的近似库存，高风险合规报告必须等待完整 backfill。
2. 新业务定义要求新口径，旧消费者仍依赖历史口径；全局覆盖会破坏旧决策，永远保留旧口径又阻止合法演化。
3. 同一个缺失字段对聚合趋势任务无实质影响，却决定个体资格筛选；全局 completeness 阈值会过拦或漏拦。
4. 快速 consumer-specific compatibility view 能暂时恢复关键任务，但长期保持双轨会增加不一致和维护成本；策略需要随证据和时间转换行动。

若所有实例都由 always-dual-run、always-backfill、always-quarantine 或“更多测试”支配，理论没有产生有价值的方向冲突，候选撤销。

## 4. 拟议算法工件

### 4.1 输入和张量

每个 episode 的可见输入包括任务文本、仓库快照、SQL/Python/manifest、source schema 与版本化元数据、dbt lineage、有限数据样本、consumer query/decision specification、时间预算和已有测试。隐藏 event ledger、gold repair、terminal decision labels 和 test answer 不进入推断。

拟议状态由两个图和一组连接边组成：

- 制造图 $G^M=(V^M,E^M)$，节点为 source、transform、storage、inspection、boundary 和 sink；节点特征包含代码表示、schema、单位、event-time 规则、版本、数据摘要和可见 quality metadata。
- 使用图 $G^U=(V^U,E^U)$，节点为 information product、consumer task、decision predicate 和 outcome；节点特征包含任务约束、允许时延、损害函数和所需粒度。
- 连接张量 $R_{mcu}$ 表示制造节点 $m$ 的输出经信息产品 $u$ 被消费任务 $c$ 使用，并区分 required、optional、aggregatable 和 incompatible semantics。
- 质量 belief $Q_{cudt}$ 区分 consumer $c$、产品 $u$、质量维度 $d$ 与时点 $t$；intrinsic 与 contextual 通道不得在输入层直接求和。
- 改进路径 $H_{a,c,u}(\tau)$ 预测执行 repair program $a$ 后，决策误差或不完整度怎样随 wall-clock/backfill progress 改善。

这些张量的确切维数、mask、UNKNOWN 状态和更新顺序需要在正式冻结前写入字段级 manifest。目前只冻结语义，不冻结数字规模。

### 4.2 架构与损失

最强可审版本包含五个可训练部分：

1. code–data manufacturing encoder，将 AST/SQL、lineage 和执行摘要编码成 typed graph state。
2. consumer-use encoder，将 decision program 和产品需求编码成 task-relative requirement state。
3. correspondence/conformance 与 contextual-quality 多任务估计器，使用执行 oracle 产生的独立标签训练。
4. counterfactual repair-effect model，预测不同 repair program 对各 consumer 的质量路径、decision loss、时延和成本。
5. constrained hierarchical policy 与本地 code decoder。上层选择 repair program 的结构，下层 7B–9B open-weight model 通过 QLoRA 生成并修订实际仓库 patch。

候选损失为

\[
\mathcal L = \lambda_{corr}\mathcal L_{corr}
+\lambda_{ctx}\mathcal L_{ctx}
+\lambda_{path}\mathcal L_{path}
+\lambda_{dec}\mathcal L_{decision}
+\lambda_{cf}\mathcal L_{counterfactual-rank}
+\lambda_{code}\mathcal L_{code}
+\lambda_{pol}\mathcal L_{offline-policy}.
\]

$\mathcal L_{corr}$ 只学习事件对应与规则符合；$\mathcal L_{ctx}$ 按 consumer 和维度学习任务适用性；$\mathcal L_{path}$ 监督 traceability/reachability 与时间改进路径；$\mathcal L_{decision}$ 预测真实下游决策损害；$\mathcal L_{counterfactual-rank}$ 比较同一前态和随机种子下多个 repair program；$\mathcal L_{code}$ 训练可执行 patch；$\mathcal L_{offline-policy}$ 在风险约束下联合优化决策损害、正常任务成功、延迟和成本。

任何损失若只有 gold patch 或 hidden consumer oracle 才能在推断计算，必须从推断图移除。训练时可使用隐藏结果监督 critic，但 policy 的部署输入必须经过字段级 information firewall。

### 4.3 推断时实际动作

策略可以按 episode 选择并执行下列结构化程序，而不是选择一个标签：

- 读取定向 lineage、历史定义或消费 query，并运行有区分力的样本分析。
- 修改共享 source adapter 或 transform。
- 新建 consumer-specific compatibility view 或受限转换。
- 保持旧新双轨并把不同 consumer 绑定到不同版本。
- quarantine 受影响 slice，同时继续未受影响产品。
- 运行 partial 或 full backfill，并根据进度重新估计质量路径。
- 更新可见 data contract，但只有独立 oracle 证明规范确实演化时才允许替换旧合同。
- 暂存、提升、回滚或停止候选数据产品。

最终提交必须包含真实 diff、manifest/contract 变化、执行过的命令、输出表 hash、consumer binding 和验证轨迹。自然语言解释不是主要工件。

## 5. 数据构造与可识别监督

### 5.1 可复用公开底座

ADE-bench 的 Apache-2.0 代码、DuckDB/dbt sandbox、snapshot 与自定义 evaluation 机制适合作为第一底座。它已经支持 task-specific setup、solution seeds、手工 dbt tests、diff 和运行日志，但现成任务主要评价预期表或代码结果，不能直接提供多消费者的任务相对质量标签。

公开 dbt 项目、Jaffle Shop 类示例、DataEngBench 或其他可执行 analytics-engineering 资产可以扩充仓库和 transformation motif。每个上游项目的许可证必须逐项进入 manifest；不能因为 benchmark harness 是 Apache-2.0 就把源项目统一视为同一许可证。

SARC-DQ 的 GIGO-Bench 可作为“数据缺陷到真实行动损失”的外部压力测试，但其 runtime gate、priced replenishment 和 metadata predicate 不等于本文训练集。DataFlow-Harness 可提供 typed pipeline mutation 与平台可编辑性基线，不能提供本文的 consumer-relative truth。

### 5.2 必须自建的两世界任务

核心训练集必须从同一干净前态生成 paired semantic worlds。每个 family 固定 pipeline 代码骨架和表结构，仅改变一个在 $t_0$ 后才生效的业务语义，例如单位、event-time、取消口径、身份重用、空值含义、去重规则、价格有效期或聚合窗口。两个世界都必须在语法和 schema 上可运行，却要求不同修复。

每个 family 至少有两个 consumer，且至少一个 paired case 要求共享修复，另一个要求 consumer-specific compatibility 或延迟。隐藏 event ledger 记录真实业务事件，consumer oracle 用可执行 SQL/Python 决策函数从 ledger 产生干净结果。pipeline 输出与干净结果的差异直接形成 decision error、false positive/negative、金额损失或服务中断标签。

候选 repair program 不能只由同一 LLM 自由采样。训练阶段要结合：(1) 规则可枚举的 program skeleton，(2) 多个开放权重 coding-agent checkpoint 的实际 patch，(3) 人工审核的小样本高质量程序，(4) 针对失败程序的局部变体。所有程序都在共同数据种子和容器快照上执行，得到 matched counterfactual outcome。

### 5.3 切分与泄漏

最少使用 repository lineage、transformation motif、semantic-drift family 和 consumer-decision family 四重 group split。同一干净 repo、fork、模板、两世界变体、repair branch 和数据随机种子不得跨 split。另做时间截止与未见 drift×consumer 组合测试。

hidden ledger、gold repair、solution seed、terminal consumer answer、未来合同和 post-event commit message 只允许 evaluator 读取。模型训练样本必须保存 `visible_manifest.json` 与 `oracle_manifest.json` 的字段级差分，推断日志证明 policy 没有打开 oracle 路径。若基础模型可能记住历史 repo 未来版本，主结果必须使用生成于截止日之后的 sealed semantic world 或 source-code-distinct template，并报告历史 replay 仅作外部效度。

## 6. 评价、基线与本地工件

### 6.1 主要结果

主要安全结果是 silent harmful decision rate：pipeline 和公开检查未阻止提升，但至少一个 consumer 的实际决定相对 event-ledger oracle 产生超过预注册阈值的错误。还需报告损害金额或任务特定代价、受影响 consumer 数、错误持续时长、正常 consumer 保持率、pipeline 恢复成功、backfill/compute 成本、agent token/工具调用、wall-clock、over-quarantine 和拒绝率。

必须给出安全—任务成功—时延—成本 Pareto front。全 quarantine、全等待或拒绝所有变更不能获胜。

### 6.2 最强基线

- dbt schema/data tests、合同和 lineage 规则；固定 always-backfill、always-dual-run、always-quarantine。
- frontier general coding agent 与相同开放权重 base agent。
- ADE-bench 当前 agent configurations、DataFlow-Harness、可复现的 drift-aware/self-healing ETL。
- SARC-DQ metadata gate 与 decision-geometry oracle；它只拦截或替代记录，不生成 pipeline repair。
- IPMAP/quality propagation 加确定性 optimization，不训练 code policy。
- 等参数 raw heterogeneous graph Transformer、anonymous dual-graph Transformer、direct outcome predictor 和 generic constrained POMDP，获得相同可见输入、动作、标签、参数、FLOPs 与 rollout budget。
- oracle program selector 只给上界，不进入可部署比较。

### 6.3 消融与机制干预

删除或打乱 consumer–product edges，合并 intrinsic/contextual quality，交换两个 consumer 的任务需求，隐藏 time-improvement path，匿名化质量通道，移除 traceability/reachability mask，打乱 repair program 与真实执行结果。每项都要预测具体行为变化，而不是只看平均分。

最关键的 paired direction test 固定代码、数据、漂移和候选 program，只交换 consumer decision function 或允许时延。理论模型应相应改变共享修复、兼容 view、backfill 或 quarantine 的选择；全局 DQ score 和 schema-repair baseline 不应因这一变化作出正确反转。

### 6.4 算力与保存工件

预审规模建议先做 8 个独立 dbt app family、8 类 semantic drift、4 类 consumer decision、每 family 20 个 paired worlds 和至少 6 个执行 program，形成约 7,680 个 terminal executions。pilot 只验证生成器、oracle 和方向冲突，不用于论文结果。完整规模须在 pilot 后根据 replay yield 和方差估算，不能现在承诺固定数量。

训练可使用 100M–500M typed graph/effect model，7B–9B code policy 做 QLoRA，离线策略只在已执行 program 上训练。预计资源瓶颈是 DuckDB/dbt replay、backfill 与多 agent rollout，而不是参数更新。最终必须保存 graph/effect checkpoint、policy adapter、code-decoder adapter、每次容器 image digest、dataset revision、split manifest、visible/oracle firewall、随机种子、环境锁和逐 episode command/output hash。

## 7. 设计冻结前的终止门

以下任一条件成立即 NO-GO，不以“可以以后改进”为由保留：

1. 最新直接工作已同时覆盖多 consumer、任务相对质量、可执行 pipeline repair 和下游决策损害。
2. paired semantic worlds 只能靠自然语言宣称含义不同，不能由独立 event ledger 与 consumer oracle 执行验证。
3. 大多数任务被 schema tests 或简单合同完全解决，剩余优势只是更多上下文或更多测试。
4. consumer-specific action 的优势可以由 always-dual-run 或 always-backfill 在匹配成本下复制。
5. 任务相对质量状态只是 raw graph 的辅助 head；anonymous equal-parameter model 在 paired direction、OOD 组合和 Pareto front 上进入预注册等效区间。
6. accuracy–timeliness 结构只成为 reward 权重，未形成可监督的 improvement path、行动时点或系统重写差异。
7. IPMAP 只提供普通 lineage edges，删除理论语义后行为不变。
8. coding agent 只调用固定修复模板，没有生成和实施新的仓库变更。
9. hidden ledger、future contract、solution seed 或 gold repair 泄漏到推断输入。
10. 风险下降主要来自全 quarantine、延迟所有输出或降低 agent 行动量。
11. 公开项目许可证、数据库快照或可执行依赖不能形成可发布 manifest。
12. 该题与主动缓解期权格在 episode、动作和结果上无法清楚分离，或与 C3 共享真人取证作为成立前提。

## 8. 与另外两个现行候选的边界

主动缓解期权格若通过独立终审，研究的是固定主 schema migration protocol 之外可选择的缓解措施，以及 defer、exercise、abandon 的 semi-Markov 顺序。它的主要损害是 cutover 中断、数据损坏和迁移失败。本文研究上游语义变化后多个信息产品对消费任务的适用性，输出是 pipeline 与 consumer binding 的实际代码程序，主要损害是静默的下游决策错误。二者可以共享 PostgreSQL/DuckDB 基础设施，不能共享状态、policy checkpoint 或主结果。

C3 研究已固定批准点内可信证据的获取、选择和 grounding repair，主要结果来自真实开发者的 unsafe approval。本文没有人类审核动作，也不预测人会批准什么。若本文需要真人解释业务含义才能得到主要标签，说明可执行 oracle 没有闭合，应撤题或重新界定，而不是与 C3 拼接。

在三题都冻结之前，不据此建立总体主线。一个可能的上位联系是 coding agent 对系统状态、信息状态与授权状态的可靠改变，但该表述目前只是待检验的系列候选，不能进入正式论文。

## 10. 当前预审结论

该候选的实际损害、coding-agent 行动、可执行环境和本地训练工件均可以被严谨定义。ADE-bench、DataFlow-Harness 和传统信息产品研究提供了可运行底座与真实 IS 对话。与此同时，直接近邻已经占据 pipeline 构造、schema drift repair、数据合同、runtime gate 和 decision-level data loss；IPMAP 本身也早已拥有制造图、traceability 与 reachability。因此，当前只能判定 **值得进入独立红队，尚未达到 DESIGN-FROZEN**。

独立红队的核心不是问“这个题是否有用”，而是验证三个更窄的问题：多 consumer 的任务相对适用性与可执行 repair program 是否构成尚未被直接方法联合覆盖的能力；理论双图与 improvement path 是否产生可观测的方向冲突和有限样本结构；公平 anonymous graph/POMDP 是否能在相同信息、标签、参数和预算下复制。任何一项失败都应撤题。
