# 软件来源与许可证安全候选终审

> 审查日期：2026-08-16  
> 候选问题：coding agent 在检索、复制、生成代码和引入依赖时，如何识别软件来源与许可证义务，并通过可执行行动降低再分发风险。  
> 文件性质：内部选题终审，不属于论文正文。  
> 终局结论：**NO-GO。不得保留为三篇论文中的任何一个题位。**

## 0. 终局判定

这个候选所指向的损害是真实的。coding agent 可能把带有署名、通知、源代码提供、相同许可证、修改说明或其他条件的代码和依赖带入待交付系统；组织若在未辨明来源、适用范围和分发情境的情况下合并或发布这些工件，可能遭遇合并阻断、返工、供应链治理失灵、声誉损害和法律争议。GitHub 已把许可证合规做成可阻断拉取请求的组织规则，并把依赖图、传递依赖和由 Enterprise Open Source License Manager 处理的例外审批纳入工作流；SPDX 则把许可证与来源事实纳入标准化 SBOM 表达。这些公开实践足以证明问题不只是“标签分类不准”。但是，它们同时提示必须把研究结果限定为**对给定许可证文本、组织政策和分发假设的合规性**，不能把模型输出称为具有普遍效力的法律判断。[GitHub 2026](https://docs.github.com/en/code-security/concepts/supply-chain-security/open-source-license-compliance)；[SPDX Overview](https://spdx.dev/about/overview/)

然而，真实损害不足以使候选成立。终审同时发现三个实质失败。

1. **直接近邻门失败。** 来源追踪、代码相似性、许可证条款抽取、作用域推理、兼容性判断、依赖迁移、依赖移除、版本固定、项目许可证变更、许可证例外、缺失修改通知自动修复以及 agent 轨迹政策合规，均已有直接工件或 benchmark。把这些能力串成一个 agent，新增的主要是集成范围，并未形成未被占据的核心学习问题。
2. **理论不可替代性门失败。** 财产权理论、信息治理、知识产权规范、边界资源和平台控制都能解释组织为何关心权利、信息与边界，却没有导出许可证修复所必需且不可由通用图模型或 POMDP 表达的中间状态、关系运算或行动约束。最接近的组织控制理论也只会重新命名预防、侦测和纠正动作。理论删除后，算法仍能以同一输入、标签、损失和动作运行。
3. **联合监督与外部真值门失败。** 公开数据足以分别训练来源检索、条款抽取或兼容性分析，却没有提供“来源事实—适用义务—分发情境—多步可执行修复—功能保持—权威裁决”的联合样本。若用既有许可证规则求解器自动制造标签，学习模型只会复现构造者的规则；若不提供链接方式、修改事实、许可证例外、权利人许可、分发目标与法域等信息，任务本身又不可识别。

因此，候选不因“能做出一个复杂系统”而保留。下文仍把最强版本完整钢人化，目的在于证明否决发生在贡献与识别层面，而不是由于没有找到工程实现办法。

## 1. 风险对象、行动时点与 agent 删除检验

### 1.1 精确定义

研究对象不是许可证名称分类器。候选试图处理的决策单元是一次准备进入代码库或交付物的**来源获得事件**：agent 从检索结果、其他仓库、模型记忆、依赖解析器或用户提供的片段中取得候选代码，再决定是否获取、改写、替换、隔离、保留通知、补充署名、改变构建配置、固定版本、请求许可或停止分发。潜在损害发生在合并、构建、打包和分发之前，并可能影响代码所有者、贡献者、项目维护者、客户、组织法务与下游接收者。

行动前可以观察的信号包括代码与来源候选的相似度、仓库和包版本、声明许可证、许可证文件、NOTICE、依赖图、静态或动态链接方式、修改记录、构建配置、分发目标、组织政策以及历史工具轨迹。不可见或不确定的信息包括模型训练来源、未声明或冲突的版权信息、代码是否达到受保护表达的门槛、某种组合是否构成衍生作品、权利人另行授予的许可、双重许可选择、法域差异和未来分发方式。SPDX 明确说明其目标是交换事实与断言而非作法律解释，这一边界不能由增加模型参数消除。[SPDX Overview](https://spdx.dev/about/overview/)

### 1.2 正常、风险与纠正动作

最丰富且仍可执行的动作空间如下。

| 类别 | 动作 | 必须改变的外部对象 | 可观测结果 |
|---|---|---|---|
| 获得 | `acquire(source, version)`、`vendor(component)` | 源文件、锁文件、供应链清单 | 构建成功、来源记录完整 |
| 归因 | `attribute(holder, source)`、`preserve_notice`、`record_provenance` | 头注释、NOTICE、SBOM | 义务检查通过、来源可追踪 |
| 替代 | `replace_dependency`、`pin_version`、`remove_component` | manifest、lockfile、调用点 | 隐藏测试、依赖图与许可证扫描 |
| 改写 | `rewrite_implementation` | 源码与测试 | 功能保持、与受限来源的相似度下降 |
| 隔离 | `isolate_process_or_service`、`disable_feature` | 架构边界、IPC/API、构建开关 | 运行时边界、性能与部署测试 |
| 权利与审批 | `select_project_license`、`request_permission_or_exception` | 许可证、审批记录 | 权限主体确认、人工审查完成 |
| 分发控制 | `quarantine`、`distribute`、`abort_release` | 发布流水线与制品 | 不合规制品未被发布、正常制品仍可发布 |

这种动作空间比拒绝或允许丰富，也会造成可测量的功能、性能、人工负担和治理后果。但是，并非每个动作都可由 agent 合法执行。agent 无权替组织改变许可证或向权利人作出承诺；这类动作只能产生供有权主体审批的候选方案。

### 1.3 coding agent 不可删除检验

该候选没有通过 agent 不可删除检验。把“agent”从表述中删除后，研究仍可完整改写为“面向软件供应链的自动化许可证兼容分析与修复系统”。其输入仍是源码、依赖图、许可证和分发配置，输出仍是依赖替换、通知修复、构建配置和发布阻断。SILENCE 已能在 PyPI 依赖图上提出迁移、移除、版本固定、改变项目许可证和协商等策略；LiVo 已能根据提交记录写入缺失的修改通知。两者都不需要通用 coding agent 才能成立。[SILENCE](https://arxiv.org/abs/2308.05942)；[LiVo](https://arxiv.org/abs/2310.07991)

加入 shell、编辑器和测试循环只证明执行器更强，不证明研究问题因 coding agent 才出现。若把 agent 的非确定规划、工具权限和多步失败传播作为核心，则研究对象会滑向通用安全行动与政策遵从；许可证只成为一个应用域。若把许可证义务作为核心，则 agent 又可被批处理修复器替代。这一两难是终审否决的重要依据。

## 2. 检索范围与证据等级

本次检索覆盖至 2026-08-16，关键词组包括 code provenance、code clone attribution、LLM code memorization、generated code license、license clause extraction、license compatibility、license scope、dependency migration、SPDX、SBOM、agent policy compliance、repository rules、copyright-compliant agents，以及 AIS Basket 中的 property rights、information governance、intellectual property norms、boundary resources、platform control、open-source license choice 和 code reuse。技术论文优先回读主文或作者终稿；标准与产品能力优先使用官方规范和官方仓库；IS 理论使用 Otero AIS Basket 的 MinerU 全文回读。

Boyuan Li 等人在 2025 年的系统综述中把 80 篇 OSS 许可证管理论文归为识别、风险评估和风险缓解三类。本审查只用该综述检查检索覆盖面，关于具体算法、数据与结果的判断仍回到相应一手论文。[系统综述](https://arxiv.org/abs/2507.05270)

证据等级只描述本次实际回读深度，不把搜索摘要当作全文证据。

| 记号 | 含义 |
|---|---|
| F | 已打开主文或作者终稿并回读与本候选有关的方法、数据、结果和局限段 |
| R | 已打开官方代码仓库、数据仓库、标准或产品文档 |
| P | 已打开主文但仅回读与候选直接相关的部分，细节仍需二次核查 |

## 3. 直接近邻地图

### 3.1 来源追踪与生成代码相似性

| 直接工作 | 已有能力与数据 | 对候选的占位含义 | 证据 |
|---|---|---|---|
| LiCoEval，ICSE 2025 | 从 World of Code 构造 4,187 个 Python 函数，评价 14 个 LLM 的代码相似性及许可证信息生成；官方仓库公开 benchmark 与脚本 | “生成代码是否与既有代码高度相似、能否给出许可证”已有直接 benchmark；作者同时警告相似度不等于法律侵权边界 | F/R，[论文](https://arxiv.org/abs/2408.02487)，[仓库](https://github.com/osslab-pku/LiCoEval) |
| Colombo et al.，ICPC 2025 | 生成超过 70,000 个 Java 方法实现，考查 ChatGPT 输出复现 copyleft 代码的频率和幅度，以及上下文与温度的关联 | “AI 代码助手可能复现 copyleft 代码”已有大规模直接实证；它不含来源义务修复策略 | F，[论文](https://arxiv.org/abs/2502.05023) |
| SourceTracker，2026 | 以约 300M 编码器、HST 候选检索和 Winnowing 重排追踪 LLM 代码片段来源；在 The Stack V2 的千万级片段及标识符改名查询上评价 | 学习型来源检索与抗表面改写归因已被直接实现；新研究不能把“检索最相似来源”当作主要工件 | F，[论文](https://arxiv.org/abs/2605.28510) |
| OSS License Identification at Scale，MSR 2025 | 对约 550 万个不同许可证 blob 建立项目—许可证映射和时间信息 | 大规模许可证文本识别与历史数据基础设施已存在 | P，[论文](https://arxiv.org/abs/2409.04824) |

来源追踪仍存在开放问题，例如语义等价但表面差异很大的改写、训练集不可见和多源拼接。但是这些问题首先是检索与归因问题。即使解决，也不能由相似度独立推出许可证义务是否适用，更不能决定怎样修复并保持任务功能。

| 直接工作 | 已有能力 | 对候选的占位含义 | 证据 |
|---|---|---|---|
| LiDetector，TOSEM 2023 | 从许可证文本抽取权利与义务并用结构化语法表达 | 学习型条款抽取和结构表示已被直接研究 | F，[论文](https://arxiv.org/abs/2204.10502) |

这些工作各有局限，例如随机许可证句子切分会泄漏同一许可证家族，自定义许可证与情境事实仍难处理，推荐建议也未必成为可运行补丁。局限只能支持“需要更严格的划分与执行评价”，不能自动产生一个新的理论机制。

### 3.3 可执行修复

| 直接工作 | 已执行或建议的动作 | 候选还剩下什么 | 证据 |
|---|---|---|---|
| SILENCE，ASE 2023 | 在 438,967 个 PyPI 包、3,622,711 个版本的依赖空间中检查冲突，并提出依赖迁移、依赖移除、版本固定、改变项目许可证和协商等五类策略；以 SMT 搜索较小变更的替代依赖图 | 剩余空间主要是把包级修复扩展到源码级改写、隔离、通知与交互式审批 | F/R，[论文](https://arxiv.org/abs/2308.05942)，[仓库](https://github.com/osslab-pku/SILENCE) |
| LiResolver，ISSTA 2023 | 为冲突定位推荐正式许可证或生成自定义许可证及例外 | 解决动作并非候选新提出，但其执行性和权利主体约束仍不足 | F，[作者终稿](https://lingling-fan.github.io/llfan_files/issta2023_LiResolver.pdf) |
| LiVo，ISSTA 2024 | 检测 fork 中缺失的修改通知，并依据提交记录生成修复，向真实项目提交 pull request | “从历史证据到文本修复再到真实外部结果”已有很强的直接范例 | F，[作者终稿](https://chenbihuan.github.io/paper/issta24-huang-livo.pdf) |

可见，`replace/remove/pin/change-license/negotiate/fix-notice` 已被覆盖。候选若把新增能力放在 `rewrite/isolate/vendor/configure/distribute`，必须证明这些动作需要新的可训练决策状态，而不是把程序修复器接到现有许可证求解器之后。当前证据不支持这一点。

|---|---|---|---|

| AgentPex，2026 | 从 agent 行为轨迹中抽取并检查行为规则，公开代码和 424 条轨迹 | 轨迹级政策检查已有通用基线 | P/R，[项目页](https://www.microsoft.com/en-us/research/publication/willful-disobedience-automatically-detecting-failures-in-agentic/)，[仓库](https://github.com/microsoft/agentpex) |
| Copyright-Bench，ICML 2026 | 在代理式任务中评价版权约束与用户偏好、时限之间的决策 | “agent 在任务成功与版权约束间权衡”已有邻近 benchmark，虽非代码域 | A，[论文](https://arxiv.org/abs/2607.21799) |

| Gemini Code Assist 来源引用 | 当建议较长地复现来源时提供来源与许可证信息，并允许组织阻止与被引用来源匹配的建议 | 生成时来源披露已有产品能力；新方法需比较真实开发工作流，而非只与无控制 LLM 比较 | R，[官方文档](https://docs.cloud.google.com/gemini/docs/discover/works) |

这组近邻堵住了另一条退路。若把许可证问题改写成“agent 是否遵守组织政策”，最强基线已不再是许可证扫描器，而是前缀轨迹 guardrail、仓库规则 benchmark 和可阻断工作流。许可证专门知识可以提高一个域的性能，却不足以证明新的 agent governance 理论或算法类别。

## 4. 公开数据是否足以支持强工件

### 4.1 可用但分散的数据

| 学习责任 | 可用公开资源 | 能提供的监督 | 不能提供的监督 |
|---|---|---|---|
| 来源候选检索 | The Stack V2、SourceTracker 构造、LiCoEval、World of Code | 原始/改名片段与来源候选的排名或匹配 | 法律上的复制认定、适用许可证义务 |
| 许可证文本识别 | SPDX License List 3.28.0、海量许可证 blob、Software Heritage | 标准文本、例外、文本匹配、项目映射 | 自定义许可的权威解释、权利人另行授权 |
| 条款与关系 | LiDetector、ClauseBench、Catch the Butterfly、LiResolver | 条款类型、权利/义务、实体关系、部分冲突标签 | 复杂结合方式和具体发布事实下的最终法律结论 |
| 依赖兼容 | SILENCE、LiScopeLens 系列、LV-Compat | 规则库下的许可证传播与冲突 | 多法域裁决、组织接受度、源码级改写后的义务变化 |
| 修复 | SILENCE 历史案例、LiVo PR、issue/PR/commit 记录 | 少量迁移、通知、删除或版本修复轨迹 | 覆盖全部丰富动作且有成败反事实的策略数据 |
| agent 合规 | RepoComplianceBench、PolicyGuardBench、AgentPex | 规则—轨迹—合规/违规及部分干预 | 软件许可证特有的来源、构建、分发和修复联合真值 |

SPDX License List 可以作为许可证文本和例外的版本化事实源。截至审查日，官方页面列出的当前版本为 3.28.0，发布日期为 2026-02-20。[SPDX License List](https://spdx.org/licenses/)

### 4.2 不可拼接成权威联合标签

把上述数据按项目名或许可证 ID 拼接，并不能产生本研究真正需要的样本。一个可训练的执行策略至少需要同时知道：片段的真实来源与版本、来源许可适用范围、代码如何被修改和结合、交付物是否分发、采用何种链接或进程边界、组织允许哪些许可证、候选修复是否得到权利主体批准，以及修复后隐藏功能和风险是否都通过。公开资源没有为同一实例提供这些变量。

三种常见构造方式均有致命缺陷。

1. **规则合成。** 用 SPDX 文本、人工编码兼容矩阵和依赖图生成冲突，再让模型学习消除冲突。标签只证明模型拟合构造规则；与扫描器加 SMT 求解器相比没有新增经验知识。
2. **历史挖掘。** 从 issue、PR、commit 或法务讨论中抽取修复。观察到的修复没有完整候选集合和失败反事实，而且通常混入维护成本、API 质量、弃用与性能等其他原因，难以把动作归因于许可证机制。
3. **专家标注。** 让律师或维护者判断构造实例。小规模标注可以评价，但不足以监督高维多步策略；专家间分歧还可能反映未给出的事实与法域假设，而不是随机标签噪声。

因此，公开数据“足以训练多个子模型”，但“不足以识别端到端合规修复策略”。这是数据门失败，而非简单的数据清洗工作量问题。

## 5. 最强可训练工件的钢人化规格

本节不改变 NO-GO 结论。它给出在不退化为分类器、规则拦截器或提示词模板的前提下，这个候选所能达到的最强算法形态，再检查它是否仍有独立贡献。

### 5.1 输入、输出与决策时点

第 $t$ 步的输入定义为

\[
x_t=(G^{src},G^{dep},G^{lic},G^{task},\tau_{1:t},C^{org},D,\Omega_t).
\]

其中，$G^{src}$ 是片段—文件—提交—仓库—版本的来源候选图；$G^{dep}$ 是包、版本、构建目标、静态/动态链接和进程边界组成的依赖图；$G^{lic}$ 是许可证、条款、权利、义务、条件、例外与作用域的关系图；$G^{task}$ 是函数、测试、调用和需求组成的任务图；$\tau_{1:t}$ 是 agent 已执行的检索、编辑、命令和工具结果；$C^{org}$ 是组织可接受许可证、例外审批和发布策略；$D$ 是明确给出的分发情境；$\Omega_t$ 是当前可见证据及其来源可信度。

系统输出不能只是风险分数。它需要联合输出：

1. 来源候选及校准后验 $p(s\mid x_t)$；
2. 在明确事实假设下的义务后验 $p(o,scope\mid s,x_t)$，并区分文本事实、规则推演和不确定判断；
3. 候选行动序列 $a_{t:t+H}$ 与每一步的文件、manifest、NOTICE、SBOM 或发布流水线补丁；
4. 功能成功、声明规则合规、不可逆影响、人工审批次数、运行成本的联合结果分布；
5. 可供人工复核的证据包，包括来源片段、许可证版本、适用规则、执行日志和失败分支。

介入时点有三处：代码或依赖进入工作树之前的获得决策，补丁准备合并前的修复决策，以及制品准备发布前的分发决策。只在最后阻断发布会错过低成本替换窗口；只在生成时过滤又无法处理传递依赖、后续配置和分发事实。

### 5.2 张量与网络结构

来源图的节点和边表示为

\[
H_s\in\mathbb{R}^{B\times N_s\times d},\qquad
A_s\in\{0,1\}^{B\times N_s\times N_s\times K_s}.
\]

许可证图使用

\[
H_l\in\mathbb{R}^{B\times N_l\times d},\qquad
R^{lic}\in\{0,1,?\}^{B\times N_a\times N_o\times N_c},
\]

其中 $R^{lic}_{a,o,c}$ 表示某许可证动作或情境 $a$ 是否触发义务 $o$ 及条件 $c$，问号保留未决状态。依赖和任务图分别形成 $H_d,A_d,H_t,A_t$。候选动作编码为 $U\in\mathbb{R}^{B\times K\times d}$，belief state 为 $b_t\in\mathbb{R}^{B\times d_b}$。证据来源和可见性必须另有 mask，避免模型把缺失事实静默当作否定事实。

最强架构可以由五部分组成。

1. **来源编码器。** 以 SourceTracker 量级的约 300M 参数代码编码器做候选召回，再以指纹与跨编码器重排抵抗标识符改名。
2. **异构关系编码器。** relational graph Transformer 在来源、许可证、依赖、任务和组织政策之间进行有类型消息传递，并保留“文本声明、推演规则、组织决策、未知事实”四类证据来源。
3. **结果 world model。** 预测每个动作对隐藏测试、构建、依赖图、义务状态、代码相似性、审查负担和分发结果的分布，而非只预测当前风险。
4. **约束式离线策略。** 以 distributional offline POMDP、IQL 或 CQL 形式，在高风险且证据不足时选择检索、沙箱试验、请求审批或隔离，而非直接发布。
5. **类型化补丁解码器与隔离执行器。** 生成源码、配置和文档补丁，在容器中构建、测试、生成 SBOM、运行许可证规则检查，再把真实执行结果写回 belief。

这已经是一个需要本地训练、索引和执行环境的实质工件，不是提示词编排。

### 5.3 样本、监督与损失

训练可以分成四阶段，但各阶段的数据责任不可混淆。

| 阶段 | 样本构造 | 监督信号 | 主要损失 |
|---|---|---|---|
| 来源表征 | 原始片段、标识符改名、受控重写及其来源仓库 | source ID、版本、正负候选 | InfoNCE、listwise ranking、校准损失 |
| 条款与作用域 | 标准/自定义许可证句子、条款 span、实体关系和依赖情境 | 条款类别、权利/义务、作用域关系 | span loss、relation loss、graph consistency |
| 行动后果 | 可执行仓库中施加依赖、源码、NOTICE 和配置变换 | 构建/隐藏测试、规则扫描、相似度、资源成本 | 多任务 NLL、survival/cost loss、calibration |
| 策略与补丁 | 历史轨迹、搜索产生的候选轨迹和人工批准轨迹 | 回报、约束违反、补丁真值或偏好 | IQL/CQL、constraint penalty、patch NLL、verifier loss |

联合目标可写为

\[
\mathcal L=\lambda_p\mathcal L_{rank}+
\lambda_o(\mathcal L_{span}+\mathcal L_{rel})+
\lambda_c\mathcal L_{compat}+
\lambda_y\mathcal L_{outcome}+
\lambda_\pi\mathcal L_{offline}+
\lambda_x\mathcal L_{patch}+
\lambda_v\mathcal L_{verify}.
\]

外部回报不能把“拒绝”一律设为零风险。至少应同时包含任务完成 $T$、声明规则违反 $V$、不可逆发布 $I$、人工负担 $H$、修改成本 $M$ 和运行成本 $C$：

\[
r=\alpha T-\beta V-\gamma I-\eta H-\mu M-\nu C.
\]

系数不能由作者任意选择后只报告一个最优点，必须给出风险—任务—人工负担的 Pareto 前沿，并在不同组织政策下检验排序稳定性。

### 5.4 推断时真实动作

推断不能停在“建议替换”。在授权的隔离分支中，系统必须实际执行以下闭环：读取仓库政策和分发配置，召回来源与许可证证据，生成两个以上不同机制的候选方案，修改源码/manifest/lockfile/NOTICE/SBOM/构建配置，运行隐藏测试与许可证检查，更新 belief，再选择提交候选、隔离组件、请求权限主体确认或停止发布。涉及许可证变更、许可协商和组织例外的动作只能生成审批材料，不得被 agent 视作已获授权。

### 5.5 训练、验证与隐藏测试隔离

随机按文件或许可证句子切分会产生严重泄漏。最低可接受的隔离同时包括：

1. **来源族隔离。** 同一原始片段、标识符改名、格式变化和自动重写必须落在同一 split；同一 fork/镜像/提交谱系不得跨集合。
2. **仓库与包家族隔离。** 同一组织、模板仓库、包名空间和 API 兼容替代族尽量分组；不能让训练集看到测试项目的后续 commit。
3. **许可证族隔离。** 同一 SPDX 文本版本、例外及轻微变体不得跨集合；另设自定义许可证和修改许可证 OOD 集。
4. **时间隔离。** 训练先于验证、验证先于测试，防止历史修复和新版本回流。
5. **执行真值隔离。** 隐藏测试、gold 来源、规则配置、人工裁决和目标修复不进入 agent 检索空间或提示上下文。
6. **基础模型污染审计。** 对公开题目和补丁做 canary、时间后发行集、源码近邻搜索和记忆基线；不能把基础模型预训练见过的修复当作策略学习能力。

测试至少分为仓库内新风险、跨仓库、跨包生态、跨许可证家族、跨风险类型和时间外推。统计单元应以仓库或来源族为主，不能把同一仓库的数百个文件当作独立样本。

### 5.6 本地算力与复现工件

可行原型需要约 300M 参数的来源编码器、异构图网络、结果模型和一个开放权重代码补丁模型。保守的规划量级是 1–4 张 A100 80GB 级 GPU 完成表征学习、LoRA/adapter 训练和策略实验；千万级来源索引、容器 rollout、跨版本构建及隐藏测试更消耗 CPU、存储与调度时间。这个量级只是设计估计，不是已运行事实。

复现交付应包含不可变数据 manifest、来源/许可证/仓库谱系分组、SPDX 版本、组织政策和分发情境 schema、容器镜像 digest、构建与测试脚本、训练配置、checkpoint、向量索引、规则库版本、模型与检索清单、所有随机种子、失败轨迹、人工裁决协议及每次实验的调用预算。任何闭源模型只能作为额外外部基线，不能承担不可复现的训练标签生成器。

## 6. 公平比较、外部结果与撤题实验

### 6.1 最强基线

基线必须分别堵住“规则够用”“现有领域模型够用”“通用 agent 已能做”“理论命名无增量”四种解释。

| 基线族 | 具体基线 | 公平控制 |
|---|---|---|
| 标准扫描与规则 | SPDX/ScanCode/FOSSology 类扫描＋兼容矩阵＋组织规则；GitHub 式阻断；SMT 最小变更 | 使用同一 SPDX 版本、依赖图、政策与执行预算 |
| 来源与许可证领域模型 | LiCoEval、SourceTracker、LiDetector、LiResolver、LiScopeLens(+)、LV-Compat、LARK | 相同候选库、license corpus 与隐藏事实边界 |
| 修复系统 | SILENCE、LiVo、规则求解器＋程序修复器 | 同一可用动作集合；不得只让新模型拥有 rewrite/isolate |
| 通用 agent/guardrail | 最强可复现 coding agent＋扫描器；PolicyGuard-4B；RepoCompliance 提示与验证方案 | 相同工具、调用次数、token、墙钟时间与人工审批预算 |
| 简单政策 | 全部阻断、全部移除、白名单许可证、只请求人工 | 共同报告安全、任务和人工成本，防止拒绝率伪装为安全 |
| 等参数通用替代 | 相同节点/边输入、参数量和动作集合的 heterograph Transformer＋constrained POMDP；直接 patch Transformer | 唯一差异只能是理论所要求的表示或运算 |
| 上界 | oracle provenance、oracle obligation、oracle action outcome | 分解来源、语义和规划各自的性能上限 |

### 6.2 主要结果

主要安全结果只能定义为在预先声明规则和情境下的非合规合并/分发率、漏检高影响义务率和不可逆错误发布率。任务结果包括隐藏测试通过率、构建成功率、功能/性能退化和正常依赖引入成功率。成本结果包括需要人工复核的实例数、每例审查时间、变更规模、工具调用、token、GPU/CPU 时间和端到端时延。来源检索 MRR、条款 F1 与兼容性准确率是诊断指标，不能替代外部风险结果。

每项结果均需报告仓库级 bootstrap 置信区间、成对效应量、风险类型和许可证族分层、Pareto 前沿及选择性预测的 coverage-risk 曲线。没有真实实验时只能登记这些为预注册设计，不能填写数值或使用“结果表明”。

### 6.3 机制中和与终止条件

即使资源允许建设上述系统，只要出现下列任一结果，独立论文贡献就应撤销。

1. 等参数通用异构 Transformer＋POMDP 在相同输入和动作下非劣于“理论模型”。
2. 许可证扫描器＋规则/SMT＋通用程序修复器在外部风险、任务成功和人工负担上达到同一 Pareto 前沿。
3. 将理论状态打乱、置常数、交换层级或删除关系类型后，行为和结果没有稳定变化。
4. 把 coding agent 换成批处理修复器后，仍能完成同一任务且没有失去关键外部效度。
5. 公开联合标签不足，只能由待比较的规则系统或 LLM 自己合成大部分训练/测试真值。
6. 隐藏关键信息后专家无法稳定判断，公开这些信息后任务又退化为确定性规则求解。
7. 全部阻断或全部移除取得表面最低风险，而任务成功与人工负担没有被共同纳入主要判断。
8. 自定义许可证、跨生态或时间外推的性能显著崩溃，且模型依赖许可证文本近邻而非关系机制。
9. 来源追踪误差主导全部下游结果，使所谓行动策略只是上游召回率的函数。
10. 模型提出改变许可证、例外或许可协商，却没有验证执行主体是否具有相应权利和组织权限。

当前审查在实验前已经触发第 4、5 和理论层面的第 1、3 条，因此没有理由先占据论文题位再等待昂贵实验确认。

## 7. AIS Basket 理论候选终审

### 7.1 理论层级与原文责任

本节使用 Otero AIS Basket 全文回读，不依据术语相似性选理论。

| 理论候选及 Basket 原文 | 原文中的解释对象与机制 | 与本候选的层级错位 | 终判 |
|---|---|---|---|

### 7.2 最接近的理论映射也无法闭合

财产权理论是表面上最贴近“许可证权利”的候选。若严格按肖老师论文的 MEC→MAP→ALG 路径，理论必须先指出通用算法系统性忽略的机制，再导出不可替代表示，最后改变前向计算和行动。钢人化尝试如下。

| 环节 | 最强映射 | 失败原因 |
|---|---|---|
| MEC | 权利配置影响参与者的使用、排他、投资激励和机会主义；agent 获取代码会改变组织与权利人之间的控制边界 | OSS 许可中的权利配置是输入事实，不是本研究要学习的组织间契约选择；许多风险只是未履行既定义务 |
| MAP | 建立“资产×主体×权利×义务×阶段”的 residual-control tensor，并区分获取、修改、结合、分发 | 这些维度来自许可证法事实与 SBOM schema，而非 PRT 独有；通用知识图谱会自然包含同样关系 |
| ALG | 以权利冲突约束 POMDP，禁止无授权分发，并在 replace/rewrite/isolate/seek-permission 间规划 | 约束由许可证与组织政策给出。删除 PRT 名称，算法、损失与动作完全不变 |
| 外部结果 | 降低违规分发，同时保持任务完成并减少人工审查 | 是软件合规结果，无法检验 PRT 的关系专用投资或机会主义机制 |

Susarla 与 Mukhopadhyay 对知识/租金挪用的研究并没有修复这一断裂。其核心张力是外包双方既要迭代协作创造尚未确定的创新，又要通过可信承诺与或有控制权避免事前投资不足和事后 hold-up。候选中的代码来源通常由第三方权利人预先许可，coding agent 不与权利人共同议定创新合同；即使把 `request_permission` 视为控制权调整，绝大多数 `attribute/replace/remove/rewrite` 决策仍由既有许可证事实而非租金挪用机制决定。

信息治理的最强映射同样失败。可以把 provenance completeness、policy authority、evidence quality 和 review ownership 设为治理状态，并让 agent 在不完整信息时请求补证。但这些状态来自一般不确定决策与访问控制；等参数 POMDP 用相同观测即可学习。理论只解释组织为何要有数据责任与审批，没有导出不从该理论视角便难以想到的许可证动作。

Tiwana 与 Keil 的项目控制理论是比财产权或信息治理更自然的反例。组织可以被视为 controller，coding agent 是 controllee；许可证规则与允许动作可形成行为控制，隐藏测试和合规结果可形成结果控制，agent 自主权对应 self-control。其“attempted control 不等于 realized control”还能提醒研究者：写入 policy 或 guardrail 不代表控制已生效，行为不可观察、结果不可测或组织没有合法授权时，控制可能无法实现。然而，把这些机制映射到算法后只会得到观测性、结果可测性、需求波动和权限状态，再由策略分配监测、验证、自治或人工转交。相同状态已是任何风险感知 POMDP 的自然输入，且不包含来源、许可证条款或分发作用域的专门知识。若用该理论支撑论文，理论新增的是一个通用 agent governance 层，而许可证问题退化为应用案例；若坚持许可证为核心，控制理论又只负责重新命名策略动作。因此它仍未通过不可替代性检验。

### 7.3 等参数通用反证

设“理论模型”把资产—主体—权利—义务张量 $R^{PR}$ 与信息治理状态 $g_t$ 输入关系图网络，再用约束策略选择动作。构造通用替代：给它完全相同的节点、边、证据 mask、标签和动作，只把 $R^{PR}$ 改名为 relation tensor，把 $g_t$ 改名为 latent evidence state，并在同一参数预算下用 cross-attention 或 heterograph Transformer＋POMDP 学习。两者具有相同表达能力、监督和执行器。候选理论没有规定不可交换的方向差、特殊的层级聚合或独有反事实；因此不能像 DSDL 的 $S=F-E$ 那样在删除、交换或取绝对值时改变理论含义，也不能像 ACAA 的 diversity attention 那样要求算法朝与 affinity attention 相反的方向匹配。

若通用替代达到相同结果，不能把关系张量的字段名视为理论贡献。当前无法提出预先可证伪、且不依赖性能结果事后解释的理论差异，因此理论责任终局失败。

## 8. 新颖性分解与为什么不能“缩小后保留”

| 可能声称的新增能力 | 最接近直接工作 | 真正剩余增量 | 是否足以独立成篇 |
|---|---|---|---|
| 追踪 LLM 生成代码来源 | SourceTracker、LiCoEval | 与许可证规则及修复器连接 | 否，主要是流水线集成 |
| 理解自定义许可证与作用域 | LiResolver、LiScopeLens(+)、LV-Parser/LV-Compat、LARK | 更强 OOD 与情境事实输入 | 否，属于现有任务的扩展 |
| 规划许可证修复 | SILENCE、LiResolver、LiVo | 源码 rewrite、进程 isolate 和统一审批 | 当前否，动作增加但监督与理论机制不足 |
| 控制 agent 遵守仓库政策 | RepoComplianceBench、PolicyGuard、AgentPex | 许可证专门知识与真实编辑动作 | 否，域适配不等于新算法 |
| 在风险与任务间权衡 | Copyright-Bench、通用 constrained agent | 软件构建与分发结果 | 否，缺少独特理论状态 |
| 生成可审计 SBOM 与证据包 | SPDX、现有扫描和治理工具 | 将证据绑定到 agent 轨迹 | 实践有用，但不是主要可训练能力 |

把题目缩成许可证识别会退化为已覆盖的分类/抽取；缩成兼容性会进入成熟规则与图分析文献；缩成依赖替换会与 SILENCE 重叠；缩成 NOTICE 修复会与 LiVo 重叠；缩成 agent policy 会与 RepoComplianceBench 和 PolicyGuard 重叠；扩大成完整合规 agent 又会成为多个既有模块的系统集成，并遭遇联合真值缺失。不存在一个缩小后仍同时满足真实风险、coding-agent 不可删除、理论不可替代、强训练工件和公开外部评价的稳定核心。

### 9.3 肖式连续论证链是否成立

按上述句键，风险情境与方法规格可以形成 `CXT→IMP→ACK→LIM→ALG→EVAL`。断裂发生在 `MEC→MAP→ALG`：候选理论没有创造一种与通用方法方向相反、顺序不可交换或删除后语义失效的计算。理论关系张量来自许可证与组织事实，不来自财产权或信息治理机制；策略约束来自政策输入，不来自理论命题。因而不能像 ACAA 那样从注意机制逐项推出专用 attention，也不能像 DSDL 那样把期望与体验投影到同一坐标后按理论方向计算不一致。按照导师论文的逻辑标准，这不是“理论部分还需润色”，而是候选的主要理论—算法链没有成立。

## 11. 终审清单与最终处置

| 硬条件 | 证据 | 判定 |
|---|---|---|
| 损害真实且外部结果可测 | 合并/发布阻断、规则违反、隐藏测试、人工负担和不可逆分发均可测 | 通过 |
| coding agent 不可删除 | 换成批处理合规修复器仍保留同一 I/O 与大部分动作 | **失败** |

| 主要工件需要训练与本地计算 | 钢人化工件需要编码器、图网络、world model、策略和容器执行 | 通过 |

最终处置是**终局 NO-GO**。不得把本候选改名为“来源治理”“权利感知 agent”“许可证安全 world model”后继续占位，也不得把它降格成三篇论文中某一篇的子模块以弥补贡献。来源与许可证证据可以在未来入选论文中作为一个风险信号、评价维度或组织政策案例使用，但不能承担独立研究题目的理论和算法贡献。

若未来出现同时含真实来源谱系、授权/分发事实、权威义务判断、多类可执行修复、隐藏功能测试和人工审批结果的公开 longitudinal benchmark，并且某个 Basket 理论能够预先导出通用策略不会自然得到的不可交换计算，那么可以作为**全新候选**重新审查。该条件不是当前题位的保留条款。
